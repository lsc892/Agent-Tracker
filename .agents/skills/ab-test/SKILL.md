# 성능 A/B 테스트

가정 → 개선 방향 → 실제 측정 → 결과 표 → 핵심 분석까지 수행한다. 계획이나 예상 수치만으로 끝내지 않는다.

## 가정과 비교 대상

- **가정**: 어떤 병목 때문에 느린지, 무엇을 바꾸면 어떤 지표가 좋아질지를 한두 문장으로 정한다. 사용자 가정과 에이전트의 추정을 구분한다.
- **A**: 현재 작업 트리의 구현. 미커밋 변경도 포함해 소스·빌드 식별자를 고정한다. **B**: 그 가정에 대응하는 변경 하나만 적용한 후보. 별도 사본이나 워크트리에서 실험하고 제품 반영은 사용자 요청 범위를 따른다.
- [기존 벤치마크](../../../tests/benchmarks/README.md)를 먼저 확인해 재사용하고 부족한 측정만 보완한다.

## 실제 실행

1. 별도 지시가 없으면 **현재 데이터 전체(N건), 10,000건, 100건**을 모두 측정한다. 1건은 정규화된 요청 1개이며 건수는 추가 직전 기준이다. 현재 데이터는 일관된 스냅샷 사본을 사용한다. 합성 데이터는 고정 seed로 만들고 기간·세션·프로젝트 분포와 실제 건수를 기록한다. 원본 데이터는 변경하지 않는다.
2. 같은 입력·필터·시간대·고정 기간으로 실제 저장·집계 API를 호출한다.
   - **요청 1건 추가**: 같은 사전 상태에서 같은 요청을 추가하고 필요한 집계 갱신과 COMMIT까지 측정한다. 매 표본마다 사전 상태를 복원한다. 대량 저장 시간을 건수로 나눈 값으로 대신하지 않는다.
   - **기간별·세션별·프로젝트별 평균 토큰 집계**: 실제 결과 반환까지 각각 측정한다. 기간별은 기본 일별·월별을 나눈다. 평균의 분모, 완료/빈 요청 처리 등 제품의 집계 의미를 유지한다. 토큰 평균값과 실행 시간의 평균을 혼동하지 않는다.
3. 요청 추가 후와 각 집계에서 **A/B의 요청 수·토큰 합계·그룹별 평균·결과 건수 일치**를 확인한다. 공통 오류를 놓치지 않도록 원본 요청으로 계산한 기대값과도 대조한다. 불일치한 후보는 성능과 관계없이 실패다.
4. 같은 환경에서 준비 실행 3회 후 **A→B / B→A 순서를 교대해 각 10회 이상** 측정한다. 시간 단위는 ms, 대표값은 중앙값이다. 캐시 조건과 측정 범위를 명시하고 데이터 준비·사본 복원은 측정에서 제외한다. 최초 구축·마이그레이션 비용이 생기면 별도로 적는다.
5. 원시 표본, 환경, 재실행 명령, A/B 소스·빌드 및 입력 식별자, 정확성 검증 결과를 JSON으로 남긴다. 실행하지 못한 항목은 이유와 함께 **미측정**으로 표시하며 추정값으로 채우지 않는다.

## Markdown 기록

날짜는 Asia/Seoul 기준으로 잡고 `docs/benchmarks/YYYY-MM-DD/<주제>AB-YYYY-MM-DD.md`와 같은 이름의 원시 `.json`을 저장한다. 해당 날짜와 상위 벤치마크 README에서 연결한다. 프롬프트·응답 본문, credential, 개인 식별 정보는 남기지 않는다.

보고서는 아래 형식으로 짧게 작성한다. 추가 지표는 가정의 판정에 필요한 것만 넣는다.

```markdown
# <주제> A/B 테스트

가정: <병목과 예상 효과>
개선 방향: A = <현재 방식>, B = <바꾼 부분>

## 1. 결과

각 셀은 A → B 중앙값 ms (개선율)이다.
개선율 = (A - B) / A × 100. 양수는 개선, 음수는 악화. A가 0이면 N/A.

| 측정 항목 | 현재 데이터(N건) | 10,000건 | 100건 |
| --- | ---: | ---: | ---: |
| 요청 1건 추가 | — | — | — |
| 일별 평균 토큰 집계 | — | — | — |
| 월별 평균 토큰 집계 | — | — | — |
| 세션별 평균 토큰 집계 | — | — | — |
| 프로젝트별 평균 토큰 집계 | — | — | — |

측정 조건: <환경·데이터 분포·기간·평균의 분모·측정 범위·캐시·반복 수>
정확성: <기대값 및 A/B 일치 여부>. 원시 결과: [JSON](./주제AB-YYYY-MM-DD.json).

## 2. 분석

- **판정**: 가정 성립 / 일부 성립 / 기각 / 판단 유보. 근거가 되는 수치만 짚는다.
- **핵심 원인**: 맞거나 틀린 이유를 코드 경로·실행 계획·계측 등 관측 근거로 설명한다. 확인된 사실과 추정을 구분한다.
- **선택**: 채택·보류·기각 의견과 쓰기/읽기 간 손익을 요약한다. 차이가 측정 변동 범위 안이면 개선으로 단정하지 않는다.
```

스킬·벤치마크만 추가한 경우 기능 의사결정 일지는 쓰지 않는다. 제품 동작도 변경했다면 [저장소 지침](../../../AGENTS.md)에 따라 검증하고 관련 명세·일지를 갱신한다.
