# 가독성 리팩토링 실행

## 기준 문서

- [GUIDELINES.md](GUIDELINES.md)는 실행 방식을 수정하기 전 가독성 지침 원문이다. 메인 에이전트와 담당 서브에이전트 모두 작업 전에 읽고 코드 품질·동작 보존의 기준으로 삼는다.
- 지침은 고정된 기준 문서로 보존한다. 작업마다 다시 만들거나 보고서로 덮어쓰지 않고, 사용자 요청 없이 내용을 수정하지 않는다. 작업별 분석과 결과는 별도 MD에 기록한다.
- 실행 범위·승인·작업 순서·서브에이전트 역할은 이 `SKILL.md`를 따른다. 지침 원문의 분석 전용 지시나 대규모 분석 범위 전체의 승인 대기 지시 때문에 아래의 독립적인 내부 정리를 미루지 않는다.

## 바로 적용할 정리와 MD로 제안할 변경

| 구분 | 처리 |
| --- | --- |
| 기존 스크립트 안의 메소드·파일 내부 함수 추출, `if`·`switch`·조건식 정리, `try`·`catch` 범위 정리, 이름·상수·메소드 배치 조정 | 기존 동작·알고리즘·외부 호출 방식을 보존하며 서브에이전트가 별도 확인 없이 적용 |
| 핵심 계산·탐색·집계 알고리즘 교체, 핵심 처리 방식이나 실행 비용을 바꾸는 자료구조 교체 | MD에 현재 방식·대안·영향·검증 계획을 작성하고 승인받은 범위만 적용 |
| 아키텍처·의존 관계 변경, 클래스 분할, 큰 스크립트의 파일 분리, 소스 파일·폴더 생성·이동·이름 변경 | MD에 역할·경계·호출부 영향과 변경 전후 구조를 작성하고 승인받은 범위만 적용 |

- 같은 파일 안에서 끝나도 알고리즘·아키텍처 변경이나 클래스 분할이면 MD 제안 대상이다. 같은 규칙의 분기 표현이나 메소드 배치만 정리하는 것은 알고리즘 교체로 취급하지 않는다.
- 큰 변경 후보가 같은 파일에 있어도 독립적인 내부 정리는 계속 적용한다. 그 큰 변경을 전제로 해야 가능한 수정과 import 변경만 함께 보류한다. 파일 길이나 수정할 메소드 수만으로 내부 정리를 승인 대상으로 바꾸지 않는다.
- 일반적인 가독성 개선 요청은 큰 변경까지 승인한 것으로 간주하지 않는다. 이미 승인받은 변경은 승인 범위 안에서 다시 묻지 않고 진행한다.

## 서브에이전트가 작업 MD를 만들고 적용한다

1. 메인 에이전트는 요청 범위와 현재 변경 상태를 확인하고 파일별 담당을 나눈다. 담당자에게 이 스킬과 지침 경로, 소스·호출부·관련 테스트, 보존할 계약, 서로 다른 작업 MD 경로를 전달한다. 한 파일은 한 에이전트만 수정하게 하며, 테스트·보고서 등 함께 수정할 파일도 담당을 지정한다.
2. 담당 서브에이전트는 지침과 실제 코드를 읽고 작업 MD를 작성한다. 검토 위치와 현재 흐름, 문제와 근거, 바로 적용할 내부 정리, MD 제안으로 남길 큰 변경, 검증 계획·미확인 사항을 구분한다. 지침 본문이나 코드 전체를 보고서에 복사하지 않는다. 작은 작업은 필요한 내용만 짧게 적는다.
3. 작업 MD 작성 후 같은 담당자가 허용된 내부 정리를 바로 수정한다. 분석 보고만 하고 종료하거나 큰 변경의 승인 응답을 기다리지 않는다. 메소드 추출 후에도 책임 집중과 복잡한 `if`·`switch`·`try`가 남았는지 지침 기준으로 다시 확인한다. 실제 분기 규칙과 독립적인 오류 복구·자원 정리 경계는 보존한다.
4. 적용 중 알고리즘·아키텍처 변경이나 클래스·파일 분리가 필요해지면 해당 부분만 작업 MD의 제안으로 남기고 독립적인 내부 정리는 계속한다. 미승인 후보의 소스 파일·폴더를 만들거나 변경을 미리 반영하지 않는다.
5. 담당자는 변경에 맞는 검증을 수행하고 작업 MD에 적용 내용·검증 결과·남은 제안을 갱신한다. 메인 에이전트에는 MD 경로, 수정 파일, 핵심 변경, 검증 결과와 미확인 사항을 짧게 보고한다.
6. 메인 에이전트는 실제 diff와 동작 보존 여부를 검토하고 저장소의 필수 검사를 실행한다. 허용된 내부 정리가 남았는데도 후보만 보고했다면 해당 담당자에게 실제 적용하도록 후속 지시한다. 여러 작업 MD가 있으면 중복·상충·영역 간 영향을 정리해 통합 MD로 연결한다.

서브에이전트를 사용할 수 없으면 메인 에이전트가 같은 기준으로 작업 MD 작성과 내부 정리를 순차 수행하고 그 제약을 보고한다.

## 작업 MD와 완료 보고

- 작업 MD는 저장소의 기존 작업 산출물 위치에 두고, 정해진 위치가 없으면 작업별 임시 폴더에 둔다. 보고서와 그 보관 폴더 생성은 소스 구조 변경과 구분한다. [GUIDELINES.md](GUIDELINES.md)는 작업 결과 기록 위치가 아니다.
- 기존 소스·메소드·호출부·테스트는 문서 기준 상대 경로의 Markdown 링크로 연결하고, 특정 위치는 `#L41` 같은 줄 위치 fragment로 표시한다. 후보 번호는 상세 절의 앵커로 연결한다. 폴더 구조를 코드 블록으로 보여줄 때도 기존 파일을 여는 링크를 함께 제공하며, 생성 예정 경로는 예정임을 표시하고 깨진 링크를 만들지 않는다.
- 즉시 적용한 내부 정리와 승인 대기인 큰 변경을 구분하고 후보별 승인·적용 여부와 검증 결과를 남긴다. 적용 전 코드가 달라졌는지 확인하고, 적용 후 문서의 설명·링크·줄 위치·앵커도 실제 코드에 맞춘다. 문맥이나 담당자가 바뀌어도 이 MD에서 이어가며 기존 승인을 다시 묻지 않는다.
- 완료 보고에는 적용한 내부 정리, 검증 결과와 큰 변경 제안 MD 링크를 제시한다. 의사결정 기록 등 저장소의 마무리 지침도 따른다.
