# 가독성 리팩토링

코드를 읽는 사람이 각 구성요소의 책임과 처리 순서, 주요 분기와 오류 경로를 빠르게 설명할 수 있도록 실제 코드를 개선한다. 클래스·메소드 수나 줄 수보다 이해하는 데 필요한 문맥과 파일 이동이 줄었는지로 판단한다. 저장소의 언어·명명·배치 관례를 따른다.

## 먼저 확인할 것

- 요청된 범위의 진입점, 호출부, 관련 테스트를 읽고 현재 처리 흐름과 유지해야 할 계약을 파악한다. 책임이 섞인 곳과 흐름을 가리는 부분을 기준으로 변경 범위를 정한다.
- 입력과 출력뿐 아니라 예외 전파, 외부 호출 순서와 횟수, 상태 갱신 시점, 취소, 재시도, 자원 수명을 보존한다. 기존 버그로 의심되는 동작도 리팩토링에 섞어 임의로 바꾸지 않는다.
- 사용자 변경을 보존하고 관련 부분부터 정리한다. 별도 요청이 없는 공개 API 변경이나 저장소 전체의 형식 변경으로 확장하지 않는다.

## 바로 수정할 부분과 승인받을 부분

- 메소드 내부의 조건식·중첩 정리, 지역 변수·상수 이름 개선, 같은 클래스 안의 비공개 보조 메소드 추출처럼 기존 클래스·파일 안에서 끝나는 작은 수정은 별도 확인 없이 진행한다. 기존 동작과 외부에서 호출하는 방식은 유지한다. 다만 아래의 대규모 분석으로 묶어 검토하는 범위는 통합 제안서 승인 후 수정한다.
- 클래스·스크립트 분리, 파일·폴더 생성, 기존 파일 이동·이름 변경처럼 역할 배치나 프로젝트 구조를 바꾸는 작업은 먼저 후보로 제시하고 사용자가 승인하면 적용한다. 아래에서 분리나 재배치를 권하는 경우에도 이 기준을 따른다.
- 후보마다 현재 문제, 대상 파일, 분리·이동할 경로, 각 파일·폴더가 맡을 역할, 영향받는 호출부를 짧게 정리한다. 여러 파일을 묶는 안은 변경 전후 폴더 구조도 함께 보여 사용자가 구체적인 배치를 판단할 수 있게 한다.
- 승인 전에는 해당 후보의 파일·폴더를 만들거나 옮기거나 분리하지 않고, 그 변경을 전제로 한 import 경로 수정도 하지 않는다. 후보와 독립적인 메소드 내부 개선은 계속 진행할 수 있다.
- 승인받은 후보는 승인 범위 안에서 다시 확인하지 않고 진행한다. 일반적인 가독성 개선 요청만으로 파일·폴더 구조 변경까지 승인받았다고 간주하지 않는다.

## 범위가 커서 대화 문맥에 담기 어렵다면 분석을 나누고 MD로 통합한다

- 여러 기능 영역과 많은 파일을 함께 살펴야 해서 분석 근거와 변경 후보를 대화 문맥에 유지하기 어렵다고 판단되면, 기능 영역별로 서브에이전트에게 분석을 나눠 맡긴다. 작은 메소드 수정에도 이 절차를 일괄 적용하지 않는다.
- 각 서브에이전트에는 담당 범위, 관련 경로, 보존할 동작, 서로 다른 MD 출력 경로를 지정한다. 필요한 문맥만 전달하고, 소스 코드는 읽고 분석하되 수정하지 않도록 한다. 여러 에이전트가 같은 보고서를 덮어쓰지 않게 한다.
- 각 MD에는 검토한 파일·메소드 위치, 현재 처리 흐름, 문제와 근거, 변경 후보와 예상 경로·역할, 영향받는 호출부, 검증 계획, 확인하지 못한 부분을 기록한다. 코드 전체나 대화 전문을 복사하지 않고, 필요한 근거를 다시 찾을 수 있게 쓴다.
- 분석 MD는 저장소의 기존 작업 산출물 위치에 두고, 정해진 위치가 없으면 작업별 임시 폴더에 둔다. 이 절차의 분석·통합 MD 작성은 승인 전에 가능한 산출물이며, 제품의 소스 파일·폴더를 바꾸는 작업과 구분한다.
- 서브에이전트의 대화 응답은 MD 경로, 핵심 결론, 미확인 사항으로 짧게 받는다. 메인 에이전트는 보고서의 요약을 먼저 읽고 필요한 근거를 확인해, 중복·상충하는 제안과 영역 사이의 영향을 정리한다.
- 메인 에이전트는 하나의 통합 MD에 후보별 식별자, 변경 이유와 범위, 파일·폴더의 변경 전후 배치, 적용 순서, 위험과 검증 계획을 정리한다. 개별 분석 MD를 연결하고, 확인한 사실과 추가 확인이 필요한 판단을 구분한다.
- 통합 MD를 사용자가 읽을 수 있는 링크로 제시하고, 승인받은 후보만 코드에 반영한다. 이 분석으로 묶은 범위에서는 메소드 내부 수정도 승인 전에는 적용하지 않는다. 해당 범위 밖의 독립적인 작은 수정은 기존 진행 기준을 따른다.
- 적용 전에는 분석 당시의 코드와 현재 코드가 달라졌는지 확인한다. 통합 MD에 후보별 승인 여부, 적용 여부, 검증 결과와 남은 작업을 갱신한다. 대화 문맥이 정리되거나 담당이 바뀌어도 이 문서에서 이어가고, 승인된 범위를 다시 묻지 않는다. 후보의 범위가 달라지면 변경분을 제시해 승인받는다.
- 서브에이전트를 사용할 수 없으면 영역별로 순차 분석해 같은 MD 기록·통합·승인 절차를 따른다.

## 책임과 처리 흐름

### 한 클래스에 여러 작업이 섞여 있으면 나눈다

- 한 클래스에 파싱, 집계, 저장, 화면 표시가 섞여 있어 필요한 처리를 찾기 어렵다면 작업별 분리 후보를 만든다. 클래스 이름과 파일 위치만으로 어디에서 어떤 일을 하는지 알 수 있게 한다.
- 상태가 필요한 책임은 상태와 그 수명을 함께 소유하는 클래스로 묶는다. 상태 없는 계산은 함수나 모듈로 분리할 수 있다. 분리하려는 모든 일을 클래스로 만들지는 않는다.
- 상태를 여러 클래스로 흩어 서로의 내부 값을 수정하게 만들지 않는다. 의존 방향을 명확히 하고 순환 의존을 피한다. `Manager`, `Helper`, `Utils` 같은 포괄적인 이름에 책임을 다시 모으지 않는다.
- 일부 기능을 재사용하려고 상속했는데 불필요한 메소드까지 물려받거나 계속 덮어쓰고 있다면, 필요한 작업을 함수나 객체로 받아 사용하는 방식을 검토한다. 부모 클래스를 여러 단계 따라가야 동작을 이해할 수 있는지도 확인한다.

### 분리한 파일이 같은 폴더에 많아지면 하위 폴더로 묶을지 검토한다

- 클래스를 나누면서 생긴 스크립트가 같은 폴더에 계속 늘어 어떤 파일이 어떤 작업을 맡는지 찾기 어렵다면, 관련 파일을 기능·역할별 하위 폴더로 묶는 후보도 만든다. 파일 분리 후보를 제시할 때 분리 후의 폴더 배치까지 함께 검토한다.
- 함께 읽거나 수정하는 파일을 가까이 두고, 폴더 이름과 그 안의 파일 이름으로 담당 작업이 드러나게 한다. 파일 개수만으로 폴더를 나누거나 파일 하나마다 폴더를 만들지 않고, 지나치게 깊어져 처리 흐름을 따라가기 어려워지는 배치는 피한다.

### 메소드는 한 작업을 맡고, 처리 순서가 보이게 한다

- 메소드 하나에는 한 가지 작업을 맡긴다. 전체 처리를 조율하는 메소드에는 단계별 메소드 호출을 처리 순서대로 나열한다.
- 상위 메소드에서 `readInput → parseRecords → aggregateUsage → saveSummary`처럼 주요 알고리즘의 흐름이 읽히게 한다. 단계 이름 사이에 바이트 처리나 쿼리 조립 같은 세부 구현을 섞지 않는다.
- 호출 흐름을 따라가려고 파일 위아래를 계속 오가야 한다면, 저장소의 배치 관례 안에서 진입 메소드 아래에 관련 메소드를 가까이 두고 호출 순서에 맞춰 배치한다.
- 이벤트 처리기가 또 다른 이벤트를 발생시켜 여러 파일을 찾아야 전체 흐름을 알 수 있다면, 순서가 정해진 작업을 상위 메소드 한곳에서 조율하는 방식을 검토한다. 기존 구독자에게 전달되는 이벤트와 비동기 실행 시점은 유지한다.
- 분리한 메소드에는 실제 처리 내용을 드러내는 이름을 붙인다. `step1`, `handleData`, `processInternal`처럼 본문을 다시 읽어야 이해되는 이름을 피한다.
- 줄 수에 맞추기 위한 분할, 의미를 더하지 않는 전달 메소드, 한 줄을 확인하려고 여러 파일을 따라가야 하는 추상화를 만들지 않는다. 분리 전보다 이해하기 어려워지면 경계를 다시 잡는다.

### 정상 경로와 분기 조건을 드러낸다

- 잘못된 입력, 처리 대상 없음, 조기 종료 조건을 guard clause와 early return으로 분리해 정상 경로를 평평하게 만든다. 반환 위치를 옮길 때 기존 검증 순서와 부수효과, `finally`의 실행을 보존한다.
- 긴 조건식과 중첩 삼항식은 의미 있는 지역 변수나 판정 함수로 풀어 쓴다. 조건식 평가 횟수와 단락 평가를 보존하고, 상태를 바꾸는 함수를 단순 판정처럼 숨기지 않는다.
- 같은 구분 값에 대한 분기는 명확한 `switch`나 대응표로 정리할 수 있다. 실제 규칙에 맞는 표현을 선택하고, 분기 개수만을 이유로 전략 클래스나 프레임워크를 도입하지 않는다.
- 중첩을 함수 안으로 옮겨 숨기는 데 그치지 않는다. 각 분기의 목적과 다음 단계가 호출부에서도 드러나는지 확인한다. 필요한 중첩을 없애려고 흐름을 왜곡하거나 임의의 중첩 깊이를 강제하지 않는다.

### try는 오류를 처리할 작업만 감싼다

- `try` 범위는 해당 오류를 처리할 작업에 맞춘다. 서로 다른 복구나 정리 책임이 없는 중첩 `try`는 정리하고, 독립적인 복구 경계라면 그 차이가 드러나도록 분리한다.
- 오류를 빈 `catch`, 임의의 기본값, 무조건적인 성공 반환으로 숨기지 않는다. 기존 전파·재시도·부분 성공 동작을 보존한다. 오류를 변환해야 할 때는 원인과 필요한 문맥을 유지한다.
- 자원 해제와 트랜잭션 종료는 성공·실패·조기 반환 모두에서 유지한다. 로그를 여러 계층에 추가해 같은 실패를 중복 기록하지 않는다.

## 이름, 데이터와 고정값

### 이름으로 의미와 단위를 표현한다

- 변수와 반환값은 담긴 데이터의 의미를, 함수와 메소드는 하는 일을 드러내게 한다. 같은 개념에는 같은 용어를 사용한다. `data`, `temp`, `result` 같은 이름은 문맥만으로 대상이 분명할 때 사용한다.
- 시간·크기·비율은 `timeoutMs`, `sizeBytes`, `usagePercent`처럼 단위가 드러나게 한다. 판정 값과 함수는 `is`, `has`, `can`, `should` 등 코드베이스의 관례에 맞춘다.
- `saveSummary` 안에서 예상 밖의 원격 조회나 전역 초기화를 수행하는 것처럼 이름에 없는 중요한 효과를 숨기지 않는다. 순수 판정과 상태 변경이 함께 있다면 책임을 분리하거나 이름에 드러낸다.

### 고정값은 의미 있는 상수로 선언한다

- 제한값, 시간 간격, 변환 계수, 정책 문자열과 반복되는 식별자 같은 고정값은 리터럴로 박아 두지 않고 의미 있는 이름의 `const` 또는 해당 언어의 상수로 선언한다. 기존에 같은 의미의 상수가 있으면 재사용한다.
- `MAX_RETRY_COUNT`, `REFRESH_INTERVAL_MS`처럼 용도와 단위가 드러나게 하고, 적용 가능한 가장 좁은 범위에 둔다. 여러 모듈이 공유하는 정책일 때만 공통 위치로 옮긴다.
- 값이 같아도 의미와 변경 이유가 다르면 별도 상수로 둔다. 모든 고정값을 한 파일에 모으거나, 숫자를 철자로 바꾼 이름만 붙여 의미를 감추지 않는다.
- 현재 고정값을 상수로 만드는 작업과 사용자 설정을 추가하는 작업을 구분한다. 요청 없이 설정 항목을 늘리지 않는다.

### 인자·반환값의 뜻과 상태가 바뀌는 위치를 드러낸다

- `run(true, false)`처럼 호출만 보고 뜻을 알 수 없는 인자는 명명된 옵션이나 목적이 다른 함수로 표현한다. 함께 쓰이는 도메인 값은 응집된 타입으로 묶되, 인자 수를 줄이려고 무관한 값을 한 객체에 넣지 않는다.
- 성공, 실패, 값 없음, 빈 결과의 의미를 호출부에서 구분할 수 있게 한다. 기존 계약을 보존하면서 타입과 이름으로 뜻을 드러내고, 타입 단언으로 불확실성을 숨기지 않는다.
- 여러 boolean의 조합을 확인해야 현재 상태를 알 수 있고 동시에 켜지면 모순되는 경우가 있다면, 하나의 상태값과 상태별 데이터로 묶는 것을 검토한다. 성공과 실패처럼 서로 배타적인 상태가 동시에 표현되지 않게 하되, 독립적으로 바뀌는 상태는 따로 둔다.
- 계산·판단과 파일·네트워크·DB 입출력, 화면 갱신을 분리한다. 입력을 몰래 수정하거나 여러 곳에서 공유 상태를 갱신하는 흐름을 줄이고, 갱신 책임과 시점을 드러낸다.
- 지역 값은 가능한 한 재할당 없이 표현한다. 전역 변수나 클래스 필드를 단순한 중간 계산의 전달 통로로 사용하지 않는다.

## 다른 기능과 외부 데이터 연결

- API 필드명이나 DB 컬럼명이 계산·화면 코드까지 퍼져 있어 외부 형식이 바뀔 때 여러 곳을 함께 고쳐야 한다면, 데이터를 읽는 곳에서 내부에서 사용할 형태로 변환한다. 내부 코드는 변환된 값을 사용하게 하고, 단순한 데이터 전달에 불필요한 변환 단계를 늘리지 않는다.
- 다른 기능의 내부 파일이나 저장 구조를 직접 알아야 호출할 수 있다면, 외부에서 사용할 함수와 타입을 따로 공개하고 호출부는 그것을 사용하게 한다. 내부 파일을 옮기거나 구현을 바꿀 때 호출부까지 연쇄 수정하지 않도록, 필요한 작업만 공개한다.

## 중복과 설명

- 같은 코드나 비슷한 처리 흐름이 세 곳 이상 반복되면, 별도 메소드·함수 또는 공통 구조로 묶을지 검토한다. 한 곳을 수정할 때 다른 곳도 같은 이유로 수정해야 하는지, 공통 이름을 붙였을 때 역할이 더 명확해지는지 확인한다.
- 같은 종류를 구분하는 `if`·`switch`가 여러 메소드에 흩어져 있어 새 종류를 추가할 때마다 함께 고쳐야 한다면, 종류별 처리를 별도 함수나 클래스로 분리할지 검토한다. 공통 코드는 분리한 처리를 호출하게 하고, 새 종류는 해당 처리와 이를 선택하는 부분을 추가해 연결한다.
- 반복 횟수는 공통화를 검토하는 신호로 사용한다. 같은 규칙을 구현한 중복은 한곳에서 관리하되, 겉모양만 비슷하고 변경 이유가 다른 코드는 유지할 수 있다. 두 곳의 중복이라도 같은 규칙을 반드시 함께 수정해야 한다면 공통화를 검토할 수 있다. 합치기 위해 모드 플래그와 예외 분기가 계속 늘어나면 따로 두는 편이 나은지 다시 판단한다.
- 주석은 코드만으로 알 수 없는 이유, 외부 제약, 불변조건과 트레이드오프를 설명한다. 처리 순서는 이름과 코드 구조로 드러내고, 코드가 하는 일을 그대로 번역한 주석으로 복잡한 구조를 덮지 않는다.
- 분리·이름 변경으로 낡은 주석과 설명도 함께 맞춘다. 관련 범위에서 사용하지 않는 것이 확인된 잔재만 제거하고, 무관한 정리를 섞지 않는다.

## 검증과 마무리

- 변경 위험에 맞는 기존 테스트와 저장소의 필수 검사를 실행한다. 복잡한 분기나 상태 변경에 보호가 부족하면 정상·빈 입력·오류 등 실제로 달라질 수 있는 계약을 검증하는 테스트를 보강한다. 메소드 이름이나 분할 모양만 고정하는 테스트는 추가하지 않는다.
- 조건식 평가, 반복 순서, 정렬, 예외, 기본값과 null 처리, 객체 공유, 비동기 실행 순서가 유지되는지 변경 부분을 확인한다. 순차 처리를 병렬 처리로 바꾸는 일을 가독성 개선에 섞지 않는다.
- 짧은 코드로 바꾸면서 반복 조회, 불필요한 전체 순회·복사, 중간 컬렉션, 무제한 할당을 늘리지 않았는지 확인한다. 실행 비용이 달라질 근거가 있으면 해당 경로를 검증하고 비용을 설명한다. 관련 없는 벤치마크를 일괄 추가하지 않는다.
- 진입점만 읽고 주요 단계와 분기 이유를 설명할 수 있는지, 각 책임의 위치를 예측할 수 있는지 다시 읽는다. 필요한 검증이 실패했으면 원인을 해결하거나 검증하지 못한 범위를 명확히 보고한다.
- 완료 보고에는 분리한 책임, 읽기 쉬워진 흐름, 수행한 검증과 남은 제약을 짧게 적는다. 저장소가 의사결정 기록을 요구하면 해당 기준을 따른다.
