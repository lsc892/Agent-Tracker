# SQLite 보조 인덱스 제거 후 조회 실험

실험일은 2026-11-23이고 조회 시간대는 `Asia/Seoul`이다. 로컬 DB의 같은 스냅샷에서 앱이 실행한 SQL 77개와 조회 API 조건 63개를 비교했다. A는 기존 인덱스를 유지했고 B는 `CREATE INDEX`로 선언된 인덱스 9개를 제거했다. 두 후보 모두 PK, `UNIQUE` 제약의 자동 인덱스, SQLite의 `automatic_index` 기본 설정을 유지했다.

## 가장 느린 SQL

B 중앙값 기준이다. 괄호는 P10–P90이며 시간 단위는 모두 ms다. 각 행의 실제 SQL과 바인딩, A/B 실행 계획을 원시 JSON에 기록했다. [원시 결과](DbTradeoff-IndexRemovalExplain.json)

| Q12 | 전체 기간 세션별·제공자별, API 비용 포함 | 12.41 (9.47–12.89) | 12.68 (10.95–14.82) |
| Q38 | 전체 기간 월별·모델별, API 비용 포함 | 11.21 (10.04–11.76) | 11.37 (9.92–11.90) |
| Q06 | 전체 기간 일별·제공자별, API 비용 포함 | 10.28 (9.41–10.86) | 10.41 (9.76–10.97) |
| Q42 | 전체 기간 세션별·모델별, API 비용 포함 | 10.05 (8.71–11.11) | 10.38 (9.08–11.48) |

Q36의 핵심은 다음과 같다. 실제 SQL은 모델별 토큰과 비용을 정규화한 뒤 평균·합계 및 전체 그룹 수를 함께 계산한다.

```sql
-- Q36의 JOIN 및 집계 구조
FROM turn_summary t
LEFT JOIN turn_model_usage m ON m.turn_id = t.id
LEFT JOIN turn_costs c ON c.turn_id = t.id
-- 바깥 SELECT에서 시작 시각을 현지 날짜(period)로 변환
GROUP BY provider, model, period
-- 날짜와 제공자·모델 등으로 정렬한 뒤 페이지 제한
```

두 계획 모두 `turn_summary`를 끝까지 순회하며 `turn_model_usage` 및 `turn_costs`를 기본 키로 조회했다. A는 `idx_summary_project_period`, B는 `sqlite_autoindex_turn_summary_1` 순서로 순회했고, 양쪽 모두 `USE TEMP B-TREE FOR GROUP BY`와 `USE TEMP B-TREE FOR ORDER BY`가 있었다. 반환된 69개 그룹은 일치했다. 짝별 B−A는 P10 −2.34ms, P90 +1.42ms로 양방향이어서 A/B 간 시간 우열을 확정하기 어렵다.

비용을 끈 대응 SQL Q35는 `usage_model_daily`의 236행으로 같은 일별·모델별 통계를 집계했다. B에서 1.67ms (1.61–2.40)로, 관측된 최장 조회는 인덱스 제거보다 비용 포함 시 요청 단위 집계 경로를 타는 조건과 관련이 크다. 이 비교에는 입력 행 수, 날짜 변환, JOIN과 집계식 차이가 함께 들어 있다. 조회 API 전체에서도 Q36을 실행하는 조건이 B에서 가장 오래 걸렸고, 중앙값은 A 22.27ms, B 21.53ms였다.

## 인덱스 제거의 영향

| ID | 조회 | A 중앙값 | B 중앙값 | B가 느렸던 짝 |
| --- | --- | ---: | ---: | ---: |
| Q10 | 전체 기간 프로젝트별·제공자별 비용 집계 | 5.659 | 6.605 | 6/9 |
| Q28 | 프로젝트 한 달의 요청 목록, API 비용 포함 | 2.612 | 3.365 | 8/9 |
| Q24 | 프로젝트 하루의 요청 목록 | 0.789 | 1.198 | 9/9 |
| Q25 | 프로젝트 하루의 요청 수 `COUNT(*)` | 0.014 | 0.220 | 9/9 |
| Q02 | 일별 집계 사용 전 시작 시각 `MIN/MAX` 확인 | 0.0068 | 0.0935 | 9/9 |
| Q76 | `session_billing`에서 지정값 조회 | 0.0051 | 0.0051 | 5/9 |

- Q10의 중앙값 차이는 +0.947ms로 가장 컸다. B 계획에는 `GROUP BY` 임시 B-tree가 추가됐고, 짝별 차이는 P10 −0.98ms, P90 +3.32ms로 편차가 크다.
- Q28은 대상 프로젝트의 한 달 요청 337건 중 첫 100건을 반환했다. A는 제공자·프로젝트·기간을 인덱스에서 바로 좁혔다. B는 제공자에 속한 세션을 찾아 요청을 탐색한 후 프로젝트와 날짜를 걸렀다. 짝별 차이 중앙값은 +0.74ms였다.
- Q25는 상대 배율이 **15.6배**로 가장 컸고, 절대 차이는 약 **0.206ms**였다. 결과는 46건이다. A는 `idx_summary_project_period`에서 제공자·프로젝트·기간 조건을 모두 적용하고 테이블 행에 접근 없이 집계했다. B의 자동 인덱스는 `provider=?` 조건으로만 탐색했고 나머지 조건은 추가로 검사했다. 해당 요청 목록 API 전체는 1.15 → 1.62ms였다.
- Q02는 `idx_summary_period`의 커버링 탐색을 잃으면서 13.8배 느려졌다. 일별 집계 가능 여부를 확인하는 여러 조회가 이 SQL을 공유한다.
- Q76은 지정값이 없는 세션을 PK로 조회했다. 이어지는 Q77은 요청의 비용 기록에서 유형을 추론했으며 양쪽 모두 약 0.016ms였다. 두 계획은 후보 간 같았다.

## 데이터와 재현

| 원본 파일 | 프로젝트 | 세션 | 요청 | 요청별 모델 행 | 일별 요청 행 | 일별 모델 행 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 397 | 14 | 198 | 861 | 844 | 213 | 236 |

- 설치 DB v21을 읽기 전용으로 열어 SQLite backup으로 고정했다. 양쪽 사본에 현재 작업 트리의 동일한 빌드를 열어 v22 마이그레이션을 적용했다. 마이그레이션에서 추가한 winner 테이블 2개는 양쪽 모두 비어 있었다. 두 사본에서 `ANALYZE`를 실행한 뒤 읽기 전용으로 실측했다.
- 기간 케이스는 요청이 가장 많은 제공자·프로젝트 조합에서 가장 바쁜 현지 날짜(10월 24일), 그 날짜가 속한 달(2026년 10월), 같은 달 양끝을 12시간씩 줄인 경계 기간을 사용했다. 세션 케이스는 요청 41건인 가장 긴 세션을 썼다. 프로젝트 키와 세션 ID는 원시 결과에서 가렸다.
- 각 케이스를 준비 실행 2회 후 A/B 순서를 교대하며 9쌍 측정했다. SQL 시간은 준비된 statement의 결과 반환까지 포함한다. API 시간에는 SQL 준비와 실제 API가 실행한 개수 조회와 읽기 트랜잭션도 포함한다. 1회당 시간은 반복 묶음의 평균으로 계산했고, P10/P90은 9개 표본에 대해 선형 보간했다. OS 캐시를 비우는 실험과 최초 실행은 측정 범위에서 제외했다.
- 각 케이스의 SQL과 바인딩이 같은지 확인했고, 반환 순서·정수·결측값은 그대로, 비정수는 유효숫자 11자리로 정규화해 양쪽 결과를 비교했다. 전체 테이블 행 수, FK 및 무결성 검사도 일치했다. VM 연산 수와 실제 방문 행 수는 Node SQLite 바인딩에서 얻을 수 없어 측정하지 않았다.
- `dbstat` 기준 인덱스 9개가 할당한 공간은 323,584바이트(316KiB)였다. 제거 후 같은 크기의 79페이지가 재사용 가능한 페이지로 반환됐다. 파일의 할당 페이지 수는 양쪽 296페이지였다. 본 실험은 로컬 스냅샷의 조회 범위에 한정했고, 원본 파싱·쓰기 비용과 대량 데이터의 효과는 측정하지 않았다.
