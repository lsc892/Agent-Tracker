# JSONL 추가분 읽기와 SQLite 체크포인트 A/B

2026-11-28, Asia/Seoul. 사용자는 현재 JSONL에서 바뀐 부분만 읽고 필요한 상태를 SQLite에서 일괄 조회·갱신하는 후보를 실행해 정합성을 확인해 달라고 요청했다. 가정은 큰 변경 파일과 관련 원본의 재파싱을 줄이면 응답 반영 시간이 줄어든다는 것이다.

- **A**는 `e7cba67`이다. 수정 시각이 달라진 파일과 집계에 필요한 관련 파일의 본문을 읽는다.
- **B**는 검증용 워크트리에서 원본별 파서 상태, 마지막 완성 줄 위치, 응답 후보와 귀속 근거를 SQLite에 보관한다. 실험 도구가 파일 끝에만 쓰기를 수행한 경로를 알려주면, 같은 파일의 크기가 증가했는지 확인한 뒤 그 위치에서 파싱을 재개한다. 필요한 파일 체크포인트는 `SELECT` 한 번으로 가져오고, 갱신된 상태를 사용량과 같은 트랜잭션에서 저장한다. 부모 연결과 응답 확정은 TypeScript에서 처리하고 영향받은 세션의 일별 집계를 다시 만든다.

## 2. 정합성

- 69쌍의 추가 갱신과 별도로 수행한 경계 사례에서 요청·모델·도구·세션 결제 설정·원본 상태 등 영속 테이블 7개의 값과 일·월·세션·프로젝트 조회가 일치했다. 제공자·모델별 조회 평균을 JavaScript로 다시 계산했고 SQLite `integrity_check`와 `foreign_key_check`를 통과했다.
- 추가한 JSONL 행을 따로 검산해 요청 1건, 입력 123토큰, 출력 7토큰이 늘어났음을 확인했다. 합성 데이터는 생성 시 계산한 최초 요청 수·토큰 합계와 일치했다. 실로그 전체의 절대 합계는 현행 제품의 전체 파싱을 기준으로 대조했다.
- 실로그의 동일 응답 ID에 사용량 기록을 추가했을 때 263바이트를 읽었고, 요청 수 변화 없이 100토큰이 늘었다. 기존 내용을 고친 뒤 파일이 커졌지만 끝에만 썼다는 정보가 없는 경우에는 변경 파일 전체를 읽었다. 같은 크기에서 덮어쓰기, 파일 축소, 무변경 재갱신도 두 방식의 결과가 일치했다. 무변경 때는 양쪽 모두 본문을 0바이트 읽었다.
- 후보 타입 검사·린트, 실행기 구문 검사와 diff 검사를 통과했다. 제품 단위 테스트 전체 실행, 변경된 압축 로그의 이어 읽기, 자동 파일 감시를 통한 append 판정은 이 실험 범위 밖이다.

## 3. 분석

- 실로그의 1건 추가는 **51.6% 단축**됐다. 갱신당 읽은 파일이 6개에서 1개로, 원본 읽기 단계는 219.80ms에서 11.60ms로 줄었다. 이전 상태를 읽는 B의 SELECT는 표본마다 한 번 실행됐고 중앙값은 3.19ms였다. 갱신된 체크포인트 하나를 같은 저장 트랜잭션에서 썼다. B의 디렉터리 탐색은 138.77ms였다.
- 합성 입력은 관련 원본이 없고 파일이 작아 읽기량 감소가 전체 시간에 미친 영향이 작았다. 두 합성 입력의 갱신 시간 범위는 겹쳤다. 실로그 첫 수집 한 쌍은 4.44초 → 4.77초였고, 781개 체크포인트를 보관하면서 SQLite는 약 34배 커졌다.

## 4. 채택 결정

사용자 결정에 따라 기존 갱신 방식을 유지하고 측정 결과를 보관한다. 51.6% 단축은 큰 관련 로그가 있는 세션에 요청이 추가된 갱신에서 측정했다. 같은 로그를 변경 없이 다시 확인하면 기존 방식도 본문 읽기를 건너뛴다. 실로그 무변경 비교 한 쌍에서 두 방식 모두 0바이트를 읽었고 갱신은 132.97ms → 134.47ms였다. 결정에는 변경 없는 반복 갱신이 자주 발생한다는 사용자의 판단과 SQLite 크기가 1.01MiB → 34.36MiB로 늘어난 비용을 반영했다.
