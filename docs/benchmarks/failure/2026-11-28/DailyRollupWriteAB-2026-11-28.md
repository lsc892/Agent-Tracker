### 측정 조건과 정합성

- 2026-11-28 22:33–22:37(서울), Windows x64, Ryzen 5 7500F, Node 24.14.1, SQLite 3.51.2에서 실행했다. 파일 준비 Worker는 최대 4개다. 실로그는 789파일, 553,538,744바이트의 고정 사본이다. 합성 입력은 고정 산식으로 Claude·Codex를 절반씩 배치했다. 프로젝트 키는 10개이고 세션당 대화 수는 10,000건에서 50개, 100건에서 5개다. Worker의 첫 통계 범위는 서울 기준 10월 30일~11월 28일이며 추가 필터·페이지·모델·도구 요청을 실행했다.
- 입력별 준비 3회 뒤 A를 처음과 마지막에 교대하고 B 순서를 순환해 20회 측정했다. 각 표본은 추가 전 DB 사본을 복원해 시작했다. OS 파일 캐시를 유지했다. 파일·DB 사본 준비, 제품 Worker 시작, DB 열기, 결과 검산은 시간 측정 범위에서 제외했다. 피크 heap은 수집 스레드의 5ms·단계 경계 표본 중 최대값이며 피크 RSS는 조회까지 포함한 프로세스의 최대값이다. 웹뷰 화면 그리기는 측정 범위 밖이다. 기준의 `media` 해시에는 로컬 빌드가 만든 웹뷰 i18next 파일 2개가 추가로 포함된다.
- 후보별 세 규모의 빈 DB 구축 결과와 본 측정 180쌍에서 요청 수, 토큰, 집계 및 이름 테이블, 비용, 조회 평균·그룹 수, 도구 응답이 일치했다. 모든 표본에서 SQLite 무결성·외래 키를 확인했다. 합성 초기 요청 수·토큰은 생성 산식과 같았다. 세 입력의 추가분은 독립 원본 검산과 같은 **1대화·입력 123·출력 7토큰**이었다. 실로그 초기 전체 수치의 독립 검산 범위는 추가분이다.
- 기준과 세 후보의 TypeScript 컴파일, 변경 파일 ESLint, Git diff 공백 검사를 통과했다. 별도 회귀 스위트와 실사용 환경 최초 구축 성능 반복 측정은 미실행이다. 원시 표본과 소스·빌드·입력 해시는 [원시 JSON](DailyRollupWriteAB-2026-11-28.json)에 있다.

## 2. 분석

- **날짜 재사용.** 합성 1만 건에서 피크 heap이 10.616 → 10.551MiB로 줄었고 19/20쌍에서 더 작았다. SQL 날짜 변환을 줄였지만 실로그의 일별 저장 시간은 12.405 → 12.669ms였고 짝별 차이의 중간 50%가 0을 포함했다.
- **도구 변경분.** 실로그와 합성 1만 건의 WAL은 각각 **36.24 → 28.20KiB(−22.2%)**, **40.27 → 20.15KiB(−50.0%)**였으며 각각 20/20쌍에서 줄었다. 줄어든 WAL은 각각 8,240바이트와 20,600바이트다. 합성 100건의 WAL은 같았고 일별 저장 시간은 12.492 → 13.004ms였다. 불필요한 행 재쓰기를 건너뛴 만큼, 들어온 키와 기존 키의 차집합을 구하는 작업이 추가된다.
- **프로젝트 정리.** 실로그에서 정리 구간이 **0.543 → 0.157ms(−71.0%)**, 합성 1만 건에서 **0.614 → 0.144ms(−76.5%)**로 줄었다. 두 입력 모두 20/20쌍에서 더 빨랐다. 전체 시간 개선은 같은 반복에서 재현되지 않았다.
- **판정.** 세 후보 모두 전체 시간 차이의 중간 50%가 세 입력에서 0을 포함했다. 메인 DB 크기는 모든 표본에서 같았다. WAL 절감이 목표라면 도구 변경분 후보가 근거가 있다. 세 후보는 실험 브랜치에 보관했다.
