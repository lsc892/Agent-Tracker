# JSONL 경계 줄의 청크별 선택 파싱 A/B

사용자는 한 청크에서 끝나는 일반 줄은 바로 문자열로 파싱하고, 청크 경계를 넘는 줄은 읽으면서 불필요한 큰 필드를 건너뛰도록 요청했다. 긴 줄에서 전체 행의 복사·디코딩 비용을 줄이면 읽기·파싱 메모리가 낮아질 것으로 가정했다.

- **A**는 파일마다 줄 버퍼를 재사용하는 `e915791`이다. [선행 비교](../../success/2026-11-27/JsonlRowBufferReuseAB-2026-11-27.md)
- **B**는 `perf/stream-long-jsonl`의 `405d6db`다. 경계 줄을 기존 바이트 파서에 연결해 JSON 문법 상태를 이어가고, 행 유형에 따라 필요할 수 있는 후보 필드만 모은다. LF에서 축소 행을 기존 선택기로 읽어 `type`의 위치·중복과 지연 해석을 처리한다. 같은 청크의 일반 줄, 이미지 필터 및 보관 바이트 상한은 기존 흐름을 사용한다.

## 실로그 최초 수집

실로그 751파일, 506,096,130바이트, 1,731대화를 빈 DB에 수집했다. 표는 각 실행의 중앙값이다.

| 지표 | A | B | 변화 |
| --- | ---: | ---: | ---: |
| 최초 수집 전체 | 4,473.39 ms | 4,435.39 ms | −0.8% |
| 로그 읽기·파싱 | 4,019.48 ms | 3,974.92 ms | −1.1% |
| 파일 워커 `ArrayBuffer` 피크 | 60.41 MiB | 50.87 MiB | −15.8% |
| 파일 워커 V8 힙 피크 | 65.78 MiB | 69.61 MiB | +5.8% |
| 수집 스레드 V8 힙 피크 | 70.23 MiB | 70.14 MiB | −0.1% |
| 프로세스 피크 RSS | 837.85 MiB | 834.85 MiB | −0.4% |

읽기·파싱 시간은 20쌍 중 15쌍에서 낮았다. 파일 워커 `ArrayBuffer` 피크는 16쌍에서 낮았고, 프로세스 RSS는 10쌍씩 방향이 갈렸다. 축소 행을 다시 선택하는 비용도 전체 파싱 시간에 들어간다. 시간과 전체 RSS의 중앙값 차이는 작았다.

## 철회 결정

파일 워커의 임시 바이트 버퍼 피크는 15.8% 줄었다. 실로그 최초 수집 전체는 38.00ms(0.85%) 단축됐고 피크 RSS는 0.4% 줄었으며, 파일 워커 V8 힙 피크 중앙값은 5.8% 증가했다. 사용자 요청에 따라 청크별 후보 선택을 철회하고 A의 파일별 줄 버퍼 재사용으로 복원했다. 실험 구현과 원시 표본은 보존했다.

별도 실로그 1회에서 경계 줄 16,551개가 스트리밍 경로를 사용했다. 이미지 본문 필터를 통과해 바이트 문법 검사기에 들어간 392.11 MB 중 후보를 모은 축소 행은 총 11.99 MB였다. 이 값은 축소 행의 누적 크기이며 메모리 피크는 별도로 관측했다.

## 합성 입력과 대화 한 건 추가

각 셀은 A → B의 경과 시간 중앙값이다. 평균 조회는 대화 한 건을 추가한 DB에서 그룹별 전체 페이지를 읽는 시간이다.

| 지표 (ms) | 실로그 | 합성 10,000대화 | 합성 100대화 |
| --- | ---: | ---: | ---: |
| 최초 수집 전체 | 4,473.39 → 4,435.39 | 960.42 → 962.60 | 58.19 → 59.84 |
| 최초 읽기·파싱 | 4,019.48 → 3,974.92 | 351.04 → 354.01 | 32.51 → 33.50 |
| 대화 한 건 추가와 커밋 | 301.60 → 296.52 | 73.75 → 71.90 | 41.51 → 42.69 |
| 일별 평균 토큰 조회 | 2.226 → 2.338 | 1.447 → 1.518 | 1.402 → 1.338 |
| 월별 평균 토큰 조회 | 0.968 → 0.969 | 0.658 → 0.656 | 0.455 → 0.520 |
| 세션별 평균 토큰 조회 | 4.154 → 4.710 | 2.084 → 2.004 | 0.656 → 0.613 |
| 프로젝트별 평균 토큰 조회 | 1.316 → 1.381 | 0.783 → 0.809 | 0.536 → 0.486 |

합성 입력과 대화 한 건 추가의 시간 차이는 작았다. 실로그 한 건 추가의 RSS 중앙값은 71.84 → 74.10 MiB였고, 20쌍 중 10쌍씩 방향이 갈렸다. 이 시나리오와 합성 입력에서는 수집 스레드가 직접 파일을 읽었다.

## 정합성

Skill 수집 켜짐·꺼짐 각각에서 실로그 237,821줄, 합성 30,100줄과 310줄의 추출값 및 행 오프셋 해시가 일치했다. 120쌍의 SQLite 테이블·토큰·Skill·이름·원본 상태와 네 평균 조회 결과가 일치했다. 합성 입력의 최초 대화·토큰 합계는 생성값과 같았고, 대화 한 건을 추가하면 각 입력의 대화 수와 합계가 각각 1대화·130토큰 증가했다. 타입 검사·린트·diff 확인을 완료했다.

## 측정 조건

Windows x64, Ryzen 5 7500F, Node 24.14.1, SQLite 3.51.2, Asia/Seoul에서 실행했다. 파일 워커 최대 4개, Skill 수집 켜짐, OS 파일 캐시 유지 조건을 사용했다. 빈 DB 최초 수집과 기준 DB 사본에 같은 대화 1건을 추가한 갱신을 각각 준비 3회 후 AB·BA 10회씩 비교했다. 수집 시간에 SQLite 커밋과 파일 워커 종료가 들어간다. 파일 워커 메모리는 5ms 및 작업 경계 표본에서 실행당 가장 높은 워커 값을 비교했다.

```powershell
node --no-warnings tests/.cache/json-stream-long-ab/run.cjs tests/.cache/json-stream-long-ab/rerun.json
```
