# 스트리밍 JSON 라이브러리 A/B

청크를 받는 동안 필드를 고르면 긴 줄을 복사하는 부담이 줄어 최초 수집 시간과 V8 힙 피크도 낮아질 수 있다고 가정했다. 세 빌드 모두 현재 Claude·Codex의 행 유형, 필드 및 Skill 설정을 사용했다.

- **A · 현재 수집기** `d4f8b76`. 긴 줄을 조립한 뒤 `projectJson()`이 필드를 고른다.
- **B · `stream-json` 3.9.0** `perf/stream-json`의 `a30c104`. 문자열을 `stringChunk` 토큰으로 받아 사용하지 않는 조각을 버린다.
- **C · `@streamparser/json` 0.0.26** `perf/streamparser-json`의 `3acd0fd`. 토크나이저와 문법 파서로 청크를 처리하고 완성된 문자열 토큰에서 필요한 값만 남긴다.

B와 C는 현재 선택표에서 유형별 후보 필드의 합집합을 만든다. 파일 청크를 토큰으로 처리하면서 후보만 남겨 축소한 JSON을 만들고, `projectJson()`으로 마지막 `type`에 따른 선택과 지연 해석을 처리한다. 이미지 본문 제거, 줄바꿈 경계, 저장 및 조회는 같은 경로를 쓴다.

## 판정과 검산

두 후보 모두 최초 수집과 1건 추가의 시간·힙 개선 기준을 충족하지 못했다. 실로그 최초 수집 프로세스 피크 RSS는 약 19% 내려갔고, 읽기·파싱은 B에서 75.8%, C에서 54.1% 길어졌다. 후보 구현에는 토큰 생성, 후보 JSON 재구성, 축소 JSON 재파싱이 들어간다. 이 비용은 구간 전체에 포함되며 각각의 실행 시간은 미측정이다. 이 결과의 비교 단위는 기존 필드 동작을 보존하도록 만든 두 통합 구현이다.

Skill 수집 켜짐·꺼짐 각각에서 실로그 237,821줄, 합성 30,100줄과 310줄의 추출 속성·값 및 행 오프셋 해시가 모두 일치했다. 각 측정에서 대화·모델·Skill·이름·원본 상태 테이블과 일·월·세션·프로젝트 조회 결과가 일치했다. 조회 결과는 일별 원본 집계 행에서 별도로 합산한 토큰과 완료 대화 평균으로 대조했다. 두 합성 입력의 최초 대화 수와 토큰 합계는 입력 생성값과 같았고, 같은 대화 한 건을 추가한 뒤 모든 입력에서 대화 1건과 토큰 130개가 증가했다. 최종 SQLite 무결성 검사와 원본 사본 복원 후 해시 확인을 통과했다.

## 측정 조건

- Windows x64, AMD Ryzen 5 7500F, Node 24.14.1, SQLite 3.51.2, Asia/Seoul, 파일 Worker 최대 4개, Skill 수집 켜짐. 수집 스레드와 파일 Worker의 V8 `heapUsed`는 5ms 간격 및 작업 경계에서 관측했다. 파일 Worker 값은 실행마다 가장 높은 Worker 피크를 골라 중앙값을 계산했다.
- 실로그는 751파일, 506,096,130바이트, 1,731대화다. 합성 입력은 제공자를 반씩 나눈 고정 데이터로, 10,000대화는 200세션에 50개씩, 100대화는 20세션에 5개씩 넣었다.
- 첫 수집은 빈 DB, 요청 추가는 매번 같은 기준 DB 사본에서 실행했다. 각 입력·시나리오별 준비 3회 뒤 20회를 측정했고, 각 후보와 기준의 선후 순서를 10회씩 교대했다. OS 파일 캐시를 유지했다. DB 사본 준비와 결과 검산은 수집 타이머 밖에서 수행했다.
