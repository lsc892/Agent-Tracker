# 누계 검산이 있는 턴만 합산하는 A/B

누계 검산에 쓰이지 않는 턴의 합계를 만들지 않으면 최초 집계의 힙과 시간을 줄일 수 있다고 가정했다. A는 `2ef80c3`의 작업 트리다. B는 검산 항목이 없을 때 별도의 턴별 합계를 생략하고, 항목이 있을 때만 같은 키의 턴을 합산한다. 대화의 모델·토큰 반영, 누계 보정, 진단 플래그는 같은 경로를 따른다. 최초 수집 진단에서 실로그 확정 응답 29,123개 중 8,687개, 합성에서는 모든 응답에 별도 검산 항목이 없었다. ## 결과

각 값은 A → B 중앙값이다. 시간은 ms, 메모리는 MiB다.

합성 10,000대화에서는 집계가 20/20쌍 빨랐고 `finish()` 직후 힙도 20/20쌍 줄었다. 실로그에서는 피크 힙이 0.54 MiB 감소했고 집계가 20쌍 중 15쌍 느렸다. 실로그에 누계가 있으면 여전히 합성 키를 만들고 `checks` 조회를 추가한 뒤, 해당 턴의 `totals`를 조회한다. 추가 조회가 집계 시간 차이에 기여했을 가능성이 있으며 함수별 CPU는 별도로 측정하지 않았다. 관측한 손익을 근거로 이 버전은 보류했다. 별도 맵 대신 검산 항목에 합계를 직접 누적하면 같은 키의 두 번째 조회를 줄일 수 있지만 아직 미측정이다.

## 측정 조건

Windows x64, Ryzen 5 7500F, Node 24.14.1, SQLite 3.51.2, Asia/Seoul, 파일 워커 최대 4개다. 실로그 751파일·506,096,130바이트와 Claude·Codex 반씩인 두 합성 입력으로 빈 DB의 최초 수집, 같은 기준 DB에 대화 한 건을 더한 수집을 각각 준비 3쌍, 측정 AB·BA 10쌍씩 실행했다. OS 파일 캐시를 유지했다. 힙은 수집 스레드의 5 ms와 단계 경계 표본이다. 평균 쿼리는 대화 추가 후 완료 대화를 분모로 전체 결과 페이지를 읽었다.

120쌍에서 SQLite 대화·모델·Skill·원본 상태와 네 조회 결과가 일치했다. 합성 결과는 생성기 기대값, 추가 1대화·130토큰은 추가한 원본과 대조했다. SQLite 무결성 및 외래 키 검사도 통과했다. 실로그의 전체 합계는 A/B 일치까지 확인했다.
