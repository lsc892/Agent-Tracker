# Codex 대기 호출을 SQLite로 옮기는 실험 결과

Codex 서브에이전트의 대기 호출이 파일당 1,024개를 넘으면, 부모 요청을 찾는 데 필요한 ID를 `Map`에서 임시 SQLite로 옮겼다. 한 파일에 대기 호출 10,000개를 넣고, 다음 턴이 시작된 뒤 결과를 돌려주는 조건에서 기존 방식과 비교했다. 아래 값은 준비 3쌍 뒤 A/B 순서를 교대해 측정한 10쌍의 중앙값이다.

| 지표 | 기존 `Map` | 임시 SQLite |
| --- | ---: | ---: |
| 결과 대기 중 GC 후 V8 힙 | 5.95 MiB | 5.03 MiB |
| 프로세스 최고 RSS | 46.89 MiB | 47.89 MiB |
| 호출과 결과 처리 시간 | 56.09 ms | 205.64 ms |

**결론은 기존 `Map`을 유지하는 것이다.** 합성 대량 입력에서 힙은 0.92 MiB 줄었지만 프로세스 최고 RSS는 1.00 MiB 늘었고, 처리 시간은 3.67배가 됐다. 실제 Codex 로그 370개에서는 파일당 대기 호출이 최대 1개였다. SQLite 전환은 0회였고 실제 로그 갱신에서 힙 절감은 관측되지 않았다.

다음 턴 이후에 받은 합성 결과 10,000개는 모두 원래 부모 요청에 연결됐다. 실제·합성 입력의 요청 수, 토큰 합계, 일별·월별·세션별·프로젝트별 평균도 전후 일치했다.
