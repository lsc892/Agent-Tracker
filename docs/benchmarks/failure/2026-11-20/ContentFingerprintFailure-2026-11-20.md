# SHA-256·XXH3-128 전수 본문 검증 실험 실패

실험일 2026-11-19~20, Asia/Seoul.

**채택 실패.** 기존 대화에 이어 쓰는 경우가 일부이고 새 대화 생성이 대부분이라는 사용 패턴을 기준으로, 매 갱신 때 저장된 대화 파일 전체의 내용을 검증하는 두 후보를 폐기했다. 전수 재파싱을 대체하면 갱신 시간이 크게 줄었다. 평소 쓰던 manifest 방식과 대조하면 실제 로그의 기존 파일 1건 추가와 무변경 갱신이 모두 느려졌다. 새 대화 파일만 추가하는 경우의 시간과 실제 사용 빈도는 미측정이다.

## 비교 방식과 실측

- **Manifest 기준**은 선택된 파일의 경로·크기·mtime·파일 정체성을 확인하고 변경 파일과 관련 원본만 파싱한다. 파싱 중에 계산한 내용 해시는 파일 이동 검증에 사용한다. 11-20 대조 워크트리 커밋은 `d758c4092e4a4624af75a2e913c679e282f801c1`이다.
- **SHA-256 체크포인트**는 이전 완성 줄까지의 원본을 다시 읽어 지문을 확인한 뒤, 지문이 일치하면 파서·응답 후보 캐시를 사용해 뒤에 추가된 줄부터 처리한다. 11-20 대조 워크트리 커밋은 `1148a437ce5efb5b632e623ece3d8686f93117a5`이다.
- **XXH3-128·SQLite DTO**는 `1148a43` 기반 작업 빌드다. 전체 본문 지문이 일치하면 저장된 집계를 재사용하고, 변경된 파일과 관련 원본은 다시 파싱한다. 영향 세션의 요청을 임시 DTO Map에서 계산해 달라진 행을 SQLite에 반영한다. 측정한 후보의 소스 SHA-256은 `9594bf06ed05bf502ef2c2a9407653bbe824a9d5654bc48fd5b6f96be84c4755`이다.

### Manifest 일반 갱신 대비

각 시간은 준비 표본을 제외한 10회 중앙값이다. 1건 추가는 모두 기존 파일 끝에 새 요청을 붙인 시험이다. 두 실험의 입력과 Worker 설정이 다르므로 같은 날짜의 측정값끼리 비교한다.

11-19에 고정한 manifest와 SHA-256 후보의 소스 SHA-256은 각각 `982ba0f72f14ee94212ec240d803795f4e1fa486a9d9589d91e897a6797fd8f0`, `77592b9d7a0f73e8b084697dca53723526cee39b0c3431b59223364ec37830b5`이다.

| 실험 | 실제 입력 | 작업 | Manifest → 후보 | 본문 읽기 | 후보/기존 시간 비율 |
| --- | --- | --- | ---: | ---: | ---: |
| 11-19 SHA-256 체크포인트, Worker 1개 | 387파일·836요청 | 기존 파일에 1건 추가 | 332.31 → 2,751.17ms | 25.88 → 538.19MiB | 8.28배 |
| 11-19 SHA-256 체크포인트, Worker 1개 | 동일 | 무변경 갱신 | 96.32 → 2,677.48ms | 0 → 538.19MiB | 27.80배 |
| 11-20 XXH3-128·DTO, Worker 최대 4개 | 388파일·842요청 | 기존 파일에 1건 추가 | 372.06 → 734.39ms | 14.85 → 543.90MiB | 1.97배 |
| 11-20 XXH3-128·DTO, Worker 최대 4개 | 동일 | 무변경 갱신 | 102.62 → 495.79ms | 0 → 543.89MiB | 4.83배 |

11-19의 기존 파일 1건 추가에서는 SHA-256 체크포인트로 파싱 행이 **2,869 → 4줄**로 줄었다. 11-20의 일반 1건 추가에서 두 후보가 파싱한 원본은 각각 1파일이었다. XXH3-128 후보가 검증한 본문은 약 **36.6배**였다. 파일 준비 시간은 **261.96 → 614.70ms**, 연결 성분 저장 시간은 **4.86 → 4.54ms**였다. 같은 날의 합성 10,000요청·100파일 일반 1건 추가도 **34.46 → 138.77ms**, 100요청·10파일은 **10.10 → 18.85ms**였다.

### 강제 전수 재파싱 대비

11-20의 388파일·842요청으로, manifest 기준의 시험 DB에서 모든 파서 버전을 무효화해 **전수 재파싱을 강제**한 별도 조건이다. XXH3-128 후보는 일반 갱신을 수행했다.

| 작업 | Manifest 전수 재파싱 → XXH3-128 | 시간 단축 | 파싱한 파일 |
| --- | ---: | ---: | ---: |
| 내용 무변경 | 4,006.41 → 520.73ms | 87.0% | 388 → 0 |
| 기존 파일에 1건 추가 | 3,681.94 → 745.06ms | 79.8% | 388 → 1 |

같은 11-20 실험의 빈 DB 최초 수집은 **3,945.31 → 3,328.63ms**로 15.6% 줄었다. 별도의 388파일·841요청 비교에서는 SHA-256 체크포인트를 XXH3-128·DTO로 바꾸면서 기존 파일 1건 추가가 **1,280.56 → 781.21ms**, 무변경이 **1,237.05 → 529.45ms**로 줄었다. 이 수치는 해시 구현·읽기 단위·파서 상태 관리·저장 방식이 함께 바뀐 후보 전체의 효과다.

## 알고리즘 한계와 결정

- **새 대화가 많을수록 파서 재개의 대상이 줄어든다.** 새 파일에는 재개할 상태가 없어 처음부터 파싱해야 한다. 기존 파일 몇 개만 바뀌는 일반 갱신에서는 manifest가 본문을 읽을 파일을 먼저 좁힌다. 체크포인트가 절약하는 일은 이어 쓰는 기존 파일의 앞부분 파싱이다. 전체 지문 확인은 그와 별개로 이전 대화의 본문을 계속 읽는다.
- **해시를 바꿔도 전체 본문 검증의 읽기량은 전체 로그 크기에 비례한다.** 파일 수를 `F`, 전체 본문 바이트를 `B`, 변경·관련 파일의 본문 바이트를 `P`라 두면 두 방식 모두 `F`개 파일을 탐색한다. manifest의 본문 처리는 `P`에 비례하며 무변경이면 `P = 0`이다. 전수 해시 검증에는 무변경이어도 `B`에 비례하는 읽기가 남는다. 오래된 파일에 가끔 이어 쓰는 패턴에서는 해당 파일을 전체 파싱하고 변경된 요청만 저장하는 단순한 경로를 선택했다.
- **지문 저장과 본문 읽기 비용을 구분한다.** XXH3-128 지문은 원시 16바이트, hex 문자열 32바이트다. 388파일에서는 hex 지문 자체가 **12,416바이트(약 12.13KiB)**다. 11-20의 일반 1건 추가 후 SQLite 파일은 **1,302,528 → 1,323,008바이트(+20KiB)**였다. 이 차이에는 스키마·레코드·페이지가 함께 반영된다. SHA-256 체크포인트 비교에서 실제 로그의 갱신 간 파서·응답 후보 Map을 직렬화한 크기는 **15.55MiB**였다.
- **메타데이터가 그대로인 수정은 감지 범위에서 빠질 수 있다.** 크기·mtime·파일 정체성이 모두 유지된 합성 100요청 편집 시험에서 manifest는 본문 0바이트를 읽고 **18,400토큰**을 유지했다. XXH3-128은 원본 1파일을 다시 파싱해 **18,500토큰**을 반영했다. 이 확인은 1쌍의 기능 시험이며 성능 표본에서 제외했다.

환경은 Windows 10, Intel Core i5-8250U, Node 24.19.0, SQLite 3.53.3이었다. 준비 3회 뒤 순서를 교대로 바꿔 각 10회 측정했으며 OS 파일 캐시는 통제하지 않았다. 시간은 실제 `refreshSummary` 진입부터 SQLite 저장·Worker 종료를 마치고 반환할 때까지다. 로그 사본 준비·복원·DB 열기와 결과 검증 시간은 제외했다. 11-20의 manifest 대조는 본 측정 **200쌍**, SHA-256 체크포인트 대조는 본 측정 **280쌍**에서 요청·모델·도구·비용·이름 및 집계 결과가 일치했다. 요청 추가의 기대값인 **+1건·+130토큰**, 외래 키, SQLite 무결성도 확인했다.
