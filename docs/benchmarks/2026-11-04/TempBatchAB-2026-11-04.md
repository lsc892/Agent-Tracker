# TEMP 집계 묶음 A/B 테스트

가정: 사용자는 기존 갱신에서 반복되는 임시 테이블 처리를 줄이는 알고리즘의 A/B를 요청했다. 에이전트는 연결 성분마다 반복하는 집계 SQL의 고정 비용을 여러 성분의 사전 집계로 줄이면 전체 재파싱이 빨라질 것으로 가정했다.

개선 방향: A = 현재 작업 트리의 TEMP 표·인덱스 재사용과 성분별 집계. B = 영향 세션 목록의 앞 32개 seed를 연결 성분 전체로 확장해 집계를 함께 준비하고 재사용한다. 저장 트랜잭션은 기존 성분 단위를 유지한다. 고아 요청 검사·삭제 보존·요약 출력은 현재 성분으로 한정하고 TEMP 결과 탐색 인덱스를 추가한다. 연결 성분을 나누지 않으므로 32는 세션·이벤트 행 수의 엄격한 상한이 아니다.

- **입력:** 현재 로그는 Claude 33파일·Codex 520파일(압축 450파일)의 고정 사본이며 수집 실패는 0건이다. 합성은 기존 생성기를 재사용했다. seed는 ordinal-v1(난수 없음), 제공자는 세션마다 교대해 요청 수가 반반, 프로젝트는 10개, 제공자별 모델 2개를 번갈아 쓴다. 1만 건은 세션당 100요청, 100건은 세션당 10요청이며 모두 완료 상태다. 기본 시각은 2026-07-01 + sessionIndex%14일, 100요청마다 하루를 더한다.
- **반복·캐시:** 입력별 준비 3쌍을 제외한 AB/BA 교대 10쌍. 매 실행 새 프로세스를 쓰고 각 시나리오 전에 같은 checkpoint DB를 복원한다. 입력 복사·변경·복원, DB 열기, 검증, 해시, IPC는 시간에서 제외한다. OS 캐시는 비우지 않았고 백그라운드 부하는 고정하지 않았다. 첫 준비 실행 중 저장소 검사가 겹쳤으며 본 측정 전에 종료했다.
- **추가:** 제공자별 가장 긴 허용 세션에 같은 요청 1건(+130 tokens)을 붙인 뒤 실제 refreshSummary의 파일 확인·전체 세션 재파싱·집계 갱신·COMMIT·정리까지 측정한다. 매 표본 후 로그 사본을 복원한다. 대량 시간을 나눈 값이 아니며 두 제공자도 각각 같은 사전 DB에서 시작한다.
- **재파싱·구축:** 사본 DB의 manifest.parser_version만 무효화한다. 최초 빈 DB 수집의 A/B는 **미측정**이다. JSON의 initialRefreshMsAUnpaired는 준비용 A 단독 값이며 비교에 사용하지 않는다. 영속 스키마 변경·마이그레이션은 없다. 매 갱신 첫 TEMP 생성·후보 인덱스 구축 비용은 측정에 포함한다.
- **조회·평균:** 준비된 일별 rollup, 고정 범위·Asia/Seoul·제공자 기준으로 실제 queryUsagePage를 1,000행씩 호출해 전체 결과와 COUNT를 반환할 때까지 측정한다. 조회별 준비 3회 뒤 회차당 1표본, A/B 각각 총 10표본이다. 평균의 분모는 완료 요청 중 토큰이 있거나 알려진 모델이 있는 요청이며 전체 합계·건수에는 미완료·빈 요청도 포함한다. 시간 미상은 별도 그룹으로 포함한다.

정확성: 준비 실행을 포함한 **312개 갱신 상태**에서 A/B 요청 수·토큰 합계·저장 호출 수·전체 의미 해시가 일치했다. 제공자/모델 × 전체/프로젝트/세션/일/월의 raw SQL과 공개 rollup 결과를 **3,120회** 대조했다. 고정 범위의 일·월·세션·프로젝트 평균은 정규화 원본 요청(turn_summary)을 독립 JS로 합산해 요청 수·토큰·완료/기록 표본 수·그룹별 평균·결과 건수까지 확인했다. 원본 파서 자체를 독립 재구현한 검증은 아니다. FK·integrity와 종료 시 로그 사본 복원 SHA-256도 통과했다. 측정 회차 간 의미 해시도 일치한다. 원시 결과: [JSON](TempBatchAB-2026-11-04.json).

## 2. 분석

- **판정: 일부 성립.** TEMP 집계 실행 횟수는 현재 453→15(96.7% 감소), 1만 건 100→4, 100건 10→1이다. 전체 재파싱은 각각 **5.3%·3.8%·7.2% 개선**, 모두 9/10쌍에서 후보가 빨랐다. 준비 구간은 **60.6%·28.9%·63.6%** 줄었다. 서로 다른 성분의 반복 실행을 합쳤으며 동일 이벤트를 영속 캐시하거나 원본 읽기를 생략한 실험은 아니다.
- **핵심 원인:** TEMP 집계 호출이 줄어도 저장 호출은 같고, 저장 중앙값은 약 1.3%·1.5%·0.5% 늘었다. 현재 준비 구간은 902.555→356.037ms로 546.519ms 줄었지만 전체 시간의 약 0.9초 구간이므로 전체 절감은 약 0.676초에 그친다. 원본 읽기·파싱과 기존 저장 경로를 유지한 것이 전체 개선 폭을 제한한다. 원인별 CPU·정렬 비용은 별도로 분해하지 않았다.
- **단일 추가:** 현재는 Codex 3.0%·Claude 2.0%, 1만 건은 1.5%·3.5% 느려졌다. 집계는 양쪽 모두 1회라 재사용 이득이 없고 후보 준비 구간에는 앞보기·현재 성분 복원·탐색 인덱스 비용이 붙는다. 전체 회귀를 이 비용 하나로 단정하지는 않는다. 100건 Claude의 4.1% 개선도 준비 구간은 느려져 일반적인 단일 추가 가속 근거로 보지 않는다.
- **읽기·무변경:** 조회 SQL·영속 구조를 바꾸지 않았다. 현재 일/월 조회는 4.4%·8.7% 느린 중앙값도 관측됐다. 범위가 겹치는 ms 단위 표본이며 읽기 개선으로 판정하지 않는다. 변경 없는 갱신은 집계 호출이 양쪽 모두 0회다. 전체 중앙값은 현재 136.085→137.529ms, 1만 건 18.692→18.567ms, 100건 5.649→5.708ms로, 작은 차이를 이 알고리즘 효과로 해석하지 않는다.
- **선택: 제품 반영 보류.** 여러 성분의 전체 재파싱에서 효과는 확인됐다. 단일 변경에는 기존 경로를 유지하는 조건부 후보가 다음 비교 대상이다. 이번 B는 별도 사본에만 적용했다. 제품 소스·설치 확장·영속 스키마는 바꾸지 않았다. TEMP 최대 행 수·디스크 peak·RSS peak·취소 응답 지연은 미측정이며 JSON의 RSS는 검증 후 관측값이다.

검증: `npm run check`의 타입·린트·**375개 테스트**를 통과했다. 같은 후보 패치로 기존 summary·capabilities **126개 회귀 테스트**도 통과했다([결과](TempBatchValidation-2026-11-04.json)). 최초 회귀 실행은 사본의 tests/fixtures 복사 누락으로 잠금 테스트 1개가 실패했다([초기 결과](TempBatchValidation-initial-2026-11-04.json)). 실행기에 fixture 복사를 추가한 뒤 후보 변경 없이 재실행해 통과했다.

## 재실행

이 문서와 원시 JSON은 선행 시제품 측정 당시의 결과·판정을 보존한다. 후속 사용자 지시로 제품에 반영하면서 단일 성분의 직접 처리와 디스크 TEMP 세션 목록을 적용했다. 빌드 JS 문자열 패치·별도 회귀 실행기는 제거했고, [비교 실행기](../../../tests/benchmarks/temp-batch-ab.cjs)는 두 빌드 경로를 받도록 정리했다. 위의 수치를 후속 제품 버전의 재측정값으로 해석하지 않는다. 제품의 합성 후속 비교는 [별도 JSON](TempBatchProduct-2026-11-04.json)에 둔다.

두 소스를 각각 컴파일한 뒤 빈 출력 경로를 지정한다. 기존 원시 JSON의 src·A/B dist·runner/helper/candidate 해시와 입력 식별자는 수정하지 않는다. 새 실행은 두 src·dist의 해시를 기록한다. 원본 로그는 수정하지 않는다. snapshot 본문은 보존하지 않아 미래 재실행의 현재 데이터 N은 달라질 수 있다.

```powershell
npm run build
node tests/benchmarks/temp-batch-ab.cjs --before=<빌드된 이전 소스> --after=. --output=tests/results/benchmarks/temp-batch-rerun.json
npm run check
```
