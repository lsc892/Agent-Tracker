# TEMP 묶음 집계의 제품 반영 확인

사용자 지시에 따라 선행 후보를 제품에 반영했다. 세션 목록·연결 확장을 디스크 TEMP에 두고 단일 연결 성분은 직접 집계한다. 현재 component를 바꾸지 않으며 고아 검사·삭제 원본 보존·출력은 현재 성분에 한정한다. 성분별 저장·실패·취소 경계와 영속 스키마·파서 버전은 유지한다.

기존 빌드와 제품 반영본을 동일한 합성 입력·사전 DB에서 준비 3쌍 후 AB/BA 10쌍으로 비교했다. 실제 refreshSummary 반환까지의 중앙값이며 파일 조사·파싱·필요 집계와 COMMIT을 포함한다. 준비·복원·검증은 제외했다. DB/TEMP cache 각각 4 MiB, TEMP=FILE, WAL, OS 캐시 유지 조건이다. 상세 환경·입력·소스/빌드 식별자와 원시 표본은 [JSON](TempBatchProduct-2026-11-04.json)에 있다.

| 항목 | 합성 10,000건 · 100세션 | 합성 100건 · 10세션 |
| --- | ---: | ---: |
| 전체 재파싱 ms · 이전 → 제품 | 2476.077 → 2384.587 (3.7% 개선) | 79.879 → 75.768 (5.1% 개선) |
| TEMP 집계 횟수 | 100 → 4 | 10 → 1 |
| 저장 호출 수 | 100 → 100 | 10 → 10 |
| Codex 요청 1건 추가 ms | 44.756 → 45.229 (1.1% 악화) | 13.061 → 13.312 (1.9% 악화) |
| Claude 요청 1건 추가 ms | 43.864 → 43.668 (0.4% 개선) | 12.924 → 12.892 (0.2% 개선) |

단일 성분에 묶음 표·인덱스를 만들지 않는 직접 경로를 검증했지만 단일 추가의 고정적인 속도 개선은 확인하지 못했다. 범위가 겹치는 작은 차이를 무회귀 보장으로 해석하지 않는다. 합성은 기존 ordinal-v1 생성기를 쓰며 제공자별 절반·10프로젝트·제공자별 두 모델·완료 요청이다. 평균은 완료되고 사용량 또는 알려진 모델이 있는 요청을 분모로 쓴다. 기간·미상·빈 사용량 정책은 선행 비교와 같다.

208개 갱신 상태(준비 포함)의 요청·토큰·저장 호출 수·전체 의미 해시가 A/B와 일치했다. raw SQL과 제공자/모델 × 전체/일/월/세션/프로젝트 집계를 2,080회 대조했고 JS 원본 요청 합산·FK·integrity·고정 입력 복원도 통과했다. `npm run check`는 **381개 테스트**를 통과했다. 70개 독립 성분의 세 번 집계, 41개 연결 ID의 단일 직접 처리, 요청 ID 재사용, 빈 사용량, 실패 성분 제외, 뒤 성분의 고아 오류 격리, 중간 저장 실패 후 보존·진행, 취소와 TEMP 제거를 검증했다.

현재 실제 로그의 후속 제품 성능은 **미측정**이다. [선행 실제 로그 5.3% 개선](TempBatchAB-2026-11-04.md)은 JS Map과 component 복사·복원을 사용한 시제품의 결과로 보존하며 이번 제품 버전의 수치로 대체하지 않는다. TEMP/RSS peak·UI·취소 지연의 성능 측정도 하지 않았다.

실험용 빌드 JS 패치와 별도 회귀 실행기를 삭제하고 [비교 도구](../../../tests/benchmarks/temp-batch-ab.cjs)는 두 빌드를 받도록 정리했다. 재실행은 이전 소스를 별도로 빌드한 후 `node tests/benchmarks/temp-batch-ab.cjs --before=<이전 소스> --after=. --synthetic-only --output=<빈 JSON 경로>`를 사용한다. `--synthetic-only`를 생략하면 현재 로그 전체도 포함한다. 과거 원시 측정값은 변경하지 않는다.
