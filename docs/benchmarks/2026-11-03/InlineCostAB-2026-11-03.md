# 비용 JOIN 1회 제거의 조회·요청 추가·DB 용량 A/B

**결정: 기존 비용 분리 방식 A를 유지한다.** 요청과 비용을 합친 B는 조회를 조금 단축했지만, 10,000건에서 요청 추가와 최초 저장이 느려졌다. 새 DB의 공간 절감은 1% 미만이며 기존 DB 전환 직후 파일은 커졌다. 사용자 지시에 따라 통합 구현을 철회하고 측정 결과만 보존한다.

## 핵심 세 가지: JOIN을 줄여 얻은 시간과 지불한 비용

**A = 기존 `turn_costs` 별도 저장(schema v16), B = 요청의 비용 열로 통합(schema v17).** 아래는 A → B이며 `+`는 B의 시간·용량 증가, `−`는 감소다.

| 핵심 지표 | 실제 요청 1,100건 | 10,000건 / 세션당 100건 | 10,000건 / 세션당 1,000건 |
| --- | ---: | ---: | ---: |
| 비용 포함 **모델별 일 통계 조회 1회** | 9.096 → 8.798 ms (**-0.298 ms / -3.3%**) | 89.163 → 88.361 ms (**-0.802 ms / -0.9%**) | 93.496 → 91.234 ms (**-2.262 ms / -2.4%**) |
| **전체 요청 재반영 저장** · 쓰기 트랜잭션 포함 | 57.363 → 58.315 ms (**+0.952 ms / +1.7%**) | 609.334 → 619.711 ms (**+10.377 ms / +1.7%**) | 146.446 → 147.622 ms (**+1.176 ms / +0.8%**) |
| **요청 1건 추가 저장** | 4.558 → 4.580 ms (**+0.022 ms / +0.5%**) | 20.857 → 22.016 ms (**+1.159 ms / +5.6%**) | 40.946 → 45.996 ms (**+5.049 ms / +12.3%**) |
| 기존 DB 전환 직후 **파일 증가량** | **+64 KiB / +4.04%** (1,584 → 1,648 KiB) | **+476 KiB / +4.75%** (10,024 → 10,500 KiB) | **+492 KiB / +10.68%** (4,608 → 5,100 KiB) |
| 새 DB로 같은 요청을 저장했을 때 **파일 감소량** | **-12 KiB / -0.76%** (1,576 → 1,564 KiB) | **-60 KiB / -0.60%** (10,024 → 9,964 KiB) | **-40 KiB / -0.87%** (4,608 → 4,568 KiB) |

- **JOIN 1회 제거 이득**: 실제 모델별 일 통계는 9.096 → 8.798ms로 **0.298ms / 3.3% 단축**됐다. 비용 포함 행 SQL의 `LEFT JOIN turn_costs` 한 개를 없앤 효과를 포함한 전체 조회 A/B다. 전체 그룹 수 COUNT에는 기존에도 비용 JOIN이 없었다. 나머지 집계·모델 JOIN·정렬 비용은 남는다.
- **쓰기 트랜잭션 단축 여부**: 전체 요청 재반영 저장 호출은 실제 +0.952ms, 10,000건은 +10.377 / +1.176ms로 **단축되지 않았다**. 표의 조회 단축을 갱신 트랜잭션의 단축으로 읽지 않는다.
- **한 건 추가의 대가**: 기존 세션에 요청 한 건을 더한 DB 저장 호출이다. 실제 데이터는 +0.022ms로 작은 차이이고, 10,000건은 **+1.159ms / 5.6%**, 큰 세션은 **+5.049ms / 12.3%** 느려졌다. 파일에서 새 줄 하나만 읽는 성능을 측정한 것은 아니다.
- **DB 공간의 대가**: 기존 DB를 변환한 직후 파일은 **64 / 476 / 492 KiB 증가**했다. 비용 테이블을 삭제한 페이지가 재사용 가능한 빈 공간으로 남고, 비용 열을 받은 요청 테이블도 커진다. 새 DB로 저장하면 **12 / 60 / 40 KiB 감소**했지만 절감률은 0.6~0.9%였다. `VACUUM`은 수행하지 않았다.

**시간의 범위:** 조회 1회는 공개 `queryUsagePage()`의 100행 + 전체 그룹 COUNT이며 SQL 준비·조회 트랜잭션·결과 반환을 포함한다. 저장은 공개 `replaceSessions()` 진입부터 `BEGIN IMMEDIATE`·반영·`COMMIT`·함수 반환까지다. 입력 추출·DB 사본 준비·연결 열기와 파일 탐색·파싱은 저장 시간에서 제외했다. SQLite 내부 SQL 실행 시간이나 잠금 보유 시간만 따로 분해한 값은 아니다.

## 조회와 저장의 반복 결과

조회는 준비 실행 2회 후 A/B를 교대로 **9쌍**, 각 표본은 3회 호출 평균으로 측정했다. 저장은 준비 실행 1쌍 후 **5쌍**이며 매번 같은 사전 DB를 복원했다. 표는 중앙값이다. 원시 최소·최대·짝별 차이와 B가 빠른 쌍 수는 JSON에 보존한다. 작은 차이는 일관된 개선으로 일반화하지 않는다.

| 비용 포함 모델별 조회 | 실제 1,100건: A → B ms | 10,000건·100건/세션: A → B ms | 10,000건·1,000건/세션: A → B ms |

| 세션별 | 7.334 → 7.051 (-3.9%) | 41.941 → 41.867 (-0.2%) | 38.507 → 37.532 (-2.5%) |

`initial-store`는 같은 요청 입력을 빈 DB에 한 번의 세션 교체 트랜잭션으로 저장한 값이다. 실제 데이터의 manifest는 사전에 준비한다. `reapply-all`도 전체 요청을 한 번의 호출로 재반영하므로 수집기가 연결 component별로 저장하는 전체 갱신과 같지 않다. 나머지 교체는 해당 입력에서 요청 수가 가장 큰 세션 하나를 대상으로 한다. 실제 대상은 25건, 합성 대상은 각각 100건·1,000건이다. 1,000건 세션의 소수 변경에는 현재의 TEMP 묶음 비교가 적용된다.

`billing-api`와 `billing-subscription`은 선택 세션의 결제 방식을 바꾸는 호출이며 원본 재파싱 없이 저장된 모델 비용을 다시 합산한다. 비용 분류 변경과 일반 요청 추가를 같은 작업으로 합치지 않는다.

## 파일 크기와 실제 사용 중인 페이지

아래의 공간은 `wal_checkpoint(TRUNCATE)` 뒤의 DB 파일이다. 1 KiB = 1,024 bytes다. WAL을 포함한 누적 디스크 쓰기량·최대 파일 크기를 뜻하지 않는다. 새 DB 값은 마지막 최초 저장 표본의 공간 관측이고, 기존 DB 값은 동일한 schema v16 사본을 전환한 직후다. 두 표는 서로 다른 생성 이력을 가지므로 교차 비교하지 않는다.

## 측정 입력·통제·정확성

- 측정: 2026-11-03 17:15:14 ~ 2026-11-03 17:18:41, Asia/Seoul.
- 환경: AMD Ryzen 5 7500F 6-Core Processor             , Node v24.14.1, SQLite 3.51.2, win32. 메인·TEMP cache는 각각 4 MiB, TEMP는 FILE, mmap은 0이다. OS cache를 비우지 않은 비교다.
- A/B는 같은 HEAD `67608425dc9e9603688e180f01d0d4165f338b7c`의 별도 워크트리에서 컴파일했다. B만 비용 통합 소스 6개를 덮어썼다. 같은 HEAD 표기만으로 같은 코드라고 판단하지 않고, 전체 소스·컴파일 결과·잠금 파일 SHA-256을 원시 JSON에 남겼다.
- 변경 파일: `schema.ts`, `migrations.ts`, `billing.ts`, `sessions.ts`, `sessionChanges.ts`, `queries/raw/source.ts`. PK·보조 인덱스·일별 집계 구조·파서·모델 단가는 양쪽에서 동일하다.

실제 DB 사본의 비용은 1,100건 모두 미확인이다. 합성에는 API·구독·미확인을 3,334 / 3,333 / 3,333건으로 섞고 알려진·미상 모델, 다중 모델, 빈 사용량, 진행 중·실패 상태와 미상 시각을 포함했다. 두 합성 분포는 요청 수·모델 행·총 토큰은 같지만 프로젝트·세션·일별 집계 행 수가 달라 세션 크기 하나만의 효과로 해석하지 않는다.

각 입력의 32개 조회 조건은 비용 ON/OFF, 제공자/모델, 전체·일·월·프로젝트·세션·선택 프로젝트의 30일·7일 평균·요청 상세를 포함한다. 7/30일은 마지막 기록 시각 + 24시간을 끝으로 잡은 고정 범위이며 측정 당일 기준이 아니다. 빈 조회도 JSON의 결과 건수로 구분한다. 모든 기간 평균은 완료 요청당 평균이며 일수로 나눈 일평균이 아니다.

양쪽의 전체 그룹·페이지 COUNT를 원본 SQL과 비교하고 저장 뒤에도 제공자/모델·비용 ON/OFF를 검증했다. **원본 SQL 대조 총 1272회**, 96개 조회 조건의 A/B 결과 해시와 모든 저장 표본의 논리 facts 해시가 일치했으며 FK·integrity를 통과했다. 비교할 때만 비정수를 유효숫자 12자리로 정규화하고 저장 값은 반올림하지 않았다. 물리 행 ID와 재반영 시각은 해시에서 제외한다.

개인 원본 DB는 읽기 전용 backup만 수행했다. 비교 사본은 실행 후 정리했으며 보고서에 제목·세션 ID·프로젝트 경로·credential을 남기지 않았다. 실제 확장 설치·사용 DB·quota 서버는 변경하지 않았다.

## 원인 해석과 최종 선택

1. **조회**: 비용 행의 PK 조회 하나가 없어지지만 모델별 JOIN, 시간대별 날짜 계산, GROUP BY·정렬, 별도의 COUNT 집계는 남는다. 비용 제외 집계는 기존 일별 집계를 사용하므로 그 시간 차이까지 비용 JOIN 제거의 직접 효과라고 단정하지 않는다.
2. **쓰기**: A는 작은 비용 행을 INSERT/REPLACE하고 B는 토큰·제목·상태 등이 들어 있는 요청 행의 비용 열을 UPDATE한다. 실제 dbstat에서 요청 본체가 커졌다. 넓어진 행과 다른 페이지 배치가 쓰기 증가의 원인 후보지만 SQLite 내부 연산별 시간·물리 I/O를 분해해 단독 원인으로 확정한 것은 아니다.
3. **선택**: 이번 입력에서는 작은 조회 이득에 비해 10,000건의 추가·최초 저장 비용 증가와 미미한 공간 절감이 관측됐다. 사용자는 이 결과를 기록하고 기존 방식을 유지하도록 지정했다. **제품 소스·현재 명세·테스트는 비용 분리 schema v16으로 복원했다.** schema v17은 B 워크트리의 실험 구현으로만 보존한다. 기존 조건부 증분 저장·인덱스·사전 집계는 유지한다.
