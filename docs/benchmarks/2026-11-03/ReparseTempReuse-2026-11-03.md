# 전체 재파싱 대기를 줄이는 TEMP 집계 재사용

기준일: 2026-11-03, Asia/Seoul.

실제 고정 로그의 **전체 재파싱+첫 통계 조회는 15.342초 → 13.610초로 1.732초 단축(-11.3%)**됐다. 3쌍 모두 빨라졌다. 재파싱 중 집계 준비는 **2.393초 → 0.973초(-59.3%)**로 줄었다. 같은 최적화를 제품 코드에 반영했다.

합성 1만 요청·100요청/세션에서는 재파싱 대기가 **8.6%** 줄었고 3쌍 모두 빨랐다. 1,000요청/세션에서는 대기 시간 차이가 거의 없었다. 많은 세션에서 집계 표를 반복 생성하던 비용을 줄이는 변경이며, 파일 읽기·JSONL 파싱 자체를 생략하는 변경은 아니다.

## 실제 바꾼 쿼리

원본 요청의 세션 검색은 이미 `UNIQUE(provider,session_id,root_turn_id)`의 앞 두 키로 좁힐 수 있다. 세션 시간 인덱스만 추가한 [이전 A/B](SessionTimeIndexAB-2026-11-03.md)의 전체 재파싱 -2.8%는 5쌍 중 2쌍만 빨라 일관된 개선으로 채택하지 않았다.

이번에는 `prepareSummaries()`가 연결 성분마다 반복하던 아래 패턴을 바꿨다.

```sql
-- 이전: 성분마다 TEMP 표·인덱스를 제거하고 다시 생성
DROP TABLE IF EXISTS temp.component_events;
CREATE TEMP TABLE component_events AS SELECT ...;
CREATE INDEX temp.component_events_response ON component_events(...);

-- 변경: 첫 성분에서만 생성, 다음 성분부터 기존 인덱스를 유지하며 내용 교체
DELETE FROM component_events;
INSERT INTO component_events SELECT ...;
CREATE INDEX IF NOT EXISTS temp.component_events_response ON component_events(...);
```

같은 방식을 `component_events`·`winners`·`capability_winners`·`prepared_turns`에 적용했다. 매번 모든 행을 비운 뒤 현재 성분의 집계만 적재한다. 기존 제목 partial index·중복 제거·상태·모델·Skill·비용 계산과 100행 단위 읽기는 유지한다. 영속 저장에 쓰는 statement에도 영향을 주는 반복 TEMP 스키마 변경을 줄이는 방향이다.

TEMP는 기존과 같이 FILE이며 한 갱신이 끝나면 표와 인덱스를 제거한다. 영속 테이블·인덱스 추가와 schema/parser version 변경은 없다. 기존 DB를 비우거나 이번 최적화를 적용하기 위해 원본을 강제로 재파싱하지 않는다.

## 가장 긴 재파싱 대기의 전후

예열 1쌍을 제외한 3쌍의 중앙값이다. `갱신+첫 조회`는 실제 `refreshSummary()` 이후 월별 제공자 통계 첫 100행과 COUNT 반환까지다. 단위는 ms다.

| 입력 | 갱신+첫 조회 A → B | 변화 | 갱신만 A → B | 집계 준비 A → B | B가 빠른 회차 |
| --- | --- | --- | --- | --- | --- |
| 실제 1,363요청 | 15341.783 → 13609.947 | -11.3% | 15340.272 → 13608.641 | 2393.137 → 973.327 | 3/3 |
| 1만·100요청/세션 | 2993.875 → 2736.715 | -8.6% | 2992.965 → 2736.029 | 703.961 → 399.753 | 3/3 |
| 1만·1,000요청/세션 | 1634.586 → 1634.596 | +0.0% | 1633.958 → 1633.891 | 294.101 → 269.704 | 2/3 |

`집계 준비`는 `prepareSummaries()`의 중첩 구간이다. 전체 시간에 더하지 않는다. 실제 입력은 **550파일·339,727,441 bytes·1,363요청**이며 이전 인덱스 실험의 1,360요청 snapshot과 다르다. 각 A/B 안에서는 같은 고정 입력이다.

**모든 갱신을 가속한 것은 아니다.** 실제 Codex 응답 연장은 263.065 → 279.219ms(+6.1%)로 3쌍 모두 느렸다. 1만 요청·1,000요청/세션의 Claude 추가는 166.323 → 180.521ms(+8.5%)로 3쌍 모두 느렸다. 해당 단일 세션 갱신은 TEMP 표 재사용의 반복 효과가 거의 없는 구간이며, 전체 재파싱 개선율을 그대로 적용하지 않는다. 짧은 합성의 변경 없는 진입도 +2.904ms(+10.2%)였으며 그때 집계 준비 호출은 양쪽 모두 0이다. 한 장비의 순차 실행에서 관측된 회귀와 편차를 숨기지 않되 원인을 인덱스 유지 비용 하나로 단정하지 않는다.

실제 재파싱에서 관측한 세션 저장 호출의 중앙값은 1,298.393 → 1,018.927ms였다. 이 값은 JS·검증·조회·쓰기·집계 유지·COMMIT을 포함하며 쓰기 잠금 유지 시간만을 뜻하지 않는다. 원본 읽기·파싱이 남아 있어 현재 입력의 대기를 수 초 이하로 만들지는 못했다. 원본 tail만 읽으려면 응답 중복·상태·부모/자식 세션을 복구할 영속 파싱 상태가 추가로 필요하며 이번 범위에는 포함하지 않았다.

## 정확성과 측정 범위

- 변경 전 빌드를 별도 로컬 경로에 보존한 뒤 변경 후와 순차 비교했다. 두 빌드는 같은 HEAD에서 staging SQL이 달라지며, report의 소스 해시가 실제 차이를 식별한다.
- 입력마다 원본·이름 metadata를 한 번 고정하고 매 실행 새 프로세스·새 DB에서 같은 시나리오를 수행했다. 예열 1쌍 후 3쌍을 AB/BA 교대했다. DB cache 4MiB·TEMP=FILE·mmap=0·제품 optimize를 유지한다.
- 각 상태에서 요청·모델·Skill·비용·이름·진단의 의미 해시와 집계 해시, 읽기량·파싱/실패 수·요청/토큰 수를 A/B와 회차 간 비교했다. 새 요청 +1/+130 tokens, 응답 연장 요청 수 유지/+26 tokens도 검사했다.
- 측정 **108개 상태**에서 원본 SQL과 제공자/모델 × 전체/프로젝트/세션/일/월 집계를 총 **1,080회** 대조했다. 제외한 예열 36개 상태도 같은 검증을 통과했다. 모든 상태의 FK·integrity와 실행 후 원본 사본 복원 해시가 일치했다.
- `npm.cmd run check`의 타입 검사·린트·**375개 테스트**를 통과했다. 같은 요청/응답 ID의 연속 성분, 중간 빈 사용량, 제목·모델·Skill 격리를 추가 검증했다. 기존 제목 SQL A/B 도구도 새 생성/재사용 경로를 구분하도록 맞췄다.
- 시간 측정에서 입력 복사·입력 변경·검증을 제외했다. Worker IPC·UI·네트워크·quota 호출은 포함하지 않는다. OS cache와 백그라운드 부하는 통제하지 않았으며 3쌍은 성능 보장값이 아니다. RSS는 검증 후 관측값으로 peak나 SQLite 단독 메모리를 뜻하지 않는다. TEMP 표의 할당 페이지는 최대 처리 성분에 따라 갱신 종료까지 재사용될 수 있다.
