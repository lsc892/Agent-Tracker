# 배포 판단과 단순 인덱스 후보 비교

기준일: 2026-11-03, Asia/Seoul.

현재 데이터와 1만 요청 규모의 **DB 통계 기능은 배포 가능한 성능 수준**으로 판단한다. 기간·프로젝트 인덱스, 일별 사전 집계, 세션 단위 저장, manifest 재사용과 실행 계획 통계 유지가 이미 있다. 전체 확장의 배포 승인이나 모든 데이터 분포에서의 최적성을 검증한 것은 아니다. 이번에는 제품 기능을 변경하지 않고 작은 인덱스 후보를 조사했다.

현재 A의 조건별 중앙값 중 최댓값은 실제 입력 **12.011ms**, 두 1만 입력은 각각 **116.752ms·120.646ms**였다. 아래 측정은 준비된 DB의 공개 조회 API 범위이며, 실제 화면과 갱신 전체의 최대 지연을 뜻하지 않는다.

다음 개선의 우선 후보는 **E: 세션 시간 인덱스 하나와 최초 시각 SQL 한 곳의 조정**이다. 1만 건·100세션 입력에서 세션별 모델 조회가 일반 통계 **13.3%**, 비용 포함 **18.4%** 줄었다. 요청 추가는 **2.817ms 늘고**, DB는 **312KiB 늘었다**. 현재 1,100건에서는 일반 세션 조회가 소폭 느려져, 현재 규모의 배포를 위해 반드시 적용할 근거는 약하다.

## 가장 먼저 볼 조회·추가·용량

아래는 같은 실행의 A → E 중앙값이다. 시간의 음수는 단축, 양수는 증가다. 파일 크기는 KiB다.

| 항목 | 실제 1,100건 | 1만 건·100요청/세션 | 1만 건·1,000요청/세션 |
| --- | ---: | ---: | ---: |
| 일반 세션별·모델별 페이지 ms | 6.214 → 6.458 (+3.9%) | 27.057 → 23.455 (**-13.3%**) | 3.362 → 2.994 (-11.0%) |
| 비용 포함 세션별·모델별 페이지 ms | 9.472 → 8.513 (-10.1%) | 53.313 → 43.507 (**-18.4%**) | 49.161 → 44.319 (-9.8%) |
| 요청 1개 추가 저장 호출 ms | 5.088 → 5.628 (+10.6%, +0.540ms) | 21.756 → 24.573 (+12.9%, +2.817ms) | 56.836 → 54.744 (-3.7%, -2.092ms) |
| checkpoint 후 DB KiB | 1,584 → 1,652 | 10,024 → 10,336 | 4,608 → 4,912 |
| DB 증가 | +68KiB (+4.3%) | +312KiB (+3.1%) | +304KiB (+6.6%) |

일반 세션별 모델 조회에서 E가 A보다 빨랐던 회차는 실제 **4/9**, 짧은 합성 **8/9**, 긴 합성 **8/9**다. 비용 포함은 각각 **7/9·9/9·7/9**다. 요청 추가는 **0/5·0/5·4/5**였다. 긴 합성 입력의 추가 시간이 줄어든 결과까지 기록하되, 추가 인덱스가 쓰기를 항상 가속한다고 해석하지 않는다. 긴 입력은 선택 세션의 1,000요청에 조건부 증분 경로가 적용되며 짧은 입력은 100요청을 교체한다.

세션 목록 전체를 집계하는 조회와 특정 세션 하나를 선택한 조회도 구분해야 한다. 특정 세션 하나의 모델 통계는 A에서 실제 0.628ms·짧은 합성 0.650ms였고 E는 각각 0.599ms·0.605ms다. 이 범위에서는 기존 세션 키로 이미 충분히 좁힐 수 있다.

긴 합성 입력의 비용 포함 프로젝트별 조회는 E에서도 **2.625ms(+6.7%) 증가**했다. 세션 조회 개선율을 프로젝트·기간 통계에도 그대로 적용할 수 없다.

## 비교한 작은 변경

| 후보 | 변경 | 목적 |
| --- | --- | --- |
| A `current` | 현재 제품 그대로 | 기준 |
| B `raw-session-time` | 요청에 `(provider, session_id, started_at_ms)` 인덱스 1개 추가 | 세션 내 기간 검색과 원본 세션 최초 시각 조회 |
| C `daily-session-min` | 요청 일별 집계에 `(provider, session_id, min_started_at_ms)` 인덱스 1개 추가 | 일반 세션 통계의 전체 기간 최초 시각 조회 |
| D `raw-provider-time` | 요청에 `(provider, started_at_ms)` 인덱스 1개 추가 | 제공자·기간 원본 검색 |
| E `shared-session-time` | B와 같은 인덱스 1개와 최초 시각 서브쿼리 1곳 변경 | 일반·비용 통계가 같은 세션 시간 인덱스를 공유 |

E의 DDL과 일반 세션 통계의 변경 식은 다음과 같다. 기존 원본 비용 통계는 이미 동일한 의미의 `MIN(started_at_ms)`를 사용한다.

```sql
CREATE INDEX idx_summary_session_period
ON turn_summary(provider, session_id, started_at_ms);

-- 일반 세션 통계의 session_started_at_ms 식:
SELECT MIN(d.started_at_ms)
FROM turn_summary d
WHERE d.provider = turn_summary.provider
  AND d.session_id = turn_summary.session_id;
```

현재 일반 통계는 `usage_request_daily`에서 해당 세션의 `MIN(min_started_at_ms)`를 다시 구한다. E는 같은 전체 기간의 최소값을 원본의 정렬된 인덱스에서 구한다. **화면의 기간 필터를 이 서브쿼리에 넣지 않는다.** 그래야 기간을 좁혀도 세션의 원래 시작 시각이 유지된다. 시간 미상만 있는 세션의 결과는 계속 `NULL`이다.

E는 실험용 연결의 `prepare()`에서 이 SQL 식만 바꾸는 시제품이다. 나머지 공개 조회 API·집계·페이지·개수·저장 코드는 같은 빌드다. 제품 소스나 설치 DB에는 적용하지 않았다.

## 다른 단순 후보와의 비교

세션별·모델별 페이지의 각 후보 중앙값(ms)이다.

| 입력·조회 | A 현재 | B 요청 시간 | C 집계 최초 시각 | D 제공자 시간 | E 공유 시간 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 실제·일반 | 6.214 | 5.646 | 5.752 | 5.975 | 6.458 |
| 실제·비용 | 9.472 | 8.706 | 8.679 | 9.133 | 8.513 |
| 1만 짧음·일반 | 27.057 | 28.911 | 25.951 | 26.824 | 23.455 |
| 1만 짧음·비용 | 53.313 | 43.362 | 56.547 | 58.265 | 43.507 |
| 1만 김·일반 | 3.362 | 3.462 | 3.028 | 3.334 | 2.994 |
| 1만 김·비용 | 49.161 | 43.441 | 49.577 | 49.337 | 44.319 |

C는 추가 SQL 변경 없이 일반 세션 조회의 MIN을 covering index로 처리하지만, 짧은 합성에서 개선은 4.1%이고 요청 추가는 16.0% 늘며 공간은 528KiB 늘었다. E보다 우선할 근거가 부족하다. D는 짧은 합성의 비용 포함 프로젝트별 모델 조회가 **42.022 → 53.492ms(+27.3%)**, 긴 합성도 **39.244 → 46.246ms(+17.8%)**로 느려졌다. 제공자·날짜 인덱스를 더하는 것이 전체 조회에 유리하다고 볼 수 없다.

B와 E의 인덱스는 같은 구조다. 비용 포함 세션 조회의 작은 B/E 차이는 동일한 실행 계획을 사용하는 별도 표본의 차이다. E는 B의 인덱스를 일반 통계의 최초 시각 조회에도 활용해 후보를 하나로 묶는 방향이다.

일반 세션 조회의 최초 시각 서브쿼리 실행 계획은 A의 `SEARCH d USING PRIMARY KEY (provider=? AND session_id=?)`에서 E의 `SEARCH d USING COVERING INDEX bench_summary_session_time (provider=? AND session_id=?)`로 바뀌었다. 나머지 집계와 그룹 정렬 비용은 남는다.

**선택 방향:** 현재 제품으로 배포를 진행할 수 있다. 이후 세션 목록을 반복 조회하는 비용이 실제로 문제가 되면 E를 작은 개선 후보로 채택하고 제품 migration·동작 테스트를 추가한다. 이번 작업은 조사이므로 현재 schema v16·비용 분리·저장 경로·제품 SQL을 유지했다. 모든 면의 개선이나 데이터가 늘수록 개선율도 커진다는 결론은 내리지 않는다.

## 현재 인덱스에서 유지할 점

- 전체 제공자를 대상으로 한 기간 조회에는 현재 `(started_at_ms, provider)`가 맞는다.
- 제공자와 프로젝트가 정해진 기간 조회에는 현재 `(provider, project_key, started_at_ms)`가 맞는다.
- 세션 조건은 기존 UNIQUE 키 `(provider, session_id, root_turn_id)`로도 좁힐 수 있다. 여기에 시간이 없어서 B/E는 세션의 시간 범위·최초 시각을 보완한다. 이 UNIQUE 키는 요청의 중복 방지 제약이므로 유지한다.
- 모델별 `SUM/AVG`는 선택된 범위의 값을 읽고 합산해야 한다. `GROUP BY model`이 있다는 이유만으로 모델 인덱스를 추가하면 전체 집계가 즉시 끝나는 것은 아니다. 현재 일반 통계는 일별 집계를 활용해 입력을 줄인다.
- 비용 포함 일·월 통계는 원본에서 시간대 함수와 그룹화를 실행하고 행/전체 그룹 수를 각각 계산한다. 세션용 인덱스의 개선 효과를 이 경로의 개선으로 확대 해석하지 않는다.

복합 인덱스의 선두 열·범위 검색·covering index 원리는 [SQLite query planner](https://www.sqlite.org/queryplanner.html)와 [optimizer 설명](https://www.sqlite.org/optoverview.html)에 따른다. 실제 사용 여부는 보고서의 `EXPLAIN QUERY PLAN`으로 확인했다. [연결 코드](../../../src/summary/db/connection.ts)는 이미 열 때 `PRAGMA main.optimize=0x10002`, 이후 하루 간격과 종료 시 `PRAGMA main.optimize`를 사용하므로 [SQLite 권장 통계 유지](https://www.sqlite.org/lang_analyze.html)를 새 기능으로 제안하지 않는다.

## 갱신 전체 시간과 구분

[10월 31일의 실제 로그 계측](../2026-10-31/WriteProfile-2026-10-31.md)에서 최초 갱신은 약 15,493ms, 그중 세션 저장 API는 1,133ms였다. 읽기·파싱 콜백 구간은 9,616ms였고 변경 없는 진입은 약 155ms였다. 이 수치는 당시 별도 장비·입력에서 얻은 값이며 이번 조회 시간과 합산하지 않는다. 단순 인덱스 조정으로 최초 파일 읽기·파싱까지 크게 단축된다고 예상할 근거는 없다.

## 측정·정확성·재현

- 실제 설치 DB는 읽기 전용 backup으로 고정한 1,100요청·368세션·32프로젝트다. 합성 입력은 10,000요청이며 100요청/세션 100개와 1,000요청/세션 10개 분포다. 프로젝트 수와 일별 집계 밀도도 다르므로 두 합성 입력의 차이를 세션 크기 하나의 효과로 해석하지 않는다.
- 각 입력에서 같은 제품 빌드·같은 DB 사본을 5개 후보로 나눴다. 기존 인덱스·PK·테이블은 유지했다. 모든 후보에 제품과 같은 optimize를 실행했다. 강제 ANALYZE는 하지 않았다.
- 조회는 준비된 일별 집계에서 공개 `queryUsagePage()`의 SQL 준비·읽기 트랜잭션·첫 100행·전체 그룹 수 반환을 포함한다. 비용 on/off, 제공자/모델 기준, 일·월·프로젝트·세션·최근 7/30일·선택 프로젝트/세션·요청 상세의 40조건을 측정했다. 조건마다 2회 예열 후 순서를 회전·반전하며 9회, 각 2호출을 평균냈다. GC는 타이머 밖에서 실행했다.
- 기간은 마지막 기록이 속한 현지 날짜의 다음 자정에서 7/30일을 거슬러 올라간다. 현재 날짜를 기준으로 빈 구간을 조회하는 실험이 아니다.
- 쓰기는 가장 긴 세션에 요청 1개를 추가하는 공개 `replaceSessions()` 호출이며 COMMIT까지 포함한다. 매번 같은 사전 상태에서 복원하고 예열 1회 후 5회 측정했다. 기존 일별 집계 유지 비용도 포함한다. 최초 적재·전체 로그 파싱·동시 사용자·쓰기 lock 유지 시간만을 별도로 측정한 것은 아니다.
- 모든 조회 조건의 전체 SQL 결과와 COUNT·반복 공개 페이지 결과를 후보 간 비교한다. 요청 추가 후 논리 데이터 해시·FK·무결성을 비교한다. 비교 해시에서 물리 ID·갱신 시각을 제외하고 부동소수점만 12자리 유효숫자로 맞췄으며 저장 값은 변경하지 않는다.
- OS cache를 비우지 않은 한 장비의 반복 실행이다. 계획과 무관한 작은 차이·단발성 순위를 확정적인 개선으로 해석하지 않는다. Worker·웹뷰·원본 파싱·최초 사전 집계 생성은 조회 측정에서 제외한다.
- 파일 크기는 checkpoint 후 값이며 VACUUM은 실행하지 않았다. 추가 인덱스의 `dbstat` 공간도 원시 결과에 보존했다.

```powershell
npm.cmd run build
node --expose-gc tests/benchmarks/simple-index-ab.cjs --output=tests/results/benchmarks/simple-index-ab.json
```
