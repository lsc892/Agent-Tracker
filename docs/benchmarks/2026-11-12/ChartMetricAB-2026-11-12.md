# 선택 도표에 필요한 토큰 평균 계산 A/B 실험

사용자는 선택한 탭·도표에 필요한 항목만 계산해 통계 조회를 줄이도록 요청했다. 이번 실험은 이미 반영한 구성별 평균 생략의 효과를 확인한다. 에이전트의 가설은 네 평균에 필요한 SUM·AVG·COUNT와 나눗셈을 줄이면 실제 조회 시간이 감소한다는 것이다.

A는 미커밋 변경을 포함한 현재 구현이다. B는 같은 소스 사본에서 두 SQL 생성기의 `includeComponentAverages`를 항상 true로 바꾼 비교 구현이다. B에서 변경한 두 조건 외의 제품 소스는 A와 같다. 아래 표는 **B(변경 전) → A(현재)** 순서이며, 개선율은 `(B - A) / B × 100`이다.

### 평균 토큰 도표 대조군

이 도표는 네 구성별 평균을 모두 사용한다. 각 조회의 A/B SQL SHA-256이 일치했다. 동일 SQL 대조군 전체 48조건의 시간 차이는 -5.1~+6.2%였다. 이 차이는 관측된 실행 변동으로 취급한다. 요청 추가의 0.3~1.5% 차이도 속도 개선으로 판정하지 않는다.

## 2. 측정 조건과 정확성

- Windows x64, AMD Ryzen 5 7500F, 논리 CPU 12개, 메모리 약 31.6 GiB, Node 24.14.1, SQLite 3.51.2에서 2026-11-12 15시 36~37분에 실행했다. 날짜와 시각은 Asia/Seoul 기준이다.
- 실제 입력은 설치된 통계 DB의 읽기 전용 연결에서 일관된 사본을 만들었다. 요청 1,387개, 모델 사용량 1,353개, 세션 385개, 프로젝트 30개이며 미상 시각 요청은 0개다.
- 합성 10,000건은 세션 1,000개·프로젝트 20개·모델 사용량 11,829개·미상 시각 100개다. 합성 100건은 세션 10개·프로젝트 5개·모델 사용량 117개·미상 시각 1개다. 기존 `sql-explain.cjs`의 결정적 입력을 재사용했다. 세션당 10요청, 2026-07-01부터 90일 분포에 완료·진행 중·실패·빈 사용량·다중 모델을 섞었다.
- 모든 조회는 고정 사본의 전체 기간, Claude·Codex 포함, 빈 사용량 제외 설정 true, 통계 시간대 Asia/Seoul, 기간 내림차순, 첫 페이지 100행 조건이다. 평균 토큰은 사용량이 기록된 완료 요청을 분모로 쓴다. 캐시 미상과 시간 표본은 제품의 기존 의미를 적용한다.
- 규모별로 일·월·세션·프로젝트 × 제공자·모델 × 비용 숨김·표시 × 총 토큰·평균 토큰 도표의 32조건을 비교했다. 총 96조건이다. 총 토큰·요청 수·평균 시간 도표는 이번 변경에서 같은 평균 생략 조건을 사용하며, 시간 표본은 총 토큰 도표에서 수집했다.
- 실제 `SummaryDatabase.queryUsagePage`의 SQL 준비·실행·첫 페이지 반환까지 측정했다. 사전 집계와 캐시를 예열하고 준비 3쌍 뒤 AB/BA 순서를 바꿔 10쌍을 수집했다. 짧은 조회는 표본마다 1~25회 반복한 1회당 시간을 사용했다. 표는 10개 표본의 중앙값이다. 측정 범위는 DB 조회 API이며 확장 화면의 전체 응답 시간은 미측정이다.
- 요청 추가는 매번 같은 DB 사본을 복원한 뒤 `replaceMemory`로 새 세션의 정규화된 요청 1개를 저장했다. 130토큰 추가, 활성 사전 집계 갱신과 COMMIT까지 측정했다. 데이터 준비·사본 복원·DB 개방·최초 집계 구축·정확성 확인은 시간 표본에서 제외했다.
- 96조건의 전체 페이지를 읽어 요청 수·토큰 합계·총 평균·시간·품질·그룹 수를 A/B 및 독립 JS 집계와 대조해 모두 통과했다. 구성별 평균은 B와 평균 토큰 도표 A에서 독립 기대값과 일치했고, 생략 조건의 A에서는 네 필드가 NULL이었다. 요청 추가 후에도 각 규모의 16개 집계 조건을 독립 기대값과 대조했다. 복원한 26회 저장마다 추가 결과 해시·외래키·DB 무결성 검사를 통과했고 기준 사본 해시도 보존됐다.

전체 원시 표본, 조회별 SQL·입력·소스·빌드 해시, 실행 계획과 검증 결과를 보존했다. [원시 JSON](ChartMetricAB-2026-11-12.json)

## 3. 분석

가설은 이번 전체 기간·예열 조회 조건에서 성립했다. 기본 제공자별 조회는 실제 데이터에서 7.8~17.5%, 10,000건에서 7.8~16.7% 빨라졌다. 실제 데이터의 절감 시간은 한 번에 약 0.09~0.21ms다. 10,000건의 모델별 세션 조회는 약 1.58ms를 줄였다. 비용 포함 제공자별 프로젝트 조회는 10,000건에서 약 7.07ms를 줄였다.

EXPLAIN의 집계 단계 명령 수는 일별 사전 집계에서 26개에서 20개로, 비용 포함 제공자별 원본 집계에서 32개에서 24개로 줄었다. 일별 모델 조회의 전체 바이트코드 명령 수는 사전 집계 470개에서 388개로, 비용 포함 원본 집계 886개에서 718개로 줄었다. 해당 조회의 접근 경로·GROUP BY·정렬용 임시 B-tree는 유지됐다. 감소한 평균 계산이 관측된 속도 차이를 설명한다.

현재 구현을 유지할 근거가 확인됐다. 평균 토큰 도표는 같은 계산이 필요하며, 저장 시간은 이번 최적화의 개선 대상으로 확인되지 않았다. 최근 7·30·90일 조건, 부분 날짜 경계, 다른 OS와 UI 전체 응답 시간은 이번 전체 기간 실험의 측정 범위 밖이다.
