# 미사용 rollup 지표 제거 전후 노트북 1회 A/B

2026-11-10, Asia/Seoul. 사용자 요청대로 현재 데이터와 합성 10,000요청에서 A/B를 **각 1회**, 준비 반복 없이 A→B 순서로 측정했다. A는 `c9c7ecb`의 변경 전 소스, B는 공통 미사용 지표 3개와 모델별 최소 시각을 제거한 구현이다. 아래 값은 단일 관측값이며 안정적인 개선율·변동 범위를 추정하지 않는다.

가정: 불필요한 지표 계산·저장·반환을 줄이면 집계의 상수 비용과 행 폭이 감소할 수 있다. 집계 입력 행 수·PK·인덱스·정상 저장의 COMMIT 경계와 시간·공간복잡도 차수는 유지한다. B는 요청 daily 상태 41→38개, 모델 daily 41→37개이며 진단 변경 때 삭제된 지표만 갱신하던 재집계 호출도 제거했다. 원본 요청별 오류·갱신 시각과 별도 진단은 보존한다.

## 1. 갱신·저장 결과

각 셀은 A → B ms (시간 감소율)이다. 음수는 B가 느린 결과다. 상위·하위 타이머는 중첩되므로 더하지 않는다.

| 측정 항목 | 현재 798요청 | 합성 10,000요청 |
| --- | ---: | ---: |
| 최초 수집 전체 refresh | 3,699.686 → 3,681.205 (+0.50%) | 1,755.761 → 1,701.446 (+3.09%) |
| 최초 DB 저장·COMMIT 전체 | 176.908 → 164.916 (+6.78%) | 1,147.848 → 1,084.035 (+5.56%) |
| 최초 rollup 유지 구간 | 34.225 → 34.043 (+0.53%) | 269.730 → 268.088 (+0.61%) |
| 요청 1건 추가 전체 refresh | 350.091 → 321.233 (+8.24%) | 42.493 → 42.089 (+0.95%) |
| 요청 1건 추가 DB 저장·COMMIT 전체 | 7.461 → 7.990 (-7.10%) | 11.118 → 11.317 (-1.79%) |
| 요청 1건 추가 rollup 유지 구간 | 2.431 → 2.810 (-15.60%) | 3.128 → 3.956 (-26.47%) |
| 변경 없는 전체 refresh | 96.804 → 96.365 (+0.45%) | 24.290 → 29.641 (-22.03%) |

**판정:** 집계 열과 공간은 줄었지만 rollup 실행 시간의 큰 개선은 관측하지 못했다. 최초 rollup 구간 차이는 약 0.18·1.64ms다. 직접 바꾸지 않은 현재 입력의 COMMIT은 47.294→36.844ms, 합성 입력의 요청 비교·저장은 754.582→694.101ms로도 달라졌다. 이 변동과 고정 AB 순서·캐시 영향을 분리하지 않았으므로 전체 저장의 6.78%·5.56%를 열 제거의 안정적인 효과로 해석하지 않는다. 단일 추가 저장은 두 규모 모두 느려졌고 무변경 합성 갱신도 악화했다.

## 3. 저장 공간과 기존 DB 전환

최초 수집 후 `dbstat`의 두 daily **본체 B-tree** 합계다. 보조 인덱스·metadata·freelist·WAL을 포함한 총 저장 공간이나 누적 쓰기 바이트가 아니다.

| 항목 | 현재 데이터 A → B | 합성 10,000요청 A → B |
| --- | ---: | ---: |
| 요청·모델 daily 행 수 | 200·223 → 동일 | 100·200 → 동일 |
| daily 본체 페이지 수 | 28 → 26 | 18 → 15 |
| daily 본체 크기 | 112 → 104 KiB (-7.14%) | 72 → 60 KiB (-16.67%) |
| 전체 DB 논리 페이지 수 | 320 → 318 | 1,208 → 1,205 |

스키마 v19·rollup 형식 v2는 기존 파생 집계를 폐기하고 첫 조회에서 저장된 facts로 다시 구축한다. 완료된 A의 추가 후 DB 사본에서 별도 1회 측정한 결과는 다음과 같다. 복사·정확성 검증 시간은 제외했다.

| 구간 | 현재 799요청 | 합성 10,001요청 |
| --- | ---: | ---: |
| 연결 열기·v18→v19 전환·optimize | 6.855ms | 6.644ms |
| 첫 일별 조회·두 daily 재구축·결과 반환 | 63.567ms | 295.846ms |

원본 facts·manifest·모델·도구·비용·이름·ID 해시와 모든 잔존 조회 결과가 전환 전후 같았고 FK/integrity 검증을 통과했다. 파일 크기를 줄이는 VACUUM은 수행하지 않는다. [전환 원시 결과](RollupTrimUpgrade-2026-11-10.json).

## 4. 환경·정확성·한계

- 이 노트북: Windows 10.0.19045, Intel Core i5-8250U 1.60GHz·논리 CPU 8개, RAM 약 7.91GiB, Node v24.19.0, SQLite 3.53.3. WAL, synchronous=2, wal_autocheckpoint=1000, cache_size=-4096KiB, temp_store=FILE, mmap_size=0으로 동일하다.
- 현재 입력은 원본과 분리한 고정 사본 379파일·549,024,370byte, 798요청·187세션·14프로젝트다. Claude 48요청·Codex 750요청이다. 합성은 결정적 ordinal 생성의 100파일·100세션·10프로젝트·10,000요청이며 제공자별 5,000요청이다. 입력 해시·실제 시각 분포는 원시 JSON에 보존한다.
- 기간은 Asia/Seoul의 2026-01-01 이상·2027-01-01 미만, 시각 미상 포함이다. 실제 추가는 기존 Codex 세션에 요청 1건·130토큰이며 추가 전 상태는 각 최초 수집으로 구성한다. 변경 없는 갱신은 본문 읽기·성분 저장 0회다.
- A/B 각 1회·준비 반복 0회다. OS 캐시는 제어하지 않았고 입력 사본 생성·컴파일·검증이 선행했다. 양쪽은 새 프로세스·새 DB를 사용한다. A가 항상 먼저여서 순서 편향이 남는다. 완료 측정 전에 비교 실행기가 부동소수 값을 반올림한 뒤 독립 검증하던 문제로 A 실행 1회가 검증 실패했다. 원값을 검증하고 해시만 정규화하도록 수정했으며 실패한 실행은 표본에 포함하지 않았다.
- 새 DB 열기·마이그레이션·빈 rollup 활성화, 데이터 준비·append·사본 복원, 독립 결과 검증·조회·공간 계측은 refresh 타이머 밖이다. 기존 StageProfiler와 같은 원본 읽기·SQL transaction 계측을 양쪽에 적용했다. 순수 디스크 I/O·SQLite CPU 시간·xSync·총 쓰기 바이트·경쟁 writer·전원 손실·heap 피크는 측정하지 않았다.
- 제거가 승인된 `unknown_time_turns`·`stale_turns`·`last_successful_update`만 A/B 집계 반환 비교에서 제외했다. 나머지 요청·토큰·평균·캐시 NULL·기간/프로젝트/세션/모델·결과 개수, 정규화 facts·manifest와 raw/rollup 10차원, 빈 사용량 포함/제외의 독립 JS 집계, FK/integrity, 추가량과 입력 복원이 일치했다. 실데이터의 기대값은 정규화 facts 기준이며 JSONL 파서 전체의 독립 oracle은 아니다.
- `npm run check`는 타입 검사·린트를 통과하고 420개 중 414개 테스트가 통과했다. 실패 6개는 정리 전 A에서 동일하게 재현했다: rootless Codex 파싱 1개, 자식 계보·rootless/fallback 통합 4개, 취소 통합 1개다. 이번 정리의 마이그레이션·평균·NULL·미상 날짜·세션 시작·진단 보존·재오픈 검증은 통과했다. 최신 benchmark 코드 린트와 diff 검사도 통과했다. [검증 요약](RollupTrimValidation-2026-11-10.json).
- 과거 경로의 생성 파일이 모듈을 가리던 문제를 피하기 위해 A/B 모두 고정 소스에서 출력 디렉터리를 새로 구성했다. 원본 로그·설치 DB·quota는 변경하지 않았고 VSIX 설치는 수행하지 않았다.
