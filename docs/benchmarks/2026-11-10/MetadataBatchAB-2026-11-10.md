# 최종 이름·세션 결제 설정 중복 제거 1회 A/B

2026-11-10, Asia/Seoul. 사용자는 최종 결과의 이름을 한 번 저장하도록 알고리즘을 정리하고 A/B 1회를 요청했다. A는 미사용 rollup 상태 제거가 완료된 `4956423`, B는 정상 저장 묶음의 최종 프로젝트·세션 이름을 키별 한 번 UPSERT하고 사용자 결제 설정을 세션별 한 번 조회하는 구현이다. 현재 데이터와 합성 10,000요청을 각각 준비 반복 없이 A→B 1회 측정했다.

가정: 요청마다 반복하는 이름 UPSERT·결제 설정 SELECT와 성분별 이름 prune·후단의 동일 세션명 UPDATE를 줄이면 저장 비용이 감소한다. 파일 준비·요청별 facts/model/Skill/cost 비교·쓰기와 정상 묶음의 COMMIT·rollup 호출 경계는 유지한다. 새 스키마나 migration은 없다.

B에서는 기존 `storage.summaries`에 있던 이름·설정 처리를 `storage.metadata`로 옮겼다. B의 metadata는 현재 3.527ms·합성 8.809ms이며 위 비교는 겹치지 않는 `summaries + metadata`의 관측 합이다. 전체 replace와 그 하위 단계는 중첩되므로 합산하지 않는다. 원시 JSON의 A metadata=0은 별도 타이머가 없다는 뜻이며 작업이 없었다는 의미가 아니다.

**판정:** SQL 반복 제거는 실제 호출 수로 확인했다. 최초 저장의 관측 시간은 줄었지만 실데이터 전체 refresh는 약 42ms 느려졌고, 합성 1건 추가·무변경도 악화했다. rollup처럼 직접 바꾸지 않은 구간도 합성 287.051→264.826ms로 변했다. 단일 AB 순서·캐시·실행 변동과 변경 효과를 분리하지 않았으므로 전체 시간 차이를 보장되는 개선으로 일반화하지 않는다.

## 2. SQL 호출 감소와 적용 범위

실제 refresh 동안 `prepare`가 반환하는 statement의 실행 메서드를 양쪽에서 같은 방식으로 감쌌다. SQL 문자열의 종류만 분류하고 바인딩 값·이름·개인 ID는 공개하지 않는다. 호출 수는 실행 횟수이며 실제 변경 행 수·디스크 쓰기 횟수와 다르다.

| 최초 수집 SQL | 현재 A → B | 합성 A → B |
| --- | ---: | ---: |
| 프로젝트 이름 UPSERT | 805 → 36 | 10,000 → 50 |
| 세션 이름 UPSERT | 805 → 187 | 10,000 → 100 |
| 사용자 세션 결제 설정 SELECT | 805 → 187 | 10,000 → 100 |
| 위 세 종류 합계 | 2,415 → 410 | 30,000 → 250 |
| 후단 세션 이름 UPDATE | 297 → 132 | 0 → 0 |
| 프로젝트 prune | 187 → 36 | 100 → 50 |
| 세션 prune | 192 → 192 | 100 → 100 |
| 성분 저장 COMMIT | 12 → 12 | 10 → 10 |
| 요청·모델 daily DELETE/INSERT 각각 | 12 → 12 | 10 → 10 |

한 번의 단위는 **전체 스캔이 아닌 저장 transaction 묶음 안의 고유 키**다. 같은 프로젝트가 여러 묶음에 있으면 묶음마다 저장하므로 전체 프로젝트 14·10개보다 UPSERT 횟수가 많다. 최대 16성분·1,000요청 경계, 단일·특수 성분 경로와 실패 시 전체 rollback 후 개별 재시도는 유지한다.

실제 1건 추가에서는 기존 세션 snapshot을 다시 비교하므로 A는 현재 42요청·합성 101요청에 대해 각 세 종류를 반복했다. B는 해당 프로젝트·세션의 세 종류를 각각 1회 실행했다. 현재 후단 이름 UPDATE는 297→296회이며, 변경 없는 갱신은 A/B 모두 UPSERT·결제 조회 0회, 기존 세션 제목 metadata의 UPDATE 297회다. 변경 없는 제목만 바뀔 수 있어 후단 경로 자체는 보존했다.

정상 입력은 `입력 1회 색인 → 삭제 보존 대상 제외 → 최종 이름 수집 → FK 부모 이름 저장·설정 조회 → facts 순차 저장 → 영향 이름 prune → rollup → COMMIT` 순서다. 프로젝트는 마지막 이름, 세션은 마지막 nonempty 이름을 선택한다. 빈 이름은 기존 값을 지우지 않고 사용자 결제 override가 없으면 각 요청의 billing fallback을 유지한다. COMMIT 성공 후 이름만 스캔 상태에 전달해 마지막 metadata 이름과 같은 UPDATE를 생략한다.

반복 세션 snapshot·삭제·재연결을 포함하는 직접 batch API는 중간 prune·결제 설정 cascade를 보존하는 snapshot별 호환 경로다. 이 경로도 snapshot 안에서는 키별 한 번 처리한다. 입력 요청 N, 고유 프로젝트 P·세션 S일 때 정상 묶음의 이름·설정 SQL 호출은 O(N)에서 O(P+S)로 줄지만 전체 요청 처리 시간 차수 O(N)은 유지된다. 입력 색인·최종 metadata에는 O(N+P+S) 참조/보조 상태가 필요하다. 파생 계획은 transaction 범위, 성공한 이름 기록은 한 스캔 범위이며 장기 캐시를 추가하지 않는다.

## 4. 조건과 정확성

- 노트북: Intel Core i5-8250U 1.60GHz·논리 CPU 8개, RAM 약 7.91GiB, Windows 10.0.19045, Node v24.19.0, SQLite 3.53.3. WAL·synchronous=2·cache_size=-4096KiB·temp_store=FILE·mmap_size=0이다.
- 실제 고정 입력은 380파일·553,401,556byte, 805요청·187세션·14프로젝트다. Claude 48요청·Codex 757요청이다. 합성은 결정적 ordinal 규칙의 100파일·100세션·10프로젝트·10,000요청, 제공자별 5,000요청이다. 날짜는 2026-07-01 + 세션순번%14일 + 요청순번×3초이며 입력·소스·빌드 hash와 실제 분포는 원시 JSON에 있다. 원본 로그·설치 DB는 변경하지 않았다.
- 기간은 Asia/Seoul의 2026-01-01 이상·2027-01-01 미만, 시각 미상 포함·빈 사용량 제외 ON·비용 제외다. 토큰 평균은 사용량이 기록된 완료 요청 수, 시간 평균은 알려진 완료 duration 수가 분모다. 타이머 밖에서는 빈 사용량 포함/제외와 모델별 캐시 NULL·분모도 독립 JS 집계와 대조했다.
- A/B 각 1회·준비 반복 0회로 A가 먼저다. 새 프로세스·새 DB에서 최초 구축 후 같은 Codex 세션에 요청 +1·130토큰을 추가하고 무변경 갱신을 수행한다. 입력 복사·DB 열기·migration·빈 rollup 활성화·append·정확성 검증·조회·사본 복원은 refresh 타이머 밖이다. OS 캐시·GC·열·CPU 상태는 제어하지 않았다. 같은 SQL wrapper의 호출당 overhead도 별도 보정하지 않았으므로 절대 시간 차이에 그 비용이 포함될 수 있다.
- 모든 A/B에서 요청·토큰·이름·비용·모델·Skill·정규화 facts·manifest·raw/rollup 10차원·그룹별 평균·캐시 NULL·결과 개수·추가량·원본 읽기 순서와 입력 복원이 일치했다. FK/integrity도 통과했다. 독립 기대값은 정규화 facts 기준이며 실제 로그 파서 전체의 독립 oracle은 아니다.
- `npm run check`의 타입 검사·린트 통과, 전체 테스트 427개 중 421개 통과다. 남은 6개는 A에서도 동일하게 재현된 rootless/자식 계보·fallback 및 취소 테스트다. 새 이름·설정 경계 7개는 통과했다. 첫 추가 테스트 실패는 초기 fixture의 manifest 귀속이 null이라 삭제 보존 대상이 아니었던 문제로, 실제 accepted session을 설정해 보존 조건을 검증하도록 수정했다. [검증 요약](MetadataBatchValidation-2026-11-10.json).
- [transaction 직접 검증](MetadataBatchTransactionValidation-2026-11-10.json)은 독립 집계 160건·reader 원자성·전체 rollback·동일 DTO retry·16성분/1,000요청 경계·실패 격리·취소·삭제 보존·재연결·실제 scanner fallback을 통과했다. 과거 rollup 전용 검증 실행기는 A가 세 번 재집계한다는 옛 기준을 전제해 현재 A의 한 번 호출과 맞지 않아 그 횟수 assertion에서 중단했으며 통과로 기록하지 않는다. 이번 기능의 rollup·재시도 보존은 현행 전체 테스트와 transaction 검증 및 A/B로 확인했다.
- 전원 손실·프로세스 강제 종료·경쟁 writer·UI·실계정 quota·피크 heap·디스크 쓰기량은 미검증·미측정이다. 로컬 확장 설치와 커밋은 이번 범위에 포함하지 않았다.
