## 5. 구간 해석과 알고리즘 차이

- A의 원본 준비는 readJsonl의 파일 읽기·행 파싱·adapter callback·TEMP 적재 합계다. B는 parseChanged+expandRelated로 Worker 준비 결과 소비·순서 대기·변경 원본 적용을 포함한다. 순수 I/O나 파싱 CPU만의 비교가 아니며 동시 Worker 실행 시간 합계도 아니다. 전체 갱신과 함께 해석한다.
- B의 Worker 풀은 최대 4개·최대 8파일 선행이며, 작은 파일만 남아 선행 후보 합계가 1MiB 미만이면 시작하지 않는다. 이번 합성은 세션당 50요청의 작은 파일이므로 이 조건을 충족하지 않는다. 합성의 시간 감소를 Worker 병렬화 효과로 단정하지 않는다.
- A의 최종 집계는 prepareSummaries의 TEMP SQL 중복 제거·winner 준비다. B는 scan.aggregate의 메모리 winner·최종 요청 생성이다. B는 관계 역인덱스와 작업 큐를 사용하며 A의 성분별 TEMP 재구축이 제거됐다. 입력·중복·관계 분포에 따라 절대 차이가 바뀐다.
- A의 저장은 replaceSessions의 세션 전체 교체다. B는 storage.replace의 요청 비교·변경분 쓰기·이름/결제 묶음·최종 rollup·COMMIT이다. 정상 성분은 최대 16개·합계 1,000요청 단위로 묶고 특수 성분은 별도로 처리한다. 중첩 단계·각각의 중앙값은 합산하지 않는다.
- 최초 수집은 양쪽 모두 비어 있는 derived rollup에서 시작한다. 첫 조회 행에는 두 daily 구축이 포함된다. 재파싱·추가는 활성 rollup의 갱신 비용이 저장에 포함된다. COMMIT 시간/횟수는 스캔·TEMP 이벤트 적재·영속 저장 및 첫 조회의 읽기 transaction까지 포함한다. 영속 쓰기 transaction 수·fsync 횟수·쓰기 잠금 유지 시간으로 해석하지 않는다.
- A와 B 모두 일별 사전 집계·기존 기간/프로젝트 인덱스를 이미 사용한다. 과거 rollup 도입 실험의 수십 배 조회 개선을 이번 v0.2.0 비교에 합산하지 않는다. A의 공개 queryUsage+queryUsageCount와 B의 통합 queryUsagePage가 같은 행·개수를 반환할 때까지 비교했다.
- 진단용 unknown_time_turns·stale_turns·last_successful_update는 dev에서 의도적으로 공개 집계에서 제거됐다. 이 세 속성만 공통 결과 비교에서 제외한다. 물리 ID·갱신 시각은 기존 정규화 규칙으로 제외한다. 원본 요청·모델·Skill·비용·이름·진단 의미 해시도 별도로 비교한다.

### 실제 입력의 동등성 실패 원인

반복 측정의 같은 파일에서 A는 **1,075요청·1,507,810,476토큰**, B는 **809요청·1,512,226,897토큰**을 만들었다. 두 버전 모두 최초 파싱은 382파일·556,386,161byte이고 실패 파일은 0개다. 전체 10쌍·6시나리오에서 요청 수·토큰·20종 집계의 A/B 동등성은 실패했다. 각 버전 내부의 저장 facts → raw SQL/rollup/독립 JS 기대값은 통과했다. 따라서 실데이터 시간 감소율은 서로 다른 동작의 관측값이며 순수 알고리즘 개선율로 확정하지 않는다.

새 고정 사본의 별도 1회 진단에서도 요청 수 차이가 재현됐다. A에만 있는 266요청은 모두 Codex의 standalone-subagent이고 102세션·137,423,911토큰이다. B에만 있는 요청은 0개이며 공통 809요청 중 26개의 토큰이 모두 증가했다. 해당 요청의 토큰은 89,528,397 → 231,368,729이다. 부모 요청의 증가분 141,840,332에서 A 독립 자식 토큰을 빼면 순증 4,416,421토큰으로 원래 측정의 차이와 같다. dev의 aggregation/parentGroups.ts·memoryAggregate.ts와 2ec4323의 자식 사용량 부모 합산 변경은 이 차이와 일치한다. 증가한 토큰이 모두 올바른지까지는 정규화 facts 기반 reducer로 증명하지 못하므로 별도 파서/계보 정확성 검증 대상으로 남긴다. 진단 사본은 측정 사본과 hash가 다르며 성능 표본에 혼합하지 않았다.

실제 Codex 추가에서 A는 1파일·3,822,842byte, B는 9파일·7,702,884byte를 읽었다. 추가 읽기와 관련 원본 확장은 준비 구간 72.897 → 199.790ms 및 전체 지연과 함께 관측됐다. 이전 코드와 현재 코드가 같은 일을 하는 단일 파서의 속도 비교로 해석하지 않는다.

- 각 규모에서 예열 3쌍을 제외하고 AB/BA 순서를 교대해 10쌍 측정했다. 별도 현재 구현 1회는 입력 검증 및 동일 append 대상 고정용이다. 질의는 각 프로세스에서 예열 3회 후 10회, 대표값은 프로세스별 중앙값의 중앙값이다.
- 시나리오는 최초 → 변경 없음 → manifest.parser_version=0 전체 재파싱 → Codex 요청 추가 → Claude 요청 추가 → Codex 응답 연장 순서다. Codex 추가 직전은 N건, Claude 추가 직전은 N+1건이다. 추가량은 각각 +1요청/+130토큰, 연장은 요청 수 유지/+26토큰으로 확인한다.
- 준비 실행에서 시나리오별 정규화 facts·raw SQL·독립 JS로 기대 집계 해시를 고정한다. 반복에서는 매번 facts 해시가 같은지 확인한 뒤 모든 실제 집계 결과를 그 기대 해시와 대조한다. facts가 다르면 raw SQL·독립 JS 검증을 다시 수행한다. 동일 입력의 비싼 raw 날짜 변환을 매 회차 반복하지 않으며 검증은 모두 타이머 밖이다.
- 합성 비교는 파싱 파일 수·읽기량까지 같음을 추가 확인했다. 실제 비교는 읽기 생략이 가능한 구조 차이를 허용하도록 결과 동등성에서 두 계측값을 제외했다. 시간 계측은 같다.
- 합성 입력은 seed 대신 ordinal 식으로 결정적으로 생성한다. 제공자마다 절반, 세션당 50요청, 세션 번호 mod 10 프로젝트이며 100건은 2세션·2프로젝트, 10,000건은 200세션·10프로젝트다. 모두 완료 상태이며 input=100+ordinal mod 1000, output=10+ordinal mod 50이다. 실제 B의 초기 분포는 Claude 48요청·20세션·6프로젝트, Codex 761요청·169세션·11프로젝트다. 제공자 사이 프로젝트는 겹칠 수 있다.
- 조회 기간은 2026-10-11 00:00 이상·2026-11-10 00:00 미만(KST), 미상 시각 포함이다. 합성 날짜는 기준일 전 1~25일에 배치된다. 평균은 완료 요청의 합계/완료 표본 수이며 빈 사용량 제외 시 토큰 또는 모델이 기록된 완료 요청만 분모에 포함한다. 독립 JS 검증은 저장된 정규화 facts 기준이며 JSONL 파서 전체의 독립 oracle은 아니다.
- Node v24.19.0, SQLite 3.53.3, win32/x64, Intel(R) Core(TM) i5-8250U CPU @ 1.60GHz. WAL·cache 4MiB·TEMP=FILE·mmap=0의 제품 기본값을 사용한다. OS 파일 캐시를 비우지 않았고 백그라운드 부하를 통제하지 않았다.
- 새 프로세스·새 DB를 사용한다. 컴파일·입력 사본 구성·DB 열기/스키마 생성·checkpoint·append·검증·사본 복원·IPC 시작 비용은 갱신 타이머 밖이다. 최초 rollup 구축은 별도 첫 조회에 포함한다. v12→v19 기존 DB 마이그레이션, UI/worker IPC, quota, peak RSS·누적 디스크 쓰기량은 미측정이다. 원본 파일과 설치 DB는 변경하지 않았다.
