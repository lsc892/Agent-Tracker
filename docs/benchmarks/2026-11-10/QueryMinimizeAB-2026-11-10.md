# 요청 저장·일별 집계 SQL 최소화 A/B

가정: 사용자는 현재 기능을 유지하면서 서브에이전트로 병목을 조사하고, 큰 두 구간의 중복 SQL·탐색을 줄인 뒤 A/B하도록 요청했다. 에이전트는 신규 요청의 불필요한 자식 DELETE와 일별 집계식에 반복 삽입되는 사용량 판정을 줄이면 초기 DB 저장 비용이 감소한다고 보았다.

개선 방향: **A는 작업 시작 시 고정한 현재 구현**, **B는 신규 자식 DELETE 생략 + 범위를 제한한 집계 입력의 사용량 플래그 공유**다. 영속 테이블·인덱스·스키마 v19·집계 형식 v2는 그대로다. 신규 facts를 32행씩 INSERT RETURNING하던 후보는 성능 회귀로 폐기했다.

## 1. 최종 결과

측정: **2026-11-10 23:23:39–23:27:20, Asia/Seoul**. 준비 3쌍 제외, A/B 순서를 교대해 10쌍 측정한 중앙값 ms다. 개선율은 `(A−B)/A×100`이며 양수는 시간 감소, 음수는 악화다. 중첩 타이머는 합산하지 않는다.

| 측정 항목 | 현재 1,355건 A → B (개선율) | 10,000건 A → B (개선율) | 100건 A → B (개선율) |
| --- | ---: | ---: | ---: |
| 최초 요청 비교·저장 `summaries` | 52.748 → 44.256 (+16.10%) | 276.026 → 237.589 (+13.93%) | 4.011 → 4.184 (-4.30%) |
| 최초 일별 집계 `rollups` | 30.480 → 30.289 (+0.63%) | 112.898 → 107.372 (+4.89%) | 2.096 → 2.223 (-6.05%) |
| 최초 DB 저장·COMMIT 전체 `replace` | 148.727 → 141.102 (+5.13%) | 452.811 → 404.756 (+10.61%) | 8.682 → 9.185 (-5.79%) |
| 최초 전체 refresh | 3,545.415 → 3,448.680 (+2.73%) | 745.658 → 700.841 (+6.01%) | 36.556 → 36.398 (+0.43%) |
| 요청 1건 추가 DB 저장·COMMIT | 4.632 → 4.125 (+10.94%) | 5.220 → 5.063 (+3.01%) | 2.515 → 2.468 (+1.84%) |

실제·10,000건의 최초 요청 저장은 B가 **각 10/10쌍**, DB 저장 전체는 **9/10·10/10쌍** 빨랐다. 일별 집계는 **7/10·9/10쌍**이며 실제 입력의 차이는 약 0.19ms여서 안정적인 큰 개선으로 보지 않는다. 100건의 최초 DB 저장은 B가 3/10쌍만 빨랐고 약 0.50ms 느려졌다. 모든 규모에서 빠른 최적화라는 결론은 내리지 않는다.

요청 추가·평균 조회의 필수 비교는 다음과 같다. 평균 조회는 제공자 기준으로 **모든 페이지와 전체 그룹 수를 반환할 때까지** 측정했다. 모델 기준 네 조회도 원시 JSON에 보존했다.

| 측정 항목 | 현재 1,355건 A → B (개선율) | 10,000건 A → B (개선율) | 100건 A → B (개선율) |
| --- | ---: | ---: | ---: |
| 요청 1건 추가 전체 refresh | 463.682 → 469.057 (-1.16%) | 25.197 → 25.559 (-1.44%) | 8.755 → 8.783 (-0.32%) |
| 일별 평균 토큰 조회 | 2.751 → 2.604 (+5.35%) | 1.608 → 1.647 (-2.40%) | 1.023 → 0.954 (+6.68%) |
| 월별 평균 토큰 조회 | 2.252 → 2.030 (+9.87%) | 1.186 → 1.234 (-4.12%) | 0.785 → 0.846 (-7.85%) |
| 세션별 평균 토큰 조회 | 4.325 → 4.092 (+5.38%) | 1.760 → 1.691 (+3.87%) | 0.827 → 0.882 (-6.54%) |
| 프로젝트별 평균 토큰 조회 | 2.364 → 2.286 (+3.32%) | 1.199 → 1.191 (+0.68%) | 0.747 → 0.672 (+10.02%) |

일반 조회 SQL은 바꾸지 않았다. 수 ms 조회의 작은 차이와 일부 모델 조회의 악화까지 원시에 남기며 읽기 성능 개선으로 판정하지 않는다. 단일 추가 DB 저장의 B 우세도 6/10·7/10·5/10쌍으로 섞였고 **전체 추가 refresh는 세 규모 모두 조금 느렸다.** 무변경 refresh는 현재 126.772→126.635ms, 10,000건 17.760→16.835ms, 100건 4.448→4.506ms이며 모두 본문 읽기·파싱·성분 저장 0회였다.

## 2. 구간 조사와 대상 선택

서브에이전트 세 개가 읽기 쿼리, 저장 쿼리, 측정 하네스를 각각 조사했다. 현재 소스와 실행용 자산을 새 A에 고정한 뒤 새 실데이터 사본·고정 합성 입력으로 진단했다.

최초 탐색용 단일 A 관측에서 10,000건의 `summaries`는 **299.393ms**, `rollups`는 **128.975ms**, COMMIT은 **42.639ms**였다. 현재 1,355건은 각각 **55.145·36.592·53.774ms**여서 COMMIT도 컸다. 이번 요청의 쿼리 개선 범위에서는 동기화 설정·거래 경계를 유지하고 **SQL 연산이 큰 summaries·rollups 두 구간**을 선택했다. 이 탐색용 값과 위 최종 A/B의 시간을 섞어 개선율을 계산하지 않는다.

별도 읽기 프로파일의 상위는 비용 포함 달력 조회였다. 현재 일별 제공자 16.474ms, 10,000건 월별 제공자 115.040ms였고 요청 모델 정렬은 8.880·43.859ms였다. 네 분류 집계·coverage에도 중복은 있지만 이번 두 저장 구간과 서로 다른 사용자 작업이므로 한 순위로 합산하지 않았다. 이 조회 최적화와 앞서 작성한 테이블 재설계는 이번 제품 변경에 포함하지 않았다. [범위별 진단 JSON](QueryMinimizeBaseline-2026-11-10.json).

## 3. 실제 바꾼 알고리즘

### 요청 저장: 존재하지 않는 자식을 지우지 않는다

[memoryStore.ts](../../../src/summary/db/memoryStore.ts)는 신규·기존 여부를 이미 확인한다. 새 ID에는 자식이 없으므로 모델·도구 DELETE를 실행하지 않고 바로 최종 자식을 INSERT한다. 기존 요청이 변경된 경우에는 원래처럼 해당 자식을 삭제·교체한다. ID·updated_at·사용자 결제·Skill 보존·입력 순서·transaction 경계는 유지한다.

별도 SQL 진단에서 최초 저장의 실행 수는 다음과 같다. 진단 wrapper가 있는 실행이라 이 실행의 시간은 최종 중앙값에 합치지 않는다.

| 실행 수 | 현재 1,355건 A → B | 10,000건 A → B | 100건 A → B |
| --- | ---: | ---: | ---: |
| 신규 모델·도구 DELETE 합계 | 2,710 → 0 | 20,000 → 0 | 200 → 0 |
| 최초 refresh 전체 SQL 호출 | 13,273 → 10,563 | 70,761 → 50,761 | 787 → 587 |

신규 facts INSERT와 요청별 비용 저장은 기존 방식이다. 조회 자료 전체 캐시·새 영속 테이블·새 인덱스·광범위한 dirty 마스크는 추가하지 않았다. [SQL 실행 수 진단](QueryMinimizeProfile-2026-11-10.json).

### 일별 집계: 선택 입력의 사용량 판정을 한 번 확정한다

[일별 소스](../../../src/summary/db/queries/rollup/source.ts)는 변경 세션의 인덱스 범위를 먼저 적용한 뒤 집계에 필요한 좁은 열만 `scoped AS MATERIALIZED`로 계산한다. 사용량 유무는 다음처럼 확정하고 [집계 상태 식](../../../src/summary/db/rollup-state.ts)이 그 플래그를 공유한다.

```sql
CASE WHEN total_tokens > 0 THEN 1 ELSE has_model END AS has_recorded_usage
```

양수 토큰이면 모델 확인을 생략하고, 0토큰일 때만 모델 기록을 확인한다. 완료/기록 표본 평균·캐시 NULL·duration 분모·미상 모델과 날짜·모델 fallback을 보존한다. 저장뿐 아니라 부분 날짜의 `UNION ALL`에서도 쓸 수 있도록 `SELECT * FROM (WITH ... SELECT ... GROUP BY ...)`로 반환한다.

별도 보존 DB의 실제 계획은 제공자 집계의 상관 서브쿼리 노드가 **15→1개**로 줄었고, 세션 범위는 기존 UNIQUE/PK 탐색을 유지했다. `scoped`의 SCAN은 이미 좁힌 임시 입력의 순회다. 영속 facts 전체를 불필요하게 읽는 경로로 바꾸지 않았다.

**날짜 함수 호출 수 감소 가정은 성립하지 않았다.** 10,001요청 전체 집계의 날짜 UDF 호출은 A/B 모두 10,001회, 선택한 101요청 세션도 모두 101회였다. 상관 계획 노드 15개가 실제 모든 행에서 15번 실행됐다는 뜻도 아니다. 원래 OR/CASE의 조건 분기와 새 materialization 비용을 포함한 전체 SQL 손익이 최종 결과이며, 각 내부 CPU 비용은 별도 분리하지 않았다. [SQL·계획·함수 호출 수](QueryMinimizePlans-2026-11-10.json).

### 폐기한 후보

처음에는 신규 facts를 최대 32행의 VALUES INSERT RETURNING으로 묶고 반환 ID를 요청 키로 연결했다. 결과는 같았지만 10,000건의 요청 저장이 **277.785→311.710ms(-12.21%)**, 전체 refresh가 **753.216→787.081ms(-4.50%)**로 악화했다. 실제 데이터의 facts 저장도 18.169→21.951ms로 10/10쌍 느렸다.

호출 감소만으로 효과를 판단하지 않고 묶음 INSERT·RETURNING·ID Map·대기 배열을 제품에서 제거했다. 최종 소스는 신규 자식 DELETE 생략만 남긴다. 단순 materialization의 중간 비교와 양수 토큰에서도 모델 확인하던 입력을 정리한 최종 비교도 따로 보존했다. 서로 다른 실행의 개선율을 더하거나 곱하지 않는다. 실패·중간 원시 JSON과 당시 소스는 [실험 보관 ZIP](QueryMinimizeSources-2026-11-10.zip)의 observations에 있다.

## 4. 입력·조건·검증

- 현재 사본: **659파일·508,993,502byte, 1,355요청·373세션·30프로젝트**, 2,774,090,068토큰이다. 사본을 만든 뒤 추가된 실제 로그는 포함하지 않는다. 대화 원문·제목·세션 ID·설치 DB는 공개 산출물에 넣지 않았다.
- 합성: 고정 ordinal 산식으로 제공자별 절반, 10프로젝트. 10,000건은 100세션×100요청, 100건은 10세션×10요청이다. 시각은 2026-07-01 + 세션 순번%14일 + 요청 순번×3초다. 실제 입력 SHA와 분포는 원시에 있다.
- 각 variant/표본은 별도 프로세스·새 DB에서 같은 최초 상태를 만든 뒤 **같은 기존 Codex 세션에 +1요청·+130토큰**을 추가한다. 매번 사전 상태를 새로 만들고 사본 내용을 복원·검증한다. 대량 저장 시간을 요청 수로 나누지 않았다.
- Windows 10.0.19045, AMD Ryzen 5 7500F·논리 CPU 12개, Node v24.14.1, SQLite 3.51.2. WAL·synchronous=2·cache_size=-4096KiB·temp_store=FILE·mmap=0을 유지했다. OS 캐시를 비우거나 강제 GC하지 않았다.
- 고정 기간은 Asia/Seoul의 2026-01-01 이상·2027-01-01 미만, 시각 미상 포함이다. 평균 토큰은 사용량이 기록된 완료 요청이 분모이고, duration 평균은 알려진 완료 duration 표본이 분모다. 빈 사용량 포함/제외 양쪽을 별도 JS 기대값과 대조했다.
- 최종 반복은 **저장 두 구간에 집중하는 `--storage-only`** 실행이다. 전체 refresh·8개 평균 조회는 측정하고, 앞선 진단·중간 반복에서 측정한 비용/정렬/이름/네 분류/coverage의 32개 읽기 workload는 반복하지 않았다. 이 넓은 조회들의 최신 성능 개선을 주장하지 않는다.
- 실제 refreshSummary의 COMMIT·optimize 반환까지 측정한다. 프로세스 시작·DB 열기·빈 rollup 활성화·사본 준비·파일 append·검증·복원은 refresh 타이머 밖이다. SQL별 실행 수·계획·함수 호출 수는 최종 시간 표본과 분리했다.
- 최종 모든 준비·측정 쌍의 facts·요청/토큰 합계·8개 평균 결과·그룹 수·raw/rollup 10차원·FK/integrity와 원본 사본 복원이 일치했다. 독립 JS 기대값은 정규화 facts 기준으로, 비공개 JSONL 파서 전체의 독립 oracle은 아니다.
- 추가로 요청 수 **0/1/31/32/33/64/65**, 신규·기존 혼합, 입력 iterable 한 번 소비, 자식 실패의 전체 rollback·재시도, 두 시간대·미상 시간 3정책·부분 날짜·빈 페이지 **96개 A/B↔raw 대조**를 통과했다. [경계 검증](QueryMinimizeValidation-2026-11-10.json).

- `npm run typecheck`, `npm run lint`, `git diff --check`를 통과했다. 일반 자동 테스트 suite는 실행하지 않았다. UI·quota·강제 종료·전원 손실·경쟁 writer·heap peak는 미측정이다.

## 5. 판정·재실행

**일부 성립.** 실제·10,000건 초기 요청 저장의 확실한 불필요 SQL을 제거했고, 10,000건 일별 집계에도 작은 개선을 확인했다. 초기 DB 저장 전체는 각각 5.13%·10.61% 감소했다. 현재 일별 집계 효과는 미미하고 100건 DB 저장·단일 추가 전체 refresh는 개선하지 못했다. 작은 규모에 맞춘 추가 분기·캐시를 붙이지 않고 이 손익을 명시한 최소 변경을 채택한다.

```powershell
node --no-warnings tests/benchmarks/query-minimize-ab.cjs --workspace=tests/results/benchmarks/query-minimize-ab-20261110 --before=tests/results/benchmarks/query-minimize-ab-20261110/A --after=tests/results/benchmarks/query-minimize-ab-20261110/B-final --output=<새 JSON 경로> --warmups=3 --pairs=10 --readWarmups=3 --readSamples=1 --storage-only

```

`--baseline-only`는 A만 넓은 구간 순위를 만들고 `--profile-only --after=...`는 별도 A/B SQL 진단이다. 기본 데이터는 세 규모 전부이며 `--datasets=...`로 범위를 명시할 수 있다. 기존 결과를 덮어쓰지 않는다.
