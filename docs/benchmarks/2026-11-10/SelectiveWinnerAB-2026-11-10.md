# 선택 JSON 파싱·winner 비교 재사용 실패 기록

2026-11-10, Asia/Seoul. **실데이터 성능 회귀로 후보를 폐기하고 코드를 실험 전 `9eeaffa` 상태로 복원했다.** 사용자의 지시에 따라 이 실패 기록만 남기고 실험 코드·테스트·실행기·원시 JSON·소스 ZIP은 제거했다.

가정: 불필요한 본문을 객체화하지 않고 winner의 정규화 결과·input+output 비교점수를 재사용하면 원본 준비와 최종 집계가 줄어들 것이다. A는 기존 제품, B는 두 변경을 함께 적용한 후보였다. 개별 변경의 효과를 분리한 실험은 아니다.

## 관측 결과

현재 데이터와 합성 두 규모에서 준비 반복 없이 A→B를 각각 1회 실행했다. 시간 단위는 ms다.

| 데이터 | 최초 전체 갱신 A→B | 실제 요청 1건 추가 A→B |
| --- | ---: | ---: |
| 현재 817요청 | 3998.151 → 5093.928 (27.41% 악화) | 363.214 → 390.521 (7.52% 악화) |
| 합성 10,000요청 | 1846.431 → 1660.910 | 42.364 → 35.914 |
| 합성 100요청 | 70.035 → 61.431 | 13.624 → 15.390 |

현재 최초 최종 집계는 171.746→144.082ms로 줄었지만, 원본 준비가 3502.318→4650.369ms로 늘어 전체 시간이 악화했다. 원본 준비 증가가 주된 회귀 구간이며, 그 안의 순수 파싱 CPU·할당·GC 기여율은 분리 계측하지 않았다.

## 원인 분석

### 관측으로 확인한 범위

| 현재 데이터의 최초 갱신 | A | B | B−A |
| --- | ---: | ---: | ---: |
| 전체 갱신 | 3998.151ms | 5093.928ms | +1095.777ms |
| 원본 준비 | 3502.318ms | 4650.369ms | +1148.051ms |
| 최종 집계 | 171.746ms | 144.082ms | −27.664ms |

최종 집계 절감은 A 전체 시간의 약 0.69%다. 다른 구간이 같다는 가정에서 최종 집계 구간을 전부 없애더라도 절감 가능한 시간은 약 4.30%다. 원본 준비에서 늘어난 약 1.15초를 최종 집계의 약 28ms 절감으로 보완하기 어려운 구조였다. 각 구간은 순수 CPU 함수 시간이 아니며 원본 준비에는 읽기·해시·adapter·Worker 결과 대기도 포함된다. 이 표로 세부 원인의 비중을 확정하거나 상위·하위 타이머를 중복 합산하지 않는다.

### 후보 구현에서 추가된 작업

기존 경로는 청크·줄의 UTF-8 변환과 이미지 처리를 거쳐 `JSON.parse`로 객체를 만들고 adapter가 필요한 값을 골랐다. 후보도 같은 원본 읽기·SHA-256·UTF-8 변환을 먼저 수행했다. 따라서 큰 원문 문자열 자체를 만들지 않거나 파일 읽기량을 줄인 구현은 아니었다. 현재 경로의 근거는 [JSONL reader](../../../src/summary/jsonl/index.ts#L192), [원본 읽기·해시](../../../src/summary/scanner/sourceReader.ts#L52)다.

당시 선택 파서는 이벤트 종류가 뒤에 있거나 키가 중복돼도 같은 결과를 내기 위해, 분기가 필요한 객체의 직접 필드 위치를 먼저 색인했다. 이때 하위 값의 문법까지 검사한 뒤, 선택한 경로를 구성하면서 그 객체를 다시 순회했다. 필요 없는 큰 본문도 위치 확인·문법 검사를 위해 재방문할 수 있었다. 통째로 보존하는 선택 하위 객체에는 별도 구간 검사와 `JSON.parse` 호출도 발생했다. 즉, **값 생성을 줄이는 대신 구조 검사·필드 선택의 순회가 늘어난 구현**이었다.

또한 범용 재귀 처리, 키 문자열과 위치 Map, 선택 결과의 속성 정의가 추가됐다. 그 비용이 생략한 본문의 객체 생성 비용보다 컸을 가능성이 있다. 기존 reader가 이미 이미지 Base64를 제거한다는 점도 남은 절감 여지를 제한한다. 이는 구현 구조와 관측 구간에 근거한 원인 후보이며, 개별 함수 CPU나 할당량을 측정한 결론은 아니다.

### 합성 결과가 선택 파싱의 개선 근거가 되지 않는 이유

당시 B는 이미지 제거 후 행 문자열이 **1,024 UTF-16 code unit을 넘을 때만** 선택 파싱을 적용했다. [합성 생성 규칙](../../../tests/benchmarks/incremental-refresh.cjs#L142)을 메모리에서 재구성해 다음을 확인했다. 시간 측정이나 추가 A/B 실행은 하지 않았다.

| 합성 입력 | JSON 행 수 | 전체 바이트 | 최대 행 길이·UTF-16 code unit | 1,024 초과 행 |
| --- | ---: | ---: | ---: | ---: |
| 10,000요청 | 30,050 | 5,637,210 | 270 | 0 |
| 100요청 | 305 | 55,700 | 264 | 0 |

재구성한 바이트 수는 당시 기록과 일치한다. 두 합성 최초 입력은 모두 native 파싱 경로를 탔으므로, 그 시간 감소를 선택 파싱의 효과로 해석할 수 없다. 정규화·비교점수 재사용의 영향과 실행 변동도 함께 들어 있다. 실제 입력은 합성 10,000요청보다 요청 수는 적지만 원본 바이트가 약 98.9배 크다. 요청 건수만으로 파싱 작업량을 비교한 해석에도 한계가 있다. 실데이터의 선택 파싱 적용 행 수·버린 본문 비율·이미지 제거 뒤 행 크기 분포는 당시 별도로 기록하지 않았다.

### winner 판별에서 줄인 것과 남는 것

기존 [SourceWinners](../../../src/summary/aggregation/sourceWinners.ts#L33)는 이미 한 번의 순회와 Map으로 그룹당 최대 후보만 남긴다. 순서나 상한을 모르는 k개 후보 중 정확한 최대를 찾으려면 모든 후보를 확인해야 하므로, 단순히 비교를 생략하는 방식으로 차수를 개선하기 어렵다.

실제 줄일 여지가 있던 부분은 반복 정규화와 합계 재계산이었다. 당시 원복한 기준 구현에서는 SourceWinners가 정규화한 이벤트를 SourceEvidence에서 다시 정규화하고, 남은 winner를 최종 집계에서 다시 정규화했다. 비교용 input+output 합계도 원본별 선택과 최종 winner 선택에서 각각 구했다. 후보는 이 중복을 줄였지만, 선택 파싱과 함께 측정했기 때문에 단독 개선율은 모른다.

원본별 그룹과 최종 그룹은 부모·fork 제외와 Claude request 보정 이후의 귀속이 다를 수 있어 같은 판별을 무의미하게 두 번 한다고 단정할 수 없다. 낮은 점수의 후보에도 root·진단·계보 근거가 있으므로 숫자 비교에서 졌다는 이유로 관련 처리를 전부 버려서도 안 된다.

## 실패한 알고리즘에서 개선할 수 있는 부분

개선점은 있다. 다음은 재시도 후보이며 구현·성능 검증을 마친 채택안은 아니다.

| 우선순위 | 개선 방향 | 줄일 작업과 보존 조건 |
| --- | --- | --- |
| 1 | 기존 JSON 파서를 유지하고 정규화·비교점수 재사용만 분리 | 원본 winner의 정규화 결과·정확한 합계를 최종 병합에 전달한다. JS 선택 파서의 비용을 섞지 않고 평가한다. Worker 전송, BigInt, 동점 순서와 입력 객체 소유권을 보존한다. |
| 2 | 전체 색인 후 재순회를 한 번의 구조 검사로 바꾸기 | 문법을 검사하는 동안 필요한 필드의 값·구간만 수집하고, 객체 끝에서 마지막 type·call ID를 기준으로 필요한 구간만 변환한다. 불필요한 본문을 다시 순회하지 않는다. 키 순서·중복 키·손상 JSON·취소·offset을 유지하며 위치는 현재 행 처리 동안만 보유한다. |
| 3 | 범용 객체 구성 대신 고정된 작은 레코드 사용 | 필요한 경로에 고정 슬롯이나 작은 객체를 사용해 위치 Map·키 복제·속성 정의 비용을 줄인다. 문법 검증과 값 생성을 분리하고, 사용자 제목·도구 호출·자식 연결·수명주기 필드를 빠뜨리지 않는다. |
| 4 | winner의 시간순 정렬 범위 축소 | metadata가 index 증가순임을 보장할 수 있으면 winner만 index로 정렬한 뒤 metadata와 선형 병합한다. 현재 `events()`가 합친 전체 목록을 정렬하는 작업을 줄이는 별도 후보이며, 동점 순서·메모리와 실제 이득은 검증해야 한다. |
| 5 | 전체 행 길이 외에 버릴 수 있는 본문 비율을 기준으로 선택 | 큰 행이어도 대부분 필요한 도구 인자·제목이면 절감이 작다. 구조 검사 중 이미 얻은 경로·구간 길이로 적용을 판단하고, 판단을 위한 추가 전수 스캔은 피한다. 적용·미적용 횟수와 fallback 비용도 기록한다. |
| 6 | native 선택 파싱·문서 묶음 처리 검토 | JS 문법 검사 비용이 지배적일 때 검토한다. 필요한 숫자·ID만 한 묶음으로 반환하는 경로와 배포 비용을 함께 비교하며, 사용하지 않는 값의 오류까지 기존 정책대로 검출하는지 확인한다. |

순회 개선의 목표는 `전체 문법 검사 → 전체 재탐색 → 선택 값 생성`을 `한 번의 문법 검사·필요 구간 수집 → 선택 값 생성`으로 바꾸는 것이다. 전체 바이트 검사는 여전히 필요하므로 O(원본 바이트)는 유지된다. 절감 대상은 반복 순회·불필요한 값 생성·보조 객체의 상수 비용이다. native·필드 선택 개념의 기존 조사와 제약은 [파싱 개선 후보](../../research/2026-11-05/JsonlChunkParsing-2026-11-05.md#4-파서-구조를-바꾸는-추가-후보)에 있다.

재시도한다면 먼저 비교 정보 재사용만 분리하고, 선택 파서는 큰 불필요 본문·큰 필요 본문·escape가 많은 본문·작은 행을 구분해 비교한다. 원본 읽기·줄 구성/디코딩·문법 검사/값 생성·adapter/winner·Worker 전송을 구분하되 행마다 타이머를 넣는 계측 자체의 비용도 확인한다. 적용 행 수·본문 생략 바이트·재방문량·할당/GC를 함께 기록해야 단일 전체 시간만으로 원인을 추정하는 한계를 줄일 수 있다.

이번 보완은 보존된 측정값·당시 구현 내용·현재 원복된 코드에 대한 분석과 합성 입력 구조 확인이다. 삭제된 실데이터 사본·후보 코드·원시 표본을 다시 확보한 CPU 프로파일링은 수행하지 않았다.

## 조건과 검증

- 현재 입력은 383파일·557,333,047byte, 817요청·1,524,959,103토큰·190세션·14프로젝트다. 합성은 고정 ordinal로 10,000요청/100세션과 100요청/10세션을 만들었고, 토큰 합계는 각각 6,340,000·18,400이다.
- Intel Core i5-8250U·논리 CPU 8개, Windows 10.0.19045, Node v24.19.0, SQLite 3.53.3에서 같은 설정을 사용했다. 새 프로세스·새 DB로 최초 수집 후 같은 Codex 세션에 +1요청/+130토큰을 추가했다. 복사·DB 열기·검증·조회·사본 복원은 refresh 측정 밖이다. OS 캐시·GC·열 상태는 제어하지 않았다.
- 세 규모의 요청·토큰·facts·모델·도구·비용·이름·manifest·평균 결과가 A/B에서 일치했다. raw/rollup, 정규화 facts 기준 독립 JS 집계, FK/integrity, 추가량·기존 요청 보존·사본 복원도 통과했다. JSONL 파서 전체의 독립 oracle과 peak 메모리는 미측정이다.
- 후보 검증 당시 새 테스트 8개와 타입·린트가 통과했다. 전체 435개 중 429개가 통과했고, 실패 6개는 변경 전 A에서도 동일하게 재현됐다.
- 복원 후 `npm run check`에서 타입·린트가 통과하고 기존 427개 중 421개 테스트가 통과했다. 남은 6개는 같은 기존 실패다. 제품 코드·테스트·설계 명세가 실험 전 커밋과 일치하고 문서 링크·`git diff --check`가 정상임을 확인했다.

선택 파싱과 비교점수 재사용은 현재 제품에 남아 있지 않다. 이 실험은 실데이터 전체 성능 가정의 실패 기록이며, 같은 아이디어의 다른 구현까지 기각하는 근거로 사용하지 않는다.
