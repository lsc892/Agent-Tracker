# 최초 일괄 적재·추가분 INSERT의 rowid A/B

이번 실험은 사용자가 제시한 **처음에 JSONL을 읽어 일괄 적재하고, 이후에는 저장한 위치 다음의 신규 요청만 INSERT하는 경로**를 비교한다. 정규화된 요청 요약 JSONL을 사용하는 벤치마크 시제품이며, 현재 제품의 Claude·Codex 원본 로그 파서 전체 성능을 측정한 결과는 아니다. 제품 코드는 변경하지 않는다.

재현 실행기는 [sql-rowid-append.cjs](../../../tests/benchmarks/sql-rowid-append.cjs), 측정 원본은 [JSON](SqlRowidAppend-2026-10-27.json)이다. [앞선 현재 제품 저장 경로 실험](../SqlRowid-2026-10-27.md)과 구분한다.

## 측정 결과

**추가분만 적재해도 일반 rowid가 일관되게 빠르지는 않았다.** 10만 건에서 요청 1건 추가는 rowid의 중앙값이 0.155~0.312 ms 늘었다. 100건 추가는 세션당 100건에서 2.3% 줄었고 세션당 10,000건에서는 4.9% 늘었다. 이 결과만으로 제품의 일별 집계를 rowid로 바꿀 근거는 부족하다.

아래는 **A: WITHOUT ROWID → B: 일반 rowid**, 단위 ms, 다섯 프로세스의 중앙값이다.

| 초기 요청 / 세션당 요청 | 최초 적재 + 최초 집계 | 신규 1건 추가 | 신규 100건 추가 |
| --- | --- | --- | --- |
| 280 / 10 | 27.883 → 27.426 (-1.6%) | 2.737 → 4.663 (+70.4%) | 10.248 → 9.441 (-7.9%) |
| 100,000 / 100 | 7,183.215 → 9,137.349 (+27.2%) | 3.597 → 3.752 (+4.3%) | 12.186 → 11.903 (-2.3%) |
| 100,000 / 10,000 | 6,329.733 → 6,329.850 (+0.002%) | 3.163 → 3.474 (+9.8%) | 9.648 → 10.119 (+4.9%) |

280건의 100건 추가는 중앙값끼리 비교하면 rowid가 7.9% 빠르지만 실제로 빠른 쌍은 **2/5**, 쌍별 증감률 중앙값은 **1.3% 증가**다. 10만 건/세션당 10,000건의 1건 추가는 **5쌍 모두 rowid가 느렸지만**, 중앙값 차이는 0.312 ms다. 비율과 절대 시간·쌍별 방향을 함께 봐야 한다.

최초 facts 저장은 양쪽에서 같은 구조·SQL을 사용하고 대상 일별 테이블에 아직 적재하지 않는다. 그런데 이 구간에도 10만 건에서 6.2~13.6%의 중앙값 차이가 관측됐다. 따라서 전체 최초 적재 시간 차이를 일별 테이블 저장 구조의 효과만으로 설명하지 않는다. 최초 집계 생성 자체는 세션당 100건에서 rowid가 23.4% 느렸고, 세션당 10,000건에서는 0.3% 빨랐다.

### 집계 저장 공간과 WAL

단위 KiB이며 A → B 순서다. 집계 점유는 두 일별 테이블·보조 인덱스 네 개·rowid 쪽 복합 키 UNIQUE 인덱스·집계 meta의 `dbstat` 페이지 합이다. 입력 후 VACUUM은 하지 않았다. 각 조건의 반복 표본에서 집계 점유는 동일했다.

| 초기 요청 / 세션당 요청 | 초기 집계 점유 | +101건 후 집계 점유 | 1건 추가 WAL | 100건 추가 WAL |
| --- | --- | --- | --- | --- |
| 280 / 10 | 68 → 68 | 68 → 68 | 32.22 → 32.22 | 132.80 → 128.78 |
| 100,000 / 100 | 2,356 → 2,256 | 2,356 → 2,260 | 44.29 → 44.29 | 185.11 → 197.18 |
| 100,000 / 10,000 | 184 → 188 | 184 → 188 | 40.27 → 40.27 | 128.78 → 128.78 |

rowid의 초기 집계 점유는 세션당 100건에서 **100 KiB 감소(-4.2%)**, 세션당 10,000건에서 **4 KiB 증가(+2.2%)**했다. 본체·UNIQUE 인덱스·보조 인덱스의 공간 구성이 바뀌므로 어느 쪽이 항상 작다고 볼 수 없다. 전체 DB 파일·free pages·객체별 페이지·프로세스 RSS는 JSON에 따로 있다.

WAL은 표본 중앙값이며 각 작업 직전 TRUNCATE checkpoint 뒤의 파일 길이다. JSON의 `walBytes` 값은 바이트다. 요약 통계가 공통 helper를 써 내부 키 이름이 `medianMs`여도 `walBytes` 아래의 단위는 바이트로 해석한다.

### 재개와 최종 대조

정식 결과는 **3조건 × 5쌍 × 2 = 30개 프로세스**다. 기본 워밍업 6개와 재개용 워밍업 2개를 제외했다. 중단으로 짝이 완성되지 않은 B 한 표본도 주 결과에서 제외하고 JSON의 `resume.excludedSamples`에 원시 기록을 보존했다. 재개 뒤 해당 BA 쌍을 연속으로 새로 측정했다. 정상 종료 기록은 이 제외 표본까지 39개이며, 중단돼 결과를 받지 못한 프로세스와 예비 smoke 8개는 정식 결과에 포함하지 않는다.

모든 주 표본의 최초·+1·+100 상태에서 독립 raw 집계 **900회**를 대조했고 전체 결과 해시가 일치했다. DDL·인덱스·PRAGMA·입력 바이트·facts/집계 해시·외래 키·integrity 검증이 통과했다. 실행기·공유 fixture·제품 소스/컴파일 결과의 SHA-256 15개도 최종 대조했다.

## 현재 제품과 실험 경로의 차이

별도 서브에이전트가 현재 코드를 읽고 다음 차이를 확인했다.

| 단계 | 현재 제품 | 이번 시제품 |
| --- | --- | --- |
| 최초 적재 | JSONL 청크를 TEMP에 적재하고 세션 연결 성분별로 반영 | 정규화된 JSONL의 요청을 준비한 INSERT로 한 트랜잭션에 적재 |
| 변경 없음 | manifest의 경로·크기·수정 시각·파서 버전 등을 확인하고 본문 읽기 생략 | 저장한 바이트 위치와 파일 크기가 같으면 본문 읽기 생략 |
| 기존 파일에 요청 추가 | 변경 파일을 처음부터 다시 읽고 영향 세션을 재구성 | 저장 위치 뒤에서 줄바꿈으로 끝난 새 요청 요약 레코드만 읽어 INSERT |
| 기존 요청 확인 | 자연키로 기존 요청을 SELECT하고 컬럼·모델·capability를 비교 | 기존 요청에 대한 애플리케이션 사전 SELECT 생략 |
| 일별 집계 | 실제 변경이 닿은 구간을 다시 집계 | 새 facts의 집계 상태를 기존 일별 상태에 병합 |

근거는 [scanner.ts](../../../src/summary/scanner.ts)의 `discoverSources`, `parseSource`, `expandAffectedSessions`, [sessions.ts](../../../src/summary/db/sessions.ts)의 `applySummaries`, [staging.ts](../../../src/summary/staging.ts)의 응답 중복 정리다. 현재 `readJsonl(file.path,file.size_bytes,...)` 호출은 이전 위치 다음부터 읽는 호출이 아니다.

여기서 **중복 검사 생략은 기존 facts에 대한 사전 SELECT를 하지 않는다는 뜻**이다. SQLite의 PRIMARY KEY·UNIQUE 검증은 양쪽에 유지한다. 이미 수집한 파일 구간은 읽지 않지만, 새 구간에 같은 요청 키가 다시 나오거나 기존 요청의 내용이 수정되는 일반 로그까지 처리한다는 뜻은 아니다. [SQLite 공식 설명](https://www.sqlite.org/rowidtable.html).

프로젝트·세션 이름은 새 입력에서 키별로 `INSERT OR IGNORE`하며, 일별 집계도 기존 키에 대한 UPSERT를 수행한다. 요청 facts의 사전 조회를 생략하더라도 이 제약 확인·충돌 처리는 남는다. 입력 생성은 측정 밖이고 입력 ID는 미리 정해진 증가 정수이므로 실제 로그의 요청 ID 생성·매핑 비용도 포함하지 않는다.

제품의 일별 집계는 첫 통계 조회 때 생성된다. 따라서 최초 facts 저장과 최초 집계 생성을 나눠야 한다. facts 저장 시간의 차이를 일별 테이블의 rowid 효과로 해석하지 않는다. [rollups.ts](../../../src/summary/db/rollups.ts)의 `read`·`rebuild`가 근거다.

## 동일하게 유지한 인덱스와 변경 대상

| 항목 | A: WITHOUT ROWID | B: 일반 rowid |
| --- | --- | --- |
| 대상 | `usage_request_daily`, `usage_model_daily` | 같은 두 테이블 |
| 컬럼과 제약 | 현재 제품의 컬럼·NOT NULL·복합 PRIMARY KEY | 동일 |
| 명시적 인덱스 | 각 테이블의 날짜·프로젝트 인덱스 두 개, 총 네 개 | 동일 |
| 물리 저장 키 | 복합 PRIMARY KEY | SQLite의 숨은 정수 rowid |
| 복합 키의 유일성 | 본체의 PRIMARY KEY | 별도 자동 UNIQUE 인덱스 |
| facts 저장 구조 | 현재 `turn_summary.id INTEGER PRIMARY KEY` | 동일 |

DDL에서 `WITHOUT ROWID` 유무만 달리한다. 같은 논리 인덱스를 유지해도 B에서 복합 PK의 자동 UNIQUE 인덱스가 별도로 생기는 물리 차이는 실험 변수에 포함된다. 이 차이는 [SQLite 공식 문서](https://www.sqlite.org/withoutrowid.html)에 설명되어 있다. 원본 요청 facts의 정수 ID를 추가·삭제하는 실험은 아니다.

## 측정 범위와 해석의 한계

실제 Codex 서브에이전트로 측정 담당과 독립 검토 담당을 나눴다. 측정 담당은 시제품 실행기를 구현하고 A/B를 실행하며, 검토 담당은 현재 수집 경로와 실험 설계를 읽기 전용으로 확인한다. 중단 후 재개에도 같은 역할의 서브에이전트를 새로 띄웠다. 성능을 재는 Node 프로세스는 순차 실행한다. AI 서브에이전트와 측정용 자식 프로세스는 별개다.

초기 적재는 준비한 INSERT를 반복 실행하는 단일 트랜잭션 배치다. 하나의 거대한 다중 VALUES SQL과는 구분한다. 초기 JSONL 생성·스키마 준비·정합성 검증은 측정에서 제외한다. 입력 읽기·JSON 파싱·적재·커밋 및 집계 유지 비용은 각 구간과 합계로 확인한다.

재시작은 이미 적재된 DB에 다시 연결하는 범위다. OS나 VS Code 전체 시작 시간은 포함하지 않는다. 반복 실행은 OS 파일 캐시 영향을 받으므로 cold I/O 측정으로 해석하지 않는다. WAL 파일 길이는 장치의 총 쓰기량이 아니며, 프로세스 RSS·heap·최고 RSS는 SQLite만의 메모리 사용량이 아니다.

구간별 수치는 다음 범위로 해석한다.

- `initialFacts`: JSONL의 읽기·파싱·준비한 INSERT·cursor 저장·커밋. 최초 일별 집계는 포함하지 않는다.
- `initialMaterialize`: 실제 `UsageRollupStore.read()`의 최초 집계 생성. 첫 공개 조회 API 전체 호출 시간은 아니다.
- `initialTotal`: 위 두 측정 구간의 합. 구간 사이 checkpoint와 관측 비용은 제외한다.
- `restartTotal`: 재연결과 변경 없음 확인의 합. 연결 뒤 INSERT statement 준비 시간은 제외한다.
- `readParseMs`: 청크 읽기·문자열 분리·`JSON.parse` 시간. `dbMs`는 트랜잭션 시간에서 이 값과 `rollupMs`를 뺀 잔여로, JS 반복·Set·검증·BEGIN/COMMIT도 포함한다.
- `monthRead`: 최초 적재 상태에서 준비된 월별 행 100개 조회와 COUNT를 직접 호출한 합. 준비·공개 API wrapper는 제외하고, 프로세스마다 준비 실행 3회 뒤 20회씩 7표본을 측정한다.

이 경로는 기존 요청 수정·삭제, 열린 요청의 후속 응답, 중복 응답, 포크·하위 에이전트의 기여분 재계산을 구현한 제품 대체안이 아니다. 이런 동작을 지원하려면 추가 무효화·복원 정책이 필요하므로 이번 속도를 현재 제품 전체에 그대로 적용하지 않는다.

최초 facts 저장과 최초 집계 생성은 별도 트랜잭션이며, 추가분의 facts·집계·바이트 위치는 하나의 트랜잭션이다. 최초 두 단계 사이 중단이나 실제 프로세스 강제 종료를 주입하는 복구 검증은 수행하지 않았다.

합성 데이터는 완료·진행 중·실패, 시각 미상, 모델 미상·누락·다중 모델, 알려진 0과 NULL 캐시 값을 포함한다. 각 레코드는 고정된 요청 snapshot이며 진행 중인 행도 이후 갱신하지 않는다. 입력은 ASCII이며 UTF-8 다중 바이트 경계·불완전 마지막 줄·파일 회전은 이번 입력 범위에 포함하지 않는다.

## 정합성 및 SQL 계획 확인

측정 프로세스 양쪽 모두 최초 적재·1건 추가·100건 추가 뒤 기본 필터의 제공자/모델 × 전체/일/월/프로젝트/세션, 총 10개 집계를 제품의 raw SQL과 대조한다. 평균의 허용 오차는 상대·절대 `1e-9`다. 빈 사용량 제외 옵션을 켰을 때의 별도 raw 대조는 이번 검증 범위에 포함하지 않는다.

별도로 facts·모델·프로젝트/세션 이름·정렬된 일별 상태 전체의 해시를 A/B와 반복 표본 사이에 비교한다. 해시의 비정수는 합산 순서 차이를 고려해 유효숫자 10자리로 정규화하지만 저장 값은 반올림하지 않는다. 이 전체 상태 비교는 양쪽에 공통으로 있을 수 있는 집계 오류를 독립적으로 검출한다는 뜻은 아니다. 각 상태의 외래 키 검사와 종료 시 `integrity_check`도 수행한다.

추가분 집계의 입력은 `id > 이전_ID AND id <= 새_ID`다. 실행 계획은 요청 facts의 `SEARCH ... USING INTEGER PRIMARY KEY`, 모델의 `PRIMARY KEY (turn_id=?)` 탐색, 신규 구간의 임시 GROUP BY를 보여 준다. 기존 일별 키와 충돌하면 새 상태를 SUM/MIN/MAX 규칙으로 병합하므로 집계의 키 탐색은 남는다. 애플리케이션의 기존 요청 사전 SELECT 생략과 SQLite 내부 탐색을 구분한다. 실행 계획은 실제 방문 행 수나 디스크 I/O 수치를 제공하지 않는다.

월별 전체 조회는 모든 해당 일별 상태를 합쳐야 한다. 행 100개 LIMIT가 집계 입력도 100개로 줄이는 것은 아니다. 필터 없는 전체 순회와 조건으로 좁힌 탐색을 시간과 함께 해석해야 한다.

이번 월별 SQL 계획의 `SCAN turn_summary`는 쿼리 안에서 `usage_request_daily AS turn_summary`로 붙인 **일별 테이블 별칭**이다. 원본 요청 facts를 전부 읽었다는 뜻이 아니다. 날짜 조건이 없는 전체 월별 집계는 양쪽 모두 해당 일별 상태를 순회하고 GROUP BY·ORDER BY에 임시 B-tree를 사용한다. 날짜·프로젝트 인덱스가 동일하게 존재해도 이 전체 조회에서 반드시 선택되는 것은 아니다.

이 A/B는 **양쪽 모두 추가분만 적재하는 조건에서 rowid의 차이**를 측정한다. 기존 제품의 파일 재파싱을 제거했을 때의 개선 폭은 별도의 직접 비교가 필요하며, 앞선 보고서의 저장 시간과 이번 JSONL 시제품 시간을 빼서 계산하지 않는다.

## 반복 방법과 재실행

각 조건에서 워밍업 한 쌍을 제외하고 A/B 순서를 AB·BA로 번갈아 다섯 쌍을 수집한다. 매 표본은 별도 Node 프로세스·새 DB·동일 JSONL 복사본에서 시작한다. 1건 추가 뒤에는 다시 100건을 추가하므로 최종 요청 수는 초기 수 + 101이다. 월별 조회는 추가 전 초기 상태에서 측정한다.

중앙값과 P10/P90는 다섯 프로세스 표본에서 계산한다. 월별 조회는 각 프로세스 내부 7표본의 중앙값을 다시 프로세스 사이에서 비교한다. P10/P90는 선형 보간한 관측 분포이며 신뢰구간은 아니다. 쌍별 개선 수는 같은 쌍의 B 시간이 A보다 짧은 횟수다. 중앙값끼리의 비율과 쌍별 비율 중앙값은 서로 다른 통계이므로 따로 표시한다.

```powershell
npm.cmd run benchmark:sql:rowid:append -- --samples=5 --warmup=1 --output=tests/results/benchmarks/sql-rowid-append-repeat.json
```

기존 output 파일은 덮어쓰지 않는다. 제품 스키마·소스는 유지하며 로컬 설치 DB·원본 대화·실제 quota 계정은 접근하지 않는다.

최종 `npm run check`의 타입 검사·린트·365개 테스트가 통과했다. 문서의 표 수치·로컬 링크·측정 소스 해시와 `git diff --check`도 확인했다.
