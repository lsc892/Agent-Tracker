## 비교한 구조와 표의 기준

| 항목 | A: 기존 WITHOUT ROWID | B: 일반 rowid |
| --- | --- | --- |
| 변경 대상 | 일별 요청·모델 집계 두 테이블 | 같은 두 테이블 |
| 본체 저장 키 | 세션 중심 복합 PK | SQLite가 생성하는 정수 rowid |
| 논리 키 | `(provider,session_id,project_key,local_day[,model_key])` | 같은 복합 PRIMARY KEY 제약을 별도 UNIQUE 인덱스로 유지 |
| 날짜/프로젝트 보조 인덱스 | 기존 네 개 유지 | 같은 네 개 유지 |
| 요청 facts·모델 facts | 현재 구조 유지 | 같은 구조 유지 |
| 증분 처리·배칭·조회 SQL | 현재 제품 구현 | 같은 구현 |

B에는 명시적인 ID 컬럼이나 추가 세션 인덱스를 만들지 않았다. 기존 DDL에서 `WITHOUT ROWID`만 제거했다. 복합 PK의 컬럼은 모두 NOT NULL이므로 유일성과 NULL 제약도 유지된다. 일반 rowid 테이블의 복합 PK는 별도 UNIQUE 인덱스로 구현된다. [SQLite 공식 설명](https://www.sqlite.org/withoutrowid.html).

- **집계 점유**는 일별 본체 두 개·날짜/프로젝트 인덱스·B의 UNIQUE 인덱스·집계 meta의 `dbstat` 물리 페이지 합이다. WAL·TEMP·빈 페이지·SQLite schema 페이지는 제외한다.
- **초기**는 양쪽 모두 같은 PK 순서로 복사하고 VACUUM·ANALYZE한 뒤다. **작업 후**는 일곱 저장 시나리오 종료 후이며 추가 VACUUM은 하지 않았다. 파일 전체 크기·빈 페이지는 JSON에 따로 있다.
- **시간**은 작을수록 빠르다. 저장은 프로세스 3쌍의 중앙값, 조회는 각 프로세스 내 반복 중앙값의 중앙값이다. 범위·P10/P90·개별 쌍은 JSON에 보존한다. 차이·증감률은 반올림 전 값으로 계산했다.
- **WAL**은 작업 직전 TRUNCATE checkpoint 후 작업 종료 시 파일 길이다. 장치의 총 쓰기량과는 다르다. 두 값이 0이면 변화 없음으로 표시한다.
- **조회**는 실제 `queryUsagePage()`의 100행+COUNT 전체 호출 시간이다. 별도로 측정한 준비된 행 조회·COUNT 시간과 두 실행 계획도 JSON에 있다.

## 실행 계획과 원인 고찰

### 보조 인덱스의 절약과 UNIQUE 인덱스의 추가가 상쇄됐다

10만 건/세션당 100건의 초기 상태에서 날짜/프로젝트 보조 인덱스는 0.820→0.445 MiB로 **0.375 MiB 줄었다**. 정수 rowid를 행 식별 정보로 사용하는 이점이 물리 점유에서 확인됐다. 하지만 별도 복합 UNIQUE 인덱스가 0.426 MiB 추가됐고 본체도 0.020 MiB 늘어, 집계 합계는 0.070 MiB 증가했다. 보조 인덱스의 행 식별 방식은 [SQLite 파일 형식](https://www.sqlite.org/fileformat2.html#representation_of_sql_indices)을 따른다.

작업 후에는 같은 조건의 집계 점유가 2.301→2.203 MiB로 역전됐다. 같은 논리 결과도 삽입·삭제에 따른 페이지 충전 상태가 다를 수 있다. 초기 상태는 VACUUM으로 맞췄고 작업 후에는 다시 압축하지 않았으므로, 이를 rowid의 고정적인 압축률이나 장기 운영 공간 절감률로 해석하지 않는다. 세션당 10,000건에서는 집계가 90행·360행뿐이라 몇 페이지의 차이도 비율로 크게 보인다.

### 세션·월 접근 경로는 양쪽에 모두 있었다

10만 건/세션당 100건의 모델 조회 계획을 비교했다. `turn_summary`는 이 SQL에서 일별 집계를 가리키는 별칭이다.

| 조회 | WITHOUT ROWID | rowid |
| --- | --- | --- |
| 특정 세션 | `SEARCH ... USING PRIMARY KEY (provider=? AND session_id=?)` | `SEARCH ... USING INDEX sqlite_autoindex_usage_model_daily_1 (provider=? AND session_id=?)` |
| 특정 한 달 | `SEARCH ... USING INDEX idx_usage_model_daily_day (local_day>? AND local_day<?)` | 같은 날짜 범위 인덱스 탐색 |
| 전체 기간 월별 GROUP BY | 집계 본체 `SCAN`, 임시 GROUP BY/ORDER BY | `idx_usage_model_daily_project_day` 전체 `SCAN`, 임시 GROUP BY/ORDER BY |

일반 rowid에서도 세션 복합 UNIQUE 인덱스가 범위를 좁혔다. 보조 인덱스를 통한 합계 조회는 그 인덱스와 본체를 함께 사용하며, WITHOUT ROWID의 본체 PK 접근과 경로가 다르다. 따라서 “한 번 더 찾아가니 반드시 느리다”거나 “정수 키이니 반드시 빠르다”고 일반화할 수 없다. 키 폭·페이지 수·캐시·조회 컬럼을 함께 봐야 한다. [SQLite의 두 저장 구조 설명](https://www.sqlite.org/withoutrowid.html).

특정 한 달 모델 조회는 10만 건/세션당 100건에서 9.817→7.637 ms, 10,000건에서 2.274→1.936 ms로 줄었고 각각 3쌍에서 빨랐다. 반면 280건에서는 1.606→1.853 ms로 세 쌍 모두 느렸다. **월 범위를 찾는 기능은 양쪽에 이미 있었고, 그 범위를 읽고 집계하는 비용에서 차이가 난 결과**다. 새 월 선두 PK나 월 컬럼을 사용한 실험은 아니다.

이번 특정 한 달은 일별 요청 집계 행이 가장 많은 달을 선택했다. 10만 건/세션당 100건은 34,159건, 10,000건은 37,287건의 원본 요청이 해당 기간에 속했다. 전체 기간 월별 조회와 이 한 달 범위 조회를 섞어 해석하지 않는다.

### 큰 전건 변경의 이득과 소수 변경의 불확실성을 구분한다

10만 건의 전건 제목 변경은 세션당 100건에서 20.869→18.220초, 10,000건에서 22.555→16.529초로 줄었다. 두 조건 모두 3쌍에서 rowid가 빨랐다는 관측은 후속 검토의 근거다. 설치 DB의 같은 작업은 0.6%, 280건은 9.6% 느려져 작은 규모까지 같은 방향은 아니었다.

집계 전체 재입력만 떼어 보면 10만 건/세션당 100건에서 58.535→48.902 ms, 10,000건에서 4.131→3.990 ms였다. 이는 집계 유지 비용의 차이를 보는 별도 측정이다. 실제 전건 저장은 요청·모델·임시 비교·집계 작업을 함께 하므로, 이 재입력 차이를 실제 저장 시간 차이의 원인이나 기여율로 그대로 환산할 수 없다.

특히 긴 세션은 한 건만 바뀌어도 입력 10,000건을 비교한다. 일별 본체를 변경하지 않은 동일 세션 재입력에서도 중앙값 차이가 났고, 한 건 추가도 세 쌍 중 두 쌍에서만 빨랐다. 실행 순서·캐시·GC·호스트 부하의 영향을 포함한 호출 시간이다. **“rowid로 바꿔서 인덱스 비용만큼 전체 시간이 줄었다”는 원인 확정은 이번 자료로 하지 않는다.**

독립 raw 검증은 각 데이터의 첫 A 프로세스에만 추가됐고 타이머 밖에서 수행했다. 다음 작업까지 남는 캐시·GC·열 상태의 영향을 완전히 제거한 설계는 아니다. 3쌍의 관측값과 범위를 함께 보며, 실제 부하에서의 전환 판단에는 검증을 별도 프로세스로 옮긴 추가 재현과 읽기/쓰기 호출 비율을 반영한 비교가 필요하다.

### 현재 적용 범위

원본 요청의 rowid, 집계의 WITHOUT ROWID, 기존 복합 인덱스·배칭·증분 처리라는 제품 구조는 유지했다. 이번에 추가한 것은 임시 사본의 스키마 변형과 재현 가능한 측정 도구·결과 문서다. 전체 변경이 많은 대량 작업에는 rowid의 이득이 관측됐지만, 실제 데이터의 소수 변경과 WAL까지 일괄 개선한 결과는 아니므로 제품에 자동 적용하지 않았다.

## 시간·공간 복잡도와 범위

일별 집계 행 수를 D, 선택한 집계 행 수를 K라 하면 B-tree에서 범위를 찾고 그 엔트리를 순회하는 단계는 대략 `O(log D + K)`다. WITHOUT ROWID의 본체 PK 범위 조회는 이 단계에서 지표도 읽을 수 있다. rowid의 세션 인덱스처럼 지표를 포함하지 않는 경로는 행별 본체 탐색이 추가돼 최악 `O(K log D)` 범주가 될 수 있다. WITHOUT ROWID도 비커버링 보조 인덱스를 선택하면 같은 종류의 본체 탐색이 붙는다. 실제 비용은 캐시·페이지 배치에 따라 달라진다. [SQLite Query Planning](https://www.sqlite.org/queryplanner.html).

GROUP BY·정렬과 합산 비용은 별도로 남으며 전체 범위 집계는 D에 비례하는 입력을 처리할 수 있다. rowid 여부로 이 작업이 상수 시간으로 바뀌지 않는다.

WITHOUT ROWID는 복합 PK로 집계 본체에 접근한다. 일반 rowid는 복합 UNIQUE 인덱스와 본체를 따로 유지하고, 보조 인덱스의 행 식별 정보는 정수 rowid를 쓴다. 두 방식의 차이는 키 폭·트리 개수·본문 접근·페이지 구성 등 상수 비용에 있다. 공간도 모두 `O(D)`이며 실제 차이는 위의 물리 점유로 판단한다.

요청 차이 비교와 영향 날짜/프로젝트 재집계 알고리즘은 양쪽이 같다. 변경 키 32개 초과 시 세션 집합 처리로 전환하는 조건도 같다. 입력 전체 비교 비용이 남으므로 요청 한 건만 바뀌었다고 전체 호출을 `O(1)` 또는 `O(변경 건수)`로 설명하지 않는다.

- 데이터 조건마다 새 프로세스로 3쌍을 순차 실행하고 A/B 순서를 교대했다. 합성 데이터는 기존 결정적 seed를 사용했다. 양쪽 모두 집계 본체를 같은 복합 PK 순서로 입력해 초기 상태를 맞췄다. 장기간 혼합 갱신에 따른 배치 변화는 따로 시험하지 않았다.
- 조회는 세 번 준비 실행 후 프로세스마다 5개 표본을 측정했다. 표본당 1~20회 호출로 약 5 ms를 목표로 묶었다. 준비된 행 조회·COUNT는 공개 API 호출과 별도로 측정하므로 세 수치를 합해 API 시간을 재구성하지 않는다. warm 결과이며 cold I/O가 아니다.
- 저장 시간은 실제 `replaceSessions()`의 BEGIN부터 COMMIT 반환까지다. 입력 준비·checkpoint·검증·해시·schema 변환은 제외한다. 전체 입력을 스트리밍으로 소비하는 시간은 포함한다. 소수 변경 직전 원래 세션을 한 번 복원한다. 전체 입력 재적용은 직전 삭제한 한 건을 복구하며 전체를 비교한다.
- 각 데이터의 첫 A 프로세스는 초기 상태와 일곱 저장 작업 후 전체·일·월·프로젝트·세션의 모든 결과를 제공자/모델 두 기준의 독립 raw SQL과 대조했다. 필터별 raw 대조는 초기 조회 단계에서 수행했다.
- 모든 프로세스는 facts·원본 요청 ID·자식 행·논리 이름/결제 정보 해시, 모든 집계 그룹과 정렬된 일별 상태 해시, 각 필터의 전체 조회 결과 해시가 기준과 일치했다. 평균·비용의 raw 대조 허용 오차는 상대/절대 `1e-9`, 집계 해시의 비정수는 누적 순서 차이를 위해 유효숫자 10자리로 정규화했다. 저장 값 자체는 반올림하지 않는다.
- 상태마다 FK 검사를 수행했고 각 프로세스 종료 시 `integrity_check=ok`를 확인했다. 저장 작업마다 BEGIN/COMMIT 각 1회도 확인했다.
- JSONL 탐색·파싱·quota·IPC·렌더링·UI 전체 멈춤은 측정하지 않았다. 실제 호출 비율을 적용한 읽기/쓰기 종합 부하와 장기 운영 결과도 아니다.
