# 승자 DTO greedy 최소화 A/B 테스트

가정: 사용자가 제안한 대로 파싱 중 같은 키의 승자 DTO만 보관하면 중복 DTO와 임시 테이블 적재·SQL winner 비용을 줄일 수 있다. 에이전트는 원본 서명 생성도 요청별 streaming digest로 바꾸어 전체 원본 DTO 보존을 없앴다.
개선 방향: A = 기존 SQL TEMP 적재 후 SQL winner 방식, B = 읽으면서 DTO winner 선택 + 필요한 서명·의존 근거만 유지하는 방식이다. **이번 결과는 staging·서명 경로 전체의 A/B이며, max-greedy 하나의 효과를 분리한 실험은 아니다.**

실제 Codex 1/100/1,000건 추가에서는 로컬 교체가 0회였고 A/B TEMP 적재 수도 각각 672/969/3,669행으로 같았다. 그래도 1건 추가의 파싱·staging은 97.62 → 63.43 ms였다. 코드상 차이는 A가 읽는 청크마다 DTO를 SQL에 적재하는 반면 B는 메모리에서 처리한 뒤 선택 행을 한 transaction으로 적재하고, 원본 의미 서명을 SQL payload 재조회 대신 streaming digest로 만든다는 점이다. **현재 개선을 중복 개수 감소만으로 설명할 수 없다.** 각 차이의 기여도를 격리한 ablation은 하지 않았다. 영구 저장 코드가 같은데도 저장 시간은 달랐으며, TEMP·캐시·실행 상태가 영향을 주었을 가능성은 추정이다.

JSON.parse 진단은 JSONL 파싱 외에 저장된 flags·cached prepared summary·의존 키 해석도 포함한다. 실제 초회 호출 수는 A 184,606회, B 193,312회로 B가 더 많았다. 행 콜백의 B 시간에는 청크 마지막 commitBatch에서 수행하는 digest/greedy 처리가 빠지므로 행 콜백 수치만으로 알고리즘 전체 비용을 비교하지 않는다. 위 파싱·staging 시간이 그 작업까지 포함한다.

실제 Codex 추가는 기존 34요청·9,914,184바이트 파일에 수행했다. 1건 추가 뒤 9,914,836바이트 전체를 다시 읽고 1,000건 추가 뒤에는 10,600,414바이트를 읽었다. 합성 10,000건은 100요청 파일, 합성 100건은 10요청 파일에 추가했다. 짧은 파일에서는 원래 파싱 비용이 작아 Map·서명·적재 준비 비용의 영향이 상대적으로 커진다. 1,000건 추가는 후처리가 지배적이어서 파싱 절감이 총 시간에 그대로 반영되지 않는다.

## 3. 메모리와 알고리즘

| 데이터 / 초회 | 반복 실행 프로세스 HWM RSS 중앙값 MiB A → B | 진단 배치 경계 heap 최대 MiB A → B | 진단 배치 경계 RSS 최대 MiB A → B |
| --- | ---: | ---: | ---: |
| 실제 | 189.97 → 282.12 | 36.94 → 119.84 | 221.60 → 345.27 |
| 10,000건 | 159.07 → 271.43 | 11.50 → 51.84 | 130.59 → 257.55 |
| 100건 | 118.36 → 120.69 | 7.82 → 8.80 | 113.69 → 114.96 |

실제 초회 HWM RSS는 약 **190.0 → 282.1 MiB**, 배치 경계 heap 표본은 **36.9 → 119.8 MiB**였다. 메모리는 증가했다. HWM은 모듈 로드도 포함하는 프로세스 최대치이고 배치 경계 표본은 순간 최대를 놓칠 수 있다. 강제 GC를 하지 않았으며 이후 추가 시나리오는 이전 시나리오의 할당·검증 영향을 받으므로 이 수치는 순수 DTO 할당량이 아니다. A/B 모두 SQLite temp_store=FILE, main/TEMP cache 각각 4,096 KiB, mmap=0이며 native 메모리·정렬 작업 공간과 TEMP 파일 저장도 별개로 필요하다.

구체적인 순서는 다음과 같다.

1. JSONL을 기존 reader로 읽고 기존 parser가 DTO를 만든다. 청크가 성공하면 DTO를 수용한다. 실패한 청크는 버린다.
2. 원본 DTO를 버리기 전에 root별 SHA-256 digest와 response/turn 의존 근거를 갱신한다. digest의 copy는 root 결과를 꺼낼 때만 사용하며 이벤트별 hash 복사·undo는 하지 않는다.
3. 로컬 Map 키는 [fileId, rootId, responseId, requestId, threadId, turnId, schema]이다. input+output이 큰 DTO 하나만 남기고 동점이면 나중 원본 ordinal의 DTO 전체를 택한다. 안전 정수 범위를 넘는 합은 BigInt로 비교한다. records와 usage Map은 같은 DTO 객체를 참조하며 DTO 사본 두 벌을 저장하지 않는다.
4. lifecycle/check/capability 등 집계에 필요한 제어 DTO는 유지한다. legacy는 원본 순서·복사 검증용 key/signature/위치만 남겨 current 혼합 제외와 부모의 동일 접두사 제외를 수행한다. 패자 전체 DTO나 후보 목록은 없다.
5. 최종 세션/계보와 Claude requestId가 확정되면 남아 있는 로컬 승자끼리 최종 키로 합친다. Claude 키는 [provider, sessionId, responseId, 정규화 requestId 또는 'no-req', '']이고 Codex 키는 [provider, sessionId, responseId, threadId, turnId]다. Claude의 requestId가 없는 응답은 같은 세션/response에 고유한 명시 requestId가 있으면 그 키로 합치고 명시 ID가 여러 개면 no-req로 유지한다. SQL과 같은 승자·동점 규칙을 적용하고 원본 root/최초 위치는 anchor로 보존한다.
6. 예외적으로 복사 제외가 로컬 최고 DTO를 제거했는데 뒤의 유효 이벤트가 남아 있으면 그 파일만 재읽어 빈 그룹을 복구한다. 파일 정체성과 원본 해시를 확인한다. 이때도 패자 DTO를 보관하지 않는다. 실제·합성 A/B에서는 A/B의 bodyBytes/행/서로 다른 파싱 파일 수가 같아 이 예외 재읽기는 발생하지 않았다. 비용은 이번 성능 표에서 **미측정**이며 기능 테스트에서 검증했다.
7. 선택된 DTO와 anchor만 한 transaction으로 TEMP에 적재한다. 기존 SQL 집계·영구 저장을 재사용하며 SQL ROW_NUMBER winner는 제거했다. dirty root 필터는 선택 TEMP 적재 뒤에 적용된다. 이름 metadata SQL 쓰기의 기존 청크 transaction은 유지한다.

영향받아 다시 읽는 바이트를 b, 그 DTO 수를 E, dirty 이벤트를 E_d, 파일을 F, 로컬 승자 그룹을 U, 제어 DTO를 C, legacy 근거를 L, 의존 항목을 D, root를 R, 품질 flag 항목을 P, 청크 버퍼를 Q라 하자. 키 길이를 유계로 보고 Map의 평균 O(1)을 가정한다. S=U+C+R는 선택 적재 행의 상한이다.

| 구간 | A SQL TEMP | B greedy DTO |
| --- | --- | --- |
| 파일/JSON 파싱 | O(b) | O(b); 예외 복구 파일의 바이트만 추가 |
| 읽는 중 적재·승자 | E행 indexed TEMP 적재의 일반적 상한 O(E log E) | 전체 E에 대한 streaming greedy·근거 수집 기대 O(E), 직렬화·해시 바이트 비용 포함 |
| 최종 winner | dirty E_d에 SQL partition 정렬, 일반적 O(E_d log E_d); 실행 계획·분포에 영향받음 | 로컬 승자만 최종 재그룹; 제어/anchor 포함 정렬 O(S log S), S행 indexed TEMP 적재 O(S log S) |
| 원본 서명 | SQL 원본 payload 순회·해시; root/의존 SQL 작업 별도 | root digest + 의존 근거; 전체 원본 DTO 재보존 없음 |
| 추가 JS 보유 공간 | 모든 이벤트 DTO를 쌓지 않는 청크 작업 공간 O(Q) 외 공통 메타데이터·결과 공간 | O(U+C+L+D+R+P+Q); 최종 Map/정렬 배열은 같은 DTO 참조이며 같은 차수 |
| SQLite/TEMP 저장 | 원본 E행과 인덱스·dirty 결과; O(E) 계열 저장 및 native 작업 공간 | 선택 S행과 인덱스·dirty 결과; O(S) 계열 저장 및 native 작업 공간 |

이 표는 winner/staging의 차이를 비교한다. 공유하는 lineage·metadata 의존 확장·집계·저장까지 전부 O(E)라고 주장하지 않는다. 부모 탐색 active.find의 최악 O(F²)와 접두사 비교는 기존 의미를 보존한 별도 작업이다. U가 E에 가깝고 L/P도 선형일 수 있어 B 전체 공간은 최악 O(E)이며 **승자 DTO만 남긴다고 전체 공간이 O(최종 요청 수)가 되지는 않는다.**

실제 사본은 Claude 20개·Codex 560개이며 압축 파일 459개, Codex 이름 index 43,616바이트·thread metadata 559개를 포함한다. 합성은 ordinal-v1 고정 생성, provider를 세션마다 교대하고 10개 프로젝트·14일로 분포시켰다. 10,000건은 100세션×100요청, 100건은 10세션×10요청이다. 추가 요청은 건당 130토큰이며 모든 trial에서 추가 전 상태를 복원했다.

각 상태에서 요청·모델·도구·비용·프로젝트·세션·진단의 정규화 SHA, 집계 SHA, 의존 SHA, 요청 수·토큰 총합, JS 독립 일/월/세션/프로젝트 합계와 완료 요청 평균을 대조했다. provider/model별 5그룹의 raw SQL과 rollup 전체 페이지 일치, FK/integrity, 입력 원상복구 해시도 확인했다. 합성 총량은 생성기로부터 직접 계산했고 실제 파싱 의미는 고정한 이전 SQL 전체 결과를 기준으로 비교했다. 별도로 seeded 원본/이전 SQL oracle 및 예외 재읽기 테스트를 포함한 npm run check **416/416 통과** 후 B를 동결했다.

반복 20 trial×6상태×3데이터, 별도 진단 2방식×6상태×3데이터, 마이그레이션 6상태×3데이터의 **기록된 414상태가 일치**했다. 준비 실행 108상태도 검사했고 성능 표본에서는 제외했다. 기존 SQL seed로 B를 실행한 M은 아래처럼 별도 1회 진단이며 반복 중앙값에 섞지 않았다.

B는 greedy-root-v1 계층형 digest 서명으로 바뀐다. A/B의 literal metadata SHA는 다르지만 facts·dependency SHA는 모두 일치했다. 변경 없는 SQL seed는 body 재파싱 없이 기존 서명을 유지하며 실제 재파싱된 성분부터 새 서명을 적용한다. 새 B 초회와 새 M 초회 서명의 결정성도 확인했다. 마이그레이션의 일시적 재계산 비용은 위 단일 표본 외 일반화하지 않는다.
