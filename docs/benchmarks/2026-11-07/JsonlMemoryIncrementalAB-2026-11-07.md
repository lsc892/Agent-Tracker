# Manifest·파일 DTO 재사용과 메모리 집계 A/B

가정: manifest로 변경 파일을 선별하고 승인된 파일 DTO를 재사용하며, 요청·모델·도구 집계까지 메모리에서 끝내면 이벤트 TEMP 적재와 SQL 중간 집계를 줄일 수 있다.
개선 방향: A = 기존 SQL TEMP·winner·집계 경로, B = 파일 DTO 캐시·JS 집계·직접 영속 저장 경로. 이번 결과는 전체 갱신 경로의 비교이며 winner Map 하나의 효과를 분리한 실험이 아니다.

## 4. 메모리와 알고리즘

| 데이터 / 초회 | HWM RSS 중앙값 MiB A → B | 진단 경계 heap 최대 MiB A → B | 진단 refresh 반환 직후 heap MiB A → B |

| 실제 1,473요청 | 188.27 → 235.44 | 37.80 → 93.82 | 9.49 → 55.35 |
| 합성 10,000요청 | 98.97 → 143.56 | 15.82 → 50.08 | 15.82 → 45.10 |
| 합성 100요청 | 57.40 → 54.18 | 8.30 → 9.32 | 8.30 → 9.32 |

HWM은 모듈 로드도 포함하는 프로세스 최고치이고 진단 경계 표본은 순간 최대를 놓칠 수 있다. 반환 직후 heap에는 승인 DTO 캐시 외에도 statement·집계 결과·아직 GC되지 않은 객체가 포함된다. 이후 시나리오의 HWM은 앞선 검증과 복원의 영향도 받는다. 순수 캐시 할당량이나 고정 메모리 상한으로 해석하지 않는다.

처리 구조는 다음과 같다.

1. manifest를 읽고 파일 크기·mtime·dev/inode·parser version·처리 상태로 변경 파일을 고른다.
2. 변경 파일은 기존 parser로 처음부터 읽어 정규화 DTO snapshot을 만든다. 관련된 변경 없는 파일은 같은 DB 연결의 승인 DTO를 재사용하고 캐시가 없으면 필요한 원본을 다시 읽는다.
3. 파일 DTO cache는 usage 패자를 포함한 정규화 원본 이벤트 배열을 유지한다. 전체 대화 본문·이미지 Base64를 보관하는 구조는 아니다. winner Map은 유효성 검증 후 최대 input+output과 나중 원본 순번의 DTO 하나를 선택하며 정상 DTO는 참조를 공유한다.
4. 읽힌 관련 파일과 부모 문맥에서 legacy/current·복사 접두사·계보·canonical request를 반영하고 요청·모델·도구·상태·시간·품질 결과를 JS에서 만든다. 관련 파일 집계는 새 Map으로 다시 수행하며 응답별 누계 Map을 갱신 사이에 증분 유지하지 않는다.
5. MemoryStore가 기존 최종 facts와 비교해 달라진 요청·모델·도구·비용을 직접 영속 저장한다. manifest·metadata도 같은 연결 성분 transaction에서 확정하고 성공 후 새 파일 DTO를 승인한다. 같은 facts는 ID·updated_at을 보존한다. 일별 rollup 갱신과 통계 조회 SQL은 기존 영속 경로를 유지한다.
6. 캐시는 DB 연결 수명에 한정된다. 파일 교체·잘림·승자 삭제·지연된 식별자는 파일 기여 교체로 반영하고 실패 시 기존 승인 snapshot을 유지한다. 연결 재시작·설정 변경·외부 DB 변경에서는 필요한 DTO를 다시 구성한다. 별도 영속 DTO 파일이나 byte offset cursor는 추가하지 않았다.

전체 파일 수 F, 이번 로드 파일 수 F_a, 현재 보유한 파일 DTO 수 E_cache, 이번 집계 입력 DTO 수 E_a, 세션 s의 요청 수 R_s·관련 파일 수 F_s·품질 근거 수 P_s라 두면, Map 키 길이가 유계일 때 winner 선택 순회는 기대 O(E_a)다. 전체 파이프라인을 O(E_a)나 O(추가 요청 수)로 보지는 않는다.

| 구간 | A SQL TEMP | B 파일 DTO·메모리 집계 |
| --- | --- | --- |
| 파일 검사·파싱 | O(F + B_affected) 계열 manifest 조사·영향 세션 원본 재파싱 | O(F) manifest·파일 검사, 변경/캐시 없는 필요한 파일의 전체 파싱·raw 파일 SHA; 압축 해제·JSONL 바이트 비용 별도 |
| winner·집계 | 원본 E행 indexed TEMP 적재의 일반적 O(E log E) 상한, dirty 이벤트 SQL partition 정렬의 O(E_d log E_d) 상한 및 집계 | winner 기대 O(E_a), 최종 요청 R개의 O(R log R) 정렬·모델·도구 정렬과 별도 root별 작업 포함 |
| root별 작업 | SQL 원본 서명·의존 확장·준비 쿼리 | 세션 파일·품질 키 정렬과 순회가 합계 O(Σ R_s(F_s log F_s + P_s log(P_s+1))), 부모 후보 탐색은 검증 1회당 최악 O(F_a²) |
| metadata·영속 저장 | 기존 TEMP 비교·확정 metadata·facts·rollup | source 상태 문자열을 root마다 직렬화해 O(Σ R_s F_s) 항과 그 문자열 바이트가 생김. 최종 root별 indexed SELECT 비교·변경 UPSERT 및 rollup 비용 별도 |
| JS 보유 공간 | 청크 작업 공간 외 metadata·결과 공간, SQLite native cache·TEMP 저장은 별도 | O(E_cache + E_a + F) 계열 DTO·참조·집계 상태에 최종 결과와 metadata 문자열 바이트가 더해짐 |
| SQLite 임시 저장 | 원본 E행과 인덱스 등 O(E) 계열 TEMP 파일 공간 | 이벤트·집계용 명시적 TEMP 표 없음. 최종 조회·rollup의 native cache·정렬 작업 공간은 별도 |

파일 확장 과정에서 검증·계보·후보 탐색을 I회 반복할 수 있으며 위 부모 후보 탐색은 한 번의 검증에 대한 경계다. 전체 확장에는 I에 따른 반복과 파일 목록 정렬·순회 비용이 추가되므로 전체 과정을 단순 O(F_a²)로 한정하지 않는다.

원본 캐시는 전체 가용 이력에 비례하며 eviction 상한은 추가하지 않았다. 변경 파일의 기존 snapshot과 새 후보가 transaction 전까지 함께 존재할 수 있다. SQLite page cache·native 작업 공간·Zstd decoder buffer는 위 JS cache 차수와 별개다.

### 4.1 요청 100,000건의 메모리 추가 측정 — 2026-11-08

## 5. 정합성·입력·재실행

A는 원래 SQL 소스/빌드를 tests/.cache/sql-before에 고정했고 B는 430개 테스트가 통과한 tests/.cache/memory-after-v4다. source/빌드 fingerprint를 실행 시작·종료에 확인했다. 제품 dev와 이전 실험은 유지했다.

요청별 facts·모델·도구·비용·진단·전체 합계·공개 집계·독립 JS 평균·raw/rollup 결과·FK/integrity와 원본 복원 해시를 비교했다. SQL seed 전환 M과 warm/cold 결과도 같은 최종 의미를 만족해야 통과한다. 예전 literal metadata/dependency SHA는 다른 구조이므로 기록만 하고 동일성 조건에서 제외했다. B는 SQL dirty 의존성 축소 대신 필요한 관련 DTO의 전체 메모리 집계 결과를 비교한다.
독립 JS 평균 검증은 저장된 요청 facts에서 그룹별 기대값을 다시 계산한다. 실제 입력의 파싱 자체에 대한 별도 독립 구현을 뜻하지 않는다. 메모리 집계의 winner·계보·상태 의미는 SQL oracle fixture와 생성 스트림 테스트로 별도 대조했다.
