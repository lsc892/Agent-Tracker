# 읽는 즉시 winner만 남기는 방식의 로컬 정합성 실험

2026-11-07, Asia/Seoul. 별도 `experiment/jsonl-online-greedy-check-2026-11-07` 워크트리에서 실행했다. 제품 소스·빌드·설치 DB와 원본 대화 로그는 변경하지 않았다.

가정: 현재 로컬 JSONL을 읽으면서 DTO를 생성하고, 당시 식별자로 같은 그룹의 winner 하나만 유지해도 기존 결과와 일치할 수 있다. 이 실험은 정합성만 비교하며 성능·메모리 절감률은 측정하지 않는다.

## 1. 결과

현재 로컬 로그를 새로 고정한 사본 580개, 392,592,768 byte를 사용했다. SQL 기준과 정상 DTO 경로는 1,473요청·2,169,957,606토큰으로 일치했다. 파싱 실패는 양쪽 모두 0개였다.

| 사용량 선택 방식 | 전체 토큰 | SQL 기준과 차이 |
| --- | ---: | ---: |
| 기존 SQL | 2,169,957,606 | 0 |
| 정상 DTO의 최종 그룹·필터 적용 | 2,169,957,606 | 0 |
| 도착 당시 식별자, 즉시 winner만 유지, 사후 그룹·유효성 보정 생략 | 2,424,608,772 | **+254,651,166 (+11.7353%)** |
| 위 greedy 선택을 그대로 두고 기존 유효성 제외·최종 귀속만 적용하는 통제 | 2,169,957,606 | **0** |

통제 실험에서는 패자를 복원하거나 winner를 다시 계산하지 않았다. 이미 선택된 greedy winner 중 기존 파이프라인이 무효로 제외하는 행을 제거하고 최종 세션으로 귀속했을 뿐이다. 이 로컬 사본에서는 그것만으로 요청별·모델별 사용량도 일치했다. 즉 **단일 순회 max 선택 자체는 성립하지만, 원본 형식·복사 이력의 제외 규칙까지 생략하면 결과가 달라진다.**

위 표는 기존 영속 통계와 비교하기 위해 양쪽에 동일한 aborted 요청 제외를 적용한 사용량 투영이다. 상태·완료 시각·도구를 모두 greedy로 집계한 완성된 제품 후보가 아니다. 후보의 winner 선택에는 사후 정보를 쓰지 않았으며 공통 aborted 제외는 선택 후 검증기가 집계 범위를 맞추는 데에만 사용했다. 상태 확정 자체를 없앴을 때의 정합성은 이번 실험 범위 밖이다.

## 2. 차이가 생긴 실제 원인

차이는 Codex에서 발생했다. Claude 사용량은 두 방식 모두 18,205,974토큰으로 일치했다.

| 제공자 | 기존 SQL | 즉시 winner만 유지 |
| --- | ---: | ---: |
| Claude | 18,205,974 | 18,205,974 |
| Codex | 2,151,751,632 | 2,406,402,798 |

기존 `excludeLegacy()`와 `excludePrefixes()`가 실제로 제거한 usage DTO ID를 관측해, 후보에 남은 행의 출처를 분류했다. 단순히 schema 문자열만 보고 원인을 추측한 값이 아니다.

| 생략한 제외 규칙 | 추가 집계 토큰 |
| --- | ---: |
| 같은 파일에 current 사용량이 있으면 legacy 사용량을 제외 | 169,950,210 |
| 부모·fork에 복사된 legacy 연속 접두사 제외 | 84,700,956 |
| **합계** | **254,651,166** |

current 응답과 legacy 누계에서 만든 응답 ID는 서로 다르다. 따라서 같은 `responseId`의 최댓값만 고르는 Map은 둘을 별도 그룹으로 남길 수 있다. 복사된 과거 사용량도 세션·thread 조건이 달라 별도 그룹에 남을 수 있다. 점수 비교를 잘못해서가 아니라 **비교해야 할 중복의 범위가 응답 ID만으로 표현되지 않는 경우**다.

공통 aborted 제외 전의 후보에서는 정상 경로가 제외한 mixed legacy 1,569개와 복사 접두사 806개가 남았다. 이 수는 위 영속 집계 범위의 행 수와 다르다. 토큰 차이 표는 공통 제외 후 범위로 계산했다. 이 사본에서는 Claude의 늦은 request ID 보정 사례가 관측되지 않았으므로, 그것을 실제 차이의 원인으로 설명하지 않는다.

## 3. 즉시 winner 후보의 정확한 정의

파서는 기존 제공자 adapter를 그대로 사용한다. 정규화된 usage DTO가 도착할 때 다음을 수행했다.

```text
key = [provider, 당시 sessionId, responseId, 세부 그룹]
세부 그룹 = Claude의 requestId / Codex의 [threadId, turnId]

기존 winner가 없으면 저장
input + output이 더 크면 교체
동점이면 이번 파싱 순번이 더 뒤인 DTO로 교체
패자는 보관하지 않음
```

점수 합이 안전한 정수 범위를 넘으면 기존과 같이 BigInt로 비교한다. 토큰 성분별 최댓값을 합성하지 않고 DTO 전체 하나를 선택한다. Claude는 이미 관측한 request ID가 유일할 때 **그 뒤에 도착하는** 누락 ID만 그 값으로 해석한다. 앞서 들어온 미상 그룹을 합치거나 되돌리는 보정은 하지 않는다.

일부 파서는 sink의 최종 identity를 파일 종료 때 알린다. 그 시점까지 session이 없다고 가정해 잘못된 NULL 키를 쓰지 않도록, DTO 도착 당시 parser 내부에 실제로 관측된 identity를 사용했다. Codex `getIdentity()`는 현재까지 명시 root가 없으면 standalone으로 해석할 수도 있어, 이 public 메서드의 당시 값을 사용하는 별도 민감도 후보도 실행했다.

| 도착 당시 identity 해석 | 후보 토큰 | 요청 사용량 키 차이 |
| --- | ---: | --- |
| 관측된 원본 metadata identity | 2,424,608,772 | 동일 키 값 변경 90, 기준에만 150, 후보에만 139 |
| 당시 `getIdentity()`의 standalone 해석 포함 | 2,424,608,772 | 동일 키 값 변경 75, 기준에만 0, 후보에만 50 |

여기서 요청 키는 `[provider, sessionId, rootId]`이며 사용량 이벤트가 있는 키를 비교한 것이다. 기준의 전체 영속 요청 1,473개와 후보 키 개수를 직접 비교해 요청 누락 수로 해석하면 안 된다. 기준의 사용량 키는 1,299개다. 세션 귀속 차이는 총합을 바꾸지 않아도 요청별 결과를 바꾼다.

후보 Map에는 winner 하나만 남기며, 별도로 실행되는 정상 파이프라인·감사용 observer가 원본 DTO와 최종 결과를 보관한다. 그 자료는 후보의 선택이나 패자 복구에 쓰지 않는다. 따라서 전체 실험 프로세스의 메모리를 winner-only 구현의 메모리로 주장하지 않는다.

## 4. 검증

- 고정 사본에서 기존 SQL 빌드와 정상 DTO 빌드를 각각 빈 DB로 실행했다. 두 경로의 요청별 facts, 모델·도구·비용·진단, 전체 집계 페이지 hash가 일치했다.
- 일·월·세션·프로젝트 평균은 정상화 요청을 직접 합산한 JS 기대값에 대조했다. 원본 SQL 조회와 rollup 전 페이지, FK/integrity도 확인했다.
- 정상 경로의 최종 유효 DTO와 확정 그룹에 독립 정렬 기반 max를 적용해 기존 winner ID·canonical request와 일치함을 확인했다.
- 선택 usage를 JS로 직접 요청별 합산해 SQL facts의 input/output/cache read/cache write/total과 대조했다. 공통 상태 제외 후 총합이 정확히 2,169,957,606이었다.
- 후보 선택 뒤 기존 유효성·최종 귀속만 적용한 통제는 두 identity 후보 모두 요청별 토큰·모델별 토큰까지 일치했다. 패자 복구와 winner 재선정은 수행하지 않았다.
- 입력 사본 전체 hash가 실행 전후 일치했다. 원본 파일은 읽기 전용으로 복사했으며 프롬프트·응답·경로·실제 식별자는 공개 결과에 넣지 않았다.
- `npm run check`의 타입 검사·린트·기존 398개 테스트가 통과했다. 실험 알고리즘의 별도 4개 테스트도 통과했다. 고정 그룹 100개 seed 실험, 큰 정수·동점, 뒤늦은 request ID, identity·legacy 생략 조건을 포함한다.

최종 선택 함수는 응답 그룹이 고정돼 있으면 후보 수에 비례하는 한 번의 max 순회로 충분하다. 이번 결과는 그 사실과 모순되지 않는다. 이번 로컬 정합성 실패는 그 앞뒤의 유효성 규칙과 귀속을 함께 생략한 후보에서 발생했다. 임의의 미래 입력·원본 수정·삭제까지 winner만으로 처리할 수 있다는 일반 보장은 아니다.

이번 사본에서 관측한 usage DTO는 23,875개이며 같은 키의 winner 교체는 267회였다. 같은 키의 새 후보가 기존 승자에게 패한 경우는 0회였다. 따라서 이 사본은 기존 승자가 수정·삭제돼 과거 패자를 복구해야 하는 경우까지 검증한 입력은 아니다. 서브에이전트의 읽기 전용 검토에서도 후보 선택의 최종 정보 누수와 통제의 winner 재선정이 없음을 확인했다.
