# 영속 turn metadata A/B 테스트 — 서명 비교 시제품

가정: 사용자는 대상 파일 전수검사를 유지하면서 반복 TEMP 집계·중복 제거·winner 계산을 줄이도록 지시했다. A는 미커밋 JSONL 최적화까지 포함한 기존 구현, B는 turn의 의미 서명과 확정 집계를 영속 저장하고 바뀐 turn 및 응답·누계 의존성만 재계산하는 구현이다. 원본 읽기·파싱, 기존 winner 규칙과 조회 SQL은 유지한다. **이 B는 반복 서명 비교 비용이 커 채택하지 않은 선행 시제품이다. 후속 최적화의 성능으로 해석하지 않는다.**

## 2. 측정 조건·정확성

측정: 2026-11-05 21:29:04–2026-11-05 21:45:17, Asia/Seoul. win32 / Node v24.19.0 / SQLite 3.53.3 / Intel(R) Core(TM) i5-8250U CPU @ 1.60GHz. main·TEMP cache 각 4 MiB, TEMP=FILE, mmap=0, WAL과 제품 optimize를 유지한다.

- A는 별도 워크트리에 미커밋 변경을 복사해 고정했다. B도 확정 빌드를 별도 실험 사본으로 복사했다. 소스·빌드·실행기·helper·입력 SHA-256은 [원시 JSON](MetadataAB-2026-11-05.json)에 기록한다. 사전 A 단독 측정은 [별도 JSON](MetadataBaseline-2026-11-05.json)이다.
- 두 소스의 제품 변경은 metadata·스키마·저장·scanner·staging으로 한정된다. `jsonl.ts`는 A/B에서 byte 단위로 동일하며 기존 사용자 최적화를 공통 기준으로 유지했다.
- 입력별 준비 3쌍 제외, AB/BA 순서 교대 10쌍이며 각 variant는 새 프로세스다. 각 시나리오는 해당 variant의 warm DB를 복원하고 같은 원본 사본을 사용한다. OS 캐시는 비우지 않았다. 입력 복사·DB 열기·변경·복원·정확성 검증·해시·IPC는 시간에서 제외한다. 집계 처리량 COUNT 계측은 refresh 시간에 포함한다.
- 전수 재파싱은 모든 원본 사본의 mtime만 변경하고 본문과 parser version은 유지한다. 양쪽 bodyBytes가 정확히 같은지 확인한다. 실제 내용 교체와 파서 버전 변경의 정확성은 제품 테스트로 별도 검증한다.
- 요청 추가는 제공자별 가장 긴 허용 세션의 파일에 같은 요청 1건(+130 tokens)을 추가하고 실제 refreshSummary의 파일 확인·전체 파싱·집계·COMMIT·정리까지 측정한다. 매 표본 후 원본 사본과 DB를 복원한다. 추가 시 원본 크기 이상을 읽었는지도 확인한다.
- 합성 seed는 ordinal-v1(난수 없음), 프로젝트 10개, 세션별 제공자 교대, 제공자별 모델 2개 교대, 모두 완료 상태다. 1만 건은 세션당100요청,100건은 세션당10요청이다. 기간은2026-07-01+sessionIndex%14일에100요청당 하루를 더한다.
- 조회는 준비된 일별 rollup·고정 기간·Asia/Seoul·제공자 기준 queryUsagePage를 1,000행씩 호출해 전체 결과와 COUNT를 반환한다. 조회별 준비3회 뒤 회차당3표본, A/B 각각30표본이다. 평균 분모는 완료 요청 중 사용량이 있거나 알려진 모델이 있는 요청이며 미완료·빈 요청도 총량에는 포함한다.
- 준비 실행 포함 312개 갱신 상태에서 요청 수·토큰·요청/모델/도구/비용/진단 의미해시와 그룹 결과를 A/B 비교했다. 제공자/모델×전체/프로젝트/세션/일/월 raw SQL과 공개 집계는 3120회 대조했다. 고정 기간의 일·월·세션·프로젝트 평균은 원본 요청을 독립 JS로 집계해 합계·표본 수·평균·결과 건수를 대조했다. 합성 최초 수집은 생성기의 기대 요청 수·토큰과도 일치한다. 원본 JSONL 파서의 독립 재구현 검증은 아니다. FK·integrity·종료 시 원본 SHA-256 복원을 통과했다. 본문·credential·실제 원본 경로·세션 ID는 보고서에 저장하지 않았다.

## 3. 해석·트레이드오프

전수 읽기·파싱 O(N bytes+R rows)는 그대로다. B는 정규화 이벤트의 서명을 다시 비교하는 비용을 추가하고, 변하지 않은 turn의 winner·모델·도구 집계와 DB snapshot 재쓰기를 건너뛴다. 변경 집합은 공유 응답과 누계 의존성을 따라 넓어지며 최악에는 영향 세션 전체가 된다. 작은 입력·최초 구축에서는 추가 서명·영속 쓰기 비용을 함께 감수한다. JS에는 현재 행·해시 상태만 유지하고 전체 세션 Map을 올리지 않으며, 영속 DB에는 turn별 집계·모델·도구·의존성 저장 공간이 추가된다. 원본 TEMP 이벤트 적재와 dirty 집계용 TEMP는 남아 있다.

- **판정: 현재 시제품의 전체 성능 가정은 기각.** 현재·1만 건의 전수 재파싱은 각각 14.5%·35.6% 느렸고 모두 0/10쌍에서 후보가 빨랐다. 100건의 0.2% 차이는 변동 범위이며 개선 근거로 보지 않는다. 요청 한 건 추가도 세 규모의 두 제공자에서 모두 느린 중앙값이었다.
- **관측 원인:** winner 집계 SQL은 현재 460.860→37.770ms, 1만 건 681.494→35.262ms로 줄었다. 대신 B의 metadata 서명 준비만 각각 2,382.491ms·5,684.292ms 걸렸다. 1만 건 저장 구간은 4,151.086→914.833ms로 줄었지만 서명 비용을 상쇄하지 못했다. 현재 Claude 추가는 문맥·진단 의존성으로 14개 turn 모두 dirty가 되어 집계 범위도 줄지 않았다.
- **공간:** checkpoint 후 DB가 현재 1.68→9.73MB, 1만 건 4.95→19.35MB, 100건 0.16→0.32MB로 증가했다. metadata와 의존성 보존 비용이며 본문 저장은 추가하지 않았다.
- **선택: 선행 시제품 보류.** 동일한 전수 파싱·의미 서명·dirty 의존성 알고리즘을 유지하면서 SQLite에서 필요한 의미 열을 직렬화하고 반복 키 조회·빈 변경 저장을 줄이는 후속 후보를 별도로 검증한다. 이 보고서의 원시 표본·소스·빌드 해시는 보존한다. 측정한 소스는 `npm run check`의 타입·린트·398개 테스트를 통과했다.

## 재실행

두 워크트리를 빌드한 뒤 새 출력 경로를 지정한다. --workspace를 생략하면 새 frozen snapshot을 만들며 현재 데이터 건수는 달라질 수 있다. --smoke는 합성100건1쌍만 실행한다.
