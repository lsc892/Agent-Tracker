# 영속 turn metadata A/B 테스트 — 전수 파싱 후 변경 turn만 재집계

가정: 사용자는 대상 파일 전수검사를 유지하면서 반복 TEMP 집계·중복 제거·winner 계산을 줄이도록 지시했다. A는 미커밋 JSONL 최적화까지 포함한 기존 구현, B는 turn의 의미 서명과 확정 집계를 영속 저장하고 바뀐 turn 및 응답·누계 의존성만 재계산하는 구현이다. B는 SQL `json_array`로 필요한 의미 열을 직렬화하고 반복 키 조회와 빈 변경 저장을 줄인 후속 후보다. 원본 읽기·파싱, 기존 winner 규칙과 조회 SQL은 유지한다.

## 2. 측정 조건·정확성

- A는 별도 워크트리에 미커밋 변경을 복사해 고정했다. B도 확정 빌드를 별도 실험 사본으로 복사했다. 소스·빌드·실행기·helper·입력 SHA-256은 [원시 JSON](MetadataKeyedAB-2026-11-05.json)에 기록한다. 사전 A 단독 측정은 [별도 JSON](MetadataBaseline-2026-11-05.json)이다.
- A/B 소스 SHA-256에서 `src/summary/jsonl.ts`가 동일하다. 제품 코드 변경은 metadata·스키마·저장·scanner·staging으로 한정되며, 기준의 미커밋 JSONL 변경을 공통으로 포함한다. 측정 소스는 `npm run check`의 타입·린트·398개 테스트를 통과했고, 동결 후 제품 소스가 바뀌지 않았음을 다시 확인했다.
- 입력별 준비 3쌍 제외, AB/BA 순서 교대 10쌍이며 각 variant는 새 프로세스다. 각 시나리오는 해당 variant의 warm DB를 복원하고 같은 원본 사본을 사용한다. OS 캐시는 비우지 않았다. 입력 복사·DB 열기·변경·복원·정확성 검증·해시·IPC는 시간에서 제외한다. 집계 처리량 COUNT 계측은 refresh 시간에 포함한다.
- 전수 재파싱은 모든 원본 사본의 mtime만 변경하고 본문과 parser version은 유지한다. 양쪽 bodyBytes가 정확히 같은지 확인한다. 실제 내용 교체와 파서 버전 변경의 정확성은 제품 테스트로 별도 검증한다.
- 요청 추가는 제공자별 가장 긴 허용 세션의 파일에 같은 요청 1건(+130 tokens)을 추가하고 실제 refreshSummary의 파일 확인·전체 파싱·집계·COMMIT·정리까지 측정한다. 매 표본 후 원본 사본과 DB를 복원한다. 추가 시 원본 크기 이상을 읽었는지도 확인한다.
- 현재 snapshot은 Claude 30·Codex 346개 일반 JSONL이며 압축 원본은 0개다. 압축 로그의 실제 성능은 이번 입력에서 미측정이며 해당 기능은 회귀 테스트로 확인했다.
- 합성 seed는 ordinal-v1(난수 없음), 프로젝트 10개, 세션별 제공자 교대, 제공자별 모델 2개 교대, 모두 완료 상태다. 1만 건은 세션당 100요청, 100건은 세션당 10요청이다. 기간은 2026-07-01 + sessionIndex%14일에 100요청당 하루를 더한다.
- 조회는 준비된 일별 rollup·고정 기간·Asia/Seoul·제공자 기준 queryUsagePage를 1,000행씩 호출해 전체 결과와 COUNT를 반환한다. 조회별 준비 3회 뒤 회차당 3표본, A/B 각각 30표본이다. 평균 분모는 완료 요청 중 사용량이 있거나 알려진 모델이 있는 요청이며 미완료·빈 요청도 총량에는 포함한다.
- 준비 실행 포함 312개 갱신 상태에서 요청 수·토큰·요청/모델/도구/비용/진단 의미해시와 그룹 결과를 A/B 비교했다. 제공자/모델×전체/프로젝트/세션/일/월 raw SQL과 공개 집계는 3120회 대조했다. 고정 기간의 일·월·세션·프로젝트 평균은 원본 요청을 독립 JS로 집계해 합계·표본 수·평균·결과 건수를 대조했다. 합성 최초 수집은 생성기의 기대 요청 수·토큰과도 일치한다. 원본 JSONL 파서의 독립 재구현 검증은 아니다. FK·integrity·종료 시 원본 SHA-256 복원을 통과했다. 본문·credential·실제 원본 경로·세션 ID는 보고서에 저장하지 않았다.

## 3. 해석·트레이드오프

- **판정: 일부 성립.** 동일 내용의 전수 재파싱 중앙값은 현재 7.8%, 1만 건 15.1%, 100건 35.5% 줄었다. 합성 두 규모에서는 B가 10/10쌍 모두 빨랐고 시간 범위도 겹치지 않았다. 현재는 6/10쌍이며 A 14,580–19,030ms / B 14,550–19,171ms로 범위가 크게 겹치므로 실제 로그의 개선 폭이 안정적이라고 단정하지 않는다. 이는 본문 검사를 생략한 효과가 아니다. 재파싱 bodyBytes는 양쪽 모두 현재 542,640,741 / 1만 5,637,210 / 100건 55,700으로 같았다.
- **핵심 원인:** 집계 대상 이벤트를 현재 28,674→137개, 합성 1만·100건은 30,000→0개·300→0개로 줄였다. 현재·1만·100건의 저장 구간은 각각 1,331.309→739.024ms, 3,365.008→276.948ms, 76.906→14.488ms였다. 대신 B의 metadata 서명 구간 917.824 / 2,512.640 / 14.711ms가 추가된다. 현재의 137개는 확정 요청으로 저장되지 않는 root 등 남은 dirty 범위다. TEMP 생성 자체를 모두 없앤 구현은 아니며, 원본 이벤트 TEMP와 변경 turn용 TEMP는 유지한다.
- **한 건 추가는 회귀:** 현재 Codex·Claude는 중앙값 2.9%·3.2% 느렸고, 1만 건은 50.3%·44.6%, 100건은 10.2%·17.8% 느렸다. 합성 1만 건의 집계 대상이 101→1turn이어도 서명 비교 32.618 / 32.925ms와 저장 구간 50.720 / 47.040ms가 남았다. 일별 rollup은 실제 변경 시 세션 전체 재집계가 유지된다. 현재 Claude는 14turn 모두 dirty로 판정되어 집계 범위가 줄지 않았다. 이 결과를 일반적인 갱신 가속으로 표현하지 않는다.
- **조회:** 조회 SQL·인덱스는 변경하지 않았다. 표의 수 ms 차이만으로 읽기 가속·회귀를 해당 알고리즘 효과라고 단정하지 않는다. 실제 화면 렌더링·IPC·quota는 측정하지 않았다.
- **공간 비용:** DB는 현재 1.68→9.73MB, 1만 건 4.95→19.35MB, 100건 0.16→0.32MB로 증가했다. 저장한 metadata와 모델·도구·의존 키의 비용이며 전체 본문을 저장하지 않는다. 전수 재파싱 종료 시 WAL 파일 길이는 현재 4.30→4.14MB, 1만 건 4.34→2.63MB, 100건 1.10→0.26MB였고 총 쓰기량을 뜻하지 않는다. 같은 구간의 프로세스 누적 최대 RSS 중앙값은 현재 191.39→161.52MB, 1만 건 167.02→144.63MB, 100건 61.74→59.41MB였다. 검증·런타임·이전 시나리오를 포함한 관측값으로 보조 공간의 고정 상한이나 할당량 감소를 증명하지 않는다.
- **복잡도:** N은 검사한 원본 bytes, E는 정규화 이벤트 수, T는 요청 수다. A/B 모두 전체 읽기·파싱 O(N+E)가 남는다. A는 영향 세션 전체 E의 중복·상태 집계와 T개 snapshot을 매번 구성한다. B도 E를 읽어 서명을 만들고 키를 조회하지만, winner·turn 집계의 정렬·병합은 dirty 이벤트 집합에 한정한다. 인덱스 조회·정렬·의존성 확장·변경 세션 rollup의 비용은 별도이며 전체가 O(변경 수)로 바뀐 것은 아니다. 최악에는 모든 turn이 dirty가 되어 기존 전체 계산에 서명 비용이 더해진다. JS의 현재 행·해시 상태 및 DB cache 경계는 유지하고, 영속 보조 공간은 turn·모델·도구·의존 키 수와 키 문자열 bytes에 비례해 증가한다.
- **선택:** 사용자가 요청한 전수검사와 영속 turn metadata의 핵심 경로를 반영하되, 반복 재파싱의 집계·저장 감소와 단일 추가 지연·DB 공간 증가를 함께 수용한다. append 성능 개선이나 영속 응답 후보 전체 저장·byte checkpoint·원본 읽기 생략은 이번 반영 범위에 포함하지 않는다.

선행 [B1 시제품 10쌍](MetadataAB-2026-11-05.md)은 JS 행 객체 복제·직렬화와 반복 조회 때문에 현재·1만 재파싱이 14.5%·35.6% 느려 보류했다. B2는 필요한 열의 SQL 직렬화, 반복 조회 축소, 준비된 root 인덱스, 빈 변경 저장 생략으로 이 비용을 줄였다. [B2 1쌍 사전 관측](MetadataKeyedPilot-2026-11-05.md) 후 본 보고서를 실행했다. 같은 frozen 입력·A 코드라도 실행 시점과 표본이 다른 두 보고서의 A/B 시간을 서로 교차해 개선율을 만들지 않는다.

## 재실행

두 워크트리를 빌드한 뒤 새 출력 경로를 지정한다. --workspace를 생략하면 새 frozen snapshot을 만들며 현재 데이터 건수는 달라질 수 있다. --smoke는 새 workspace에서 합성 100건 1쌍만 실행하며, 보존된 workspace를 지정하면 그 안의 입력을 각각 1쌍 측정한다.

`node tests/benchmarks/metadata-ab.cjs --before=<기준 워크트리> --after=<후보 워크트리> --output=<새 JSON 경로>`
