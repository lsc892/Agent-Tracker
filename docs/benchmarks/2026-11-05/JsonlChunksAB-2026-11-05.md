# JSONL 청크 분할 A/B 테스트

가정: 사용자는 파일 전체 대신 청크를 나눠 줄별로 파싱하고 개선 정도를 검증하도록 지시했다. 기존 A도 64 KiB 스트리밍 리더다. Codex의 가정은 청크 안의 완성된 줄을 한 번에 디코딩·분할하면 줄마다 UTF-8 문자열로 변환하는 비용을 줄일 수 있다는 것이다.

개선 방향: A = 변경 직전 작업 트리의 줄별 디코딩. B = 같은 청크 안의 완성된 줄 구간만 한 번 디코딩하고 `split('\n')`한다. 경계 줄은 기존 byte buffer로 이어 붙이고 LF가 없는 청크는 분할하지 않는다. 이미지 제거·줄 예산·offset·취소·미완성 마지막 줄 규칙을 유지한다. 제품 소스 차이는 [jsonl.ts](../../../src/summary/jsonl/index.ts) 한 파일이며 SQLite·집계 SQL·청크 크기는 같다.

- **현재 데이터:** Claude 30파일·Codex 342파일의 변경하지 않는 사본이다. 수집 실패 0건이며 이번 사본에는 Zstd 파일이 없다. 이름 metadata도 사본으로 고정했다. 원본 로그는 수정하지 않았다.
- **합성 데이터:** 기존 생성기 ordinal-v1을 재사용하며 난수는 없다. Claude·Codex 요청을 절반씩, 프로젝트 10개, 제공자별 모델 2개, 모든 요청을 완료 상태로 만든다. 1만 건은 100세션×100요청, 100건은 10세션×10요청이다. 시각은 2026-07-01 + sessionIndex%14일, 100요청마다 하루 추가로 고정한다. 입력·토큰 합계·SHA-256은 JSON에 기록했다.
- **반복·캐시:** 제품은 규모마다 준비 3쌍 뒤 AB/BA 순서를 교대해 각 10회 측정했다. 각 실행은 새 프로세스이며 시나리오마다 같은 checkpoint DB를 복원한다. OS 캐시를 비우지 않았고 백그라운드 부하는 고정하지 않았다. 원본 복사·입력 변경과 복원·DB 열기·정확성 대조·IPC는 제품 시간에서 제외했다.
- **추가·재파싱:** 제공자별 가장 긴 허용 세션 사본에 같은 요청 1건(+130 tokens)을 추가하고 실제 `refreshSummary`의 파일 확인·세션 재파싱·집계 갱신·COMMIT·정리를 측정했다. 매 표본 후 사전 상태로 복원했다. 재파싱은 사본 DB의 manifest.parser_version만 무효화한다. 최초 빈 DB 수집의 A/B는 **미측정**이며 initialRefreshMsAUnpaired는 A의 준비용 값이다. 스키마·parser version 변경이나 마이그레이션은 없다.
- **조회·평균:** 준비된 rollup에서 실제 `queryUsagePage`를 1,000행씩 호출해 전체 결과와 COUNT를 반환할 때까지 측정한다. 고정 기간·Asia/Seoul·제공자 기준이며 조회마다 준비 3회 후 회차당 1표본, 각 10표본이다. 평균 분모는 토큰이 있거나 모델이 알려진 완료 요청이며 미완료·빈 요청도 전체 건수·합계에는 남는다. 시간 미상은 별도 그룹으로 포함한다.
- **리더 단독:** 결정적으로 생성한 CRLF·UTF-8 행을 고정 파일로 읽었다. 각 새 프로세스에서 준비 3회 후 1회 측정하며 AB/BA 10쌍이다. 시간은 파일 열기·읽기·JSON 파싱·건수/토큰 확인·닫기를 포함한다. 해시·GC·메모리 샘플·IPC·입력 준비는 시간에서 제외한다. 메모리는 GC 후 별도 읽기의 배치 종료 시점에 표본을 잡았다. 표의 최대 RSS는 모듈 로딩·준비·검증을 포함한 OS 프로세스 high-water다. 배치 내부 순간 할당량과 실제 제품의 peak RSS는 **미측정**이다.

정확성: 준비 실행을 포함해 A/B의 요청 수·토큰 합계·전체 facts/집계 해시·그룹별 평균·결과 건수가 일치했다. 각 상태에서 제공자/모델 × 전체/프로젝트/세션/일/월의 raw SQL과 공개 rollup 결과를 대조했다. 정규화된 원본 요청 `turn_summary`를 별도 JS로 합산해 일·월·세션·프로젝트 평균의 분모·합계와 비교했고, 합성 요청 수·토큰 합계는 생성기의 기대값으로도 확인했다. 리더는 생성한 원본 행의 기대값·이미지 제거 결과·원본 byte offset을 스트리밍 해시로 대조했다. 실제 제공자 파서 자체를 독립 재구현한 검증은 아니다. FK·integrity·사본 복원 SHA-256 검사를 통과했다. 원시 결과: [제품 JSON](JsonlChunksProductAB-2026-11-05.json), [리더 JSON](JsonlChunksReaderAB-2026-11-05.json).

## 2. 분석

- **판정: 일부 성립.** 짧은 줄이 많은 리더 단독 입력의 디코딩 비용은 줄었다. 실제 전체 갱신의 변화는 현재 +0.25%, 1만 건 −0.38%, 100건 +0.81%이며 B가 빠른 쌍은 각각 3/10·5/10·5/10이다. 전체 갱신 가속을 확인한 결과로 해석하지 않는다.
- **핵심 원인:** 변경은 UTF-8 변환을 줄별 호출에서 청크의 완성 구간당 한 번으로 줄인다. 읽는 byte·파일 수·JSON.parse 횟수와 SQLite 저장/집계는 같다. 긴 줄·이미지의 경계 처리도 같은 경로다. 실제 갱신에는 이 밖의 비용이 남아 리더의 차이가 전체 시간에 그대로 반영되지 않는다. 원인별 CPU 비용은 별도로 분해하지 않았다. 조회 SQL은 같으므로 조회 시간 차이를 이 변경의 조회 개선으로 판정하지 않는다.
- **시간·공간:** A/B 모두 원본 byte N에 시간 O(N), 청크 C와 보관 줄 한도 K에 reader 보조 공간 O(C + min(L,K))다. B는 청크 안의 디코딩 문자열·줄 배열에 O(C) 임시 공간을 사용한다. 파일 전체 문자열·줄 배열은 만들지 않으며 파싱 결과 객체·제공자 파서·DB 메모리는 별도다. 기존 A도 청크 방식이므로 이 변경의 메모리 복잡도 개선은 없다.
- **선택:** 사용자가 요청한 청크 안의 분할을 제품에 반영했다. 짧은 줄의 리더 성능에 한정한 이득이며 전체 갱신·일반적인 요청 추가의 성능 향상은 보장하지 않는다. 현재 로그 Claude 추가의 8.1% 증가와 임시 줄 배열의 공간 비용을 함께 기록한다. 경계 줄을 별도 원본 조각으로 지연 처리한 [선행 후보](JsonlChunksBufferedPilot-2026-11-05.json)는 시간 이득이 확인되지 않아 채택하지 않았다.

검증: `npm run check`의 타입 검사·린트·**384개 테스트**를 통과했다. 새 테스트는 UTF-8이 청크 사이에서 잘리는 긴 줄·CRLF·미완성 마지막 줄, 이미지 앞의 긴 일반 구간과 줄 예산/잘못된 escape, UTF-8 치환 후 원본 byte offset을 확인한다. 압축 JSONL의 경계·예산·오류·취소는 기존 단위 테스트를 통과했다. 실제 압축 corpus 성능과 VS Code 화면·설치는 이번 비교 범위에 포함하지 않았다.

## 재실행

두 소스를 각각 컴파일한 폴더를 A/B 경로로 지정한다. A는 변경 직전 작업 트리의 src/dist 고정 사본이며 Git HEAD는 `02bcffc9b0ad1723347ce9b68e26af48c21b43bf`다. 원시 제품 JSON에는 전체 src·dist와 실행기·도우미·package-lock의 SHA-256을, 리더 JSON에는 리더 src/dist·실행기·입력 SHA-256을 기록했다. 아래 출력 경로는 새 파일이어야 한다. 미래 실행의 현재 데이터는 당시 사본이므로 원본 내용이 같다고 가정하지 않는다.

node tests/benchmarks/jsonl-chunks-ab.cjs --before=C:/bench/A --after=C:/bench/B --output=tests/results/benchmarks/jsonl-reader-new.json
node tests/benchmarks/temp-batch-ab.cjs --before=C:/bench/A --after=C:/bench/B --hypothesis=Decode-and-split-complete-lines-once-per-64KiB-chunk --output=tests/results/benchmarks/jsonl-product-new.json
