# 관계 역인덱스·작업 큐의 극단 기간 조건 A/B

2026-11-09 17:29:02–17:34:52, Asia/Seoul. [원시 JSON](ScanQueueRawRangeAB-2026-11-09.json)을 변경 없이 보존한 보조 실험이다. 운영 기본 경로의 최종 결과는 [본 보고서](ScanQueueAB-2026-11-09.md)를 따른다.

같은 고정 A/B 빌드·현재 1,308요청/642파일·합성 10,000요청/100파일을 준비3쌍·AB/BA10쌍 비교했다. 정확성·원본 읽기 순서·추가 +1요청/+130토큰·독립 JS 평균·FK/integrity 검사는 모두 통과했다.

## 실제 실행 조건의 정정

실행 당시 filter는 fromMs=-8,640,000,000,000,000, toMs=8,640,000,000,000,000, unknownTime=include, excludeEmptyUsage=true였다. 제품의 calendar 범위 지원 밖이므로 네 평균 조회는 raw SQL 경로였다. 초기 빈 DB 일별 조회 역시 rollup 후보가 없어 usage_rollup_meta를 만들지 않았다. 따라서 최초 refresh는 rollup 비활성이고, 최초 검증에서 helpers.verify가 날짜 경계 없는 조회를 호출한 뒤에 rollup이 활성화되어 추가 refresh에는 rollup 유지 비용이 포함됐다.

원시 JSON의 timing 조건에서 초기 호출을 'empty rollup activation'이라고 적은 것은 의도와 달랐다. 새 별도 DB에서 metadata 행수를 확인한 결과 초기0 → 극단 기간 조회후0 → 날짜 경계 없는 일별 조회후1이었다. reader.ts는 buildRollupUsageQueries가 후보를 만들지 못하면 UsageRollupStore.read에 진입하기 전에 raw로 반환한다. 이 측정 조건 때문에 최초 저장·평균 조회 시간을 이전 ScanStages 또는 본 보고서의 기본 rollup 경로와 직접 비교하면 안 된다.

## 보존한 전체 시간

단위는 A → B 중앙값 ms이다. 각 값은 같은 조건의 A/B 비교이며 운영 기본 조건의 대표값으로 사용하지 않는다.

| 항목 | 현재 1,308요청 | 합성 10,000요청 |
| --- | ---: | ---: |
| 최초 수집 | 7807.627 → 7635.811 | 775.448 → 642.899 |
| 1건 추가 | 564.344 → 554.598 | 21.983 → 21.819 |
| 무변경 | 99.934 → 102.254 | 15.403 → 15.521 |

원시 표본과 실행 당시 runner SHA-256은 JSON에 유지한다. 후속 실행기는 날짜 경계 없는 전체 범위를 기본으로 사용하고, --raw-range로 이 조건을 선택할 수 있다. 원본 입력과 A/B 제품 소스·빌드는 두 측정에서 동일하다. 별도 [구조 진단 JSON](ScanQueueStructure-2026-11-09.json)도 이 극단 기간 조건에서 1쌍을 실행한 것이며, 큐·검색 카운터만 참고하고 그 시간은 본 중앙값에 섞지 않는다.
