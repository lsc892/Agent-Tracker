# 관계 역인덱스·작업 큐 A/B 테스트

2026-11-09 17:38:35–2026-11-09 17:43:47, Asia/Seoul.

가정: 사용자는 관계 ID별 파일 집합과 중복 제거 작업 큐를 적용하고 watcher는 보류하도록 지시했다. 에이전트의 가정은 관련 확장의 전체 목록 반복 검색·정렬과 성분별 전체 filter를 줄이면 관계 처리와 최초 저장 조율 비용이 감소하지만, 관련 원본 재읽기를 유지하므로 append 전체 개선은 제한될 수 있다는 것이다.

### 1.1 이론적으로 줄인 시간복잡도

**관련 파일의 반복 전체 검색·정렬 항은 `O(R·F log F)`에서 색인 구성·우선순위 큐의 `O(F + Q log F)`로 바뀌었다. 성분별 멤버 검색도 `O(C·(F+T+H))`의 반복 전체 filter에서 한 번의 색인 구성과 해당 성분 멤버 조회로 바뀌었다.** [수집기](../../../src/summary/scanner/index.ts)와 [큐·멤버 색인](../../../src/summary/scanner/worklist.ts)의 코드 구조로 분석한 식이며, 전체 갱신의 최악 시간복잡도가 모두 이 식으로 바뀐다는 뜻은 아니다.

기호는 `F`=manifest와 관측 목록의 전체 파일 수, `V`=탐색한 디렉터리 항목 수, `K`=이번에 읽기를 시도하는 파일 수, `R`=관련 확장 반복 수, `Q`=두 큐의 실제 삽입·제거 대상 수, `C`=저장할 연결 성분 수, `T`=최종 summary 수, `H`=orphan 수다. `n_i`는 성분 i에서 모으는 파일·summary·orphan 수의 합이고, `U`는 경로 fallback을 수행하는 서로 다른 미해결 참조 수, `q_j`는 원본 j와 source identity가 같은 후보 수다. Map·Set은 평균 상수 시간 조회, 경로·식별자 비교 길이는 고정한 모델을 사용한다.

| 변경한 구간 | 기존 A의 비용 모델 | 적용 B의 비용 모델 | 줄어든 이유·남은 조건 |
| --- | --- | --- | --- |
| 관련 확장의 전체 목록 재순회·pending 정렬 | `O(R·F log F)` 상한 | 색인 구성과 큐 처리 `O(F + Q log F)` | 관련 후보만 최소 힙으로 처리한다. 미해결 경로 검색·계보 재계산은 이 행에서 제외한다. |
| 성분 확정 후 파일·summary·orphan 검색 | `O(C·(F+T+H))` | `O(F+T+H + Σ n_i log n_i)` 상한 | 전체 목록은 한 번 색인한다. 선택한 멤버만 기존 순서로 정렬하며, 작은 성분이 많으면 정렬 합도 작다. 실제 SQL 저장 비용은 별도다. |
| source identity별 이동 후보 검색·순서 유지 | `O(K·F)` | `O(F + Σ q_j log q_j)` 상한 | 같은 identity 후보만 조회·정렬한다. 같은 identity의 파일이 많으면 후보 처리 비용도 커진다. snapshot 본문 검증 비용은 별도다. |
| 전체 발견·metadata 비교 | `O(V+F)` | `O(V+F)` | 전체 디렉터리 탐색·stat은 유지하며 B에는 관계 색인의 구성 비용이 추가된다. root 수는 고정한 모델이다. |
| 변경 파일의 최초 ID 정렬 | `O(F log F)` 상한 | `O(F log F)` 상한 | 기존 읽기 우선순위를 유지하는 공통 비용이다. |

예를 들어 `R=Θ(K)`, `K=Θ(F)`, `Q=O(K)`인 경우 **첫 행의 반복 검색·정렬 상한만 보면 `O(F² log F) → O(F log F)`**로 줄어든다. 저장 성분도 `C`가 파일 수에 비례하고 각 성분이 소수의 멤버만 가지면 두 번째 행은 반복 전체 검색의 이차 항을 없애고 입력 크기에 비례하는 비용에 가까워진다. 파일이 두 배가 될 때마다 전체 시간을 특정 배수만큼 줄인다는 실측 예측은 아니다.

**최종 전체 갱신에는 다음 비용이 계속 남는다.** 새 미해결 참조별 경로 substring fallback은 `O(U·F)` 모델이고, 새 Codex 원본이 준비될 때마다 준비 원본의 계보를 다시 계산한다. 계보 판정에 앞선 정렬만 해도 `Σ O(P_j log P_j)` 상한이 남으며 `P_j`는 j번째 재계산 시 준비된 Codex 원본 수다. 원본이 한 개씩 늘어나는 패턴에서는 이 합도 이차에 로그를 곱한 상한까지 커질 수 있다. 초기 정렬·winner 병합·본문 읽기/압축 해제/파싱·SQL·COMMIT도 유지한다. 따라서 **이번 반영은 반복 검색 항을 줄였으며, 전체 최악 복잡도가 선형 또는 `O(F log F)`가 되었다고 보장하지 않는다.** 무변경 갱신은 양쪽 모두 전체 발견 비용 `O(V+F)`가 남는다.

### 1.2 실제 작업량과 최종 시간은 얼마나 줄었나

현재 +1건의 별도 구조 진단에서는 관련 확장의 전체 catalog 방문 **17,976회와 pending 정렬 입력 누계 17,570개**를 반복하는 경로가 제거되고, B는 **큐 삽입 28건·제거 28건**을 기록했다. 파일을 실제 읽는 수는 양쪽 28개로 같았다. 서로 다른 종류의 연산 횟수이므로 `17,976÷28`을 실제 속도 향상 배수로 계산하지 않는다. 새 참조의 경로 fallback과 계보 비용도 별도로 남는다.

시간 표본에서 본문 읽기를 제외한 변경 처리·관련 확장 잔여 합계는 현재 **6.197→1.395ms, 77.5% 감소(약 4.44배 속도)**였고 합성에서는 **0.143→0.064ms, 55.0% 감소**였다. 최초 저장 조율 중 실제 `replaceMemory` 바깥의 잔여 중앙값도 현재 **155.239→11.516ms**, 합성 **136.254→10.620ms**로 줄었다. 잔여 시간에는 검색 외의 조율·콜백·Worker 양보·타이머 비용이 포함된다. 상세 계산과 구조 진단의 범위는 [분석](#5-분석)에 기록했다.

사용자가 기다리는 **갱신 시작부터 잠금 획득·파일 탐색·저장·optimize 완료까지의 전체 시간**을 기준으로 하면 다음과 같다. 절감 ms는 반올림 전 A 중앙값−B 중앙값을 계산한 뒤 소수 셋째 자리까지 표시하며 양수는 단축, 음수는 증가다. 따라서 표에 반올림해 표시한 두 시간의 차이와 끝자리가 다를 수 있다.

관련 조율을 77.5% 줄여도 현재 +1건에서 약 440ms의 원본 처리가 그대로 남아 전체 단축은 4.887ms(0.9%)에 그쳤다. 최초 수집은 성분별 반복 검색 감소가 전체 시간에도 반영됐고, 무변경에는 색인 구성 비용이 추가됐다. 즉 **이론적 개선은 반복 검색·정렬의 증가 항을 줄인 것이고, 실제 효과는 최초 전체 1.9%·13.6% 단축과 변경 조율 77.5%·55.0% 감소로 확인됐다.** 두 데이터셋은 파일 수·본문 크기·압축·관계 분포가 달라 이 두 점만으로 점근 차수를 실험적으로 입증하거나 전체 처리의 이차→준선형 전환을 주장하지 않는다.

| COMMIT | 244.912 → 239.795 (2.1%) | 1.984 → 0.904 (54.4%) | 106.101 → 104.651 (1.4%) | 1.147 → 1.743 (-51.9%) |

저장 항목은 서로 중첩된다. COMMIT은 WAL 동기화·가능한 checkpoint·OS 대기를 포함할 수 있다. 두 구현 모두 연결 성분별 transaction이며 무변경 갱신은 replaceMemory를 실행하지 않았다.

## 4. 정확성과 측정 조건

- 모든 준비·측정 A/B 쌍에서 요청·모델·Skill·비용·프로젝트·세션·manifest 진단 의미해시와 provider/model 기준 total·project·session·day·month의 10차원 조회가 일치했다. 물리 ID와 갱신 시각만 정규화 제외했다.
- 네 평균은 정규화 요청을 별도 JS reducer로 계산한 합계·완료 분모·평균·그룹 수와 대조했다. 평균의 분모는 완료 요청 중 사용량이 기록된 요청이다. 고정 전체 기간, 미상 시각 포함, provider 기준, 비용 제외, Asia/Seoul로 전체 페이지를 반환했다.
- 합성 초기값은 생성기 산식과 일치했다. 추가는 정확히 +1요청·+130토큰이고 기존 요청 행은 유지됐다. 현재 실제 본문의 초기 파서 결과 전체에 대한 독립 oracle은 수행하지 않았다.
- 모든 쌍에서 읽은 원본 집합과 읽기 순서 해시·파싱 수·본문 바이트·실패 수가 일치했다. 무변경은 본문0byte·파싱0·replaceMemory0이며 FK·integrity 검사를 통과했다.
- 환경: win32 10.0.19045, Node v24.14.1, SQLite 3.51.2, AMD Ryzen 5 7500F 6-Core Processor             . OS 캐시는 비우지 않았고 입력 사본 및 선행 실행으로 warm 상태다. 강제 GC는 하지 않았다.
- 각 variant/표본은 별도 프로세스·새 DB에서 최초 구축 후 같은 추가 전 상태를 만든다. DB 열기·migration·빈 rollup 활성화·사본 생성·append·검증·복원·조회는 refresh 타이머 밖이다. 갱신 시간은 실제 refreshSummary의 COMMIT·optimize 반환까지다.
- 날짜 경계 없는 전체 입력을 조회하며 빈 DB에서 일별 조회로 rollup을 활성화했다. 모든 시간 표본에서 갱신 전후 `usage_rollup_meta` 1행과 네 조회의 `rollup-active` 경로를 확인했다. 최초 수집부터 rollup 유지 비용을 포함한다. 앞서 극단 날짜 범위로 raw 경로를 측정한 결과는 [별도 보고서](ScanQueueRawRangeAB-2026-11-09.md)에 정정·보존하고 본 중앙값에 섞지 않는다.
- 제품 StageProfiler와 동일한 stat/read wrapper를 사용했다. 큐 메서드별 계측은 본 시간 표본에 추가하지 않았다. 계측 오버헤드는 별도 보정하지 않았다. UI·IPC·quota·heap/GC peak는 미측정이다.
- 입력 SHA-256과 A/B 전체 소스·빌드 fingerprint, runner/helper SHA-256, 모든 표본은 [원시 JSON](./ScanQueueAB-2026-11-09.json)에 있다. 원본 대화와 설치 DB는 변경하지 않았으며 고정 사본 복원 SHA-256을 확인했다. 공개 결과에는 본문·제목·세션 ID·원본 경로를 저장하지 않는다.

## 5. 분석

**판정: 반복 검색·저장 조율 감소 가정은 성립하지만 모든 갱신의 전체 지연 개선은 성립하지 않는다.** 최초 수집은 현재 1.9%, 합성 13.6% 줄었고 두 입력 모두 B가 10/10쌍에서 빨랐다. 현재 +1건의 전체 중앙값 차이는 4.887ms(0.9%)이고 B가 빠른 쌍은 6/10이다. 합성 +1건은 0.478ms(2.3%) 늘고 B가 빠른 쌍은 3/10이므로 추가 전체 성능이 일관되게 좋아졌다고 주장하지 않는다. SQL과 네 평균 조회의 구현은 바꾸지 않았으며 작은 시간 차이를 조회 알고리즘의 개선·악화로 귀속하지 않는다.

**관련 원본 검색:** [별도 구조 진단](ScanQueueStructure-2026-11-09.json)은 동일 고정 A/B·입력의 +1건에서 다음을 기록했다. 구조 진단은 극단 기간 조건의 1쌍이며 그 실행 시간은 본 중앙값에서 제외한다. 아래 카운터는 서로 다른 종류의 작업량이므로 같은 비용의 연산으로 환산하지 않는다. 본 시간 표본에서 `structureInstrumented=false`인 검색·큐 카운터의 0은 미계측을 뜻한다.

| +1건의 구조 지표 | 현재 A | 현재 B | 10,000 A | 10,000 B |
| --- | ---: | ---: | ---: | ---: |
| 관련 확장의 전체 catalog 방문 | 17,976 | 반복 순회 제거 | 100 | 반복 순회 제거 |
| 반복 pending 정렬 입력 누계 | 17,570 | 반복 정렬 제거 | 99 | 반복 정렬 제거 |
| 작업 큐 enqueue / dequeue | 해당 없음 | 28 / 28 | 해당 없음 | 1 / 1 |
| 실제 읽은 파일 | 28 | 28 | 1 | 1 |
| 그중 관련 원본 재읽기 | 27 | 27 | 0 | 0 |

본문 읽기를 제외한 관련 확장 잔여 시간은 현재 6.099→1.305ms(78.6%)다. 다만 색인 갱신 일부가 변경 원본 처리로 이동하므로 그 구간의 잔여 시간도 더해야 한다. 각 표본에서 `changedControlMs + relatedControlMs`를 먼저 합산한 뒤 중앙값을 구한 결과는 다음과 같다.

| +1건의 변경 처리·관련 확장 잔여 합계 | A ms | B ms | 감소율 | B가 빠른 쌍 |
| --- | ---: | ---: | ---: | ---: |
| 현재 | 6.197 | 1.395 | 77.5% | 10/10 |
| 합성 10,000요청 | 0.143 | 0.064 | 55.0% | 10/10 |

이 합계는 원본 읽기 바깥의 계보·색인·큐·조율·콜백·타이머 비용이고 순수 CPU 시간은 아니다. 탐색 단계의 색인 구성 비용은 별도로 남는다. 현재 +1건에서는 A/B 모두 변경 원본 18,937,886byte와 관련 원본 47,657,997byte, 합계 66,595,883byte를 읽었다. 약 440ms의 readSource가 유지되므로 약 5ms의 조율 감소가 전체 지연을 크게 줄이지는 못한다.

**최초 저장 조율:** `commitComponents`는 현재 546.417→395.669ms, 합성 630.639→508.933ms다. 각 표본에서 `commitComponents − storage.replace`를 계산한 잔여 중앙값은 현재 155.239→11.516ms, 합성 136.254→10.620ms다. 성분마다 전체 files·summary·orphan을 filter하던 부분을 그룹 색인 조회로 바꾼 경로에서 감소했다. 잔여에는 멤버·DTO 준비와 Worker 양보도 포함되므로 전부를 순수 검색 시간으로 해석하지 않는다. 실제 `replaceMemory`·SQL·COMMIT의 구현은 동일하다.

**추가 비용과 남은 한계:** 현재 무변경 전체는 99.396→103.289ms로 3.892ms(3.9%) 늘었고 B가 10/10쌍에서 느렸다. 탐색 구간도 88.068→91.723ms여서 전체 탐색 중 관계 색인을 구성하는 추가 비용과 부합한다. 합성 무변경은 14.246→14.814ms(4.0%)이며 B가 빠른 쌍이 4/10으로 변동도 섞여 있다. 무변경에 유리한 후보라고 설명하지 않는다. source identity 후보 검색은 줄었지만 이동 snapshot 검증 호출은 양쪽 모두 0회여서 prefix 검증 I/O 개선은 확인하지 못했다. 비Windows dev/inode 후보 색인은 Windows에서 실행되지 않았으며 해당 운영체제의 실제 경로는 미검증이다.

**선택:** 최초 성분 처리와 반복 관계 검색 감소를 위해 구현을 반영하고, 무변경 비용 증가와 작은 추가 전체 효과를 함께 기록한다. 전체 manifest·디렉터리 탐색, 새 미해결 참조별 경로 substring fallback, 준비된 Codex 원본의 계보 재계산은 남는다. 큐는 기존 순서를 유지하는 최소 힙이므로 후보당 `O(log K)`가 들며 전체 처리가 선형이라는 보장은 없다. watcher·metadata 동시성·append checkpoint·영속 원본별 상태는 이번에 적용하지 않았다.

**회귀 검증:** 새 통합 회귀 4건(숨은 파일명 동일 세션 확장, 이전·새 세션 귀속, 복수 부모 동점 순서, 겹친 root 중복 준비)을 포함한 계보 테스트 7/7이 통과했다. 같은 크기 재작성 때문에 mtime 정밀도에 의존하던 기존 fixture 5곳은 빈 줄을 추가해 크기도 바뀌도록 안정화했다. 최종 `npm run check`의 타입·린트는 통과했고 Node 테스트는 419건 중 414통과·5실패다. 남은 rootless 자식의 독립 세션 기대 관련 5개는 고정 A에서도 동일하게 실패했으며 이번 변경과 무관한 기대값·파서 동작은 수정하지 않았다. 코드·diff 검토와 현재 소스·컴파일 결과가 측정 B의 fingerprint와 같은지도 확인했다.

## 6. 재실행

`node --no-warnings tests/benchmarks/scan-queue-ab.cjs --workspace=<기존 고정 사본 폴더 또는 새 폴더> --before=<A 고정 소스·dist 루트> --after=<B 고정 소스·dist 루트> --output=<새 JSON>`

기본은 준비3쌍·교대10쌍이다. `--prepare-only`는 A를 기준으로 현재·합성 입력 사본만 만든다. `--structure --pairs=1 --warmups=0`는 별도 구조 진단용이며 그 시간은 본 중앙값에 섞지 않는다. 기존 JSON은 덮어쓰지 않고 각 실행의 DB를 새 비공개 하위 폴더에 보존한다.
