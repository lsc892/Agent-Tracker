# 파일 준비 Worker 풀 A/B 테스트

> 후속: [가독성 정리](../../research/2026-11-09/SourcePoolReadability-2026-11-09.md)에서 동작·스케줄링을 보존해 내부 조건과 처리 단계를 정리했다. 아래 수치는 원시 JSON에 식별된 리팩토링 전 고정 후보 B의 값이며, 후속 소스에서 A/B를 재실행하지 않았다.

2026-11-09 19:49:53 - 2026-11-09 19:54:11, Asia/Seoul.

가정: 사용자는 기존 역인덱스·작업 큐로 필요한 파일을 각각 읽고 결과를 모아 DB에 반영하는 병렬 구조를 적용하고 현재 데이터와 합성 10,000요청의 구간별 A/B를 요청했다. 에이전트는 큰 원본의 독립 계산을 분산하면 준비 시간이 줄지만 작은 파일에서는 Worker 시작·전송 비용이 이득을 상쇄할 수 있다고 예상했다.

개선 방향: A는 요청 시점 작업 트리의 순차 읽기 구현을 고정한 소스·빌드다. B는 최대 4개 파일 준비 Worker와 8파일 선행 창을 적용한다. 후보가 하나뿐이거나 선행 후보의 원본 크기 합계가 1 MiB 미만이면 Worker를 시작하지 않는다. Worker는 한 갱신 안에서 재사용하고 갱신 종료 시 정리한다. 기존 논리 처리 순서·관계 확정·연결 묶음별 저장 transaction을 유지했다. SQL·schema·metadata 동시성·watcher·append checkpoint는 변경하지 않았다.

각 셀은 A → B 중앙값 ms (감소율)이다. 감소율=(A−B)/A×100이며 양수는 단축, 음수는 증가다. 준비 3쌍을 제외하고 AB/BA 교대 10쌍을 측정했다. Worker 생성·시작 대기·결과 전송·종료를 전체 갱신 시간에 포함했다. 사본 생성·append·검증·migration·조회는 refresh 타이머 밖이다. 평균 토큰 조회 표는 요청 1건 추가 후의 값이다.

## 4. 정확성과 측정 조건

- 환경: Windows 10.0.19045, Node v24.14.1, SQLite 3.51.2, AMD Ryzen 5 7500F 6-Core / 논리 CPU 12개.
- 각 variant·표본은 별도 프로세스·새 DB에서 최초 구축 후 같은 요청을 추가한다. DB 열기·migration·빈 rollup 활성화·입력 복원·append·검증·조회는 refresh 밖이다. 잠금 획득부터 COMMIT·optimize·Worker 종료까지 갱신 시간에 포함한다.
- OS 캐시는 비우지 않았고 입력 사본·선행 실행으로 warm 상태다. 강제 GC는 하지 않았다. 차가운 디스크 캐시의 성능은 미측정이다.
- 모든 준비·측정 A/B 쌍에서 facts·모델·Skill·비용·프로젝트·세션·manifest 의미해시, provider/model 기준 total·project·session·day·month의 10차원 조회가 일치했다. 물리 ID와 갱신 시각은 정규화 제외했다.
- 네 평균은 정규화 요청에서 별도 JS reducer로 계산한 합계·완료 분모·평균·그룹 수와 대조했다. 합성 초기값은 생성기 산식과 일치했다. 추가는 정확히 +1요청·+130토큰이며 기존 요청 행을 보존했다.
- 논리 읽기 순서·원본 집합·파싱 수·본문 바이트·실패 수가 일치했다. 사용하지 않은 선행 읽기가 없었고 실제 최대 선행 작업은 8개였다. 구조상 긴급 부모 1개를 추가할 수 있다. FK·integrity 검사를 통과했다.
- 두 입력의 무변경 갱신은 Worker0·본문0byte·파싱0·replaceMemory0이었다. Worker별 stat 호출은 부모 프로세스의 stat wrapper에 잡히지 않으므로 stat 카운터 감소를 성능 근거로 사용하지 않는다.
- 제품 StageProfiler에 논리 읽기 wrapper와 B의 제출 수 카운터를 더했다. A는 원본 reader, B는 풀의 결과 소비 지점을 계측하므로 Worker 내부 서비스 시간과 구분한다. 계측 오버헤드는 별도 보정하지 않았다.
- 조회는 고정 입력 전체 기간·미상 시각 포함·provider 기준·비용 제외·excludeEmptyUsage=true·Asia/Seoul이며 전체 페이지와 전체 그룹 수를 반환한다.
- 실제 초기 파서 전체의 독립 oracle, 오류·취소·파일 교체 전용 시나리오, UI·quota·heap/GC·피크 메모리는 미측정이다. 일반 자동 테스트는 실행하지 않았다.
- 원본 대화와 설치 DB는 변경하지 않았다. 고정 사본 복원 SHA-256을 확인했다. 공개 산출물에 본문·제목·세션 ID·원본 경로를 기록하지 않는다.
- A/B 소스·빌드 fingerprint, 입력 SHA-256, 실행기·helper 식별자·환경·모든 표본은 [원시 JSON](SourcePoolAB-2026-11-09.json)에 있다. 비공개 workspace의 설정·입력·DB를 보존했다.

## 5. 분석

- **후속 순서 분석**: [코드·보존 DB 대조](../../research/2026-11-09/SourcePoolOrderAudit-2026-11-09.md)에서 각 입력 10쌍의 논리 읽기 순서·저장 단계 호출 수·최종 요청/파일 ID 배치가 일치했다. 측정 범위에서 저장 저하를 순서 오류나 재저장 증가로 설명할 근거는 없었다. GC·메모리 원인과 조기 종료 효과는 별도로 미측정이다.
- **판정: 큰 실제 입력에서 성립, 작은 합성 입력의 최초 전체 시간은 차이 없음.** 현재 최초 수집은 8,030.476→3,279.872ms로 4,750.604ms(59.2%, 약 2.45배) 줄었고 10/10쌍 모두 B가 빨랐다. 현재 +1건도 566.363→409.511ms로 156.852ms(27.7%) 줄었고 10/10쌍에서 빨랐다.
- **주요 감소 구간은 파일 준비다.** 현재 최초 변경 파일 준비는 7,386.311→2,589.241ms(64.9%)이며, +1건의 관련 파일 확장·준비는 317.828→147.397ms(53.6%)다. 읽기 집합·바이트를 줄이지 않고 같은 결과를 준비하는 경과 시간이 감소했다. I/O·압축 해제·파싱·해시·winner 계산은 섞여 있으므로 순수 JSON 파싱 개선율로 해석하지 않는다.
- **직렬 구간과 비용은 남는다.** 현재 최초 최종 집계는 124.859→133.295ms, 저장 조율은 410.623→434.583ms로 늘었고 Worker 종료 6.252ms가 추가됐다. DB 병렬 쓰기의 효과는 없으며 원본 준비가 빨라진 비율만큼 전체가 그대로 빨라지는 구조도 아니다.
- **합성은 작은 파일 때문에 순차 경로를 유지했다.** 최초 835.617→834.878ms(0.1%)이며 B가 빠른 쌍은 6/10이고 범위가 겹친다. +1건은 22.848→22.314ms(2.3%)·5/10쌍이다. 이 입력에서는 일관된 갱신 개선을 주장하지 않는다. 최초 저장 조율 543.568ms가 준비 180.877ms보다 커 파일 준비만 바꾸는 효과에도 한계가 있다.
- **무변경·조회 차이를 스레드 병렬화 효과로 해석하지 않는다.** 무변경은 현재 5.2%·합성 12.0% 감소했지만 Worker를 시작하지 않았다. 잠금·관측 기록 등의 시간 차이는 관측됐으나 원인을 분리하지 않았다. 조회 SQL도 변경하지 않았으며 작은 조회 시간 증감으로 알고리즘의 개선·악화를 판단하지 않는다.
- **선택: 제한된 풀과 작은 입력의 순차 경로를 채택한다.** 큰 실제 원본 준비에서 시간이 줄었고 결과가 일치했다. 1 MiB와 최대 4개는 이번 후보의 보수적 시작 기준이며 모든 환경의 최적값을 증명한 것은 아니다. 선행 결과 수는 제한하지만 이미 준비한 winner·관계 근거는 최종 집계까지 남고 Worker 버퍼·복사도 있으므로 메모리가 감소했다고 주장하지 않는다.
