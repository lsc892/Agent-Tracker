## 6. 판정과 검증 범위

- **현재 최초 수집:** readSource 8,117.41ms로 전체의 약 89.5%다. 이 입력에서는 원본 처리가 우선 비용이다. 실제 입력이 합성 입력보다 약 88배 크므로 10,000요청이 더 빨랐다는 사실은 요청 수 증가에 따른 개선을 뜻하지 않는다.
- **현재 1건 추가:** 28파일·66,595,883byte를 읽었다. 그중 관련 원본 27개·47,657,997byte를 확장에서 읽었고, 관련 확장 전체는 352.77ms다. 변경 처리+관련 확장은 477.52ms, 그 안의 readSource 누계는 470.66ms여서 차이는 6.86ms다. 반복 전체 검색은 17,836방문으로 관측됐지만 이번 입력에서 검색·정렬 자체가 주병목이라는 가정은 뒷받침하지 않는다. 순수 확장 검색 시간은 별도로 분리하지 않았다.
- **무변경 갱신:** 본문 0byte·파싱 0·replaceMemory 0회. 현재 데이터의 탐색 104.83ms는 전체 116.62ms의 약 89.9%다. metadata 최적화가 겨냥할 구간이 확인됐다.
- **합성 최초 수집:** 성분별 저장 조율 808.33ms가 전체 1,106.67ms의 약 73.0%다. replaceMemory 내부에서는 요청 비교·쓰기 330.73ms가 COMMIT 118.43ms보다 크다. 반대로 현재 데이터 최초 replaceMemory에서는 COMMIT 270.01ms가 요청 비교·쓰기 63.46ms보다 크다. 저장의 주비용도 입력별로 달랐다.
- **미관측·보류:** 이동 snapshot 검증 경로는 호출되지 않았으므로 해당 경로의 실제 읽기 비용은 판단하지 않는다. heap·GC·메모리 피크·watcher·역인덱스 후보·metadata 동시성·append checkpoint의 개선 효과도 미측정이다. 단일 표본이므로 변동 폭이나 개선율은 주장하지 않으며 제품 알고리즘은 변경하지 않는다.

6회 갱신 모두 실패·중단 없이 완료됐다. 합성 초기 요청 수·토큰 합계는 생성기 기대값(10,000요청·6,340,000토큰)과 일치했다. 두 append 모두 정확히 +1요청·+130토큰이었고 기존 요청 행은 유지됐다. 두 무변경 실행은 본문 읽기·replaceMemory를 생략했다. 매 상태의 네 묶음 첫 페이지와 전체 개수는 raw SQL과 일치했다. 읽기 바이트 합계와 모든 고정 사본의 복원 SHA-256도 확인했다. 실제 데이터의 초기 파서 결과 전체에 대한 독립 oracle 검증과 UI/IPC·quota 호출은 수행하지 않았다.

실행기 구문 확인, TypeScript 컴파일, 코드·참조·diff 검토를 수행했다. 요청한 성능 측정 이외의 자동 테스트와 `npm run check` 전체는 실행하지 않았다. 기능 동작을 변경하지 않아 기능 의사결정 일지는 추가하지 않는다.
