# 현재 조회 SQL 병목 조사

기준일: 2026-10-31, Asia/Seoul.

측정한 53개 조건에서는 비용을 제외할 때 **모델 열로 정렬한 모델별 요청 목록**, 비용을 포함하면 **일별·월별 원본 집계**가 가장 느린 계열이다. 통계 집계만 비교하면 비용 제외 시 **세션별·모델별 통계**가 가장 느리다. 모델 열 정렬은 출시일·버전 순서를 사용한다. 저장된 사용자·현재 워크스페이스 설정에 `agentTracker.usage.showApiCosts` 값이 없었으며, 확장의 기본값은 `false`다. 실행 중인 다른 창이나 프로필의 설정을 조사한 것은 아니다.

설치 DB 사본은 **1,030 요청·924 모델 행·279 세션·14 프로젝트·362 manifest 행**이다. 일별 사전 집계는 제공자 기준 306행·모델 기준 366행이다. Node v24.19.0·SQLite 3.53.3·Windows·Intel Core i5-8250U에서 측정했다.

## 현재 조회 구조

| 용도 | 실제 읽는 데이터와 처리 |
| --- | --- |
| 일반 토큰 통계 | `usage_request_daily` 또는 `usage_model_daily`를 다시 합산한다. 일·월·프로젝트·세션별 차원과 완료 표본 기준 평균을 지원한다. |
| 하루 중간부터 시작하거나 끝나는 기간 | 완전한 날짜의 사전 집계에 양끝 날짜의 원본 집계를 `UNION ALL`한다. |
| 비용 표시 | `includeCosts`가 켜지면 원본 `turn_summary` 기반으로 대체한다. 모델 기준은 `turn_model_usage`, 비용은 `turn_costs`를 연결한다. |
| 요청 상세·이름·도구·진단 | 원본 테이블을 조회한다. 요청 목록은 정렬·페이지, 이름은 그룹화·정렬, 도구는 분류별 합계·순위를 계산한다. |
| 표의 페이지 | 행 조회 SQL과 전체 그룹 수 SQL을 각각 실행한다. Worker는 추가로 진단 페이지를 읽어 coverage를 붙인다. 도표는 표의 행을 재사용한다. |

사실 테이블에는 날짜·프로젝트/날짜 인덱스가 있고, 일별 집계에는 `(provider, session_id, project_key, local_day[, model_key])` PK와 날짜·프로젝트/날짜 인덱스가 있다. `LIMIT 100`은 집계 후 반환 행을 제한하며, 합산할 입력을 100행으로 제한하지 않는다.

관련 구현: [조회 선택](../../../src/summary/db/reader.ts), [일별 집계 조회](../../../src/summary/db/queries/rollup/usage.ts), [원본 집계](../../../src/summary/db/queries/raw/usage.ts), [Worker 응답](../../../src/summary/worker.ts).

가장 무거운 10만 요청 비용 포함 일별·모델별 행 SQL의 실행 계획:

```text
CO-ROUTINE (subquery-2)
SEARCH t USING INDEX idx_summary_project_period (provider=?)
SEARCH m USING PRIMARY KEY (turn_id=?) LEFT-JOIN
SEARCH c USING INTEGER PRIMARY KEY (rowid=?) LEFT-JOIN
USE TEMP B-TREE FOR GROUP BY
SCAN (subquery-2)
USE TEMP B-TREE FOR ORDER BY
```

## 시간이 늘어나는 구조

1. [비용 조건](../../../src/summary/db/queries/rollup/usage.ts)에서 일별 사전 집계를 사용하지 않는다. 기간을 제한하지 않으면 원본 요청 범위를 합산한다.
2. 원본 달력 집계는 `agent_tracker_period(started_at_ms, ?, ?)`로 JS 시간대 변환 함수를 호출하고, 날짜·모델별 `GROUP BY`를 수행한다. 제공자 기준 원본은 모델 기록 여부를 `EXISTS`로 조회하고, 모델 기준 원본은 요청을 모델별 행으로 확장한다.
3. 페이지 행 SQL과 그룹 수 SQL이 같은 범위의 날짜·모델 그룹화를 각각 수행한다. `COUNT(*)`도 이미 저장된 단일 개수를 읽는 형태가 아니다.
4. 세션 통계는 이름과 전체 기간의 최초 시각을 관련 서브쿼리로 구한다. 기본 정렬에 이 최초 시각이 쓰이며, 그룹화와 전체 결과 정렬을 마친 뒤 페이지를 자른다.
5. 요청 목록의 모델 열 정렬은 원본·모델·프로젝트·세션을 연결한 행에 `agent_tracker_model_release`·`agent_tracker_model_key` JS 함수를 적용해 정렬한다. 실행 계획에 `USE TEMP B-TREE FOR ORDER BY`가 있으며, 전체 후보를 정렬한 뒤 첫 100행을 반환한다. [정렬식](../../../src/summary/db/queries/common/sorting.ts)과 [요청 SQL](../../../src/summary/db/queries/raw/turns.ts)에 해당 경로가 있다.

이 설명은 현재 SQL과 실행 계획에 따른 원인 해석이다. 각 연산의 소요 시간을 독립적으로 분해하거나 SQLite 내부 방문 행 수·물리 I/O를 측정한 결과는 아니다. 개선을 진행한다면 비용 제외 조회의 요청 목록 정렬·세션 그룹화와 비용 조회의 원본 재집계·개수 집계 반복이 우선 조사 대상이다. 인덱스·쿼리·제품 동작은 이 조사에서 변경하지 않았다.

## 측정 범위와 재현

- 사용 중인 설치 DB를 읽기 전용으로 열고 SQLite backup으로 고정 사본을 만들었다. 이후 마이그레이션·최적화·사전 집계 생성은 사본에서만 수행했다.
- 제품과 같은 캐시 4,096 KiB·`temp_store=FILE` 설정을 사용했다. 강제 `ANALYZE`는 하지 않았으며 제품의 optimize 경로를 사용했다.
- 합성 입력은 기존 SQL fixture의 세션당 10요청·20프로젝트·90일 분포다. 비용·도구·manifest 행을 추가했다. 실제 로그 파싱 성능이나 긴 단일 세션 갱신 성능을 뜻하지 않는다.
- 첫 조회와 사전 집계 생성 포함 여부는 JSON의 `firstReadMs`·`firstReadIncludesRollupBuild`에 별도로 기록했다. 위 표는 사전 집계가 준비된 반복 조회다.
- 주측정은 47조건·95개 SQL이며 [원시 JSON](QueryProfile-2026-10-31.json)에 있다. 비용 제외 요청 목록의 6조건·12개 SQL은 [추가 측정 JSON](QueryProfile-requests-without-costs-2026-10-31.json)에 보존했다. 최종 실행기는 이 두 범위를 합쳐 53조건·107개 SQL을 지원한다. 각 파일에 SQL 원문·마스킹한 파라미터·실행 계획·원시 시간 표본·결과 해시·해당 실행 당시 소스 해시가 있다. 대화 내용·제목·실제 프로젝트 경로·세션 ID는 저장하지 않았다.
- 각 조건을 반복 실행해 결과 해시의 안정성을 확인했다. OS 캐시를 비우지 않았고 백그라운드 작업을 중지하지 않았으므로 최초 디스크 읽기나 독점 장비에서의 지연을 뜻하지 않는다. 수집·파싱·세션 저장 SQL과 Worker 대기·통신·웹뷰 렌더링은 측정 범위 밖이다.
