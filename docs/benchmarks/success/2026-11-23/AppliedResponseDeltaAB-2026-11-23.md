# 응답별 반영값 차분 적용 A/B 테스트

2026-11-23, Asia/Seoul. 사용자는 최종 요청 합계와 부모 연결 메타, 응답별 마지막 반영값으로 갱신하도록 요청했다. 원본별 후보 저장을 걷으면 DB 공간과 첫 수집 쓰기가 줄고, 관련 파일을 다시 읽어야 하는 증분에서는 시간이 늘 수 있다고 예상했다.

- **A**는 직전 v22 작업 트리 빌드다. 원본별 winner와 접힌 파서 상태를 SQLite에 저장해 변경되지 않은 관련 원본의 본문을 건너뛴다.
- **B**는 v23 작업 트리 빌드다. 원본 관계 메타를 `source_file`에 두고 응답별 마지막 토큰을 `applied_response`에 저장한다. 여섯 열과 `(turn_id, response_key)` 기본 키가 요청 연결과 조회를 함께 맡는다. 영향 세션의 관련 파일을 파싱해 최종 모델·요청 상태를 계산하고, 기존 SQL 합계에는 응답별 차분을 적용한다.

## 3. 확인한 손익

- 실제 1건 추가에서 B는 20쌍 중 19쌍 느렸다. 저장한 파서 상태를 없애면서 파싱 파일이 1→4개, 본문 읽기가 16,160,125→27,140,525바이트로 늘었다. 원본 읽기·파싱은 114.94→283.50ms였고, 최종 집계는 4.49→1.84ms로 줄었다. 합성 입력은 파일을 한 개씩 읽는 조건이 양쪽에서 같았고 1건 추가 차이는 각각 3.01ms와 0.12ms였다. [관련 원본 준비](../../../../src/summary/scanner/refresh/relations.ts) · [응답 차분 적용](https://github.com/lsc892/Agent-Tracker/blob/76f8ea74ba8a286e373b2947ffa4e79970e6d71a/src/summary/aggregation/appliedUsage.ts)
- 실제 전체 재수집에서 SQLite COMMIT은 121.38→63.96ms로 줄었고, 전체 시간 중앙값은 5.92% 늘었다. 두 빌드가 같은 418개 파일을 읽었고 전체 시간의 쌍별 방향은 나뉘었다. 합성에서는 전체 재수집 중앙값이 10,000요청에서 3.45%, 100요청에서 17.74% 단축됐다. 평균 토큰 조회 중앙값 차이는 세 입력에서 0.21ms 이내였다.
- 실제 DB에서는 원본별 후보 18,497행을 응답별 마지막 반영값 14,985행으로 줄였다. 메타 본문은 3,539,845→111,052바이트였다. 새 `applied_response`의 사용 페이지는 약 3.15MiB이며 별도 외래 키 인덱스를 두지 않는다. 기존 DB 이관은 빈 페이지를 재사용한다. 실제 v22 사본 1회의 이관은 18.95ms였으며, 첫 스캔 4,838.46ms 뒤 사용 중인 페이지는 약 4.63MiB였다. 해당 파일의 전체 할당 페이지는 약 10.41MiB였다. ## 4. 측정 조건과 정합성

- Windows x64, Intel Core i5-8250U, Node 24.19.0, SQLite 3.53.3에서 빌드별 별도 프로세스와 최대 4개 파일 Worker를 사용했다. 작업·입력마다 준비 3쌍을 거친 뒤 A→B와 B→A를 각각 10쌍씩 실행했다. 같은 고정 입력 사본으로 비교하고 OS 파일 캐시는 유지했다. 타이머는 `refreshSummary` 호출부터 COMMIT과 종료까지다. 입력 추가·원복·빈 DB 스키마 생성·강제 GC·검증은 타이머 밖에서 수행했다. 최근 미리보기는 껐다.
- 실제 입력은 418개 일반 JSONL, 616,959,493바이트, 922요청, 1,849,943,425토큰이다. 합성은 Claude·Codex를 절반씩 배치해 10개 프로젝트와 최대 14일로 나눴다. 10,000요청은 100세션·세션당 100건, 100요청은 10세션·세션당 10건이다. 초기 기대 토큰 합계는 6,340,000과 18,400이다.
- 평균 조회는 갱신 직후 `queryUsagePage`로 일·월·세션·프로젝트별 모든 페이지를 읽었다. 범위는 2020-01-01 UTC 이상, 2035-01-01 UTC 미만이고 시각 미상 요청을 포함했다. 일·월 경계는 Asia/Seoul이며 빈 완료 요청을 포함한 모든 완료 요청을 분모로 사용했다.
- 준비를 포함한 207쌍에서 요청 수·토큰과 요청·모델·도구·비용 행 해시가 일치했다. 모든 추가분은 1요청·130토큰이었다. 조회 1,104건을 독립 계산해 그룹 수·토큰·평균을 대조했고 원본 사본 해시를 확인했다. 별도의 SQL 재합산에서 세 입력 모두 논리 응답 중복과 요청 토큰 불일치가 0건이었다. v22 이관 전후와 첫 스캔 뒤에도 기존 통계 해시가 일치했다. [원시 표본과 입출력 해시](AppliedResponseDeltaAB-2026-11-23.json)

## 재실행

직전 v22와 최종 v23의 고정 빌드·입력을 지정한다. 새 입력을 만들 때는 `--workspace` 옵션을 생략한다.

```powershell
node --no-warnings tests/benchmarks/mtime-refresh-ab.cjs --before="<v22 빌드>" --after="<v23 빌드>" --workspace="<고정 입력>" --output="<새 JSON>" --repetitions=20 --rebuild=true
```
