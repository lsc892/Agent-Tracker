# JSONL 행별 디코딩 제품 A/B

수정 전 `fe187d1`의 제품 빌드와 수정 후 제품 빌드의 `prepareSource`를 비교했다. 두 방식은 JSONL 파일을 최대 64KiB 단위로 읽는다. 수정 전에는 청크 안의 완성된 줄 전체를 디코딩하고 나눴다. 수정 후에는 LF 경계를 찾고 한 줄을 디코딩해 즉시 파싱한다.

## 실측

각 값은 수정 전 → 수정 후 5회 중앙값이다. RSS와 Heap은 개별 실행의 피크를 비교한다.

| 입력 | 파일 수 · JSONL 행 수 | 가장 긴 원본 행 (바이트) | 피크 RSS (MiB) | 피크 V8 Heap (MiB) | 읽기·파싱 (ms) |
| --- | ---: | ---: | ---: | ---: | ---: |
| 실제 887요청 · 572.59MiB | 402 · 123,101 | 4,800,393 | 153.88 → 145.01 | 62.34 → 55.31 | 8296.35 → 8102.90 |
| 가장 큰 Claude 파일 · 36.33MiB | 1 · 1,593 | 1,476,446 | 78.96 → 78.30 | 14.21 → 13.82 | 368.88 → 359.63 |
| 가장 큰 Codex 파일 · 15.41MiB | 1 · 1,299 | 4,521,811 | 49.69 → 49.17 | 8.81 → 8.79 | 115.31 → 115.48 |
| 합성 10,000요청 · 5.38MiB | 100 · 30,050 | 270 | 83.44 → 82.69 | 25.46 → 25.18 | 347.38 → 358.89 |
| 합성 100요청 · 54.39KiB | 10 · 305 | 264 | 45.81 → 45.38 | 8.15 → 8.03 | 18.40 → 19.48 |

- **실제 로그 전체**에서 피크 Heap이 **7.03MiB(11.3%)**, RSS가 **8.87MiB(5.8%)** 줄었다. 수정 전후 Heap 범위는 61.92–63.33 → 43.14–59.78MiB였다. 다섯 쌍 모두 Heap과 RSS가 낮았고 읽기·파싱 시간도 짧았다. 시간 중앙값은 193ms(2.3%) 단축됐다. 시작 직후를 뺀 추가 Heap은 56.17 → 49.15MiB, 추가 `arrayBuffers`는 19.86 → 19.58MiB였다.
- **대형 단일 파일**의 Heap 감소는 Claude 0.38MiB, Codex 0.01MiB였다. 입력 버퍼가 기존에도 64KiB로 제한되어 있어 단일 파일에서 줄 단위로 디코딩한 효과는 작았다.
- **합성 로그**의 Heap 피크는 0.28MiB와 0.12MiB 낮았다. 합성 10,000요청의 읽기·파싱은 11.51ms(3.3%) 늘었고 5쌍에서 모두 느렸다. 100요청은 중앙값 차이가 1.08ms였고 실행 범위가 겹쳤다.

## 측정 방법

- 수정 전 소스와 빌드를 별도 워크트리에 고정하고 제품 변경 전에 전체 실제 로그에서 기준 실행을 기록했다. Windows x64·Intel Core i5-8250U·Node v24.19.0에서 본 비교는 준비 2회 뒤 5회씩 AB/BA 순서를 교대했다. OS 파일 캐시는 비우지 않았고 프로세스를 하나씩 실행했다. 기준 실행은 본 비교 중앙값에 포함하지 않았다.
- 시간은 새 프로세스의 첫 메모리 측정 뒤 GC하고 두 번째 읽기에서 쟀다. 제품의 `prepareSource`가 수행하는 파일 I/O·JSONL 파싱·Claude/Codex adapter·SHA-256·원본별 winner 선택을 포함한다. 계측 콜백, DB 저장·조회, 정합성 해시는 시간에서 제외했다.
- RSS는 프로세스의 최대 working set이다. Heap은 청크 시작·완료, 첫 행과 매 64행, 파일 완료 시점에서 관측한 `heapUsed`의 최대값이다. 파일 `Buffer`의 데이터는 `arrayBuffers`에서 관측했고 RSS와 합산하지 않았다. Heap 표본 사이의 순간 피크는 놓칠 수 있다. 여러 Worker의 동시 피크와 VS Code 전체 메모리는 미측정이다.
- 실제 입력은 설정 기본 경로에서 고정 바이트 경계까지 복사했다. Claude와 Codex의 가장 큰 일반 JSONL을 별도로 측정했다. 합성 10,000요청은 파일당 100요청, 합성 100요청은 파일당 10요청이며 두 입력 모두 제공자별 파일 수가 같다. 원본 행 크기는 사본에서 LF 사이 바이트 수를 별도로 세었다. 보관 바이트 분포와 Zstd 입력 성능은 미측정이다.

## 코드와 정합성

일반 JSONL의 원본 바이트 N에 대한 시간 O(N)과 청크 C·한 행 보관량 L·행 예산 K에 대한 보조 공간 O(C + min(L,K))은 같다. 행별 디코딩은 청크 문자열과 완성된 줄 배열의 동시 할당을 없애며, 완성된 줄이 예산을 초과하면 원본 바이트에서 이미지 제거와 예산 검사를 수행한다. 청크 경계의 행 상태, Zstd 해제, 파서 객체와 winner 상태는 각자 같은 경로에서 처리한다.

두 빌드는 파일별 SHA-256, 파싱 행 수, 부분 행, identity와 winner 출력이 일치했다. 별도 제품 갱신에서 동일한 요청·모델·도구·비용 facts와 전체 토큰 합계를 SQLite에 저장했다. 일·월·세션·프로젝트의 각 집계와 완료 요청 평균을 독립 JavaScript 합산과 대조했다. 합성 집계는 생성기의 기대값과 일치했다. 변경 없는 재갱신은 본문을 0바이트 읽었다. `npm run check`의 타입 검사·린트·Node 테스트 441개가 통과했으며 일반·Zstd JSONL의 이미지 제거, 줄 한도, 바이트 위치, 잘림·취소 테스트를 포함한다.
