# 최근 30일 통계 첫 화면 A/B

사용자는 최근 30일을 먼저 표시하고 SQLite 갱신 성공 뒤 필터를 열도록 변경했을 때의 첫 화면 시간을 요청했다. 최근 파일이 전체의 일부일수록 나머지 파싱과 디스크 저장을 뒤로 미룬 효과가 커지고, 이미 집계가 있는 경우에는 메모리 재집계 비용이 첫 표시까지 더해진다는 가정으로 비교했다.

- A는 `247e712`의 스캔 완료 후 SQL 통계를 표시하는 방식이다. 날짜 선택만 30일로 맞췄다.
- B는 현재 작업 트리의 30일 메모리 페이지와 영속 갱신 후 전환 방식이다.
- 기존 DB 시나리오에서는 예전 캐시 우선 진입 순서도 대조했다. 이전 저장본을 먼저 조회한 뒤 스캔을 시작하도록 A의 통계 진입을 계측기에서 구성했다.

## 빈 DB

10회 중앙값이며 모든 시간은 ms다. 열 안의 순서는 A → B다.

| 입력 | 창 틀 | 첫 30일 표 | 첫 표 단축 | SQLite 갱신 후 표 |
| --- | ---: | ---: | ---: | ---: |
| 로컬 로그 사본 883요청 | 112.5 → 104.0 | 3,964.0 → 1,732.5 | 56.3% | 3,964.0 → 3,944.9 |
| 합성 10,000요청 | 101.2 → 76.4 | 1,983.7 → 220.8 | 88.9% | 1,983.7 → 1,971.6 |
| 합성 100요청 | 73.0 → 71.8 | 151.4 → 113.3 | 25.2% | 151.4 → 187.1 |

로컬 사본 883요청에는 검증용 요청 1건이 포함된다. 최근 30일은 248요청이었다. 첫 표 시간은 A에서 3,822.6~4,738.8ms, B에서 1,662.6~2,017.1ms였다. 합성 10,000요청은 500파일 중 10파일·200요청이 최근 범위에 들고 합성 100요청은 10파일 중 1파일·10요청이 들어간다. 첫 응답의 이득은 오래된 파일 처리를 첫 화면 뒤로 옮긴 데서 나왔다. 로컬과 합성 10,000건의 SQLite 갱신 후 표 시간 차이는 실행 변동 범위 안에 있었다.

## 일별 집계가 준비된 DB에 요청 1건 추가

사전에 기본 일별 조회를 실행해 일별 집계를 만든 DB 사본을 사용했다. 각 수치는 10회 중앙값 ms다. [기존 DB 원시 JSON](DashboardFirstPageWarmAB-2026-11-21.json).

| 입력 | 기존 캐시 우선의 첫 표 | 기존 캐시 우선의 갱신 표 | 첫 최신 표 A → B | SQLite 갱신 후 표 A → B |
| --- | ---: | ---: | ---: | ---: |
| 로컬 로그 사본 883요청 | 131.8 | 262.3 | 242.8 → 278.8 | 242.8 → 313.7 |
| 합성 10,000요청 | 126.4 | 240.8 | 212.5 → 226.8 | 212.5 → 263.6 |
| 합성 100요청 | 119.3 | 150.4 | 145.4 → 132.9 | 145.4 → 165.0 |

로컬에서 B의 최신 첫 표는 A 중앙값보다 36.0ms 늦었고 개별 실행 범위는 일부 겹쳤다. 캐시 우선의 첫 표에는 10회 모두 추가 요청이 빠졌다. 일별 집계가 준비돼 있으면 A는 변경 파일을 처리한 뒤 바로 조회할 수 있다. B는 저장된 최근 요청과 새 요청을 메모리에서 합쳐 먼저 그리고 영속 갱신 결과를 한 번 더 그린다. 각 처리 비용의 비율은 따로 계측하지 않았다.

합성 입력의 첫 표와 최종 표는 원본 생성 시 계산한 요청 수·토큰 합계와 일치했다. 로컬은 독립적으로 읽은 원본 요청 행의 기간 내 합계와 비교했고, B는 빈 DB와 요청 추가 모두 첫 표부터 기대값과 일치했다. 빈 DB와 기존 DB 재측정의 로컬 로그는 각각 시작 시점의 별도 사본이다. 요청 수는 883건으로 같았고 총 토큰 수와 해시는 각 JSON에 기록했다.

## 측정 조건

이미 실행 중인 격리 VS Code에서 `Dashboard.open()`을 호출하기 직전부터 Webview가 첫 통계 결과를 렌더링한 프레임까지 측정했다. 창 틀은 DOM 준비 후 첫 프레임, 최종 표는 갱신 완료 뒤 SQLite 결과를 렌더링한 프레임이다. 호출 전 Worker와 DB 스키마는 초기화했고 원본 사본 준비와 DB 사본 복원은 타이밍에서 제외했다.

Windows의 Intel Core i5-8250U 8논리 코어에서 격리된 VS Code 1.147.0과 확장 호스트 Node 24.22.1을 사용했다. 각 입력·시나리오에서 3쌍 예열 후 A/B 순서를 교대로 10쌍 측정했다. 실험의 30일 범위는 Asia/Seoul 기준 2026-10-23부터 2026-11-21까지다. 버전·소스와 빌드 해시, 원시 시간, 입력별 요청과 토큰 합계는 [빈 DB와 일별 집계 미구축 DB 표본](DashboardFirstPageAB-2026-11-21.json)에 있다. 로컬 로그는 수정 시각을 보존한 비공개 임시 사본으로 실행했다. 기존 DB 시나리오에서 사전 상태에 있던 검증용 세션에 110토큰짜리 요청 1건을 추가했다.

재실행 명령

```powershell
node tests/benchmarks/dashboard-first-page-ab.cjs --before=247e712 --output=tests/results/benchmarks/DashboardFirstPageAB-rerun.json
```

일별 집계가 준비된 DB만 다시 측정할 때는 `--scenario=warm`을 붙인다.
