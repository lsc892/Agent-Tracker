# 선택적 winner 맵 A/B 테스트

측정일은 2026-11-22(Asia/Seoul)이다. 사용자는 파싱 뒤 중복 가능 후보만 dictionary에 올리도록 변경하고 실제 절감량을 측정해 달라고 요청했다. 파일별 맵을 배열로 넘기고 최종 맵을 세션 단위로 제한하면 전체 재수집의 최종 집계 시간과 피크 힙이 줄어들 것으로 예상했다.

A는 변경 직전 `bd5364aeba1c4d1e2527c04862c31a9676a2f82f` 빌드다. B는 같은 리비전에 파일별 후보 배열, 선택적 세션별 최종 맵, 소비한 스냅샷 참조 해제를 적용한 작업 트리 빌드다. 양쪽의 소스·빌드·입력 해시는 원시 JSON에 기록했다.

## 2. 메모리와 맵 항목 수

피크 값은 표본마다 관측한 최대의 중앙값(MiB)이다. 힙은 통계 실행 스레드의 `heapUsed`, RSS는 파일 Worker와 SQLite 메모리도 포함하는 프로세스 값이다.

최종 맵 항목 수는 시간 표본과 분리한 각 빌드·입력의 빈 DB 수집 1회에서 세었다. `Winners.add` 호출이 맵 조회 1회다. 파일 병합 시작 시 남은 세션 맵 항목을 합산하고, 그 파일에서 새로 들어온 항목을 더해 동시 보유 최대값을 구했다. 단일 파일의 파싱 맵과 관계·요청 상태는 이 항목 수의 범위 밖이다.

## 3. 검증과 해석

- Windows x64, AMD Ryzen 5 7500F, Node 24.14.1, SQLite 3.51.2에서 빌드별 독립 프로세스와 최대 4개 파일 Worker를 사용했다. 입력·작업마다 준비 3쌍 뒤 순서를 교대해 20쌍을 측정했다. OS 파일 캐시는 유지했다. 갱신 타이머는 파일 탐색부터 SQLite 반영과 갱신 종료까지다. 사본 복원, 빈 DB 생성, 강제 GC, 정합성 검사는 타이머 밖이다. 힙·RSS는 5ms 간격과 진행 콜백에서 관측했다. 미리보기 없이 `refreshSummary`와 통계 조회 API를 직접 호출했다.
- 실제 데이터 사본은 688파일(압축 655개), 364.92MiB, 1,456요청, 3,004,594,870토큰이다. 1건 추가는 가장 큰 읽기 가능한 일반 Codex 메인 파일의 사본에 수행했다. 전체 재수집의 본문 읽기 382,650,470바이트와 1건 추가의 15,774,622바이트가 A/B에서 같았다. 합성 입력은 고정 산식으로 Claude·Codex를 절반씩 배정해 10개 프로젝트·최대 14일에 배치했다. 10,000요청은 100세션·세션당 100요청, 100요청은 10세션·세션당 10요청이다.
- 전체 207쌍에서 요청 수·토큰 합계와 요청·모델·도구·비용 행 해시가 일치했다. 합성 최초 합계는 생성기의 기대값과 같았고, 세 입력의 추가분은 모두 1요청·130토큰이었다. 변경 없음과 추가 결과의 일·월·세션·프로젝트 조회 1,104건을 정규화된 요청에서 독립적으로 계산해 건수·토큰·그룹별 평균을 대조했다. 평균은 완료 요청 기준이며 2020-01-01 UTC 이상, 2035-01-01 UTC 미만과 시각 미상 요청을 포함해 Asia/Seoul 기준으로 조회했다. 표본마다 사본 복원을 확인했고, 종료 후 로그 파일 해시를 다시 확인했다.
- **판정** — 실제 전체 재수집에서 최종 집계와 피크 힙은 각각 20쌍 모두 줄었다. 전체 재수집 시간은 B가 11쌍에서 빨랐고 범위가 겹쳤다. 실제 로그 읽기·파싱 단계 중앙값이 약 3.1초로, 최종 집계의 개선이 전체 시간에 미치는 폭은 작았다.
- **원인** — 실제 최종 맵의 조회 수가 44.47%, 동시 최대 항목이 93.46% 줄었다. 합성 세션은 파일 하나씩 구성되어 최종 맵을 생략했다. 10,000요청에서는 최종 집계가 18쌍에서 빨랐으나, 변경 파일 준비가 157.43 → 163.90ms로 늘고 피크 힙도 방향이 갈렸다. 맵 항목 수와 갱신 전체의 관측 피크에는 서로 다른 할당이 포함된다. [파일별 후보 전달](../../../../src/summary/aggregation/sourceWinners.ts) · [최종 맵 범위](../../../../src/summary/aggregation/memoryAggregate.ts)
- **적용 판단** — 실제 전체 수집의 집계·힙 절감은 확인했다. 1건 추가의 시간과 통계 조회는 표본 범위에서 일관된 개선을 확인하기 어려웠다. 실제 1건 추가의 피크 힙은 20쌍 중 17쌍에서 B가 같거나 높았다. 이때 시작 힙도 A 8.14MiB, B 9.04MiB였으므로 이번 계측만으로 증가분 전체를 winner 처리에 귀속할 수 없다.

## 재실행

같은 의존성으로 빌드한 A·B 루트를 지정한다. 이전 실험의 고정 입력이 있으면 `--workspace=<사본 폴더>`를 추가한다.

```powershell
node --no-warnings tests/benchmarks/mtime-refresh-ab.cjs --before="<A>" --after="<B>" --output="<새 JSON>" --repetitions=20 --rebuild=true
```
