# JSONL 긴 줄 연속 복사와 버퍼 재사용 A/B

외부 스트리밍 파서 실험에서 나타난 임시 바이트 버퍼 감소를 현재 필드 선택기와 조합할 수 있는지 확인했다. A는 `d4f8b76`의 수집기다. B는 제품에 유지한 `perf/reuse-jsonl-row-buffer`의 `e915791`이다. [라이브러리별 선행 비교](../../failure/2026-11-27/StreamingJsonLibrariesAB-2026-11-27.md)

## 외부 파서에서 관측한 비용

같은 실로그를 별도로 한 번씩 수집해 파일 Worker 4개의 실제 CPU 시간에 활성 CPU 표본의 함수별 비율을 적용했다. 아래 시간은 워커 합산 추정값이다.

| 구간 | `stream-json` | `@streamparser/json` |
| --- | ---: | ---: |
| 라이브러리 내부 | 10.48초 | 8.83초 |
| 토큰 전달과 후보 행 구성 코드 | 5.15초 | 2.49초 |
| 축소 행의 기존 필드 선택기 | 1.61초 | 2.00초 |

`stream-json`은 청크의 구조와 문자열 조각을 토큰으로 내보낸다. `@streamparser/json`은 토크나이저에서 문자열을 완성하고 별도의 `TokenParser`에서 문법 상태를 처리했다. 내부 CPU 시간 8.83초는 토크나이저 6.82초와 문법 파서 2.01초다. 두 실험 모두 라이브러리가 내보낸 토큰에서 후보 JSON을 구성하고 기존 선택기가 한 번 더 읽는다.

두 구현은 긴 줄을 다 모았다가 넘기던 바이트 복사를 제거했다. 별도 관측에서 각 스레드 최신 표본을 시점별로 모은 `arrayBuffers` 합계의 피크는 A 72.67 MiB, `stream-json` 35.09 MiB, `@streamparser/json` 40.21 MiB였다. 이 표본은 임시 바이트 버퍼의 감소를 보여준다. 프로세스 RSS 변화의 전체 원인은 V8 예약 힙, OS 작업 집합 및 네이티브 할당까지 포함하므로 이 값만으로 귀속할 수 없다.

## 재사용 후보

현재 파서는 64 KiB 청크가 올 때마다 따옴표·이스케이프 등을 확인하며 작은 구간을 버퍼 블록에 여러 번 복사한다. 여러 블록을 사용한 줄은 디코딩 직전에 다시 `Buffer.concat()`으로 합친다. B는 같은 스캔과 이미지 검증을 수행하고, 보존할 연속 구간마다 한 번씩 파일 리더의 버퍼에 복사한다. 처리한 줄은 그 버퍼에서 바로 디코딩해 기존 `projectJson()`에 전달한다. 기존 행 상한을 지키며 256 KiB를 넘게 성장한 버퍼는 해당 줄을 끝내면서 놓는다.

별도 실로그 1회 계측에서 파일 Worker 4개의 줄 조립 `Buffer.copy()` 호출 합계가 42,842,391회에서 38,127회로 줄었다. 기존 구현에서 14,499회 실행된 `Buffer.concat()`도 사라졌다. 버퍼를 키울 때 발생한 복사까지 포함한 누적 조립 바이트는 787,328,150바이트에서 526,336,799바이트로 33.1% 줄었다. 이 집계는 줄 조립에 해당하며 압축 입력 복사와 UTF-8 디코딩은 포함하지 않는다.

## 정합성

Skill 수집 켜짐·꺼짐 각각에서 실로그 237,821줄, 합성 30,100줄 및 310줄의 추출 속성·값과 행 오프셋이 일치했다. 120개 비교 쌍에서 대화·모델·Skill·이름·원본 상태와 일·월·세션·프로젝트 조회 결과가 일치했다. 합성 합계는 생성값과 같았고, 대화 한 건을 추가하면 각 입력에서 1대화와 130토큰이 증가했다. 평균과 조회 건수는 저장된 일별 행의 완료 대화와 토큰으로 별도 검산했다.

## 측정 조건과 재실행

- Windows x64, AMD Ryzen 5 7500F, Node 24.14.1, SQLite 3.51.2, Asia/Seoul, 파일 Worker 최대 4개, Skill 수집 켜짐. 실로그 751파일과 합성 10,000·100대화의 고정 입력을 사용했다. 시간과 메모리 표는 각 조건에서 20회 실행한 중앙값이다. 워커 지표는 각 실행에서 가장 높은 워커 값의 중앙값이다.
- 빈 DB의 최초 수집과 기준 DB 사본에 같은 대화 1건을 추가하는 시나리오에서 준비 3쌍 뒤 AB·BA 순서를 각각 10쌍 실행했다. OS 파일 캐시를 유지했다. 수집 시간에 파싱·SQLite 커밋·작업 종료가 들어가며, 데이터 준비와 검산은 타이머 밖이다.
