# 턴 누계 직접 검산과 일별 삭제 키 A/B

사용자가 선택한 두 후보를 `7a718a1`로 `dev`에 반영했다. 공통 기준 `540397d`와 각 후보를 개별 비교했다. 표는 A → B 중앙값이다. 시간은 ms, 힙·RSS는 MiB, SQLite 크기는 KiB다. 각 후보의 실로그·합성 두 규모 120쌍에서 저장값과 네 평균 조회가 일치했다. 병합 상태의 성능은 다시 측정하지 않았다.

## 1. 검산 항목에 응답 합계를 직접 누적

`92aaf93` 후보는 별도 `totals` 맵을 제거한다. 검산 항목을 한 번 조회해 해당 항목에 합계를 누적하고, 검산 항목이 없는 수집에서는 키 생성을 생략한다. 0토큰의 응답이 있었던 턴과 응답이 없던 턴을 구분한다.

### 어떤 합계를 줄였나

확정 응답을 처리할 때는 대화에 토큰·모델·결제 정보를 더한다. 이와 별도로 로그에 남은 **턴 누계와 대조**하기 위한 합계가 있다. 그 합계에는 입력·출력·캐시 읽기·캐시 쓰기 토큰이 들어간다.

| 단계 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 원본 등록 | `checks`에 제공자·세션·스레드·턴별 최신 검산 항목을 등록 | 같은 키와 순서로 등록하고 항목에 선택적 `sum`을 둠 |
| 확정 응답 반영 | 모든 응답을 대화에 반영하고 같은 턴 키의 `totals`에도 누적 | 모든 응답을 대화에 반영하고, `checks`에 해당 턴이 있을 때만 `sum`에 누적 |
| 최종 검산 | `checks`를 순회하면서 각 키로 `totals`를 다시 조회 | 각 검산 항목에 붙은 `sum`을 바로 읽음 |

지원하는 수집 흐름은 모든 파일과 검산 항목을 먼저 등록한 뒤 `finish()`에서 확정 응답을 반영한다. 이 순서라면 응답을 처리할 때 검산이 필요한 턴을 이미 알 수 있다. 같은 로그 사본의 앞선 계측에서 확정 응답 29,123개 중 8,687개는 연결된 검산 항목이 없었다. 합성 입력에서는 검산 항목이 없어 턴별 검산 키 생성·조회·누적을 모두 건너뛴다. [응답별 계측](../../../research/2026-11-27/SummaryReduction-2026-11-27.md)

### 결과를 보존하는 조건

- 같은 턴에 검산 항목이 여러 개 있으면 전체 이벤트 순서에서 가장 뒤의 항목을 사용한다. 응답 중복 판정과 winner 반영 순서도 기존 규칙을 따른다.
- 첫 확정 응답이 있는 시점에만 `sum`을 초기화한다. 0토큰 응답이 들어와도 `sum`이 생기고, 응답이 없으면 `sum`은 비어 있다. 이 차이는 누계로 토큰을 보정할 수 있는지 판정할 때 쓰인다.
- 로그 누계가 입력 150·출력 30이고 확정 응답 합계가 입력 120·출력 20이면 부족분은 입력 30·출력 10이다. 검증 근거가 있고 두 부족분이 0 이상이면 기존 규칙으로 대화에 보충한다. 일치하면 보정 없이 끝내고, 차이가 있으며 보정 조건을 충족하지 못하면 `token-total-mismatch`를 남긴다.

확정 응답 `N`개와 검산 항목 `C`개의 누적·검산은 해시 조회를 평균 상수 시간으로 보면 전후 `O(N+C)`다. 검산용 상태는 기존의 전체 고유 턴 `U`를 포함한 `O(C+U)`에서 `O(C)`로 줄어든다. 실로그에서 `finish()` 직전 힙은 44.65 → 44.71 MiB, 직후는 52.50 → 51.73 MiB였다. 전체 피크 RSS는 826.79 → 827.22 MiB, 새 DB는 996 → 996 KiB였다.

## 2. SQLite 삭제 대조에 일별 키만 전달

`60021e1` 후보는 대화의 현지 날짜를 한 번 계산해 제공자·모델 UPSERT에서 재사용한다. 이전 키와 비교해 삭제할 때는 각 일별 그룹의 키만 넘긴다. 소실 원본의 보존 범위, NULL과 빈 모델명의 구분, 트랜잭션 경계는 유지한다.

### 어떤 행을 삭제하나

SQLite는 영향을 받은 세션의 일별 합계를 갱신한다. 새로 계산한 행은 UPSERT하고, 교체 범위에서 새 집계에 없는 키는 `EXCEPT`로 찾아 삭제한다. 예를 들어 같은 세션의 기존 일별 키가 11월 26일과 27일이고 새 집계에 27일만 있으면, 일반 교체에서는 27일의 합계를 반영하고 26일 키를 삭제한다. 소실 원본을 보존하는 세션은 이번에 재집계한 날짜만 교체 범위에 넣으므로 이 예에서 26일 키가 남는다.

| 용도 | 변경 전 SQLite 입력 | 변경 후 SQLite 입력 |
| --- | --- | --- |
| 제공자·모델 UPSERT | 대화별 전체 값과 시작 시각. SQLite에서 현지 날짜를 계산 | 대화별 전체 값과 미리 계산한 현지 날짜 |
| 제공자 삭제 대조 | UPSERT와 같은 전체 JSON을 다시 바인딩하고 SQLite가 키만 읽음 | 중복 제거한 `[provider, session_id, project_key, local_day]` 배열 |
| 모델 삭제 대조 | 모델 UPSERT와 같은 전체 JSON을 다시 바인딩하고 SQLite가 키만 읽음 | 위 키에 원래 모델명을 붙인 배열. SQLite가 UPSERT와 같은 식으로 `model_key`를 계산 |

`dailyFacts()`는 제공자·세션·프로젝트·날짜가 같은 대화를 하나의 삭제 대조 키로 모은다. 모델은 그 키에 연결된 이름을 집합에 담는다. 날짜는 DB에 저장된 시간대로 계산하고 날짜 미상은 빈 문자열로 표현한다. 모델 키는 `NULL`일 때 `N`, 빈 문자열일 때 `V`, 이름이 있으면 `V`와 이름을 이은 값이다. UPSERT 값이 같은 행은 기존처럼 갱신을 생략한다. 삭제 대상 범위, Skill 저장, 커밋과 롤백 경계도 같은 경로를 따른다.
