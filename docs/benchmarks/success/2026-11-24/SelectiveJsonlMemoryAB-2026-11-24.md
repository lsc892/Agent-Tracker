# JSONL 선택 파싱의 최초 수집 메모리 비교

사용하지 않는 값을 만들지 않으면 최초 수집 메모리가 줄 것으로 예상했다. A는 JSONL 전체 행을 `JSON.parse`하는 `21ff22b`다. B는 같은 커밋에 작업 트리의 제공자·행 종류별 필드 선택을 적용한 빌드다. [선택 파싱 코드](../../../../src/summary/jsonl/projection.ts)

## 결과

실제 Claude·Codex 로그 700파일의 고정 사본을 사용했다. 총 410,184,912바이트이며 668파일이 압축 로그다. Windows x64, Node 24.14.1, SQLite 3.51.2에서 파일 Worker 최대 4개와 기본 도구 통계 설정으로 실행했다. 각 수집은 새 Node 프로세스와 빈 SQLite DB에서 시작했다. 예열 3쌍을 제외하고 A→B와 B→A를 번갈아 10쌍 측정했다. 운영체제 파일 캐시는 비우지 않았다.

| 항목 | A 중앙값 | B 중앙값 | B − A |
| --- | ---: | ---: | ---: |
| 전체 프로세스 피크 RSS | 500.84 MiB | 878.03 MiB | +377.19 MiB (+75.3%) |
| 메인 스레드 피크 V8 사용 힙 | 71.86 MiB | 69.72 MiB | −2.14 MiB (−3.0%) |
| 수집 종료·강제 GC 후 프로세스 RSS | 413.78 MiB | 639.28 MiB | +225.50 MiB (+54.5%) |
| 최초 수집 및 저장 시간 | 3,319.06 ms | 3,649.11 ms | +330.05 ms (+9.9%) |
| 변경 원본 준비 시간 | 2,860.59 ms | 3,183.23 ms | +322.64 ms (+11.3%) |

RSS는 모든 Worker와 네이티브 메모리를 포함한 Node 프로세스 값이다. 5ms 간격과 수집 진행 시점에 표본을 얻었다. V8 사용 힙 표본은 메인 스레드 값이다. B의 관측 피크 RSS는 10쌍 모두 A보다 높았다. 관측 범위는 A 481.14~517.32 MiB, B 845.91~892.07 MiB였다. [원시 표본·환경·빌드 해시](SelectiveJsonlMemoryAB-2026-11-24.json)

## 파일 Worker 관측

본 측정과 분리해 `--trace-gc-nvp`로 빌드별 한 번 수집했다. 각 파일 Worker의 GC 전후 `memory_size` 최댓값은 A에서 74.5~76.1 MiB, B에서 145.1~150.3 MiB였다. 각 Worker에서 서로 다른 시점에 관측한 범위다. 이 관측은 선택 파싱 경로의 Worker V8 메모리 증가를 보여 준다. RSS 증가분 전체를 설명하는 할당 지점과 장시간 메모리 누수 여부는 확인 범위 밖이다.

## 정합성과 재실행

모든 수집에서 요청 1,540건, 토큰 3,165,991,387개, `applied_response` 24,443행 및 요청·모델·도구·비용 해시가 일치했다. 일·월·세션·프로젝트별 평균 조회는 독립 집계와 대조했다. SQLite 무결성과 외래 키, 사본의 입력 해시를 확인했다.

```powershell
node --no-warnings tests/benchmarks/mtime-refresh-ab.cjs '--before=<A 빌드 루트>' '--after=<B 빌드 루트>' '--output=<새 JSON>' --datasets=current --scenarios=initial --repetitions=1 --warmups=0
```

첫 실행이 출력한 폴더를 `--workspace=<사본 폴더>`로 전달하면 이후 표본에서 같은 입력을 쓴다. 매 쌍의 `--before`와 `--after`를 교대하고, 출력 경로는 표본마다 지정한다. Worker 진단은 같은 실행기의 자식 프로세스에 `--trace-gc-nvp`를 추가한 별도 표본이다.
