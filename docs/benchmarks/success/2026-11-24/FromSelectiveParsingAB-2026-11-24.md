## 사용 케이스별 갱신 시간

A → B 중앙값은 ms다. 개선율은 `(A − B) / A × 100`이며 `n/20`은 B가 더 빨랐던 측정 쌍 수다.

| 사용 케이스 | 실데이터 1,473건 | 합성 10,000건 | 합성 100건 |
| --- | ---: | ---: | ---: |
| 무변경 갱신 | 112.46 → 110.04 (+2.15%, 16/20) | 13.18 → 11.81 (+10.38%, 18/20) | 3.61 → 3.13 (+13.31%, 20/20) |
| 요청 1건 추가 | 122.65 → 117.47 (+4.22%, 18/20) | 18.18 → 18.19 (-0.05%, 7/20) | 5.69 → 5.49 (+3.52%, 13/20) |
| 전체 재수집 | 2,858.99 → 2,933.44 (-2.60%, 5/20) | 461.74 → 519.66 (-12.54%, 0/20) | 15.63 → 14.94 (+4.39%, 15/20) |
| 기존 응답 토큰 갱신 | 125.63 → 123.85 (+1.42%, 14/20) | 미측정 | 미측정 |
| 본문 동일·수정 시각 변경 | 122.65 → 123.22 (-0.46%, 7/20) | 미측정 | 미측정 |

실데이터에서 무변경과 1건 추가는 각각 2.15%, 4.22% 빨랐고 전체 재수집은 2.60% 느렸다. 1만 건은 1건 추가가 0.01 ms 차이였고, 전체 재수집은 20쌍 모두 느렸다. 100건에서는 세 케이스 모두 중앙값이 낮았고 차이는 0.20~0.69 ms였다.

무변경 갱신은 세 입력 모두 두 빌드에서 JSONL 본문을 읽지 않았다. 1건을 추가하면 각각 4,259,877바이트, 66,945바이트, 7,170바이트의 파일 한 개를 두 빌드가 똑같이 읽었다. 실데이터 1건 추가의 파일 읽기·파싱은 16.18 → 14.19 ms, 최종 집계는 0.306 → 0.252 ms, 저장 단계 전체는 2.03 → 2.40 ms였다.

기존 응답 갱신은 같은 응답 키의 토큰이 130개 늘어난 이벤트를 파일 끝에 추가했다. 요청 수는 1,473건으로 유지됐고, 두 빌드가 각각 4,259,789바이트를 읽고 요청 합계를 한 번 썼다. 파일 읽기·파싱은 17.16 → 14.89 ms, 저장 단계는 2.04 → 2.54 ms였다. 본문은 같고 수정 시각만 바꾼 경우에는 양쪽 모두 4,259,275바이트를 읽었다. A는 SHA-256 일치 확인 뒤 재집계와 파일 갱신을 건너뛰었다. B는 세션을 재집계하고 파일 수정 시각을 저장했다. 두 빌드 모두 요청 합계 쓰기는 0회였다. 이 두 케이스는 실제 로그에서의 동작을 확인하기 위해 실데이터로 측정했다.

## 시간·공간복잡도

`F`는 디렉터리 항목과 저장된 파일 행의 수, `B`는 디스크에서 읽은 바이트 수, `Z`는 압축 해제 후 JSONL 바이트 수, `W_s`는 영향받은 세션 `s`의 파일별 winner 후보 수다. `W = Σ W_s`, `P`는 영향 세션에서 이미 저장한 응답별 반영값의 수, `U`는 새로 선택한 서로 다른 응답의 수, `R`은 해당 세션에서 비교할 요청 수다. `Q`는 조회 SQL이 범위 안에서 읽는 요청 또는 일별 집계 행 수, `G`는 결과 그룹 수다. ID 길이와 고정 Worker 수는 상수로 보고 SQLite 인덱스와 관계 탐색 비용은 별도로 본다.

| 사용 케이스 | A | B |
| --- | --- | --- |
| 무변경 갱신 | 파일 발견과 목록에 시간·공간 `O(F)`. 안정 상태에서는 본문을 읽지 않는다. Windows에서 직전 스캔 시작 시각의 8ms 여유 구간과 겹치면 다시 읽을 수 있다. | 파일 발견과 목록에 시간·공간 `O(F)`. 안정 상태에서는 같은 경로의 저장된 수정 시각을 비교해 본문 읽기를 생략한다. |
| 전체 재수집 | 파일 탐색·입력 읽기·winner 비교의 기대 시간 `O(F + B + Z + W)`. 최종 winner Map은 `O(U)` 공간을 차지한다. | 같은 탐색·읽기에 최종 winner 비교 최악 `O(Σ W_s log(1+W_s))`가 든다. 해당 비교의 임시 공간은 `O(max W_s)`이며, 최종 반영 목록은 `O(U)`다. |
| 요청 1건 추가·기존 응답 토큰 갱신 | `O(F)` 탐색 뒤 영향 파일 전체를 읽고 해당 세션의 후보를 병합한다. 바뀐 요청당 INSERT 또는 UPDATE 한 번으로 저장한다. | 탐색·영향 파일 전체 읽기를 유지한다. 세션별 정렬 후 반영값과 합계를 대조하는 JS 작업이 기대 `O(P + U + R)` 추가된다. 바뀐 요청당 최종 합계로 UPSERT 한 번을 실행하고 응답 반영값도 같이 쓴다. |
| 본문 동일·수정 시각 변경 | 파일 전체를 읽고 해시를 비교한다. 본문이 동일하면 최종 winner 병합과 저장이 생략된다. | 파일 전체 읽기에 영향 세션의 winner 병합과 응답별 반영값 비교가 추가된다. 파일 수정 시각을 갱신한다. |
| 일별·월별·세션별·프로젝트별 평균 조회 | 조회 범위의 `Q`행을 그룹화하고 `G`개 결과를 정렬한다. SQLite가 두 정렬에 임시 B-tree를 쓰는 경우 페이지 요청당 시간 상한은 `O(Q log(1+Q) + G log(1+G))`, 임시 공간 상한은 `O(Q + G)`다. | 두 빌드의 조회 SQL과 rollup 구현이 같다. 인덱스·필터 조건에 따라 같은 비용을 적용한다. |

- 파일별 Map 조회는 평균 상수 시간이다. A의 파일 해시는 읽은 바이트를 함께 처리하므로 파싱 시간의 선형 차수를 바꾸지 않는다. A가 파일 이동을 확인할 때는 이전 범위에 대한 추가 읽기가 생길 수 있다. 큰 압축 파일의 파싱 비용에는 Zstd를 풀어 나온 입력도 들어간다. [파일 발견](../../../../src/summary/scanner/refresh/discovery.ts) · [파일 읽기](../../../../src/summary/scanner/sourceReader.ts)
- 두 방식 모두 파일별 후보와 관계·진단 근거, 요청·모델·도구 상태를 수집한다. 전체 보조 공간은 이렇게 유지하는 후보·근거·결과의 양에 선형이다. 파일 Worker 한 개의 JSONL 파싱에는 64KiB 입력 청크와 버퍼에 남긴 최대 행 크기 `L`에 비례하는 `O(L)` 공간이 든다. 압축 입력은 별도의 스트리밍 디코더 상태를 사용한다. ## 측정과 정합성 검증

- Windows x64, Ryzen 5 7500F, Node 24.14.1, V8 13.6, SQLite 3.51.2에서 빌드마다 별도 프로세스와 DB를 사용했다. 파일 Worker는 4개다. 입력·케이스별로 준비 3쌍 후 AB·BA 각 10쌍을 교대해 측정했다. 메모리는 5ms 간격과 갱신 진행 지점에서 샘플링했다.
- 실데이터는 Claude·Codex 로그 689개, 372,649,102바이트, 1,473요청과 3,021,943,042토큰의 고정 사본이다. 합성 10,000건은 100파일, 5,637,210바이트, 6,340,000토큰이고 100건은 10파일, 55,700바이트, 18,400토큰이다. 같은 Codex 일반 파일에 두 빌드 모두 602바이트를 추가해 새 요청 1건과 토큰 130개를 만들었다. 합성 100건의 첫 시도에서는 빠른 추가·복원으로 수정 시각이 구분되지 않은 표본이 발생했다.
