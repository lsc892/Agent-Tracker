# 파일별 winner와 요청당 한 번의 UPSERT A/B

2026-11-24, Asia/Seoul. 파일 안에서 반복 응답을 줄이고 최종 집계를 세션 단위로 처리하면, 같은 원본 전체를 다시 읽어도 최종 집계 시간과 관측 힙이 줄 것으로 예상했다.

- A는 직전 검증의 전역 winner Map 빌드다. [이전 A/B의 B 빌드](../../failure/2026-11-24/SingleWinnerMapAB-2026-11-24.md)
- B는 파일을 읽으며 winner를 고르고 세션별 정렬로 최종 키를 병합한다. 쓰기 트랜잭션에서 이전 값을 읽고 최종 합계를 변경 요청당 한 번 UPSERT한다. [집계 코드](../../../../src/summary/aggregation/memoryAggregate.ts) · [저장 코드](../../../../src/summary/db/memoryStore/index.ts)

전체 재수집은 세 쌍 모두 빨랐고, 최종 집계와 관측 피크 힙도 세 쌍 모두 줄었다. B는 파일에서 반복 후보를 줄이고 한 세션씩 비교 결과를 합산한다. 두 방식이 읽은 파일 수와 바이트는 같았다. 통계 Worker의 관측 힙은 줄었고 네이티브 할당과 파일 Worker를 포함한 프로세스 피크 RSS는 늘었다. 1건 추가 전체 시간은 중앙값 차이가 3.76ms였으며 세 쌍 중 두 쌍에서 B가 빨랐다. 1건 추가에서 요청 facts 쓰기는 A/B 모두 표본당 1회였다. 조회 시간과 1건 추가의 전체 개선 여부는 세 표본의 변동 범위에서 판단을 유보한다.

## 조건과 정합성

- 같은 로컬 사본 689파일·372,649,102바이트·1,473요청을 재사용했다. Windows x64, AMD Ryzen 5 7500F, Node 24.14.1, SQLite 3.51.2, 최대 4개 파일 Worker로 시나리오마다 AB → BA → AB를 한 번씩 실행했다. 사전 DB 구축, 입력 복원, 독립 검증은 타이밍 밖에서 수행했다. 합성 데이터, 별도 예열, 기존 v21 DB를 v22로 처음 여는 비용은 이번 측정 범위 밖이다.
- 9쌍 모두 요청·모델·도구·비용 행의 해시가 일치했다. 추가 후 요청은 1,474건, 토큰은 3,021,943,172개로 매번 +1요청·+130토큰이었다. 조회는 2020-01-01 UTC 이상 2035-01-01 UTC 미만, 시각 미상 포함, Asia/Seoul 기준으로 완료 요청을 평균 분모에 포함했다. 네 종류의 조회를 전 페이지에 걸쳐 독립 JS 집계와 대조했다.
- 기준 상태로 복원한 두 DB를 별도 SQL로 검증했다. 응답별 반영값 23,769행의 해시가 일치했고, 논리 응답 키 중복과 토큰 합계 불일치는 0건이었다. 측정 뒤 입력 파일 SHA-256도 일치했다. [원시 표본과 빌드 식별자](FileWinnerUpsertAB-2026-11-24.json)
