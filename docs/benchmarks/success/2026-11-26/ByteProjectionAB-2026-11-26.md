# JSONL 고정 필드 바이트 선택 A/B

사용자는 로그 줄 전체를 문자열로 만들던 경로에서 집계에 필요한 값만 문자열화해 달라고 요청했다. A는 `310442a`다. B는 짧은 줄과 청크 경계·이미지 줄이 같은 바이트 선택기를 사용한다. 선택기는 버리는 값도 JSON 문법을 검사하며 필드 조회에 필요한 후보 키와 축소 행을 디코딩한다. 이미지는 버리는 본문도 바이트로 검사한다. [변경 전 힙 진단](../../../research/2026-11-26/SummaryHeapProfile-2026-11-26.md)

별도 계측에서 실로그 파일 Worker 피크 힙은 **21.34 → 15.54 MiB(−27.2%)**였다. 각 실행에서 네 Worker 중 가장 높았던 값의 3쌍 중앙값이다. 전체 범위는 A 21.30–21.44 MiB, B 15.17–19.30 MiB였다. V8의 16 KiB 간격 할당 프로파일을 한 쌍 수집했을 때, 파일 Worker 네 개의 누적 할당 추정치는 **2,357.49 → 1,130.29 MiB(−52.1%)**였다. 회수한 객체를 포함한 추정치다. `parseChunk`의 문자열 생성과 기존 고정 필드 조각 배열이 줄었으며, 새 바이트 선택기의 상태와 선택 행 디코딩에서도 할당은 발생한다. 함수별 귀속은 구현 사이에 이동하므로 총량을 비교했다. [Worker 프로파일 원시 표본](ByteProjectionHeapAB-2026-11-26.json)

최초 수집의 파일 Worker 힙과 RSS 절감이 확인됐다. 전체 갱신 시간과 1건 추가 RSS에는 비용이 있었다. 사용자 요청에 따라 바이트 선택 경로를 적용했다.

## 2. 정확성과 측정 방법

- Windows x64·AMD Ryzen 5 7500F·Node 24.14.1·SQLite 3.51.2에서 진행했다. 실로그 733파일·466,960,401바이트(압축 668파일)와 Claude·Codex를 절반씩 넣은 합성 10,000·100응답을 같은 고정 사본에서 비교했다. 시간대는 Asia/Seoul이며 조회는 미상 일자를 포함한 전체 기간이다. 평균의 분모는 완료 스레드다.
- 입력·조건마다 새 프로세스에서 준비 3쌍 뒤 AB·BA 10쌍씩을 실행했다. 최초 수집은 빈 SQLite, 1건 추가는 동일 기준 DB의 사본에서 출발했다. OS 파일 캐시는 유지했다. 파싱·SQLite 갱신과 Worker 종료까지 측정하고, DB 사본 복원과 검산은 타이머 밖에서 했다.
- 두 파서의 선택 행과 원본 바이트 오프셋 해시는 실로그 227,584행, 합성 30,100행과 310행에서 일치했다. 120쌍에서 제공자별 입력·출력 토큰, 최종 저장 행, 일·월·세션·프로젝트 조회 해시가 일치했다. 독립 JSONL 검산과 SQLite 무결성·외래 키 검사를 통과했고, 1건 추가는 각 입력에서 130토큰 증가했다. [전체 갱신 원시 표본](ByteProjectionAB-2026-11-26.json)
- Worker 피크와 누적 할당은 같은 빌드·실로그로 공개 통계 클라이언트를 실행해 별도로 수집했다. VS Code 렌더러·실계정 quota·일반 자동 테스트는 실행하지 않았다. 타입 검사·린트·diff 검사를 통과했다.
- 측정 뒤 리더의 선택기 참조와 콜백, 선택기의 루트 상태를 정리했다. 표와 원시 자료는 계측 당시의 빌드를 식별한다. 후속 정리는 타입 검사·린트·diff로 확인했다.

