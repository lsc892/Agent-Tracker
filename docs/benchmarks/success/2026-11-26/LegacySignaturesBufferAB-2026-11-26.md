## 2. 분석

초기 구현에서 서명 데이터는 힙 밖으로 옮겼지만 `Buffer.compare`를 호출하는 경로의 임시 할당이 별도 할당 표본에서 약 2 MiB였다. 최종 구현은 바이트를 직접 대조하고 누계 갱신을 네 필드에 직접 써서 임시 할당을 줄인다. 실로그의 집계 종료 시점 힙은 24.59 → 23.43 MiB였다. 구형 Codex 서명이 들어간 최초 수집의 힙과 최종 집계 시간 개선을 근거로 적용했다. 프로세스 RSS의 중앙값 상승과 큰 표본 변동이 있었다.

공개 통계 클라이언트로 별도 계측했다. 집계 직전 강제 GC를 한 한 쌍에서 수집 스레드 힙은 25.02 → 20.96 MiB였고, B의 서명·인덱스 버퍼는 3.83 MiB였다. V8의 16 KiB 간격 할당 표본 한 쌍에서 `legacyIncrease`에 귀속된 누적 할당 추정은 3.00 → 0.33 MiB였다. 경량 계측 세 쌍에서 수집 Worker의 최초 갱신 피크 중앙값은 31.43 → 29.75 MiB였고, 실행마다 가장 높게 관측된 파일 Worker의 피크 중앙값은 19.60 → 21.71 MiB였다. 파일 Worker는 파일 준비를 마칠 때 문자열을 버퍼로 변환한다. ## 3. 측정 조건 및 검증

- Windows x64·AMD Ryzen 5 7500F·Node 24.14.1·SQLite 3.51.2에서 실로그 733파일·466,960,401바이트와 고정 합성 10,000·100응답을 사용했다. 합성 입력은 Claude·Codex가 절반씩이고 스레드당 50·5응답을 저장 프로젝트 두 개에 나눴다. 합성 입력에는 구형 Codex 누계가 없다. 조회는 Asia/Seoul 기준 전체 기간과 미상 일자를 포함하며 평균의 분모는 완료 스레드다.
- 각 조건에서 준비 3쌍과 AB·BA 10쌍씩을 실행했다. 실행마다 새 프로세스에서 최초 수집은 빈 DB로 시작하고 1건 추가는 같은 기준 DB 사본을 복원했다. OS 파일 캐시는 유지했다. 갱신에는 파싱·SQLite 반영과 Worker 종료가 포함되며 사본 준비와 검산은 타이머 밖에서 수행했다. 수집 스레드의 힙은 5 ms 간격과 진행·집계 경계에서 표본을 수집했다. RSS는 SQLite와 파일 Worker를 포함하는 프로세스 전체다.
- 120쌍에서 제공자별 토큰과 8개 SQLite 테이블의 행 해시, 일·월·세션·프로젝트 조회 결과가 일치했다. 독립 JSONL 검산은 실로그에서 복사 누계 4,711행을 확인했으며, 1건 추가는 세 규모에서 각각 입력 123·출력 7토큰 증가로 맞았다. SQLite 무결성·외래 키 검사, 타입 검사, 린트를 통과했다. 일반 자동 테스트는 실행하지 않았고 VS Code 화면과 실계정 quota는 미측정이다. [전체 갱신 원시 표본](LegacySignaturesBufferAB-2026-11-26.json)
- 측정 후 빈 구형 누계 상태와 중간 토큰 객체 생성을 제거했다. 표와 원시 자료는 계측 당시의 빌드를 식별한다. 후속 정리는 타입 검사·린트·diff로 확인했다.
