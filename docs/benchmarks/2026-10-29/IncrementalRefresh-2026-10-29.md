# 증분 저장 전후: 실제 로그의 워크트리 집계 비교

측정: 2026-10-29 16:30:08 ~ 2026-10-29 16:34:07, Asia/Seoul.

## 판단

**현재 실제 데이터에서는 증분 저장에 따른 일관된 전체 속도 개선을 확인하지 못했다.** 같은 원본을 전체 재파싱하는 경우 전체 중앙값은 14.177→14.097초(-0.6%), 실제 저장 구간은 1.215→1.155초(-5.0%)였다. Codex·Claude 요청 1건 추가의 전체 시간은 각각 0.6%·3.6% 줄었으나 빠른 쌍은 1/3·2/3이었다. 저장 구간 자체는 오히려 10.6%·13.6% 늘었다. 추가 응답으로 기존 요청을 갱신할 때는 저장 구간이 16.9% 줄었지만 전체 시간은 0.5% 늘었다.

변경 없는 갱신은 두 버전 모두 manifest 재사용으로 본문 읽기·집계 준비·요청 교체가 0이다. 이 경우 관측된 9.6% 증가를 증분 저장 작업 자체의 비용으로 귀속하지 않는다. 최초 갱신 역시 전체 시간은 1.6% 줄었지만 저장 구간은 11.8% 늘어 전체 차이를 기능의 이득으로 단정하지 않는다.

이번 결과는 기존 합성 10만 건의 SQL 저장 벤치마크를 대체하거나 반박하는 수치가 아니다. 현재 실데이터는 요청 1,167건이며, 추가 대상으로 선택된 기존 세션은 Codex 25건·Claude 2건이다. 원본 파싱·파일 metadata 확인·집계 준비가 남는 제품 전체 경로를 측정했으며, 이 데이터의 요청 추가에서는 DB 저장이 전체의 약 2~3%였다. 저장 단계의 최적화가 전체 체감 속도로 이어지는지는 데이터 밀도와 갱신 형태에 따라 달라진다.

- 순차 실행 3쌍, AB/BA 순서 교대. 워밍업 1쌍 제외. 각 프로세스는 새 DB에서 여섯 시나리오를 순서대로 수행한다. OS 파일 캐시는 비우지 않았다.

## WAL 파일과 읽기량

단계 직전 `wal_checkpoint(TRUNCATE)` 이후 단계 종료 시 WAL 파일 길이의 중앙값이다. 디스크 총 쓰기량이나 누적 WAL frame 수를 측정한 값은 아니다. 자동 checkpoint·페이지 재사용의 영향이 있으므로 영구 DB 용량 변화로도 해석하지 않는다.

## 정확성

모든 전후 및 반복 표본에서 요청·모델·Skill·비용·이름·파일 진단의 의미 해시와 전체/프로젝트/세션/일/월 집계 해시를 비교했다. 정식 6개 프로세스 × 6개 상태에서 제공자·모델 × 5개 그룹의 raw SQL 대조를 총 360회 수행했고 FK 및 integrity 검사를 통과했다. 물리 ID·요청 갱신 시각·집계 최종 갱신 시각은 구현 의도에 따라 달라져 해시에서 제외한다. 비정수 비교만 유효숫자 10자리로 정규화하며 저장 값은 변경하지 않는다.

원본 snapshot SHA-256은 모든 실행 종료 후 다시 확인했다. 개인 본문·제목·세션 ID·경로는 보고서에 저장하지 않는다. 실패한 원본 파일은 양쪽의 동일한 오류 수·진단 해시로 비교하며 오류 수는 JSON에 남긴다. UI·IPC·quota 조회는 측정하지 않았다. RSS는 검증 이후 프로세스 관측값으로 SQLite만의 메모리나 고정 상한이 아니다.

## 재실행

`node tests/benchmarks/incremental-refresh.cjs --before=<빌드된 이전 워크트리> --after=<빌드된 이후 워크트리> --real --pairs=3 --warmups=1 --report=<새 Markdown 경로>`

--real을 생략하면 작은 Claude·압축 Codex fixture로 검증한다. 기존 보고서를 덮어쓰지 않으며 원본 사본과 실험 DB는 종료 후 삭제한다.

이번 실행의 두 빌드 워크트리는 `tests/.cache/incremental-worktrees-20261029/before`, `tests/.cache/incremental-worktrees-20261029/after`에 남겼다. 제품 코드·스키마·인덱스·설치된 VS Code 확장은 변경하지 않았다. 재현 실행기와 결과 문서만 추가했으며, 현재 작업 트리의 다른 SQL 리팩토링은 비교 대상에 섞지 않았다.
