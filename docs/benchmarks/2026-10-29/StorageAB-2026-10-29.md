# 저장·조회 방식의 시간–공간 트레이드오프

측정: 2026-10-29 · 정리: 2026-10-30, Asia/Seoul.

후속 실제 제품 적용 결과는 [2026-10-31 단계별 증감률](../2026-10-31/StorageProduct-2026-10-31.md)에 있다. 아래 시제품 결과와 구분해, 기존 일괄 저장 제품 대비 월 PK·세션 조회 보완·선택적 묶음 저장을 같은 입력으로 비교했다.

갱신 트랜잭션 단축을 기준으로 한 현재 결정은 [쓰기 트랜잭션 직접 비교](../2026-10-31/StorageTransactions-2026-10-31.md)를 따른다. 집계 월 PK는 철회하고 세션 PK에서 큰 세션의 선택적 묶음 비교를 적용했다.

**어떤 케이스에서 시간을 줄이는 대신 무엇을 더 사용하는지** 주제별로 정리했다. 각 소제목 아래에서 같은 케이스의 시간·공간 비용과 판단을 함께 비교한다. 시간은 각 행의 비교 기준 대비 실측 증감률이다. 공간은 **DB 저장량·임시 WAL·메모리/캐시를 구분**했다. `O(...)`는 코드에서 확인되는 저장량·남는 처리량을 설명하며, 시간 측정만으로 복잡도 차수가 개선됐다고 판정하지 않는다.

## 1. 날짜·월 클러스터링: 조회 범위에 따라 달라지는 이득

월 PK는 읽기 시간을 줄이는 대신 공간과 일부 갱신 비용을 늘렸다. 날짜 PK는 좁은 기간 조회에서 이득이 있었지만 전체 기간 조회에서는 크게 느려졌다.

| 케이스·비교 기준 | 시간 트레이드오프 | 공간 트레이드오프 | 판단 |
| --- | --- | --- | --- |
| **월 클러스터링 · 한 달 조회**<br>총 10만 건·세션당 100건, 기존 세션 PK 대비 | 제공자 조회 **68.4% 단축**, 모델 조회 **52.6% 단축**.<br>반면 요청 한 건 저장은 **3.3% 증가**. | 집계 DB **7.0% 증가**: 59.887→64.074 MiB.<br>저장량 차수는 `O(D)` 유지. | 기간 조회 시간을 줄이는 대신 저장 공간과 일부 갱신 비용을 더 쓴다. |
| **월 클러스터링 · 모든 달 조회**<br>총 10만 건·세션당 100건, 기존 세션 PK 대비 | 제공자 조회 **59.6% 단축**, 모델 조회는 **9.2% 단축**. | 위와 같은 월 PK이므로 집계 DB **7.0% 증가**. | 월별 제공자 집계에는 이득이 크지만 모델 집계에는 이득이 작다. 같은 공간을 쓰더라도 조회 종류에 따라 가치가 달라진다. |
| **월 클러스터링 · 집계 행이 적은 경우**<br>총 10만 건·세션당 10,000건, 모든 달 모델 조회 | **3.0% 단축**, 절약 시간은 약 **0.069 ms**. | 집계 DB **8.4% 증가**: 0.699→0.758 MiB.<br>`O(D)` 유지. | 이미 집계 행이 1,980개뿐인 조건이다. 읽기만 보면 공간 증가에 비해 절대 이득이 작다. |
| **날짜 클러스터링 · 좁은 기간과 전체 기간**<br>총 10만 건·세션당 100건, 기존 세션 PK 대비 | 한 달 조회는 제공자 **30.5%**, 모델 **41.6% 단축**.<br>모든 달 조회는 제공자 **189.5%**, 모델 **265.3% 증가**. | 집계 DB **1.6% 증가**.<br>`O(D)` 유지. | 좁은 기간 조회의 이득과 전체 기간 조회의 큰 회귀를 교환한다. 이번 SQL·실행 계획에서는 일괄 대체하기 어렵다. |

## 2. 월 컬럼·보조 인덱스: 저장 공간을 더 쓸 가치가 있는가

월 컬럼을 저장하는 것만으로는 탐색이 빨라지지 않았다. 월 PK에 세션 인덱스를 더하는 방식도 추가 공간·쓰기 비용에 비해 읽기 이득이 작았다.

| 케이스·비교 기준 | 시간 트레이드오프 | 공간 트레이드오프 | 판단 |
| --- | --- | --- | --- |
| **월 컬럼만 저장하고 월 조건으로 조회**<br>세션 PK 유지, 총 10만 건·세션당 100건 | 한 달 조회가 제공자 **821.2%**, 모델 **671.7% 증가**. | 집계 DB **3.0% 증가**.<br>`O(D)` 유지. | 월 선두 탐색 경로가 없어 전체 SCAN한다. 공간만 늘리고 기간 탐색도 느려지는 조합이다. |
| **월 PK에 세션 보조 인덱스 추가**<br>총 10만 건·세션당 100건, 인덱스 없는 월 PK 대비 | 한 달 제공자 조회는 약 **0.087 ms 단축**.<br>요청 한 건 저장은 **6.0% 증가**. | 집계 DB **20.7% 추가 증가**: 64.074→77.324 MiB.<br>`O(D)`의 상수 비용 증가. | 작은 읽기 이득을 위해 인덱스 공간·유지 비용을 더 쓴다. 이번 측정으로 필수 인덱스라고 볼 근거는 부족하다. |

## 3. SQL 묶음 비교: 큰 세션의 소수 변경과 전건 변경

TEMP에 입력 전체를 모으는 비용은 공통으로 든다. 큰 세션에서 일부 요청만 바뀔 때는 그 비용을 회수했지만, 작은 세션이나 모든 행을 쓰는 경우에는 불리했다.

| 케이스·비교 기준 | 시간 트레이드오프 | 공간 트레이드오프 | 판단 |
| --- | --- | --- | --- |
| **SQL 묶음 비교 · 작은 세션에 한 건 추가**<br>세션당 10·25·100건, 요청별 증분 비교 대비 | 각각 **30.8%·27.0%·12.5% 증가**. | 요청·모델·Skill을 한꺼번에 담는 TEMP **`O(N+M)` 추가**.<br>TEMP 실제 바이트·메모리 피크는 미측정. | 작은 입력에서는 묶음 준비 비용이 절감 효과보다 크다. 입력 전체 비교도 남는다. |
| **SQL 묶음 비교 · 큰 세션의 소수 변경**<br>10,000건에 한 건 추가 | 요청별 증분 비교보다 **18.5% 단축**.<br>일괄 교체보다 **39.2% 단축**. | TEMP **`O(N+M)` 추가**.<br>WAL은 요청별 증분과 같은 **466.75 KiB**, 일괄 교체 대비 **88.4% 감소**. | 임시 공간을 더 써서 반복 비교 호출을 줄인다. 기존 증분 대비 WAL 이득은 없고, 일괄 교체 대비로는 쓰기 저널도 줄인다. |
| **SQL 묶음 비교 · 최초 저장/전건 변경**<br>10,000건, 일괄 교체 대비 | 최초 저장 **44.0% 증가**.<br>전건 제목·모델·Skill 변경 **43.3% 증가**. | TEMP **`O(N+M)` 추가**.<br>WAL은 최초 저장에서 같고, 전건 변경에서 **1.6% 증가**. | 결국 모든 행을 쓰면서 비교 비용까지 부담한다. 이 케이스에서는 일괄 교체가 유리했다. |

## 4. 작은 세션·혼합 경로: 크기만으로 선택하면 놓치는 비용

100건 이하에서 일괄 교체를 선택하는 규칙은 같은 데이터를 재저장할 때 유리하지 않았다. 세션 크기와 함께 최초 저장 여부·변경 비율도 판단에 필요하다.

| 케이스·비교 기준 | 시간 트레이드오프 | 공간 트레이드오프 | 판단 |
| --- | --- | --- | --- |
| **100건 기준 혼합 · 100건 그대로 재저장**<br>100건 이하는 일괄 교체를 선택 | 요청별 증분 비교보다 **64.1%**, 묶음 비교보다 **75.6% 증가**. | 선택한 일괄 교체 경로의 공간 비용을 따른다.<br>큰 입력에서는 묶음 경로의 TEMP 비용을 따른다. | 크기만으로 경로를 고르면 재저장 성격과 맞지 않을 수 있다. 최초 저장 여부·변경 비율도 고려해야 한다. |

## 5. 파싱 재사용: 추가형 파일과 재작성 파일

이벤트 캐시를 유지하면 반복 파싱은 줄지만, 전체 파일 검증과 기존 이벤트 재적재는 남는다. 파일을 재작성해 캐시를 재사용할 수 없으면 검증 비용 뒤에 전체 파싱 비용도 든다.

| 케이스·비교 기준 | 시간 트레이드오프 | 공간 트레이드오프 | 판단 |
| --- | --- | --- | --- |
| **파싱 재사용 · 파일에 새 요청 추가**<br>10,000건, 전체 재파싱 대비 | 파싱은 Codex **78.4%**, Claude **84.3% 단축**.<br>이벤트 재적재·집계까지 포함하면 **15.1%·11.6% 단축**. | 기존 이벤트 캐시 **`O(E)` 추가 유지**: 직렬화 크기 Codex **6.112 MiB**, Claude **6.165 MiB**.<br>후보의 전체 파일 버퍼는 **`O(B)`**. | 캐시 공간으로 반복 파싱을 줄인다. 다만 파일 검증 `O(B)`와 기존 이벤트 재적재 `O(E)`가 남아 추가분에만 비례하는 갱신은 아니다. |
| **파싱 재사용 · 파일 내용 재작성**<br>10,000건, 전체 재파싱 대비 | 재적재·집계 포함 시간이 Codex **5.9%**, Claude **0.9% 증가**. | 기존 캐시 `O(E)`를 유지한 채 파일 버퍼 `O(B)`도 사용한다.<br>실제 메모리 피크는 미측정. | 재사용 가능성 검사 후 전체 파싱도 한다. 추가가 잦은 파일과 달리, 재작성이 잦으면 캐시 부담만 남을 수 있다. |

## 표의 공간·복잡도 표기

`D`는 일별 요청·모델 집계의 총 행 수, `N`은 교체 대상 세션의 요청 수, `M`은 그 요청의 모델·Skill 행 수, `B`는 파일 바이트 수, `E`는 정규화 이벤트 수다. PK 변경은 조회 경로·그룹화 비용과 저장 상수를 바꾼다. SQL 묶음 비교에도 입력 전체 검증·적재가 남고, 파싱 재사용에도 전체 prefix 검증·기존 이벤트 재적재가 남는다.

DB 수치는 집계 본체와 보조 인덱스의 live 공간이다. WAL은 checkpoint 후 호출 종료 시 파일 길이로, 영속 DB 크기나 누적 디스크 쓰기량과 다르다. 캐시 MiB는 JSON 직렬화 크기이며 실제 heap/RSS가 아니다. 이 세 공간 비용을 합쳐 하나의 공간 개선율로 계산하지 않았다.

- PK 비교는 모든 후보를 같은 입력 순서로 재작성한 [최종 PK 대조 JSON](StorageLayoutBalanced-2026-10-29.json)을 사용한다. 날짜·프로젝트 보조 인덱스는 동일하게 유지했다. 월 PK는 `local_month`를 필터·GROUP BY에 직접 사용한다.
- PK의 두 세션 밀도 조건은 세션 수·프로젝트 수·집계 행 수도 달라 서로의 시간 차이를 세션 크기 하나의 효과로 해석하지 않는다. 세션당 100건에서는 집계 198,000행, 10,000건에서는 1,980행이었다.
- SQL 저장 비교는 한 세션 DB에서 수행했다. 파싱 시간과 이벤트 재적재·집계 포함 시간은 별도 구간이며, 어느 쪽도 확장 전체 refresh 시간은 아니다. 상세 표본·WAL·캐시·결과 해시는 [저장·파싱 원시 JSON](StorageAB-2026-10-29.json)에 있다.
- DB 설정은 WAL, foreign keys ON, TEMP FILE, main/TEMP cache 각 4 MiB, mmap 0이다. PK 후보는 모두 ANALYZE했다. 환경은 Windows, Ryzen 5 7500F, Node v24.14.1, SQLite 3.51.2다.
- 전체 결과·원본 SQL·해시·FK·integrity 대조를 통과했다. 저장 42개 시나리오, 파싱 22개 시나리오, 최종 PK 2개 데이터 조건 × 8개 후보를 검증했다. 당시 `npm run check`의 365개 테스트도 통과했다.
- 실제 로그·OS cold I/O·미상 시각/부분 날짜 경계의 새 월 SQL·다른 시간대·장기 캐시 운용은 이번 비교에 포함하지 않았다. 제품 동작은 변경하지 않았다.
