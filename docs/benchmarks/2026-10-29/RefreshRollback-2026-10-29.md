# manifest 갱신·증분 저장 롤백과 주요 통계 조회의 실제 비용

측정: 2026-10-29 17:44:53~17:50:13, Asia/Seoul. 현재 실제 로그와 합성 요청 10,000건을 롤백 직전·직후의 워크트리 빌드에서 비교했다.

## 결론과 이전 설명의 정정

**요청별 증분 저장·영향 날짜 재집계는 사용자 지시에 따라 기존 세션 일괄 교체로 롤백했다. 다만 롤백에 따른 일관된 속도 개선은 확인되지 않았다.** 실제 데이터에서는 작은 차이가 섞였고, 합성 10,000건의 같은 데이터 재집계는 2.531→3.519초로 39.0% 느려졌다. 앞서 “현재 증분 구조가 느리므로 기존 방식이 더 낫다”라고 일반화한 판단은 이 통제 비교로 뒷받침되지 않는다.

사용자가 기대한 것은 manifest를 활용해 전체 갱신 작업을 줄이는 것이었다. 기존 manifest가 이미 변경 없는 파일의 본문 읽기를 생략하고 있었다. 추가한 요청별 증분 저장은 그 뒤의 DB 반영 구간만 바꿨다. **전체 파일 metadata 확인과 변경 세션의 원본 재파싱은 그대로 남아 전체 갱신 지연을 크게 줄이지 못했다.**

현재 실제 데이터의 변경 없는 갱신은 약 126 ms이며 약 103 ms가 파일 확인 단계다. 최초·강제 전체 갱신은 약 13초 중 약 9초가 파싱 단계다. DB 저장을 없애도 이 앞단 비용은 남는다. 반면 10,000건에서는 반복 재삽입을 생략하는 증분 저장의 이득이 분명히 관측됐다.

### 측정 후 최종 판단과 현재 코드 상태

**이번 통제 비교에 따른 성능 권고는 롤백 전 증분 버전을 유지하거나 복원하는 것이다.** 실제 1,180건에서는 전체 시간 차이가 작고 일관된 우열이 없었지만, 합성 10,000건에서는 강제 전체 재집계와 요청 추가·기존 요청 갱신 모두 증분 버전이 3/3쌍에서 빨랐다. 전체 재집계는 증분 2.531초, 세션 일괄 교체 3.519초였다. 모든 규모·작업에서 증분이 최적이라는 의미로 확대하지 않는다.

앞선 롤백 권고는 소규모 측정의 작은 차이를 일반화한 성급한 판단이었다. **전체 갱신을 크게 단축하지 못했다는 사실을 증분 저장 자체가 느리다는 판단과 혼동했다.** 전체 앞단의 지연이 남는 것과 DB 반복 쓰기를 줄이는 이득은 함께 존재한다. 성능 개선을 이유로 세션 일괄 교체를 선택할 근거는 이번 결과에서 확인하지 못했다.

사용자는 이 후속 판단을 문서에 남기도록 요청했다. **현재 소스는 앞서 요청한 세션 일괄 교체로 롤백된 상태이며, 증분 버전 복원 권고는 아직 코드에 반영하지 않았다.** 이 후속 기록은 문서 정정이며 제품 코드·기존 측정값·원시 JSON은 변경하지 않았다.

## 1. 롤백 범위와 비교 통제

- **전(before)**: 현재 SQL 리팩토링까지 포함한 요청별 차이 저장·영향 날짜 재집계.
- **후(after)**: 같은 소스에서 `sessions.ts`, `rollups.ts`, `billing.ts`만 증분 도입 직전 `066de27`의 동작으로 복원했다. 세션·집계·비용의 일괄 교체를 사용한다.
- manifest 재사용, 원본 누락 이력 보존, Skill 보존, 중간 실패 rollback, PK·보조 인덱스·schema 13, 현재 SQL 책임 분리는 유지한다. 원본 로그와 사용 중인 확장 DB는 변경하지 않았다.
- 정상 재삽입되는 요청의 논리 키는 같지만 내부 행 ID 유지는 보장하지 않는다. `updated_at`을 생략하면 재반영 시각을 기록한다. 이 두 변화는 기존 방식 복원에 포함된다.
- 두 워크트리는 모두 HEAD `929c0c4`에서 만들고 현재 미커밋 소스·새 SQL 파일까지 복사했다. 코드의 실제 차이는 위 세 TypeScript 파일뿐이며 원시 JSON에 전체 `src/` 파일별 SHA-256을 보존했다. 같은 revision 문자열만으로 전후를 구분하면 안 된다.
- 빌드 경로는 `tests/.cache/rollback-worktrees-20261029/before`, `tests/.cache/rollback-worktrees-20261029/after`다. 설치된 VS Code 확장은 이 작업에서 업데이트하지 않았다.

## 2. 입력과 측정 방법

| 조건 | 현재 실제 로그 | 합성 10,000건 |
| --- | ---: | ---: |
| 초기 요청 수 | 1,180 | 10,000 |
| 파일·세션 배치 | 파일 494개 | 파일·세션 100개 × 요청 100건 |
| 원본 파일 bytes | 280,471,904 | 5,637,210 |
| Zstd 파일 | 427개 | 없음 |
| 초기 토큰 합계 | 1,607,116,410 | 6,340,000 |
| 구성 | Claude 33파일·Codex 461파일, 실제 이력·진단·도구·연결 포함 | Claude/Codex 각 5,000요청, 제공자마다 두 모델, 완료 요청만 생성 |

합성 입력은 최근 30일에 요청을 나누고 처리시간을 2초로 생성했다. 이미지·도구 출력·fork·손상 로그는 없다. **실제 데이터의 크기를 그대로 10,000건까지 확대한 입력은 아니다.** 실제 로그는 요청 수가 적어도 본문 byte와 파일 수가 훨씬 많아서 합성 10,000건보다 파싱 시간이 길다. 두 입력 사이의 시간 비율을 실제 서비스의 요청 수 증가 예측값으로 사용하지 않는다.

- Windows, AMD Ryzen 5 7500F, Node v24.14.1, SQLite 3.51.2, parser 14, schema 13, Asia/Seoul. 같은 잠금 파일의 의존성과 컴파일 명령을 사용했다.
- 입력마다 워밍업 한 쌍을 제외하고 독립 프로세스 3쌍을 AB/BA/AB 순서로 순차 실행했다. 각 프로세스는 새 DB에서 여섯 시나리오를 순서대로 수행했다. OS 파일 캐시는 비우지 않았다.
- 모든 시간은 ms, 세 프로세스의 중앙값이다. 전체는 `refreshSummary`와 월별 첫 100행+COUNT 조회까지이며 UI·IPC·quota는 제외한다.
- 파일 사본 생성·추가 입력 작성·checkpoint·정확성 검증은 타이머 밖이다. 각 단계 뒤의 동일 검증이 다음 단계의 캐시·GC에 줄 수 있는 영향은 남는다.
- 파일 확인은 제품 progress의 scanning 단계이며 디렉터리 순회, stat, manifest 비교·방문 기록, 누락 파일 및 이름 metadata 처리를 포함한다. 순수 파일 stat 시간만을 뜻하지 않는다.
- 파싱 단계에는 JSONL 읽기·Zstd 해제·정규화·TEMP 적재·세션 연결 확장도 포함된다. 집계 준비는 `prepareSummaries`, DB 저장은 `replaceSessions` 호출 합계다. 두 구간은 committing 단계 안의 하위 구간이다.
- 단계별 중앙값을 별도로 계산하므로 합계가 전체 중앙값과 정확히 같지 않을 수 있다. 단계 사이 공통 처리·정리·대기 시간도 있다.

## 4. INSERT·DELETE 자체의 시간과 호출 수

제품 영속 표에 대한 INSERT/DELETE statement 직접 실행 시간을 같은 관측기로 측정했다. **호출 수는 SQL 실행 횟수이며 변경된 행 수가 아니다.** INSERT SELECT·조건부 UPSERT·DELETE cascade를 포함하며 COMMIT 동기화·입력 비교·TEMP 처리·statement 준비 등은 제외한다. 따라서 DB 저장 전체 시간과 구분한다.

| --- | --- | ---: | ---: | ---: |
| 실제·변경 없음 | 양쪽 | 0 / 0 | 0 / 0 | 0 |
| 실제·강제 전체 | 증분 | 1976 / 167.179 | 1194 / 26.642 | 1022.402 |
| 실제·강제 전체 | 롤백 | 5511 / 257.157 | 1194 / 47.395 | 1146.430 |

## 5. 주로 사용하는 통계 트랜잭션

사용자가 제시한 동작을 공개 `queryUsagePage`의 행 조회+COUNT로 측정했다. 프로세스마다 준비 실행 3회 후 7개 표본의 중앙값을 구하고 다시 3개 프로세스의 중앙값으로 비교한다. 첫 100행의 페이지이며 COUNT는 대상 전체를 센다. SQL 생성·prepare·snapshot·rollup/raw 경계 선택을 포함한 warm DB API 시간이고 화면 렌더링 시간은 아니다.

최근 7일/30일은 각 입력의 측정 시작 시각을 고정해 `fromMs <= started_at_ms < toMs`로 조회했다. 실제 최근 30일 대상은 요청 513건이다. 합성도 같은 의미의 기간을 사용한다. 일·월별 조회는 최근 30일을 일/월로 GROUP BY한다. 주 단위 GROUP BY API는 없어 최근 7일의 합계·평균을 한 범위로 반환한다.

평균 토큰은 **해당 기간의 완료 요청 한 건당 평균**이며 일평균이나 `합계÷7/30`이 아니다. 세션 시간은 현재 `avg_duration_ms`인 **평균 처리시간**이고 세션 총 소요시간은 API가 직접 반환하지 않는다. 다중 모델 요청은 각 모델에 포함되며 모델별 시간은 해당 모델을 포함한 요청 전체의 시간이다. 새로운 평균 정의나 총 시간 열은 이번에 추가하지 않았다.

| 최근 7일 합계·평균·모델 | 1.351 → 1.399 | 10.063 → 9.751 |
| 최근 30일 합계·평균·제공자 | 1.672 → 1.673 | 12.741 → 12.004 |
| 최근 30일 합계·평균·모델 | 1.857 → 1.876 | 22.057 → 22.939 |

프로젝트는 전 기간에서 요청이 가장 많은 제공자·프로젝트를 고정해 선택했다. 실제 세션별 결과는 제공자 기준 150행, 모델 기준 221행 중 첫 100행을 측정했다. 합성은 각각 10/20행이다. 최근 30일도 같은 프로젝트를 측정한 보조 두 조건은 실제 입력에서 0행이어서 대표 성능 표에서 제외하고 원시 JSON에 남겼다. 합성의 일별 모델 결과는 120행이므로 첫 100행+전체 COUNT의 시간이다.

## 6. 기대한 incremental 개선으로 이어지지 않은 이유

1. **최적화 위치가 기대와 달랐다.** manifest는 이미 변경 없는 원본을 재사용한다. 추가한 증분 저장은 요청별 DB 비교·저장을 바꿨고, 전체 파일 metadata 확인과 변경 세션 재파싱을 줄이지 않았다.
2. **실제 작은 세션에서는 저장 구간이 짧다.** Codex 25건·Claude 2건의 전체 약 140~190 ms 중 저장은 약 3~6 ms다. 절약할 시간이 작은 반면 요청별 기존 행 SELECT·모델/Skill 비교·TEMP·변경 키 추적 비용이 추가된다.
3. **비교 비용과 쓰기 절감 효과가 모두 있다.** 이번 10,000건 재집계에서는 증분 저장이 반복 쓰기를 줄였다. 단순히 “증분은 느리다”고 할 수 없다. 롤백 후 INSERT 시간 87.936→859.127 ms, 저장 전체 1.154→2.117초가 이를 보여 준다.
4. **다른 실험의 증감률을 그대로 적용할 수 없다.** 이전 DB 전용 벤치마크는 준비된 facts와 다른 분포·트랜잭션 경계에서 측정했다. 이번 실제/합성 입력도 파일 수·byte·날짜 분포가 다르다. 공통 처리의 시간 차이까지 증분 저장만의 영향으로 보지 않는다.

현재 실제 데이터의 전체 약 13초를 줄이려면 약 9초의 읽기·파싱·정규화와 약 1.9초의 집계 준비를 더 살펴볼 여지가 크다. 변경 없는 갱신 약 126 ms에는 약 103 ms의 발견·metadata 처리가 남는다. 이 구간의 추가 최적화는 이번에 구현하지 않았다.

## 7. 정확성·재현·남은 범위

두 입력의 정식 72상태를 독립 raw SQL로 720회, 주요 12조회×6프로세스×2입력을 144회, **총 864회** 대조했다. 전후·반복의 facts/집계/조회 해시가 일치했고 FK·integrity 검사, 초기 10,000건/6,340,000 tokens, 추가 요청 +1건/+130 tokens, 추가 응답 +26 tokens, 입력 복구 SHA-256을 확인했다. 파싱 오류는 전 단계에서 0이었다.

내부 행 ID·재반영 시각은 롤백의 동작 차이여서 비교에서 제외한다. 비정수만 유효숫자 10자리로 정규화해 비교하며 저장 값을 반올림하지 않는다. 개인 본문·제목·세션 ID·실제 파일 경로·credential은 보고서에 남기지 않는다. 시험 원본 사본과 DB는 실행 종료 후 삭제했다.

- [10,000건 원시 JSON](RefreshRollback-10000-2026-10-29.json)

재실행은 빌드한 두 워크트리를 `--before`/`--after`에 지정하고 실제 입력에는 `--real`, 합성에는 `--requests=10000 --turns-per-session=100`을 사용한다. `--pairs=3 --warmups=1 --report=<새 JSON>`으로 실행한다. 실행기·helper·전체 src의 SHA-256을 JSON에 보관해 현재 작업 트리가 추가로 바뀌어도 측정 소스를 추적할 수 있다.

롤백 후 `npm run check`의 타입 검사·린트·365개 테스트를 통과했다. 세션 일괄 교체, Skill/삭제 원본 보존, 날짜 이동·모델 변경·다수 날짜 집계·잘못된 입력과 중간 실패 rollback을 확인했다. VS Code 화면 실측·실계정 quota·cold disk·장기 운영·실제 로그 10,000건에 대한 외삽은 수행하지 않았다.
