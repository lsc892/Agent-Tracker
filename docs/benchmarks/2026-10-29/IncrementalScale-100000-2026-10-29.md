# 증분 저장 전후: 합성 10만 요청의 세션 밀도별 비교

측정: 2026-10-29 16:50:17~17:15:51, Asia/Seoul. 기존 실제 1,167건 측정의 후속으로 같은 두 빌드 워크트리에서 생성한 JSONL 요청 100,000건을 처리했다.

**동일 데이터 전체 재집계는 9.8~16.0% 단축됐다. 소수 변경은 세션 크기에 따라 달랐다.** 세션당 10,000건에서는 요청 추가가 11.2~16.6% 빨라졌지만, 세션당 100건에서는 추가·기존 요청 갱신의 전체 시간이 5.1~15.3% 늘었다. 새 DB에 모두 넣는 최초 집계의 이득은 확인하지 못했고, 긴 세션에서는 9.1% 느려졌다.

## 조건과 측정 범위

- 전 `066de272092ab2dda209ff006d117fda4133a793`, 후 `410289cc3bb088cd46e4c82a43a578be955699d2`. 증분 저장 변경만 구분한 기존 워크트리 빌드를 재사용했다. 현재 작업 트리의 SQL 리팩토링은 포함하지 않는다.
- 두 조건 모두 요청 100,000건, Claude·Codex 각 50,000건, 총 63,400,000 tokens다. 한 조건은 세션·파일 1,000개에 100건씩, 다른 조건은 10개에 10,000건씩 넣었다. 논리 요청 수와 파일 수는 구분한다.
- 모든 요청은 완료 상태이며 제공자별 두 모델을 번갈아 사용한다. 100개 요청마다 날짜를 바꾼다. 이미지·도구 출력·fork·손상 로그·미완료 요청은 생성하지 않았다. 합성 입력의 실제 제품 처리 경로 측정이며 실제 대화 10만 건을 확보한 결과는 아니다.
- Windows, AMD Ryzen 5 7500F, Node v24.14.1, SQLite 3.51.2, schema 13, parser 14. 앞선 10월 26~27일 DB 전용 측정과 환경·입력·범위가 달라 절대 시간이나 개선률을 섞지 않는다.
- 각 조건 3쌍의 별도 프로세스에서 AB/BA/AB 순서로 실행하고 워밍업 1쌍을 제외했다. 성능 프로세스는 동시에 실행하지 않았다. 각 프로세스는 새 DB에서 동일한 여섯 단계를 순차 실행한다.
- 전체 시간은 원본 발견·manifest 비교·파싱·집계 준비·DB 반영을 수행하는 `refreshSummary`와 월별 100행+COUNT 조회까지다. 초기 조회에는 최초 일별 집계 구축이 포함된다. UI·IPC·quota는 포함하지 않는다.
- 전체 재집계는 파일을 수정하지 않고 manifest의 parser_version을 0으로 만들어 강제 재파싱한다. 요청 추가는 기존 세션 파일에 새 요청을 하나 넣고, 기존 요청 갱신은 그 요청에 응답을 하나 더 넣는다. 추가 레코드는 시험 준비로 타이머 밖에서 쓴다.
- 결과 검증·checkpoint·해시·합성 파일 생성은 타이머 밖이다. 검증을 양쪽의 각 단계 뒤에 똑같이 수행하므로 다음 단계 캐시에 영향을 줄 수 있다. OS 파일 캐시는 비우지 않았다.

## 전체 시간과 증감률

각각 세 번의 중앙값이다. 증감률은 `(후 중앙값 / 전 중앙값 - 1) × 100`으로 계산했다. 음수는 단축, 양수는 증가다.

| 작업 | 1,000세션 × 100건: 전 → 후 | 증감률 | 10세션 × 10,000건: 전 → 후 | 증감률 |
| --- | ---: | ---: | ---: | ---: |
| 최초 집계 | 33.191 → 33.049초 | -0.4% | 17.778 → 19.391초 | +9.1% |
| 변경 없음 | 224.967 → 199.136 ms | -11.5% | 15.657 → 17.810 ms | +13.8% |
| 같은 데이터 전체 재집계 | 46.829 → 39.333초 | **-16.0%** | 20.895 → 18.846초 | **-9.8%** |
| Codex 요청 1건 추가 | 258.686 → 271.881 ms | +5.1% | 1.957 → 1.633초 | **-16.6%** |
| Claude 요청 1건 추가 | 242.536 → 279.563 ms | +15.3% | 2.100 → 1.863초 | **-11.2%** |
| 기존 Codex 요청에 응답 추가 | 247.012 → 270.611 ms | +9.6% | 1.934 → 1.884초 | -2.6% |

변경 없는 단계는 두 버전 모두 본문 읽기·집계 준비·요청 교체가 0이다. 이 단계의 시간 차이를 증분 저장 자체의 비용이나 이득으로 해석하지 않는다. 두 배치 간 절대 시간 차이도 파일 수·세션 수·날짜 분포가 함께 달라진 결과이며 요청 수만의 효과가 아니다.

## DB 저장 구간만 비교

전체 시간 안의 실제 `replaceSessions` 호출 합계다. 입력 원본 파싱·집계 준비·조회는 제외하며 해당 호출의 BEGIN/COMMIT과 일별 집계 유지 비용은 포함한다.

| 작업 | 세션당 100건: 전 → 후 ms | 증감률 | 세션당 10,000건: 전 → 후 ms | 증감률 |
| --- | ---: | ---: | ---: | ---: |
| 최초 집계 | 13284.560 → 14307.035 | +7.7% | 9976.594 → 11633.110 | +16.6% |
| 같은 데이터 전체 재집계 | 18935.814 → 14322.687 | **-24.4%** | 14142.401 → 11849.915 | **-16.2%** |
| Codex 요청 1건 추가 | 15.354 → 15.833 | +3.1% | 1321.871 → 1024.919 | **-22.5%** |
| Claude 요청 1건 추가 | 15.977 → 18.186 | +13.8% | 1366.801 → 1189.524 | **-13.0%** |
| 기존 Codex 요청에 응답 추가 | 15.506 → 17.301 | +11.6% | 1287.809 → 1201.433 | -6.7% |

변경이 없는 세션을 건너뛰는 manifest 재사용은 기존에도 있었다. 증분 저장은 처리 대상 세션 안에서도 같은 요청의 영속 쓰기를 생략하지만 입력 비교와 원본 재파싱은 남는다. 최초 집계에서는 모두 새 행을 쓰면서 조회·TEMP 준비 비용도 추가된다. 이 구조가 초기 비용의 가능한 원인이지만, 각 내부 연산의 기여를 별도로 계측해 확정한 결과는 아니다.

## 편차와 해석

- 전체 재집계는 두 배치 모두 3/3쌍에서 후가 빨랐다. 단, 긴 세션의 세 번째 쌍은 19.964→19.950초로 약 13 ms 차이여서 큰 개선이 매번 재현된 것은 아니다.
- 긴 세션의 Codex·Claude 추가와 기존 요청 갱신은 각각 2/3쌍에서 후가 빨랐다. 특히 기존 요청 갱신의 전체 중앙값 2.6% 감소는 범위가 겹치므로 일관된 큰 이득으로 보지 않는다.
- 짧은 세션의 Codex 추가는 후가 빠른 쌍이 1/3, Claude 추가·기존 요청 갱신은 각각 0/3이었다. DB 구간뿐 아니라 파일 metadata 확인·파싱·집계 준비·GC·호스트 부하의 영향을 함께 포함한 전체 호출 시간이다.
- 긴 세션의 요청 추가에서 종료 시 WAL 파일 길이 중앙값은 Codex 6,948.508→96.594 KiB, Claude 7,515.813→120.734 KiB로 줄었다. checkpoint 직후부터 단계 종료까지의 파일 길이이며 실제 디스크 총 쓰기량이나 누적 frame 수를 의미하지 않는다.
- 자동 임계값·결과 캐시·파일 tail 이어 읽기·새 인덱스는 적용하지 않았다. 이번 측정으로 제품을 추가 변경하지 않는다.

## 정확성과 보관

정식 표본은 조건당 6프로세스 × 6상태, 두 조건 합계 72상태다. 각 상태에서 제공자/모델 × 전체/프로젝트/세션/일/월의 raw SQL을 대조해 **720회** 일치했다. 초기 요청 수 100,000건·토큰 63,400,000, 새 요청의 +1건/+130 tokens, 추가 응답의 요청 수 유지/+26 tokens도 확인했다. 모든 단계의 파싱 오류는 0이며 FK·integrity 검사, 전후 및 반복 표본의 facts·집계 해시가 일치했다.

물리 행 ID와 통계 갱신 시각은 기능의 의도에 따라 달라 해시에서 제외한다. 비정수는 합산 순서 차이를 위해 유효숫자 10자리로 비교 정규화하며 저장 값을 반올림하지 않는다. 파일 사본은 실행 종료 후 최초 SHA-256으로 복구를 확인하고 실험 DB와 함께 삭제했다. 빌드 워크트리와 보고서는 남겼다.

최종 `npm run check`의 타입 검사·린트·365개 테스트를 통과했다. 두 원시 보고서의 실행기 SHA-256과 현재 재현 실행기가 일치하며 보고서의 로컬 링크와 `git diff --check`도 확인했다.
