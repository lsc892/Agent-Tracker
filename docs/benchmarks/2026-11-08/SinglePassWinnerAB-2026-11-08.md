# 단일 읽기 winner A/B 테스트

2026-11-08 18:08:39–2026-11-08 18:16:04, Asia/Seoul.

가정: 사용자는 선행 유효성 근거 읽기를 제거하고 파일 한 번 읽기 → 동일 그룹 winner 비교 → 더 좋은 후보의 DTO 갱신 → 패자 폐기를 요청했다. 두 번째 파일 읽기를 없애면 읽기·파싱 비용이 줄어들 것으로 예상했다.

개선 방향: A = 변경 직전 작업 트리의 두 번 읽기 구현, B = 단일 읽기에서 원본별 winner를 갱신하고 남은 DTO를 최종 그룹으로 병합하는 구현. 원본 캐시를 유지하던 더 이전 제품과의 비교는 별도 과거 측정이다. 모델 기록의 경계 정합성은 본문에서 별도로 적는다.

## 2. 분석

- **판정: 두 번째 읽기 제거에 따른 수집 시간 개선을 확인했다.** 현재 사본의 초회 수집은 **45.18%**, 한 건 추가는 **43.19%** 단축됐다. 초회 A 13,882.62–14,177.43ms와 B 7,617.14–7,812.53ms, 추가 A 987.91–1,029.55ms와 B 562.48–593.01ms는 범위가 겹치지 않는다. 1만·100요청의 초회 수집도 각각 10.87%·18.58% 단축됐고 범위가 겹치지 않는다. 작은 입력의 추가 시간은 범위가 겹쳐 중앙값 차이만 기록한다.
- **핵심 원인: 같은 원본을 한 번만 읽고 파싱한다.** 현재 사본의 초회 본문은 893,909,018 → **446,954,509byte**, 추가 본문은 133,031,312 → **66,515,656byte**로 정확히 절반이다. 원본별 그룹의 더 좋은 후보는 같은 DTO에 덮어쓰고 패자의 숫자 벡터를 버린다. 최종 세션·request 귀속은 남은 winner와 같은 읽기에서 수집한 식별 근거로 병합한다. 별도 선행 읽기와 선택을 위한 재읽기는 없다.
- **패자 모델의 표시 기준 변경:** 기존 legacy 회귀 입력은 큰 복사 후보와 나중의 0토큰 후보가 같은 그룹에 있다. 사용자는 중복 그룹의 패자 모델까지 따로 표시할 필요가 없다고 정했다. 따라서 폐기된 `gpt-6-sol` 0토큰 후보를 복원하지 않고 최종 `gpt-5.6-sol` 100토큰 모델 행만 남긴다. 이 경계에서는 과거 모델 행과 의도적으로 다르며, 테스트를 새 기준에 맞췄다. 본 성능 입력 세 규모에서는 이 경계 차이가 없어 모델·도구·비용까지 A/B 일치했다.
- **조회·변경 없는 갱신:** 네 평균 조회와 변경 없는 갱신의 표본 범위는 겹친다. 조회 JS 12개 파일은 A/B 동일하고 변경 없는 본문 읽기는 모두 0byte이므로 이 항목의 속도 개선을 주장하지 않는다.
- **선택:** 사용자가 지정한 단일 읽기·winner DTO 갱신·패자 폐기를 제품 수집 경로에 반영했다. 관련 세션이 바뀌면 변경 없는 형제 원본도 이번 갱신에서 한 번 읽는다. 이전의 전체 DTO 캐시 제품과 비교하려면 이 차이도 함께 측정해야 하며, 여기의 개선율은 **직전 두 번 읽기 구현 대비**다. [이전 DTO 캐시 비교](StreamingWinnerAB-2026-11-08.md)의 다른 기준 수치와 섞어 전반적인 개선으로 해석하지 않는다.

### 메모리와 한계

단위는 MB(1,000,000byte), 초회 수집 완료 시 10표본의 중앙값이다.

| 측정 항목 | 현재 1,518건 | 10,000건 | 100건 |
| --- | ---: | ---: | ---: |
| 수집 후 강제 GC 보유 heap A → B | 8.37 → 8.22 | 7.41 → 7.43 | 6.97 → 6.98 |
| 초회 완료 시 프로세스 high-water RSS A → B | 280.30 → 266.27 | 157.16 → 153.25 | 56.02 → 56.13 |

현재 사본에서 high-water RSS 중앙값은 약 5.01% 낮지만 각 메모리 표본 범위가 겹친다. 보유 heap도 비슷한 수준이며 메모리 감소를 확정하지 않는다. GC 정지 시간·연속 JS heap peak·cold OS 파일 캐시·DB 마이그레이션·다른 추가 대상 분포는 **미측정**이다. 사용량 패자 DTO는 보관하지 않지만 비사용량 이벤트·legacy 서명·root 위치·원본별 winner와 최종 winner는 갱신 동안 메모리에 남는다. 고정 메모리 사용을 주장하지 않는다.

## 3. 구현과 검증

- [SourceWinners](../../../src/summary/aggregation/sourceWinners.ts)가 파싱 callback에서 그룹 비교·동일 DTO 갱신·패자 폐기를 수행한다. [scanner](../../../src/summary/scanner/index.ts)는 파일당 `readSource()`를 한 번 호출하고 남은 winner를 [최종 집계](../../../src/summary/aggregation/memoryAggregate.ts)에 전달한다. parser version 16으로 이전 manifest를 다음 갱신에서 새 규칙으로 수집한다.
- 단일 읽기 byte 경계·읽기 완료 뒤 append/재작성의 다음 갱신 반영·취소·동일 DTO 유지·정확한 큰 정수 비교·패자 모델 폐기를 검사했다. **`npm run check`: 타입·린트·415개 테스트 통과.** 독립 SQL oracle의 공통 집계 계약도 통과했다.
- A는 변경 전에 소스와 빌드를 별도 사본으로 고정했다. B도 측정 시작에 빌드를 고정하고 각 쌍은 별도 프로세스·DB에서 실행했다. 측정 후 제품 코드의 수정은 설명 주석 정리에 한정하며 검증 JSON에 컴파일 코드의 주석 제외 동일성을 기록한다. 원본과 측정용 사본 601개의 내용 hash를 종료 시 다시 확인한다.

원시 표본은 위 [JSON](SinglePassWinnerAB-2026-11-08.json), 재실행 명령·소스·추가 검증은 [검증 JSON](SinglePassWinnerVerification-2026-11-08.json)에 보존한다. 기존 출력은 덮어쓰지 않으므로 재실행에는 새 이름을 사용한다.
