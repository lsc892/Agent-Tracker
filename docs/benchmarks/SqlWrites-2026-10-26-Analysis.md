# DB 최적화 A/B 원인 고찰 — 월 우선 배치의 이점이 작았던 이유

작성: 2026-10-27, Asia/Seoul. [실험별 결과표](SqlWrites-2026-10-26.md)와 [원본 측정값](SqlWrites-2026-10-26.json)을 해석한 문서다. 기존 측정·실행 계획·현재 소스를 대조했으며, 추가 성능 실험은 실행하지 않았다.

**현재 측정이 뒷받침하는 선택은 기존 세션 중심 PK 배치·기간/프로젝트 복합 인덱스·transaction batching을 유지하고 증분 처리를 적용하는 것이다.** 월 우선 배치 후보는 일부 조회를 개선했지만 저장 공간과 집계 재입력 비용이 함께 증가했다. 여기서 “최적”은 이번 후보와 측정 작업 안에서의 판단이다.

특히 **이번 월별 조회는 전체 기간을 월별로 묶는 조회였다. 특정 한 달로 바로 이동하는 조회의 효과는 직접 측정하지 않았다.** 이 차이가 월 단위 탐색의 기대와 실험 결과를 구분하는 핵심이다.

## 1. 현재 데이터가 저장되는 순서

현재 작업 소스는 SQLite를 사용한다. 일반 테이블은 rowid를 기준으로, `WITHOUT ROWID` 테이블은 복합 PK를 기준으로 B-tree를 구성한다. 집계 테이블에는 이미 PK에 따른 클러스터링이 적용돼 있다. [SQLite: WITHOUT ROWID](https://www.sqlite.org/withoutrowid.html).

| 대상 | 본체 B-tree의 기준 | 현재 구조의 의미 |
| --- | --- | --- |
| 원본 요청 `turn_summary` | `id INTEGER PRIMARY KEY` | 정수 ID 순서. 날짜나 세션 순서로 본체를 재배치하지 않았다. |
| 요청별 모델 `turn_model_usage` | `(turn_id, model)`, `WITHOUT ROWID` | 같은 요청의 모델 행이 PK 순서에서 모인다. |
| 일별 요청 집계 `usage_request_daily` | `(provider, session_id, project_key, local_day)`, `WITHOUT ROWID` | 제공자 → 세션 → 프로젝트 → 날짜 순서다. |
| 일별 모델 집계 `usage_model_daily` | `(provider, session_id, project_key, local_day, model_key)`, `WITHOUT ROWID` | 같은 세션·프로젝트·날짜 안에서 모델별로 모인다. |

예를 들어 일별 요청 집계는 다음 순서가 된다. 아래 식별자는 설명용이다.

```text
claude / 세션 A / 프로젝트 P / 2026-09-30
claude / 세션 A / 프로젝트 P / 2026-10-01
claude / 세션 B / 프로젝트 P / 2026-09-30
claude / 세션 B / 프로젝트 P / 2026-10-01
```

세션 A의 행을 모으고 그 안에서 날짜를 정렬한다. 그래서 `provider + session_id`로 해당 세션 범위를 찾거나, 변경된 집계 키를 교체하기에 맞는다. PK 순서에서 가까운 행이라는 뜻이며 디스크의 연속된 섹터나 월별 파일에 저장된다는 뜻은 아니다.

다른 접근 순서는 별도 보조 인덱스로 제공한다.

| 대상 | 기간 인덱스 | 프로젝트·기간 인덱스 |
| --- | --- | --- |
| 원본 요청 | `(started_at_ms, provider)` | `(provider, project_key, started_at_ms)` |
| 일별 집계 두 테이블 | `(local_day, provider)` | `(provider, project_key, local_day)` |

즉, 세션 기준 본체 배치와 날짜 기준 탐색 경로를 함께 가진 구조다. 실제 선택은 필터와 비용 추정에 따라 달라진다. 정의는 [schema.ts](../../src/summary/db/schema.ts), [rollup-state.ts](../../src/summary/db/rollup-state.ts)에 있다.

## 2. 월별 배치 실험에서 실제로 바꾼 것

월→세션 후보는 일별 집계 PK를 `(local_month, provider, session_id, project_key, local_day[, model_key])`로 바꿨다. 월→모델 후보는 모델 집계에 `(local_month, provider, model_key, session_id, project_key, local_day)`를 사용했다. 원본 요청 테이블의 정수 PK는 유지했다.

이것은 **한 테이블 안의 PK 정렬 순서를 바꾼 실험**이다. 월마다 별도 테이블·파일을 만들거나 파티션을 나눈 실험은 아니다. 또한 기존 날짜/프로젝트 인덱스를 유지하면서 두 집계 테이블에 세션 인덱스, 모델 집계에 모델 인덱스를 추가했다. 따라서 PK 순서 변경과 보조 인덱스 추가가 묶여 있다.

쓰기 비용은 같은 일별 집계 snapshot 전체를 지우고 다시 넣는 작업으로 측정했다. 월 후보에 제품의 증분 저장 API를 연결해 실제 요청 한 건의 추가·수정·삭제를 비교한 결과는 아니다. 구현은 [sql-writes.cjs의 `layout()`과 `worker()`](../../tests/benchmarks/sql-writes.cjs)를 따른다.

## 3. 해당 월로 바로 이동하는 이점이 드러나지 않은 이유

### 3-1. 월별 GROUP BY에는 특정 월을 찾는 조건이 없었다

실행기는 `buildRollupUsageQueries({}, 'month', ...)`를 호출했다. 첫 인자인 필터가 비어 있어 시작일·종료일·특정 월 제한이 없다. SQL의 핵심은 다음과 같다. 지표 대부분과 정렬·페이지 조건은 생략했다.

```sql
SELECT provider,
       substr(NULLIF(local_day, ''), 1, length(local_day) - 3) AS period,
       SUM(total_tokens)
FROM usage_request_daily
WHERE (local_day <> '' OR local_day = '')
GROUP BY provider, period;
```

이 조회는 모든 달의 합계를 만들어야 하므로 각 달의 입력을 읽는다. “2026년 10월의 시작점으로 이동해 다른 달을 건너뛴다”는 탐색 이득을 얻을 조건이 없다. `LIMIT 100`도 이번 계획에서는 그룹화 입력을 100행으로 줄이지 않는다.

반대로 다음과 같은 **한 달 범위 조회**는 다른 달을 제외할 수 있다. 아래는 비교 설명용 SQL이며 이번에 시간을 측정한 SQL은 아니다.

```sql
-- 현재 구조에도 날짜 선두 보조 인덱스가 있다.
WHERE local_day >= '2026-10-01' AND local_day < '2026-11-01'

-- 월 선두 PK 후보를 직접 사용하는 조건의 예다.
WHERE local_month = '2026-10'
```

따라서 “월별 배치면 한 달 접근이 빨라질 것”이라는 예상에는 타당한 근거가 있다. 이번 조회는 그 효과를 직접 비교하는 조건이 아니었다. 현재 구조도 날짜 인덱스로 범위를 찾을 수 있어, 제대로 비교할 때는 **기존 날짜 인덱스 탐색과 월 PK 탐색의 차이**를 측정해야 한다. 복합 인덱스의 선두 키와 범위 탐색 원리는 [SQLite Query Planning](https://www.sqlite.org/queryplanner.html)에 설명돼 있다.

### 3-2. SQL이 새 월 컬럼을 사용하지 않았고 임시 그룹화가 남았다

후보에는 저장된 `local_month`를 추가했지만 제품 SELECT builder는 유지했다. 조회는 계속 `local_day`에서 `substr(...)`로 월을 계산했다. 월 PK를 만들었다고 기존 표현식의 GROUP BY가 자동으로 그 순서를 활용한 것은 아니다.

요청 100,000건·세션당 100건 조건의 보존된 실행 계획은 다음과 같다. 각 후보의 세 프로세스에서 같은 형태를 확인했다.

| 월별 조회 | 기존 배치 | 월→세션 / 월→모델 후보 |
| --- | --- | --- |
| 제공자 기준 입력 | `SCAN turn_summary` | `SCAN turn_summary USING INDEX idx_usage_request_daily_session` |
| 모델 기준 입력 | `SCAN turn_summary` | `SCAN turn_summary USING INDEX idx_usage_model_daily_model` |
| GROUP BY | `USE TEMP B-TREE FOR GROUP BY` | 동일하게 남음 |
| ORDER BY | `USE TEMP B-TREE FOR ORDER BY` | 동일하게 남음 |

여기서 `turn_summary`는 SQL 안에서 붙인 **일별 집계 테이블의 별칭**이다. 원본 요청 100,000행을 그대로 순회한다는 뜻은 아니다. 후보의 `SCAN ... USING INDEX` 역시 월 조건으로 좁힌 `SEARCH`가 아니라 인덱스 전체 순회다.

복합 인덱스는 WHERE 조건과 정렬·그룹 키가 맞을 때 탐색이나 임시 그룹화를 줄일 수 있다. 이번 월 후보에서는 임시 그룹화 제거가 확인되지 않았다. [SQLite Optimizer Overview](https://www.sqlite.org/optoverview.html#order_by_optimizations).

**추론:** 후보가 선택한 보조 인덱스에는 합계 계산에 필요한 지표 전체가 없다. 따라서 인덱스를 순회하면서 집계 본체의 지표도 찾아야 하는 접근이 비용을 늘렸을 가능성이 있다. 실제 모델 조회는 느려졌지만, 캐시 적중·실제 페이지 읽기 횟수·CPU 구간별 시간은 측정하지 않아 이 요인의 기여율은 확정할 수 없다.

### 3-3. 시작점을 찾은 뒤에도 해당 범위의 합산은 남는다

한 달의 시작 위치를 빠르게 찾아도 그 달의 모든 세션·프로젝트·모델 집계 행을 합산해야 한다. 현재 조회 대상은 이미 일별로 줄여 놓은 데이터이고, 측정도 준비 실행 이후의 warm 조회다. 이 조건에서는 최초 디스크 접근이나 긴 탐색을 줄이는 효과가 전체 시간에서 작을 수 있다.

이는 구조와 측정 조건에서의 해석이다. cold I/O, 장기간 누적된 대형 DB, 특정 한 달 조회에서의 이득이 작다는 실측 결론은 아니다. 월별 사전 집계 테이블을 따로 두어 읽을 행 수 자체를 더 줄이는 방식도 이번 월 PK 실험과는 별도다.

## 4. 저장 공간과 쓰기 비용이 늘어난 원인

대표 조건인 **100,000건·세션당 100건**의 월→세션 후보를 `dbstat` 항목별로 나누면 다음과 같다. 세 프로세스의 점유 중앙값이며 WAL·TEMP·빈 페이지를 제외한다.

| 구성 | 기존 → 월→세션 | 변화 |
| --- | --- | --- |
| 집계 본체 두 개 | 1.391 → 1.383 MiB | 0.008 MiB 감소 |
| 기존 날짜/프로젝트 보조 인덱스 네 개 | 0.906 → 0.984 MiB | 0.078 MiB 증가 |
| 새 세션/모델 보조 인덱스 세 개 | 0.000 → 0.887 MiB | 0.887 MiB 증가 |
| 집계 meta | 0.004 → 0.004 MiB | 변화 없음 |
| **합계** | **2.301 → 3.258 MiB** | **0.957 MiB 증가, 41.6%** |

증가분의 약 **92.7%는 새 보조 인덱스 세 개의 점유**다. 월 PK 자체의 크기 증가만으로 설명할 결과가 아니다. 본체의 페이지 점유는 오히려 소폭 감소했으며, 페이지 충전 상태도 점유에 영향을 주므로 이를 데이터 압축 효과로 해석하지 않는다.

`WITHOUT ROWID`의 보조 인덱스는 원본 행을 찾기 위한 PK 컬럼도 저장한다. 인덱스에 이미 있는 동일 컬럼은 중복 저장을 생략한다. 월 후보는 PK에 `local_month`를 추가했으므로 기존 보조 인덱스가 보유하는 행 식별 정보도 달라진다. [SQLite 파일 형식: 보조 인덱스](https://www.sqlite.org/fileformat2.html#suppression_of_redundant_columns_in_without_rowid_secondary_indexes).

집계 재입력 때는 본체뿐 아니라 추가 인덱스에도 행을 넣어야 한다. 이 유지 비용 증가와 함께 재입력 시간이 49.83→69.17 ms, **38.8% 증가**했다. 다만 PK 변경만 한 후보와 인덱스만 추가한 후보를 분리하지 않았으므로 38.8%를 각각의 요인으로 배분할 수는 없다.

월 선두 PK에서는 같은 세션의 여러 달이 서로 다른 월 구간에 나뉜다. 세션 단위 접근을 보완하려고 인덱스를 추가한 선택에도 공간·쓰기 비용이 붙는다. 실제 세션 집계 계획에서도 기존에는 없던 `USE TEMP B-TREE FOR GROUP BY`가 월 후보에 나타났다. 한 접근 순서를 바꾸면 다른 조회·갱신 경로도 함께 평가해야 한다.

## 5. 수치가 보여 주는 채택 판단

아래는 모두 **100,000건·세션당 100건** 조건이다. 첫 세 행은 같은 물리 배치 실험 회차다. 마지막 행은 별도 최종 증분 실험이므로 시간 자체를 앞 행들과 비교하지 않는다.

| 측정 작업 | 기존 → 후보 | 판단에 미친 영향 |
| --- | --- | --- |
| 월→세션: 월별 제공자 조회 | 7.17 → 6.23 ms, 13.1% 단축 | 조회 이득은 있었고 절대 차이는 0.94 ms였다. |
| 월→세션: 월별 모델 조회 | 22.02 → 28.82 ms, 30.9% 증가 | 같은 월별 조회도 집계 기준에 따라 결과가 달랐다. |
| 월→세션: 집계 전체 재입력 | 49.83 → 69.17 ms, 38.8% 증가 | 집계 공간 41.6% 증가와 함께 유지 비용이 늘었다. |
| 증분 처리: 요청 한 건 추가 | 24.12 → 15.93 ms, 33.9% 단축 | WAL도 217.30→72.45 KiB로 줄었다. |

월→모델 후보는 세션당 10,000건 조건에서 월별 모델 조회가 2.73→2.20 ms로 **19.3% 단축**되기도 했다. 따라서 월 배치의 읽기 이득이 전혀 없었던 것은 아니다. 읽기·쓰기 호출 비율을 적용한 종합 부하 시험은 하지 않았고, 현재의 반복 갱신 요구와 저장 비용을 기준으로 채택하지 않았다.

증분 처리에도 비용이 있다. 100,000건·세션당 100건의 전건 제목 변경은 17.750→25.668초로 **44.6% 증가**했다. 모든 행이 달라지면 입력 비교와 실제 쓰기를 모두 부담한다.

## 6. GROUP BY가 많아서 복합 인덱스가 유리한가

**유리한 이유는 GROUP BY의 개수보다 실제 필터·그룹·정렬 키와 인덱스 순서가 맞기 때문이다.** PK에 의한 클러스터링 자체도 복합 키로 구성할 수 있으며, 현재 집계 PK가 그 사례다. 복합 인덱스와 클러스터링은 함께 설계하는 요소다.

| 수단 | 줄이려는 비용 | 현재 적용의 의미 |
| --- | --- | --- |
| 세션 중심 복합 PK | 세션 범위 접근·변경 집계 키 탐색 | 세션 입력과 영향 날짜/프로젝트 갱신에 맞는 본체 순서 유지 |
| 날짜/프로젝트 복합 보조 인덱스 | 조건에 맞는 입력을 찾는 비용 | 본체 순서를 바꾸지 않고 다른 탐색 경로 제공 |
| 일별 사전 집계 | 조회 때 읽고 합산하는 입력 행 수 | 전체 요청 대신 병합 가능한 일별 상태 조회 |
| 증분 처리 | 달라지지 않은 facts·자식 행·집계의 반복 쓰기 | 변경 요청과 이전/새 날짜·프로젝트 구간만 반영 |
| transaction batching | 트랜잭션 시작·커밋의 반복 | 기존 구현 유지. 이번에는 독립 효과를 측정하지 않음 |

인덱스 순서와 맞지 않는 GROUP BY에는 여전히 임시 B-tree가 필요할 수 있다. 현재 기간 인덱스도 모든 지표를 포함하는 커버링 인덱스가 아니므로, 모든 GROUP BY를 인덱스만으로 끝낸다고 설명할 수 없다.

이번 증분 개선은 기존 PK와 인덱스를 유지한 채 영속 쓰기를 줄여 얻었다. 요청 차이 저장과 영향 구간 재집계를 함께 적용했으므로 두 요소의 기여도도 분리하지 않았다. 집계 갱신은 영향 구간의 현재 facts에서 합계·분모·MIN/MAX를 다시 계산하며, 변경 키가 32개를 넘으면 세션 집합 재집계로 전환한다. 입력 전체를 읽고 비교하는 비용은 남는다. 구현은 [sessions.ts](../../src/summary/db/sessions.ts), [rollups.ts](../../src/summary/db/rollups.ts)에 있다.

## 7. 월 단위 접근의 이점을 더 확인할 실험

이번 결과로는 현재 후보의 미채택을 설명할 수 있다. 사용자가 예상한 특정 월 탐색 이득까지 판단하려면 다음 조건을 나누어 측정해야 한다.

1. **변경 요인 분리:** 기존 배치, PK만 월 우선으로 변경, 보조 인덱스만 추가, 둘 다 변경한 구성을 비교한다. 세션 갱신 비용도 함께 본다.
2. **조회 목적 분리:** 전체 기간 월별 GROUP BY와 특정 한 달 조회를 나눈다. 후자는 기존 `local_day` 범위 조건과 후보 `local_month` 조건을 비교하고, 가능한 조회는 월 컬럼을 GROUP BY에도 직접 사용한다.
3. **기간·선택도 분리:** 여러 해에 걸친 데이터에서 한 달·여러 달·전체 기간을 나눈다. warm 조회와 별도로 통제된 cold I/O를 측정한다.
4. **실제 갱신 연결:** 월 후보에서도 제품 증분 저장 API로 한 건 추가·날짜 이동·삭제를 수행하고 결과·WAL·시간을 대조한다.
5. **읽기·쓰기 비율 반영:** 실제 호출 빈도를 확보해 조회 절감 시간과 갱신 증가 시간을 함께 계산한다. 월별 사전 집계 후보는 저장·유지 비용을 포함해 별도로 비교한다.

이 실험들은 후속 검증 항목이며 이번 문서 작성 중 실행하지 않았다. 현재 자료에서 확정되는 사실은 전체 기간 월별 조회의 임시 그룹화가 남았다는 점, 월 후보에 추가 인덱스 비용이 붙었다는 점, 그리고 소수 변경 저장에서 증분 처리의 이득이 확인됐다는 점이다.
