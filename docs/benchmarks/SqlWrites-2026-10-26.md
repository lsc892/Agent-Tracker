## 표를 읽는 기준

- **DB 점유**: main DB의 표·인덱스가 차지하는 물리 페이지 합(`dbstat`). WAL·TEMP·빈 페이지를 제외한다. `.sqlite` 파일 전체 크기와는 다르다. A의 DB 점유는 모든 시나리오를 마친 후 측정한 값이다.
- **집계 점유**: 일별 집계 표 두 개·meta·관련 보조 인덱스의 물리 페이지 합. B~D는 이 범위의 저장 공간만 비교한다.
- **WAL 파일**: 작업 직전 TRUNCATE checkpoint 후 작업이 끝났을 때의 파일 크기다. 영구 DB 크기나 디스크 장치의 총 쓰기량을 뜻하지 않는다.
- **시간**: 기존→실험 중앙값과 절대 차이·증감률을 함께 표시한다. 작은 값일수록 빠르다. 차이와 비율은 반올림 전 수치로 계산했다. 원시 표본과 최소·최대는 JSON에서 확인할 수 있다.
- **대조군**: A는 최종 보완본의 새 3쌍 비교, B~E는 초기 증분본을 포함한 별도 인덱스 실험 회차다. transaction batching은 양쪽에 이미 적용돼 있었다.

## 측정 조건과 범위

환경: Node v24.19.0, SQLite 3.53.3, Intel(R) Core(TM) i5-8250U CPU @ 1.60GHz, win32.

실제 DB는 2026-10-26의 읽기 전용 고정 사본이다. 요청 952건·모델 facts 847건·세션 261개·원본 파일 313개이며, 원본 metadata 갱신과 JSONL 재파싱 비용은 측정 범위에 포함하지 않았다. 합성 데이터는 실제 로그 파일 수를 의미하지 않는다.

A는 데이터마다 별도 프로세스로 최종 3쌍을 순차·교대 실행했다. B~D의 전체 재입력은 3개 프로세스×3회=9표본 중앙값이며 조회는 각 프로세스 3회 중앙값의 중앙값이다. 같은 데이터라도 실험 회차가 달라 대조군 시간이 다를 수 있다. 위 증감은 항상 해당 실험 회차의 대조군에서 계산했다.

초기 실험의 전건 제목 변경 기준 표본 하나에는 약 2,420초의 비정상 대기가 기록됐다. 해당 원본은 JSON의 indexExperiments에 보존했지만 A의 최종 쓰기 비교에 재사용하지 않았다. B~D의 집계 재입력 시간에도 해당 전건 제목 변경 표본은 포함하지 않는다.

- 기준 소스: `d8ef1bdb6fd93ecad56019b5df836174da636002`. 변경 전 `src`·`dist`와 SHA-256을 로컬 `tests/.cache/sql-write-baseline-d8ef1bd`에 보존했다. 기준 측정을 먼저 실행하고 수정한 제품을 비교했다.
- 실제 설치 DB는 읽기 전용 SQLite backup으로 복사했다. 원본의 데이터·스키마·통계·인덱스를 수정하지 않았다. 보고서에는 원본 경로·세션 식별자·제목·본문을 넣지 않았다.
- 합성 데이터는 결정적 seed를 사용한다. 저장된 모델 단가 버전과 비용을 제품 형식으로 준비해 fixture 버전 교체를 무변경 저장 비용으로 세지 않았다.
- 데이터마다 3쌍 이상을 순차 실행하며 구현 순서를 교대했다. 각 표본은 별도 Node 프로세스다. 소수 변경 직전 동일 세션을 한 번 복원해 준비 실행하고 checkpoint 후 측정한다. 조회는 최초 실행을 제외한 3회 warm 측정이다.
- 쓰기 시간은 실제 `replaceSessions()` 호출의 BEGIN부터 COMMIT 반환까지다. 입력 준비·복원·checkpoint·해시 계산·정확성 비교는 제외한다. 전체 저장의 스트리밍 입력을 소비하는 비용은 호출 안에 포함한다. WAL 자동 checkpoint와 synchronous 설정은 제품 기본값을 유지한다.
- JSONL 탐색·파싱·worker IPC·UI·quota 호출과 manifest 파일 metadata 갱신 비용은 측정하지 않았다. 실제 데이터 측정도 저장된 요청 facts를 재입력하는 DB 단계 비교다. 3초 UI 정지 전체를 재현하거나 해소했다고 해석하지 않는다.
- 인덱스 후보의 쓰기는 같은 일별 집계 snapshot 전체를 한 transaction에서 지우고 재입력하는 별도 replay다. 월 후보의 실험 schema는 제품 저장 API로 갱신하지 않았다. 따라서 이 replay 시간과 `replaceSessions()` 시간을 직접 비교하지 않는다.
- 월/일 후보는 PK 물리 배치와 보조 인덱스 효과를 비교하며 제품 SELECT builder를 유지한다. 월 전용 SELECT 재작성이나 별도 월별 materialized view의 효과까지 검증한 결과는 아니다.

### PK와 증분 처리의 구현 범위

기존 일별 집계 PK는 `(provider,session_id,project_key,local_day[,model_key])`다. 월→세션 후보는 월을 앞에 추가하고, 월→모델 후보는 모델 집계에 `(local_month,provider,model_key,session_id,project_key,local_day)`를 사용한다. 일→제공자 후보는 `(local_day,provider,session_id,project_key[,model_key])` 순서다.

SQLite의 `WITHOUT ROWID` 표는 PK가 물리 배치를 정한다. 원본 `turn_summary`의 정수 ID 자동 생성과 FK는 유지했다. `WITHOUT ROWID`가 `last_insert_rowid()`를 갱신하지 않는 점도 원본 표를 그대로 둔 이유다. [SQLite 공식 설명](https://www.sqlite.org/withoutrowid.html).

A의 증분 집계는 영향 구간의 현재 facts에서 합계·표본 수·MIN/MAX를 정확하게 다시 계산한다. 영향 키가 32개를 넘으면 기존 세션 집합 SQL로 전환하고 이후 구간 수집을 생략한다. 현지 날짜 경계 캐시는 32개다. 변경 한 건의 숫자만 더하고 빼는 delta-only 방식은 아니다.

입력 `updated_at`은 명시되면 그대로 사용한다. 생략된 동일 요청은 기존 시각을 유지하고 통계가 달라진 요청만 현재 시각을 기록한다. 정상 재검사 시각은 `manifest.recorded_at`에 남는다. Skill 보존·삭제 원본 사용량 보존·일괄 rollback·단일 소비 iterator 계약도 유지한다.

## 정확성과 실행 계획

초기 실험의 첫 기준 표본에서 각 추가·수정·삭제·전체 저장 후 전체·일·월·프로젝트·세션의 모든 결과 행을 제공자/모델 두 기준의 raw SQL과 대조했다. 최종 측정은 같은 DB 파일 해시를 확인하고 모든 표본의 facts와 전체 집계 결과 해시를 이 독립 기대값과 비교한다. 정수와 식별 문자열은 그대로 비교하고 raw 대조의 실수 허용 오차는 상대 `1e-9`다. 집계 해시의 비정수는 물리 순서에 따른 부동소수 누적 차이만 무시하도록 유효숫자 10자리로 정규화한다. 저장 결과 자체는 반올림하지 않는다. FK 검사는 각 변경 후 수행한다.

`EXPLAIN QUERY PLAN`과 `EXPLAIN`은 월·세션·전체 조회, 두 집계 기준 모두 기록한다. 현재 제품의 세션 조회는 PK 앞 두 키로 좁힐 수 있고 날짜·프로젝트 보조 인덱스는 유지한다. 전 범위 월/전체 집계는 입력 rollup 전체를 방문할 수 있으며, 월이 선두인 PK를 만들어도 기존 날짜 표현식과 GROUP BY에 임시 B-tree가 남을 수 있다. `SCAN USING INDEX`를 선택 범위 탐색으로, `EXPLAIN`을 실제 방문 행 수나 cold I/O 측정으로 해석하지 않는다.

추가 테스트는 영속 테이블의 INSERT/UPDATE/DELETE를 trigger로 관측해 동일 입력의 쓰기 0회, 추가 요청 외 기존 ID 보존, 영향 없는 날짜의 집계 쓰기 생략을 확인한다. 날짜/프로젝트 이동·삭제·모델 변경·Skill 보존·DST·지원 범위 밖 시각·중복/중간 실패 rollback·33개 이상 구간의 집합 처리도 검증한다.

## 복잡도와 비용

`N`: 전체 저장 요청 수, `R`: 교체 입력의 요청 수, `M`: 해당 모델·Skill 행 수, `C`: 실제로 달라진 요청 수, `D`: 영향 날짜/프로젝트 키 수, `K`: 그 구간의 현재 요청 수다.

| --- | --- | --- |
| 입력/검증 | `O(R+M)` 및 인덱스 탐색 | 입력 전체를 여전히 비교. `O((R+M) log N)` 범주의 탐색·TEMP 비교가 추가됨 |
| 영속 facts 쓰기 | 요청·모델·Skill·비용 전체 재삽입, 약 `O((R+M) log N)` | 달라진 요청·자식 묶음과 사라진 요청만 쓰기. 새 비용과 변경된 비용만 저장 |
| 일별 유지 | 교체 세션 전체 입력을 GROUP BY | 희소 변경은 영향 구간의 `K`건을 집계. 보조 범위 인덱스가 없으면 구간 탐색은 같은 세션의 다른 행도 읽어 최악 `O(D·R)` 가능. `D>32`는 세션 집합 SQL |
| JS 보조 공간 | streaming 입력과 요청별 상태 | 같은 streaming 경계 + 날짜 경계 캐시 32개. 전체 요청 Map은 만들지 않음 |
| TEMP 공간 | 세션/원본 보존·기존 Skill 저장 | 방문 요청 `O(R)`, 요청별 모델/Skill staging, 영향 키/입력 `O(D+K)` 추가. FILE TEMP와 기존 cache 예산 사용 |

행 수 전체에 대한 입력 비교가 남으므로 100,000건이 들어오는 저장을 `O(C)`라고 부를 수 없다. 개선의 핵심은 영속 B-tree·FK 자식·WAL·집계 행의 불필요한 변경 감소다. 전건 변경에서는 비교 비용과 실제 쓰기를 함께 부담한다. 최초 구축·시간대 전환·오류 진단의 세션 재집계와 원본 재파싱도 남는다.

RSS/heap은 검증 후 관측값과 별도 프로세스의 lifetime peak다. 입력 fixture·전체 결과 검증·런타임·GC도 포함하므로 transaction만의 최대 할당량이나 고정 메모리 상한을 뜻하지 않는다. DB 공간은 `dbstat`의 실제 object 크기로 비교하고, 물리 배치 비교에서는 원본 제목 변경의 영향을 피하도록 rollup 표/인덱스 공간을 따로 본다.

## 재실행

보존된 기준 snapshot이 있는 이 작업 폴더에서는 다음 명령을 사용한다. `--real-db`에는 비교할 설치 DB를 지정하며 모든 변경은 임시 backup에서 수행한다.

```powershell
npm.cmd run benchmark:sql:writes -- --baseline=tests/.cache/sql-write-baseline-d8ef1bd "--real-db=C:\path\agent-tracker.sqlite" --output=tests/results/benchmarks/sql-writes-repeat.json
```

기본은 280건과 100,000건(세션당 100/10,000건), 3쌍, 모든 후보다. `--variants=before,incremental`, `--sizes=100000`, `--turns=100,10000`으로 범위를 제한할 수 있다. 기준 snapshot이 없다면 위 commit을 별도 checkout에서 설치·빌드하고 `dist`와 `manifest.json`의 `head`·`sourceSha256`을 준비한다. JSON의 baseline hash로 원본 소스를 대조할 수 있다.

`--expected=<기존 JSON> --variants=incremental`은 정확히 같은 DB 파일 SHA-256을 가진 합성 snapshot에 한해 검증된 기존 기준 표본을 재사용한다. 최종 보완본의 모든 변경 후 facts·집계 해시는 이 기준 결과와 다시 비교한다. 시각이나 입력이 달라져 snapshot hash가 다르면 이 경로는 실패한다.
