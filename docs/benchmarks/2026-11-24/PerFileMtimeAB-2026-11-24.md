# 파일별 수정 시각과 원본 해시 제거 A/B

2026-11-24, Asia/Seoul. 파일 내용 SHA-256, 읽기 전 파일 확인, 이동 재연결과 관련 저장 데이터를 제거하면 같은 입력에서도 읽기·파싱과 저장 시간이 줄 것으로 예상했다.

- A는 전체 스캔 기준 시각과 원본 내용 SHA-256을 사용한 직전 v23 빌드다. [이전 A/B의 B 빌드](FileWinnerUpsertAB-2026-11-24.md)
- B는 경로마다 `mtime_ms`를 비교하고 새 파일과 수정 시각이 다른 파일을 처음부터 읽는 v24다. 파일별 winner와 응답별 차분·요청 UPSERT 로직은 같다. [변경 판정](../../../src/summary/scanner/refresh/state.ts) · [파일 읽기](../../../src/summary/scanner/sourceReader.ts)

전체 재수집과 파일 읽기·파싱은 3쌍 모두 단축됐다. 양쪽 모두 689파일·372,649,102바이트를 읽었다. 파일 읽기·파싱 60.15ms와 SQLite COMMIT 13.69ms가 줄었다. 읽기 계측에는 Worker 결과를 기다리는 구간도 포함되므로 SHA-256 단독 비용은 분리하지 않았다. 최종 집계는 0.12ms 차이였다. 전체 재수집 피크 힙과 RSS의 쌍별 방향은 엇갈렸다.

1건 추가에서는 같은 파일의 같은 4,259,877바이트를 읽었다. 파일 읽기·파싱은 3쌍 모두 빨랐고, 전체는 3쌍 중 2쌍 빨랐지만 중앙값 차이는 4.18ms 늘었다. 무변경은 양쪽 모두 본문 0바이트였다. 1건 추가와 무변경의 전체 시간 및 평균 조회 성능은 표본 차이의 방향과 범위를 함께 봐야 한다.

## 조건과 정합성

- 이전 A/B와 동일한 689파일·1,473요청 사본을 사용했다. Windows x64, AMD Ryzen 5 7500F, Node 24.14.1, SQLite 3.51.2, 최대 4개 파일 Worker에서 시나리오마다 AB → BA → AB로 측정했다. 사전 DB 구축과 입력 복원은 타이밍 밖에서 수행했다. 합성 데이터, Webview 미리보기, 경로 이동, 수정 시각만 바뀐 같은 내용의 파일과 스키마 이관 시간은 이번 비교 범위 밖이다.
- 모든 9쌍에서 요청·모델·도구·비용 행의 해시와 조회 결과가 일치했다. 요청을 추가하면 매번 1,474요청·3,021,943,172토큰으로 +1요청·+130토큰이 반영됐다. 기간은 2020-01-01 UTC 이상 2035-01-01 UTC 미만이고, 시각 미상을 포함했다. Asia/Seoul 기준 일·월·세션·프로젝트 평균을 독립 계산으로 대조했다.
- 응답별 반영값 23,769행을 SQL로 재합산해 A/B 해시 일치, 응답 키 중복 0건, 합계 불일치 0건을 확인했다. 두 빌드가 처음부터 구성한 비교 DB는 1,940→1,894페이지로 184KiB 줄었다. v23 DB 사본을 v24로 열어 689개 원본 행의 ID·수정 시각과 1,473개 요청·응답 반영값이 보존되고 구형 열·테이블·인덱스가 삭제된 것도 확인했다. [원시 표본과 검증 결과](PerFileMtimeAB-2026-11-24.json)
