# 최종 winner Map 하나로 통합한 A/B

2026-11-24, Asia/Seoul. 사용자는 현재 로그에서 세 번만 비교하도록 요청했다. 파일별 비교를 없애면 파일 준비 비용이 줄 수 있고, 모든 유효 후보를 하나의 Map에 넣으면 최종 집계와 힙 사용량이 늘 수 있다고 가정했다.

- A는 `76f8ea7`의 파일별 winner Map과 중복 가능성이 있는 세션의 최종 Map이다.
- B는 작업 트리의 단일 winner Map이다. 파일에서는 후보를 모으고, 최종 집계에서 제공자·세션·응답 키로 winner를 한 번 선택한다.

## 측정 결과

B는 파일에서 걸러내던 반복 후보까지 최종 집계로 보내며, 모든 대상 세션의 winner를 한 Map에 모아 마지막에 합산한다. 최종 집계 시간과 관측 피크 힙이 늘어난 방향과 맞는다. 같은 689개 파일을 읽는 구간은 약 3.1초로, 전체 재수집 시간 차이는 12.05ms였고 세 쌍의 방향이 엇갈렸다. 1건 추가는 세 쌍에서 1.13~5.54ms 빨랐지만 최종 집계 자체는 0.052ms 늘었다. **단순화 효과는 확인했으며, 처리 속도 개선은 판단을 유보한다.** [기존 분기 제거](../../../src/summary/aggregation/memoryAggregate.ts)

## 조건과 정합성

- Windows x64, AMD Ryzen 5 7500F, Node 24.14.1, SQLite 3.51.2에서 각각 별도 프로세스와 최대 4개 파일 Worker를 썼다. 시나리오마다 AB → BA → AB로 3쌍을 측정했다. 각 빌드의 초기 사전 DB 구축과 조회 준비는 측정에서 제외했다. 별도 예열 표본과 합성 입력, 기존 v20 DB를 v21로 처음 갱신하는 비용은 미측정이다.
- 고정 사본은 Claude 12파일·15요청, Codex 677파일·1,458요청으로, 합계 689파일·372,649,102바이트·1,473요청·3,021,943,042토큰이었다. 1건 추가 시 두 빌드는 같은 Codex JSONL에 602바이트를 추가해 1파일·4,259,877바이트를 처리했다. 로컬 원본은 읽기 전용으로 열었다.
- 전체 재수집·무변경 갱신과 추가 표본 모두에서 요청·모델·도구·비용 facts 해시가 일치했다. 추가 결과는 매번 1,474요청·3,021,943,172토큰으로 **+1요청·+130토큰**이었다. 일·월·세션·프로젝트 평균 조회의 모든 페이지를 가져오고, 시작 시각 미상을 포함한 `2020-01-01 UTC` 이상 `2035-01-01 UTC` 미만을 대상으로 완료 요청을 분모에 넣었다. 각 조회의 그룹 수, 토큰, 요청 수와 평균은 JS 독립 계산과 일치했다.
- 추가분 복원 후 `applied_response`를 별도 SQL로 재합산했다. A/B 모두 23,769행과 해시가 일치했고, 최종 응답 키 중복과 요청 합계 불일치는 0건이었다. 측정 후 입력 사본의 파일별 SHA-256을 다시 확인했다. [원시 표본과 식별자](SingleWinnerMapAB-2026-11-24.json)
