## 2. 알고리즘과 정당성

기존은 전체 원본 DTO를 보관한 뒤 최종 winner Map을 만들었다. B의 non-legacy usage는 [fileId, rootId, responseId, originalRequestId, threadId, turnId, schema]를 키로 하는 같은 collector Map에 승자 DTO를 직접 저장한다. 원본 이벤트는 먼저 파일/root SHA 스트림과 응답·turn 의존성에 반영하며 탈락 DTO를 유지하지 않는다. 파일별 원본 순번을 해시에 포함해 순서 변경도 감지하고, 전역 절대 순번은 서명에 넣지 않는다.

최종 키는 제공자·최종 세션·응답과 Claude canonical request 또는 Codex thread/turn이다. 파일·root·원래 request ID를 분리한 provisional 그룹은 최종 그룹의 세분화다. 따라서 늦은 request ID 보정과 세션 귀속은 남겨둔 그룹을 합치는 단계가 된다. null request와 실제 문자열 no-req의 기존 SQL 충돌 규칙도 그대로 유지한다.

비교 순서는 (input+output, 원본 순번)의 최대다. 이 순서에 대해 max(max(A),max(B))=max(A∪B)이므로 각 세분 그룹의 승자만 비교해도 전체 원본의 승자와 같다. 합계가 안전한 정수 범위를 넘으면 BigInt로 비교한다. 토큰·모델·과금 필드를 원본 한 행에서 함께 선택하며 필드별 최대를 합성하지 않는다.

legacy usage는 연속 복사 접두사 비교에 순서 전체가 필요하므로 검증까지 보존한다. 도구·제어 이벤트도 접두사 제외가 끝날 때까지 보존한다. root를 provisional 키에 포함하므로 이후 필터가 다른 root의 생존 후보를 잃지 않는다. 탈락 행의 파일/root별 최초 순번·최소 offset은 anchor로 남긴다. 청크 undo는 승자 교체 이전 DTO·해시·새 의존성·anchor·파일 순번까지 복구하며 성공하면 즉시 해제한다.

최종 보정 단계에는 축약 후보 참조를 가리키는 임시 인덱스가 남는다. 이것은 전체 원본 DTO 사본이 아니다. SQL에 후보를 전수 적재하거나 SQL에서 이벤트를 읽어 Map을 구성하지 않는다. 선택된 DTO·제어 이벤트·anchor만 한 번 적재한다.

### 서명 버전 전환

기존 SHA는 늦게 확정되는 세션 정보 뒤에 원본 이벤트와 파일 metadata를 이어 붙인다. 같은 SHA bytes를 만들려면 원본 payload 보관이나 재읽기가 필요하다. B는 memory-events-greedy-v1의 파일/root 스트림과 memory-greedy-v1의 최종 metadata 결합으로 변경했다. 따라서 이전 SHA 문자열과의 동일성은 요구하지 않으며 원본 변화 감지·의존성과 집계 결과를 검증한다.

기존 DB에서 처음 재파싱한 범위는 한 번 dirty로 계산한다. 재파싱하지 않은 범위는 기존 서명을 유지한다. 영속 schema·parser version은 바꾸지 않는다. B는 새 방식 seed에서 정상 갱신을 측정하고 M은 이전 SQL seed 전환을 별도로 검사했다. B/M의 새 DB 초회 서명은 같고 M의 무변경 갱신은 기존 서명을 유지한다. M 시간은 상태별 한 번의 전환 검증 표본으로, 반복 성능 중앙값으로 해석하지 않는다.

## 4. 복잡도와 측정 조건

원본 byte B, 정규화 이벤트 E, 보정 전 후보 P, 보류 legacy/제어/도구 L, 고유 의존성 D, root R, 파일 F, 한 청크 undo J라고 하자. reader는 변경하지 않아 O(B)다. greedy usage 비교는 평균 O(E), collector 공간은 O(P+L+D+R+F+J)다. P는 최종 고유 응답 U보다 클 수 있고 모든 이벤트가 고유하면 O(E)다. flag buffer, 최종 참조 배열과 SQL/reader 메모리는 별도다.

전체 알고리즘이 선형인 것은 아니다. 원본 순서를 되찾기 위한 후보 정렬 O((P+L)log(P+L)), metadata의 정렬, 기존 부모 탐색 최악 O(F²)와 반복 prefix 필터 비용이 남는다. 중복이 적으면 저장량 절감이 작고 새 SHA·키·undo 비용이 더 클 수 있다.

각 데이터는 준비 3쌍 후 AB/BA 10쌍으로 측정했다. 각 변형/쌍은 새 프로세스이며 추가 상태는 매번 해당 변형의 seed를 복원한다. 추가분은 각각 독립적으로 같은 사전 상태에서 붙인다. 파일 전체 재파싱 정책은 그대로다. DB open/schema 생성·데이터 준비·검증·복원은 refresh 시간에서 제외하고 refreshSummary 반환의 COMMIT까지 포함한다. OS cache는 flush하지 않고 GC를 강제하지 않았다. 조회는 각 표본 준비 3회와 측정 10회이며 완료 요청 평균 분모를 유지한다.

실제 사본은 560파일·347,801,017 bytes·1,419요청이다. 합성 1만 요청은 100파일/세션당100요청, 100요청은 10파일/세션당10요청이며 제공자를 교대하고 10프로젝트·14일에 분포한다. 원본 로그·credential·대화 본문은 보고서에 저장하지 않는다.

## 5. 판단

알고리즘 정합성 가정은 성립했다. 메모리 절감은 반복 정정 10,000건에서 DTO 1개 보관으로 확인했지만 실제 입력 전체에서는 collector 보관 DTO가 39873 → 39606개(0.67% 감소)였다. 실제 진단 heap 표본은 96.68 → 107.73 MiB로 늘어 process 전체 메모리 이득은 확인되지 않았다.

실제 초회 시간 15055.10 → 14870.67 (+1.2%)의 분포는 A 12891.74–15584.70, B 13068.36–15406.18 ms로 겹친다. 큰 속도 개선으로 단정하지 않는다. 안전하게 즉시 합칠 수 있는 중복이 적고, 파일/root SHA 상태·의존성·키·정렬·undo 비용이 추가된다. 코드상의 추가 비용과 측정값은 확인했지만 각 요인의 시간·메모리 기여율은 분리 측정하지 않았다.

greedy 통합과 정합성 검증 결과는 과거 실험 기록으로 보존한다. 후보를 철회한 뒤 실험 워크트리는 최초 전체 DTO 방식으로 복원했으며 제품 dev의 성능 개선으로 채택하지 않았다.

## 6. 후보 철회와 최초 DTO 방식 복원

2026-11-06 사용자의 선택에 따라 greedy 후보를 철회하고 최초 DTO A/B의 B 구현으로 복원했다. 정합성 통과와 성능 개선을 구분하며, 이번 후보는 파싱·메모리 개선안으로 선택하지 않는다.

구체적인 구성은 다음과 같았다.

1. DTO·토큰 객체를 복사하고 문자열을 정규화했다.
2. `[fileId, rootId, responseId, originalRequestId, threadId, turnId, schema]`로 보정 전 후보를 세분화해 승자를 선택했다. 최종 키가 같은 응답도 파일·root·원래 request ID가 다르면 후보로 남았다.
3. 원본 서명을 파싱 중에 갱신하면서 같은 root의 해시 상태를 이벤트마다 복사하고 undo 복구 함수를 만들었다. 서명 계산 자체는 원래 필요했던 작업이며, 처리 위치 이동과 새 복구 비용을 구분해야 한다.
4. 접두사 검증과 최종 중복 제거에서 후보를 정렬·순회하고 별도 최종 winner Map을 구성했다. SQL 적재 전 결과 정렬과 파일별 서명용 정렬도 수행했다.

승자 비교의 최대값 결합법칙은 맞았지만 전체 파이프라인의 작업량은 충분히 줄이지 못했다. 실제 보관 DTO 감소가 267개에 그친 상태에서 키·해시 상태·복구 객체·순회·정렬이 남았다. 파싱 구간은 측정한 모든 경우에서 악화했고 실제 heap 표본은 96.68→107.73 MiB로 증가했다. 각 내부 비용의 기여율을 분리 측정한 것은 아니므로 특정 작업 하나가 악화분 전부를 만들었다고 단정하지 않는다.
