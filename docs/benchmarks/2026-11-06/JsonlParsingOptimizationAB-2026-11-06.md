# JSONL 파싱·중복 제거 A/B

측정 기준일: 2026-11-06, Asia/Seoul. A는 `80fc586`의 현재 구현이다. 별도 `experiment/jsonl-parsing-2026-11-06` 워크트리에서 줄 공급과 응답 중복 제거만 비교했다. `dev`에는 반영하지 않았다.

가정: 줄별 바이트 구간 참조가 문자열 분할 비용을 줄이고, Map이 SQL 응답 정렬·반복 조회를 줄일 수 있다. 이는 에이전트의 검증 가정이며, 사용자 요구는 파싱·중복 제거 범위에서 초회·소량·대량 추가 갱신의 시간과 공간을 비교하는 것이다.

## 1. 현재와의 차이

| 요구 방식 | 현재 A | 실험에서 추가한 차이 |
| --- | --- | --- |
| LF 검색·원본 offset | 이미 숫자 인자 `Buffer.indexOf(10, start)` 사용. 원본 바이트 길이로 offset 계산 | 기존 검색 재사용. 별도 native SIMD S1은 미구현·미측정이며, 이 PC의 SIMD 명령 실행을 확인했다고 주장하지 않음 |
| R1: 제한된 청크와 줄 구간 참조 | 64KiB 청크 안의 완성 구간을 한 번 UTF-8 변환·`split`; 경계 줄만 조립 | 완성된 줄마다 `subarray(index, end).toString('utf8')`. 이미지·경계 줄의 기존 조립 경로 유지 |
| R2: 전체 파일 Buffer | 원본을 64KiB 이하씩 읽고 즉시 파싱 | 관측한 원본 전체를 먼저 Buffer에 읽고 64KiB view로 공급. R1과 같은 줄 해석을 사용해 입력 공급 차이를 분리 |
| P1/P2: 표식으로 관련 기록 선별 | 비어 있지 않은 모든 완성 줄을 JSON 해석한 뒤 제공자 파서로 전달 | 기존 오류·메타정보 계약을 보존하는 생략 근거가 없어 미구현·미측정. 아래 반례 참조 |
| 안정 키 Map 중복 제거 | SQL `row_number()`로 응답별 승자 선택. Claude의 누락 request ID 보정 | 원본 TEMP 이벤트는 보존하고, 두 차례 순회하는 Map으로 승자 ID만 선정한 뒤 기존 형태의 `winners` 구성 |
| dirty 요청 처리 | 전수 파싱 뒤 기존 영속 turn metadata의 의미 서명을 비교해 변경 요청만 반영 | 기존 구현 재사용. 집계 쿼리·영속 저장 스키마·캐시 형식은 변경하지 않음 |

Worker/LPT 병렬화, 추가 구간만 읽는 offset 캐시, `.pkl` DTO 캐시와 dirty SQL 저장 구조 변경은 사용자가 좁힌 파싱·중복 제거 범위에서 제외했다. 파일 발견·quota·화면 기능도 변경하지 않았다.

### 표식 선별을 생략 최적화로 구현하지 않은 근거

원본 빌드에서 다음 반례를 실행해 확인했다.

- `usage`가 없는 무관해 보이는 줄도 잘못된 JSON escape가 있으면 `parse-error`를 내야 한다. 큰 줄은 LF에 도달하기 전에도 이미지 escape·제어 문자·보관 byte 예산 검증이 필요하다.
- Claude의 알려지지 않은 이벤트도 `promptId`, `sessionId`, `cwd`, 결제 문맥을 변경할 수 있다. Codex의 알려지지 않은 `event_msg` 내부 종류도 root·turn 문맥을 변경할 수 있다.
- `us\u0061ge`는 원본에 `"usage"` 표식이 없지만 JSON 해석 후 유효한 usage 키다. 공백과 청크 경계 역시 고정 문자열만으로 선별할 수 없다.
- 제목·도구 호출·모델·요청 시작/종료·누계 검증에는 usage가 없는 기록도 필요하다. prefix 뒤의 필드와 JSON 오류를 보지 않고 버릴 수 없다.

이 계약을 지키려면 불확실한 줄을 기존 경로로 보내거나 별도 JSON 검증·필드 선별기를 구현해야 한다. 전자는 JSON 해석 횟수를 줄이는 근거가 없고, 후자는 이번 최소 변경 범위를 넓힌다. 따라서 `R1+P1`, `R2+P1`, `R1+P2`의 유효한 생략 경로 성능은 **미측정**이다. 아래 R1/R2 수치는 기존 JSON 전체 해석을 유지한 줄 공급 비교다.

## 2. 후보별 결과

Windows, Node v24.14.1, AMD Ryzen 5 7500F에서 실행했다. 각 후보를 직렬로 측정해 다른 벤치마크와 겹치지 않게 했다. 준비 3회 후 AB/BA 교대로 각 10회 이상 측정했으며, OS 파일 캐시는 비우지 않았다. 표는 중앙값 ms이고 개선율은 `(A-B)/A×100`이다. 양수는 개선, 음수는 악화다. 서로 다른 실행의 A 수치를 섞어 비율을 만들지 않았다.

### 줄 공급: A와 R1/R2

읽기 표본은 요청 모양의 JSON 행으로, 실제 제공자 요청 집계가 아닌 리더 단독 비교다. 짧은 줄은 100행 30,090bytes와 10,000행 3,029,890bytes, 긴 줄은 100행 13,111,690bytes, 이미지 입력은 1행 8,388,813bytes다. CRLF·UTF-8·고정 token 수열을 사용했다.

| 입력 | A → R1 ms (개선율) | A → R2 ms (개선율) |
| --- | ---: | ---: |
| 짧은 줄 100행 | 0.758 → 0.887 (-17.0%) | 0.802 → 0.891 (-11.1%) |
| 짧은 줄 10,000행 | 13.236 → 15.054 (-13.7%) | 13.312 → 14.140 (-6.2%) |
| 긴 줄 100행 | 46.867 → 45.472 (+3.0%) | 43.059 → 42.829 (+0.5%) |
| 이미지 8MiB 1행 | 13.310 → 13.410 (-0.7%) | 13.153 → 13.916 (-5.8%) |

R2는 R1의 줄 해석도 포함하므로, 위 A→R2 결과만으로 전체 Buffer의 독립 효과를 판정하지 않았다. 같은 생성기로 만든 R1과 R2의 직접 비교는 다음과 같다.

| 입력 | R1 → R2 ms (개선율) | R2가 빠른 쌍 |
| --- | ---: | ---: |
| 짧은 줄 100행 | 0.870 → 0.802 (+7.8%) | 5/10 |
| 짧은 줄 10,000행 | 14.867 → 14.922 (-0.4%) | 5/10 |
| 긴 줄 100행 | 43.759 → 44.083 (-0.7%) | 6/10 |
| 이미지 8MiB 1행 | 12.688 → 13.850 (-9.2%) | 2/10 |

측정 구간은 open/read/JSON 해석/행·token 계수/close이며 입력 준비·해시·GC·IPC는 제외했다. 별도 읽기에서 batch 후 RSS·heap을 표본화했다. 프로세스 high-water RSS에는 모듈 적재·준비 실행·시간 측정도 포함되며, 표본 heap은 순간 최대값이 아니다.

R1의 10,000 짧은 줄은 10쌍 모두 A보다 느렸다. 긴 줄의 작은 개선은 7/10쌍에 그쳐 일반적인 개선으로 채택하지 않았다. R2의 high-water RSS 중앙값은 10,000 짧은 줄에서 A 49.87→58.50MiB, 긴 줄에서 65.22→85.27MiB, 이미지에서 47.62→71.56MiB였다. 전체 원본 Buffer 비용이 늘었고, 직접 R1→R2 비교에서도 일관된 시간 이득이 없었다.

R2는 정확성 기준도 통과하지 못했다. 정상·경계 입력 42건은 비교 항목이 일치했지만, 관측 크기보다 실제 파일이 짧은 경우 A는 정상 prefix 1행을 parser에 전달한 뒤 `file-truncated-during-read`를 냈고 R2는 0행을 전달했다. 오류 코드는 같아도 실패 파일에서 보존할 identity·metadata가 달라질 수 있으므로 **기각**했다. 조기 종료·오류 시의 read callback 시점과 선행 읽은 byte/batch 수는 정상 동등성 판정에서 제외했으며, 오류 전 prefix 차이는 별도로 실패로 기록했다.

원시 결과: [A→R1](JsonlParsingReaderR1AB-2026-11-06.json), [A→R2](JsonlParsingReaderR2AB-2026-11-06.json), [R1→R2](JsonlParsingReaderR1R2AB-2026-11-06.json), [R2 오류 계약](JsonlParsingReaderR2Validation-2026-11-06.json).

### 응답 중복 제거: SQL과 Map

동일한 TEMP 이벤트·파일 metadata에서 승자 선택만 측정했다. 아래 건수는 정규화 요청 수가 아니라 **usage 이벤트 수**다. 고유 입력과 응답당 10개 반복 입력을 나눴으며, Claude의 request ID 없음·단일 후보·복수 후보를 섞었다. 입력·테이블·인덱스 구축·검증·GC·프로세스 시작은 시간에서 제외했다.

| 입력 이벤트 | SQL → Map ms (개선율) | SQL → Map high-water RSS MiB |
| --- | ---: | ---: |
| 100개, 고유 | 0.557 → 0.828 (-48.7%) | 44.16 → 44.43 |
| 100개, 중복 | 0.590 → 0.675 (-14.4%) | 43.04 → 44.19 |
| 10,000개, 고유 | 28.812 → 82.187 (-185.2%) | 107.37 → 124.63 |
| 10,000개, 중복 | 29.759 → 60.676 (-103.9%) | 66.46 → 74.89 |

별도 GC 후 선택 직후 heap은 10,000 고유 입력에서 SQL 8.45→Map 31.16MiB, 중복 입력에서 7.90→13.85MiB였다. 이는 순간 최대 heap이나 Map의 살아 있는 객체 크기만을 뜻하지 않는다.

기존 선택 의미를 보존했다. 제공자·세션·응답·Claude canonical request 또는 Codex thread/turn을 키로 사용하며, `input+output`이 큰 **원본 행 전체**를 선택하고 동률은 최신 event ID로 결정한다. root·모델·비용·시각을 별도 max로 만들지 않는다. 예를 들어 `(input,output)=(100,30)` 뒤 `(110,10)`이면 기존 승자는 130token의 첫 행이다. 필드별 max `(110,30)`은 원본에 없는 140token을 만들어 정확성 실패다. 안전한 정수 성분의 합이 JS 안전 범위를 넘는 경우에는 정확한 합 비교도 유지했다.

모든 표본에서 독립적으로 지정한 승자 ID·canonical request·원본 필드와 A/B 해시가 일치했다. 누락 request ID 보정, `no-req` sentinel 충돌, 파일 간 복사, 제공자/세션/thread 구분, root 제외, 최신 동률, 정정 token과 큰 정수 합 경계도 검증했다. 원시 결과: [Map 중복 제거](JsonlParsingDedupAB-2026-11-06.json).

조회 SQL과 결과 의미는 변경하지 않았다. 위 시간 차이는 같은 결과를 반환한 별도 프로세스·DB 상태의 관측값이며 조회 최적화 효과로 주장하지 않는다.

정확성: 측정 360개 갱신 상태와 준비 108개 상태에서 요청·토큰·행 수·실패·raw fingerprint·이름/모델/도구/비용/진단 해시 및 독립 그룹 평균이 일치했다. 진단 36개 상태도 최종 A/B 대조를 추가로 통과했다. 실제 로그는 파싱 실패 0건이며, 합성 입력의 원본 기대 요청·토큰과 추가 건당 130token도 대조했다. raw SQL/rollup, FK/integrity, 스냅샷 복원 검증을 통과했다. 입력은 각 규모의 측정 전후 전체 해시를 확인했다.

원시 표본·환경·입력/소스/빌드 식별자: [전체 갱신 JSON](JsonlParsingRefreshAB-2026-11-06.json). 실행 기간: 2026-11-06 17:16:46 ~ 2026-11-06 17:34:48 (Asia/Seoul).

전체 갱신은 `refreshSummary` 반환까지이며 세션 COMMIT을 포함한다. DB 열기·빈 DB 스키마 생성·사본 준비/복원·검증은 제외한다. 무변경·각 추가 표본은 같은 A seed DB와 같은 원본 상태에서 시작한다. 소량은 Claude 1건·Codex 1건, 대량은 같은 Codex 파일에 100/1,000건을 추가한다. 추가량을 요청 수로 나눈 값을 1건 추가 시간으로 대체하지 않았다.

`parseAndStageMs`는 줄 구성·JSON 해석·제공자 처리·TEMP 적재를 포함하는 동기 batch 시간이다. `readerMs`, 집계 준비와 영속 저장 시간은 서로 포개질 수 있어 단순 합계나 차감으로 순수 디스크 시간·순수 중복 제거 시간을 만들지 않는다. 제목 metadata JSONL도 reader 계측에 포함되므로, 무변경 본문 `bodyBytes=0`이어도 metadata 행 처리량은 0이 아닐 수 있다.

별도 diagnostic 실행의 `adapterMs`는 `onRow` 안의 동기 TEMP INSERT까지 포함하고, `jsonParseMs`는 cached DTO 복원도 포함한다. 상세 clock·메모리 계측은 성능 판정용 10쌍과 분리했다. batch 후 메모리 표본은 순간 최대값을 놓칠 수 있고 프로세스 high-water는 앞선 시나리오와 검증까지 포함한다. 일/월/세션/프로젝트 조회는 완료 요청을 평균 분모로 사용하고 모든 결과 page를 반환할 때까지 확인한다. 고정 기간에는 10월 28일 추가 fixture도 포함한다.

## 3. 시간·공간복잡도와 판정 근거

기호: `B`는 처리하는 비압축 JSONL byte, `C=64KiB`, `L`은 최대 보관 줄 byte, `J`는 현재 JSON 객체 크기다. `E`는 중복 제거 대상 usage 이벤트, `U`는 승자 키 수, `R`은 Claude response 문맥 키 수, `T`는 전체 TEMP 원본 이벤트 수다. 식별자 길이는 고정된 것으로 보고 Map 접근은 평균적인 상수 시간을 가정한다. 실제 메모리에는 SQLite page cache·TEMP 파일·Zstd decoder가 별도로 있다.

| 구간 | 시간복잡도 | 추가 작업 공간 |
| --- | --- | --- |
| A: 청크 일괄 UTF-8·split | LF 검색·일반 JSON 해석의 선형 모델에서 `O(B)` | `O(C+L+J)`. 청크 문자열·분할 배열 포함 |
| R1: 줄별 Buffer view | `O(B)`. `subarray`가 UTF-8 문자열·JSON 객체 생성까지 없애지는 않음 | `O(C+L+J)`. 청크 분할 배열 대신 줄별 view·문자열 생성 |
| R2: 전체 원본 Buffer | `O(B)`. 파일을 한 번에 적재해도 모든 byte를 읽고 파싱 | 직렬 파일 처리에서 `O(Fmax+L+J)`, `Fmax`는 현재 파일의 원본 byte. 모든 파일 크기의 합을 동시에 유지한 것은 아님 |
| 기존 SQL 응답 선정 | 정렬은 대체로 `O(E log E)`. 누락 request ID의 상관 조회는 같은 response 후보를 반복 방문해 최악의 경우 이차 작업량 | TEMP 후보·정렬 공간 `O(E)` 계열. SQLite 임시 파일로 넘길 수 있어 전부 JS heap은 아님 |
| Map 응답 선정 | Map 핵심 두 순회는 기대 `O(E)`. 실제 구현은 `U`개 원본 event PK 조회·winner 인덱스 반영 비용도 필요해 `O(U log T)` 계열 비용이 추가됨 | canonical/승자 Map 추가 heap `O(R+U)`. 기존 `O(T)` TEMP 원본은 그대로 유지 |

SQL 상관 조회의 더 구체적인 row 방문량은 response별 누락 ID 행 수 `m_r`와 해당 response 후보 수 `q_r`에 대해 `Σ m_r q_r`다. 후보가 하나의 response에 몰리면 최악 `O(E²)`이며, JOIN·DISTINCT·인덱스 비용은 별도다. 이 최악 입력이 이번 실제 로그의 지배 병목이라고 확인한 것은 아니다. Map 키 직렬화·hash 비용까지 보면 키 문자열 길이도 작업량에 더해진다. Map으로 바꿔도 공통 TEMP 적재·인덱스·metadata·집계의 복잡도는 사라지지 않는다.

압축 입력은 원본 압축 byte와 해제 byte를 구분해야 한다. 압축·해제가 선형인 일반 모델에서 두 크기를 읽고 처리하는 비용과 decoder 공간을 더하며, 압축 원본 byte만으로 JSON 처리량을 설명하지 않는다.

초회에는 전체 대상 파일을 읽는다. 이후 추가 갱신도 변경된 파일의 시작부터 다시 읽고 영향받은 세션의 살아 있는 원본들을 재파싱한다. 따라서 파싱 비용은 **추가 byte만의 `O(ΔB)`가 아니라 실제 재파싱한 전체 byte에 비례**한다. 기존 turn metadata의 dirty 재사용은 후속 집계·저장 범위를 줄이는 기능이며 원본 추가분 전용 파싱 캐시가 아니다. 무변경 본문 파싱은 0이지만 파일 발견·metadata 처리 비용은 남는다.

- **R1 보류**: 차수가 줄지 않았고 대표적인 짧은 줄에서 악화했다. 현재는 청크 일괄 변환으로 UTF-8·문자열 처리 호출을 분담하고 있어, 줄별 view가 곧 전체 파싱 개선을 뜻하지 않는다.
- **R2 기각**: 읽기 전략만 비교해도 일관된 시간 이득이 없고 전체 Buffer 메모리가 늘었다. 잘림 오류 전 prefix 전달 계약도 달라졌다.
- **Map 보류**: 단독 선택에서는 모든 규모·분포가 느려졌다. 관측한 구조에는 SQLite→JS 후보 전달 두 차례, 키 문자열·Map 객체, JS→SQLite 승자별 INSERT가 있다. 정렬 절감보다 이 비용이 컸다는 해석이며, 각 내부 비용의 개별 CPU 시간을 직접 분리 측정한 것은 아니다.
- **제품 유지**: 유효한 조합을 채택할 근거가 없어 `dev`의 기존 리더·SQL 중복 제거를 유지한다. 워크트리에는 Map 후보와 필요한 검증·재생성 도구만 보관한다. JSONL 제품 소스는 A로 복원했으며 R1/R2는 테스트용 빌드 생성기로 재현한다.

## 4. 재현

최종 `npm run check`에서 타입 검사·린트·400개 테스트를 통과했다. 기존 제목 트랜잭션 벤치마크는 분리된 SQL 중 실제 `prepared_turns` 생성문을 캡처하도록 계측 어댑터만 맞췄다. 제품 measured source·build는 변경하지 않았으며, 최종 소스와 컴파일된 reader/staging이 측정 M과 같음을 확인했다. 실행기·공통 helper·의존성 lock 해시와 검사 결과는 [최종 검증 JSON](JsonlParsingVerification-2026-11-06.json)에 둔다. 문서 링크와 `git diff --check`도 확인했다. VS Code 설치·화면과 실제 quota는 이번 범위에서 검증하지 않았다.

기준 `80fc586`을 별도 위치에서 같은 의존성으로 컴파일해 A를 고정한다. M은 그 기준에 실험 워크트리의 `src/summary/staging.ts` 변경만 적용해 컴파일한다. A와 M 모두 JSONL 리더는 동일해야 한다. 빌드 사본의 소스·컴파일 파일 해시와 실행기 해시는 각 JSON에 남겼다.

R1/R2 생성기는 고정 A의 **컴파일된 reader만 변환**한다. 복사된 TS의 해시만으로 변형을 구분할 수 없으므로 `reader-variant.json`의 generator/build 해시와 raw JSON의 reader build 해시를 함께 확인한다. 아래 `<A>`, `<M>`, `<R1>`, `<R2>`는 서로 다른 고정 빌드 폴더로 치환한다. 출력은 기존 결과를 덮어쓰지 않는 새 경로를 사용한다.

```text
node tests/benchmarks/jsonl-full-build.cjs --source=<A> --output=<R1> --variant=R1
node tests/benchmarks/jsonl-full-build.cjs --source=<A> --output=<R2> --variant=R2
node tests/benchmarks/jsonl-chunks-ab.cjs --before=<A> --after=<R1> --output=<새-R1-JSON>
node tests/benchmarks/jsonl-chunks-ab.cjs --before=<A> --after=<R2> --output=<새-R2-JSON>
node tests/benchmarks/jsonl-chunks-ab.cjs --before=<R1> --after=<R2> --output=<새-직접비교-JSON>
node tests/benchmarks/jsonl-full-validate.cjs --before=<A> --after=<R2> --output=<새-계약검증-JSON>
node tests/benchmarks/jsonl-dedup-ab.cjs --before=<A> --after=<M> --output=<새-중복제거-JSON>
node tests/benchmarks/jsonl-parsing-ab.cjs --before=<A> --after=<M> --output=<새-갱신-JSON>
```

갱신 실행기의 `--workspace=<기존 snapshot 폴더>`는 동일한 원본 사본과 seed를 재사용한다. 새 실계정 snapshot을 만들면 현재 로그가 달라질 수 있으므로 입력 hash도 확인해야 한다. snapshot·DB·로컬 경로와 제목 metadata는 ignored `tests/.cache`에만 보관하며 보고서에는 본문·경로·세션 ID·credential을 남기지 않는다. 정상적인 R2 오류 재현 완료는 제품 정확성 통과를 뜻하지 않는다.
