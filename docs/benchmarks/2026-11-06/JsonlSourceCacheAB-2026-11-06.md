## 4. 구현과 정합성

SourceCache는 DB 연결을 key로 하는 WeakMap에 파일별 parser 결과를 보관한다. provider·경로·source root·크기·mtime·dev/inode·parser version과 이전 content hash/source identity가 일치하는 unchanged 관련 파일만 재생한다. 캐시 재생 직전 파일 상태를 다시 검사한다. 설정(수집 여부·line budget·parser version)이나 외부 DB writer의 data_version이 바뀌면 cache를 비운다. DB close·clearData도 cache를 해제한다.

캐시에 넣는 원본은 계보·legacy/prefix 제외 전 정규화 DTO와 parser identity다. 실패한 후보를 공개하지 않으며, 해당 연결 성분의 DB transaction이 성공한 뒤에만 새 snapshot을 승격한다. 파일이 바뀌면 기존 기여를 새 snapshot으로 교체한다. lifecycle 이벤트는 재생할 때 복사해 standalone main 보정이 캐시 원본을 바꾸지 않게 한다.

WinnerIndex는 파일별 원본 usage 후보를 provider/session/response bucket에 연결한다. 변경 파일에서도 같은 이벤트 위치의 값이 같으면 이전 DTO 참조를 재사용한다. 이전/새 응답의 후보 참조가 같은 bucket은 winner를 재사용하고 추가·수정·삭제된 응답만 다시 계산한다. 파일의 상대 순서가 바뀌면 그 파일의 응답도 무효화해 기존 (input+output 최대, 동점이면 최신 순번) 규칙을 보존한다. 원본 사용량이 감소하거나 파일이 삭제되면 다른 파일의 남은 후보로 winner를 선택한다.

전역 순번 숫자는 갱신마다 달라질 수 있으므로 cached winner는 현재 row 위치로 다시 연결한다. Claude의 늦은 request ID·모호성·no-req 충돌, Codex thread/turn 구분, legacy 복사 접두사 제외와 capability 중복 제거를 유지한다. 원본 서명·dirty 의존성·요청 부분 계산은 최초 DTO 방식과 같은 경로를 사용한다. 변경 없는 응답의 winner 계산은 생략하지만 영향 DTO의 참조 순회·원본 서명·선택 결과 SQL 적재는 남는다.

일반 입력 3규모와 별도 multi-source에서 요청별 facts·모델·도구·비용·진단·전체 합계·그룹 평균·기존 metadata SHA·의존성이 일치했다. 공개 rollup 조회는 원본 SQL 조회에, 평균은 정규화 요청을 직접 더한 JS 기대값에 대조했다. 합성 입력의 초기 요청/토큰 기대값과 추가 요청당130토큰, FK/integrity, 입력 전체 hash 복원을 확인했다. A source/build는 기존 SQL 커밋80fc586과 정합성을 검증한 최초 DTO B의 source/build와 정확히 같다.

npm run check의 타입 검사·린트·426개 테스트가 통과했다. 파일 cache12개, winner index8개, 원본 전체/이전 SQL winner oracle4개를 포함한다. 실패·삭제·동점·부모/legacy·late request ID·설정변경·close/reopen·clearData·외부writer·metadata commit실패·partial-line과 100회 고정 seed 교체 스트림을 확인했다.

## 5. 측정 방법과 복잡도

입력마다 준비3쌍 뒤 AB/BA10쌍을 같은 환경에서 실행했다. 각 variant/pair는 새 process와 빈 DB에서 initial을 측정해 cache를 채운 뒤 동일 DB 연결을 유지한다. initial 후 DB를 checkpoint해 seed를 만들고 다음 시나리오마다 persistent table 데이터만 같은 연결에서 복원한다. main.data_version이 변하지 않았는지 검사한다. source tail·mtime도 원복한다. 복원·추가 데이터 생성·검증·DB open은 refresh 시간에서 제외하고 세션 COMMIT까지 포함한다. 각 추가 시나리오는 동일한 기본 요청 상태에서 시작한다. file/index cache는 같은 worker의 연속 갱신 상태이며 직전 추가 후보는 다음 변경 파일 교체에서 제거한다.

OS cache를 flush하거나 GC를 강제하지 않았다. 별도 진단1회씩도 결과를 대조했다. 기간·timezone·완료 요청 평균 분모와 pagination 조건을 고정했다. 원시 표본에는 source/build/runner/input 식별자, 파싱 byte·파일 수·cache hit·winner 재계산/재사용·heap/RSS와 cold reopen 결과를 보존한다.

실제로 다시 읽는 변경 파일 전체 byte를 B_c, 영향 DTO를 E_a, 전체 보관 DTO를 E_c, 무효화한 응답 후보 수를 W_Δ, 파일 수를 F라고 하자. 캐시가 없는 관련 파일도 B_c에 포함한다. reader/adapter는 O(B_c), cache 재생과 참조 확인·기존 서명 처리는 O(E_a), winner 재선정은 해당 후보 W_Δ에 비례한다. 파일 metadata 전수 확인 O(F), 파일 순위 정렬과 기존 prefix 부모 탐색·metadata/SQL 비용은 별도로 남는다. 새로 추가된 byte만 읽거나 추가 요청 수에만 비례하는 알고리즘은 아니다. 장기 cache 공간은 O(E_c+응답 후보 참조 수+F)이고 갱신 중 staging과 SQL 메모리가 더해진다. 원래 DTO 방식보다 worker의 갱신 사이 메모리가 늘어나는 선택이다.

## 6. 판단

파일 재파싱과 winner 계산량을 줄인다는 가정은 일부 조건에서 성립했다. 일반 입력과 큰 unchanged sibling이 있는 별도 입력을 합쳐 하나의 보편적 개선율로 제시하지 않는다.

기존 실제 입력의 Codex1건 추가는 345.14 → 326.75 (+5.3%)였고 B가 빠른 쌍은 6/10이다. 두 방식 모두 파일 한 개를 읽으므로 본문 I/O 감소는 없다. winner는 신규1개만 재계산하고 기존288개를 재사용하지만, 변경 파일 전체 파싱과 기존 서명·SQL 준비·저장 비용은 남는다. 범위가 겹치고 빠른 쌍의 비율이 낮으면 일반적인 성능 개선으로 단정하지 않는다.

여러 파일 세션의 Codex1건 추가는 155.25 → 100.66 (+35.2%)이고 B가 빠른 쌍은 10/10이다. unchanged sibling의 본문 읽기·파싱을 생략하는 차이를 직접 확인했다. 이 합성 fixture는 큰 변경 없는 파일이 있는 경우의 효과이며 모든 실제 사용량에 같은 개선율을 적용하지 않는다. 초회 비용·메모리·cold reopen 조건과 함께 결과를 판단한다. 개별 내부 비용의 기여율을 분리 측정한 것은 아니다.

## 7. SQL TEMP와의 직접 비교

위 결과의 A는 최초 DTO 구현이다. 기존 SQL TEMP와 현재 캐시 Map의 구간별 직접 비교는 [후속 비용 분석](./JsonlStageCostAB-2026-11-06.md)에 따로 기록한다. 읽기·DTO 입력·실제 INSERT·winner·원본 서명·집계·저장의 중첩을 제거해 비교하며, 기존 SQL의 dirty 우선 처리와 현재 Map의 전체 영향 후보 처리 순서 및 공간복잡도를 구분한다.

후속 분석에서는 최초 DTO 전환 시 이름 metadata의 SQL batch까지 사라진 부작용을 확인했다. 전체 무변경 흐름에서 이름 수집은 기존 SQL 7.52ms, 현재 Map 60.99ms, 이름 SQL batch만 복원한 Map 7.98ms였다. 이 부작용은 최초 DTO와 현재 캐시가 공유하므로 위 DTO→캐시 비교의 차이 원인과 구분해야 한다. SQL→Map 전환의 지연을 Map winner 알고리즘 자체에 귀속한 설명은 후속 원인 분리 결과로 정정한다.
