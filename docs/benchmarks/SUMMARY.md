# 벤치마크 SUMMARY: 병목을 줄여 온 과정

정리: 2026-10-31, Asia/Seoul. 개선은 **원본 읽기·파싱 → 조회 때 합산할 입력 → 갱신 때 반복해서 쓰는 데이터** 순서로 진행됐다. 그 과정에서 조회만 빨라지고 갱신이 느려지는 선택을 되돌렸고, 현재는 큰 세션의 소수 변경에만 추가 비교 비용을 쓰도록 좁혔다.

아래는 당시 기록을 연결한 설명이다. **단계별 입력·장비가 달라 개선율을 곱해 전체 누적 개선율로 계산할 수는 없다.** 같은 입력으로 네 구조를 다시 비교한 마지막 표에서만 단계 간 변화와 최종 개선율을 함께 제시한다. 비율은 원시 중앙값의 `(후 / 전 − 1) × 100`이며, 시간 감소는 개선·증가는 악화다. 작은 관측 차이가 일관된 개선을 뜻하지는 않는다. 이번 문서 정리에서 새 성능 실험은 실행하지 않았다.

## 1. 처음에는 원본을 읽고 집계를 준비하는 비용부터 줄였다 — 10/08~09

출발 상태는 변경 파일을 읽어 바이트별로 전처리하고, 요청·모델·제목을 집계한 뒤 세션 전체를 저장하는 구조였다. manifest는 이미 변경 없는 파일의 본문 읽기를 생략했다. 따라서 먼저 **변경 파일을 처리하는 내부 비용**을 살폈다.

제목 탐색에는 제목이 있는 메인 이벤트만 담는 **TEMP partial index**를 적용했다. 요청마다 제목 후보를 넓게 찾는 비용을 줄이려는 선택이었다. 하지만 실제 252파일에서 최초 전체 갱신은 **15.139→15.046초, 0.6% 개선**에 그쳤다. 실제 component가 최대 41요청·13제목 후보여서 절약할 탐색량이 작았다. 추가 공간도 component별 TEMP 최대 **4,096 B**, 영속 DB **0 B**였다. [제목 실험](2026-10-08/RequestTitleTransactions.md)

다음으로 모든 바이트에 JS 검사를 수행하던 reader를 **일반 줄 직접 파싱·연속 Buffer 처리**로 바꿨다. 같은 실제 입력 53,271 JSONL행의 파싱은 **4,941.028→1,718.516 ms, 65.2% 개선**됐다. JSON.parse 자체보다 줄 구성·검사·복사 비용을 줄인 결과다. 영속 저장은 늘지 않았다. 다만 이 값은 파싱 구간만의 개선으로, 전체 갱신이 65.2% 빨라졌다는 뜻은 아니다. 이후에는 파일 처리와 별도로 **DB 조회가 반복하는 계산**을 줄이는 단계로 넘어갔다. [파싱 실험](2026-10-09/JsonlParsingBranches-2026-10-09.md)

## 2. 인덱스로 찾은 뒤에도 많이 합산하므로, 일별 결과를 저장했다 — 10/15

이때 조회는 날짜·프로젝트 인덱스로 원본 TURN을 찾은 뒤 합계·평균을 계산했다. 인덱스 유지/제거 비교에서 100,000 TURN의 프로젝트·30일·모델 조회는 **77.132→7.575 ms, 90.2% 개선**됐다. 그러나 기간을 좁히지 않는 전체 통계는 여전히 많은 TURN과 모델을 읽어야 했다. [인덱스 비교](2026-10-15/SqlExplainBenchmark-2026-10-15.json)

그래서 기존 facts를 보존하면서 **일별 요청·모델 사전 집계**를 추가했다. 100,000 TURN/세션100 조건에서 요청 집계 입력은 **100,000→1,991행, 98.0% 감소**, 프로젝트 평균 조회는 **872.847→4.137 ms, 99.5% 개선**됐다. 평균도 일별 평균의 단순 평균이 아니라 완료 표본의 합계÷건수로 병합한다.

실행 계획도 변화와 맞는다. 적용 전에는 원본 `SEARCH t USING INDEX idx_summary_project_period`와 모델의 반복 `SEARCH m USING PRIMARY KEY`가 있었고, 적용 후에는 `usage_request_daily`의 프로젝트 인덱스를 읽는다. `USE TEMP B-TREE FOR ORDER BY`는 남았다. **정렬을 모두 없앤 것이 아니라, 합산 입력과 반복 모델 탐색을 줄인 개선**이다. [계획·실측 원본](2026-10-15/SqlRollupProductBenchmark-2026-10-15.json)

대신 요청 집계 **1,991행**·모델 집계 **5,175행**과 metadata가 추가됐다. 표·인덱스·metadata는 **2,412,544 B**, 전체 DB 할당 증가분은 **2,416,640 B, 7.8% 증가**였다. 같은 100 TURN 세션 교체도 **7.588→10.372 ms, 36.7% 악화**됐다. 조회를 빠르게 만든 뒤 다음 과제는 **저장할 때 생기는 반복 쓰기와 집계 유지 비용**이 됐다. [제품 적용 결과](2026-10-15/SqlExplainBenchmark-2026-10-15.md)

## 3. 저장 순서를 바꾸기보다, 같은 데이터를 다시 쓰는 일을 줄였다 — 10/25~27

사전 집계가 있는 상태에서 날짜 중심 배치를 시험했다. 기간 조회에는 유리할 수 있지만, 제공자·날짜 PK 후보는 세션 교체를 **1.665→13.846 ms, 731.6% 악화**시켰다. 기존 세션 PK의 탐색 범위를 잃었기 때문이다. 세션 인덱스를 보충하면 갱신은 회복됐지만 저장 공간 절감도 거의 사라졌다. [배치 실험](../DateStorageAB-2026-10-25.md)

반복 쓰기를 직접 줄이는 방법으로는 **요청별 차이 저장·영향 날짜 재집계**를 적용했다. 기존 PK·인덱스·트랜잭션 배칭을 유지하면서 바뀌지 않은 요청을 다시 쓰지 않는 방식이다. 100,000 TURN/세션100의 1 TURN 추가는 **24.12→15.93 ms, 33.9% 개선**, 종료 WAL은 **217.30→72.45 KiB, 66.7% 감소**했다. 반면 전건 제목 변경은 **17.750→25.668초, 44.6% 악화**됐다. 모두 달라지면 비교와 쓰기를 함께 부담했다. 이때부터 **변경이 적은 경우와 많은 경우를 구분해야 한다**는 근거가 생겼다. [증분 저장 실험](2026-10-26/SqlWrites-2026-10-26.md)

10/27에는 양쪽 모두 증분 저장을 사용한 채 일별 집계를 일반 rowid로 바꿔 보았다. 실제 DB의 1 TURN 추가는 **6.938→7.602 ms, 9.6% 악화**됐고, 일부 대량 전건 변경에서는 개선됐다. 본체 저장 형식만 바꿔 모든 갱신을 줄일 수는 없어 기존 구조를 유지하고 전체 갱신 경로를 확인했다. [rowid 실험](2026-10-27/SqlRowid-2026-10-27.md)

## 4. DB 구간의 개선이 전체 갱신에서도 보이는지 다시 확인했다 — 10/29

실제 로그를 처음부터 처리하니 DB 저장만 줄여서는 전체 시간이 크게 변하지 않았다. 실제 494파일·1,180 TURN의 최초 갱신은 약 13초였고, 그중 **읽기·파싱·정규화가 약 9.1초**였다. 변경 없는 갱신도 약 126 ms 중 파일 확인이 약 103 ms였다. 요청별 증분 저장은 이 앞단을 줄이지 않았다.

이 과정에서 세션 일괄 교체로 되돌렸지만, 후속 통제 비교의 합성 **10프로젝트 × 10세션 × 100 TURN**에서는 같은 데이터 강제 재집계가 **증분 2.531→일괄 3.519초, 39.0% 악화**됐다. **전체 체감 개선이 작다는 이유로 증분 저장 자체가 느리다고 판단한 설명은 정정했다.** 전체 앞단의 병목과 반복 DB 쓰기 절감은 함께 존재했다. 이후에는 작은 세션·최초 적재까지 모두 비교하는 대신, 이득이 확인되는 큰 세션의 소수 변경에 적용 범위를 좁혔다. [전체 경로 재검증과 판단 정정](2026-10-29/RefreshRollback-2026-10-29.md)

## 5. 월 배치로 조회를 더 줄였지만, 쓰기 목표와 충돌했다 — 10/29~31

이어서 일별 집계의 세션 PK를 월 선두로 바꾸면 기간 조회가 더 짧아지는지 시험했다. 월 컬럼만 추가한 후보는 `SCAN turn_summary`여서 한 달 모델 조회가 **5.084→39.236 ms, 671.7% 악화**됐다. 월 PK와 월 조건을 함께 쓰자 `SEARCH turn_summary USING PRIMARY KEY (local_month=?)`로 바뀌어 **5.084→2.408 ms, 52.6% 개선**됐다. 여기서 `turn_summary`는 일별 집계 테이블의 별칭이다.

하지만 프로젝트·기간 인덱스가 이미 범위를 좁히던 조회는 **0.307→0.290 ms, 5.6% 개선**에 그쳤다. 전 기간 월별 조회도 `SCAN`과 임시 GROUP BY·ORDER BY가 남아 **258.293→234.449 ms, 9.2% 개선**이었다. **월 PK는 해당 월 탐색에 유리했지만 모든 조회를 같은 폭으로 줄이지는 않았다.** 이 수치는 100,000 TURN/세션100의 별도 통제 실험이다. [실행 계획·측정 원본](2026-10-29/StorageLayoutBalanced-2026-10-29.json)

실제 제품에 적용할 때는 세션 조회·갱신을 보완할 세션/월 목록까지 필요했다. 같은 100,000 TURN/세션100 입력에서 목록 **3,928행**이 추가되고 집계 live 공간은 **63.148→72.938 MiB, 15.5% 증가**했다. 실제 DB 1,100 TURN의 전체 월별 모델 조회 이득은 **1.584→1.246 ms, 21.4% 개선**이지만 절대 절감은 약 0.338 ms였다. 갱신 지연을 우선하는 목표에 비춰 월 PK를 최종 유지할 이유가 부족했다. [월 PK 제품 실험과 철회 근거](2026-10-31/StorageProduct-2026-10-31.md)

## 6. 최종적으로 큰 세션만 묶음 비교하고, 세션 PK를 복원했다 — 10/31

월 PK 적용 뒤에는 입력을 TEMP에 한 번 모아 SQL로 비교하고 변경분만 쓰는 **선택적 묶음 비교**를 더했다. 300 TURN 세션의 이득은 불안정해 최소 크기를 **1,000 TURN**으로 올렸고, 변경은 **10% 이하이면서 최대 32 TURN**으로 제한했다. 마지막으로 월 PK·월 목록을 제거하고 세션 PK를 복원했다.

개선 과정을 분리하기 위해 **총 100,000 TURN·대상 세션 10,000 TURN에 1 TURN 추가**라는 같은 입력으로 네 제품 빌드를 다시 대조했다. 시간은 **BEGIN 성공 직후부터 COMMIT 반환까지**이며 파싱은 제외한다.

| 순서 | 구조 | 쓰기 구간 | 직전 단계 대비 |
| --- | --- | ---: | --- |
| 출발 | 세션 PK·일괄 저장 | **801.791 ms** | 기준 |
| 월 배치 적용 | 월 PK·일괄 저장 | **827.836 ms** | **3.2% 악화** |
| 반복 쓰기 감소 | 월 PK·선택적 묶음 비교 | **474.597 ms** | **42.7% 개선** |
| 세션 접근 복원 | 세션 PK·선택적 묶음 비교 | **431.769 ms** | **9.0% 개선** |

최종 결과는 출발 대비 **46.1% 개선**이다. 동일 snapshot은 **801.099→244.735 ms, 69.5% 개선**됐지만, 전건 변경은 **822.043→926.832 ms, 12.7% 악화**됐다. 작은 변경에서 반복 쓰기를 줄인 대가로, 전건 변경에는 비교 준비 비용이 남는다.

같은 1 TURN 추가의 집계 live 공간은 **변화 없음(0.0%)**, TEMP 할당은 **32→3,896 KiB, 12,075.0% 증가**, 종료 WAL은 **4,325.227→181.086 KiB, 95.8% 감소**였다. TEMP 할당은 메모리 피크가 아니며 WAL 길이도 누적 디스크 쓰기량은 아니다. 현재 선택은 **기간·프로젝트 인덱스와 일별 사전 집계의 조회 이득을 유지하고, 세션 PK에서 큰 세션의 소수 변경만 부분 반영**하는 것이다.
