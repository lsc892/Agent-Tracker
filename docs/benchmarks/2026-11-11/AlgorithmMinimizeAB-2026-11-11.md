# 기능 보존 알고리즘 최소화 A/B

가정: 확정한 root·그룹·메타데이터를 재사용하고 반복 파싱·SQL을 줄이면 기존 결과를 유지하면서 갱신·조회 비용이 감소할 것이다. 사용자는 직전 최소화 작업의 성능과 정합성 측정을 요청했다.

개선 방향: **A는 최소화 직전 HEAD `72e414f`**, **B는 직전 작업을 모두 반영한 미커밋 소스**다. 계보·파싱·조회·저장 변경을 함께 비교하며 각 후보의 독립 기여를 분리한 실험은 아니다. 제품 코드는 측정 중 변경하지 않았다. [적용 범위](../../research/2026-11-11/AlgorithmMinimize-2026-11-11.md).

## 4. 입력·환경·재실행

현재 입력은 **663파일·505,894,489byte, 1,360요청·374세션·30프로젝트, 2,827,988,805토큰**의 고정 사본이다. 원본·설치 DB는 변경하지 않았다. 사본 이후 추가된 실제 로그는 포함하지 않는다. 복사한 Codex 이름 index/state metadata의 상대 파일명·크기·SHA도 최종 입력 해시에 포함하고 종료에 불변성을 재확인했다. 원문·제목·세션 ID는 공개 산출물에서 제외한다.

합성은 고정 ordinal-v1 산식으로 제공자별 절반·10프로젝트다. 10,000건은 100세션×100요청, 100건은 10세션×10요청이며 각각 6,340,000·18,400토큰이다. 일반 요청·모델 기록만 만들고 Skill/subagent/plugin 호출 밀도는 늘리지 않았다. 따라서 합성 네 분류 결과를 모든 실제 도구 분포로 일반화하지 않는다. 시각은 2026-07-01 + 세션 순번%14일 + 요청 순번×3초다.

Windows 10.0.19045, AMD Ryzen 5 7500F·논리 CPU 12개, Node v24.14.1, SQLite 3.51.2. WAL·synchronous=2(FULL)·cache_size=-4096KiB·temp_store=FILE·mmap=0을 유지했다. 각 variant/쌍은 새 프로세스·새 DB에서 시작하고 최초 갱신 전에 빈 rollup만 활성화했다. 프로세스 시작·DB 열기·사본 준비·복원·append·정합성 검사는 갱신 타이머 밖이다. OS cache는 통제하지 않았고 강제 GC는 하지 않았다. 정합성 검사·컴파일은 최종 성능 측정과 겹치지 않게 실행했다.

고정 조회 범위는 Asia/Seoul 2026-01-01 이상·2027-01-01 미만, 미상 시간 포함이다. 원본/빌드 fingerprint와 원시 표본은 최종 JSON, 파일별 SHA와 A/B 소스·컴파일·실행기는 [보관 명세](AlgorithmMinimizeSources-2026-11-11.json)와 [ZIP](AlgorithmMinimizeSources-2026-11-11.zip)에 둔다. ## 5. 판정

**일부 성립.** 조회·이름·도구·coverage·세션 결제는 반복 SQL 제거와 함께 측정상 개선됐다. 현재 전체 갱신도 원본 준비 구간 감소와 함께 소폭 개선됐다. 그러나 세션 평균·최초 요청 저장·작은 입력의 일부 조회/추가는 악화했고, 10,000건 추가 전체 갱신은 0.18%·5/10쌍으로 사실상 혼합이다. 모든 알고리즘·규모에서 빨라졌다는 결론은 내리지 않는다.

기능 보존·쿼리 최소화 결과는 유지하되 **초기 저장 속도 개선으로 채택했다고 주장하지 않는다**. 이번 측정만을 이유로 새 임계값·캐시·추가 분기를 붙이지 않았다. 큰 조회 개선과 작은 갱신·저장 손익은 서로 다른 사용자 작업이므로 합산한 단일 개선율을 만들지 않는다.
