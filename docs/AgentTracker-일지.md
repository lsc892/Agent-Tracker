# Agent Tracker 기능 의사결정 일지

2026-11-10부터의 기능 의사결정을 기록한다. 2026년 10월과 11월 초의 결정은 [이전 일지 · 2026-10-01~11-09](refrences/AgentTracker-일지.md)에서 볼 수 있다.

## 현재 설계 결정 요약

- 일반·압축 JSONL은 디렉터리를 순회하면서 발견한 위치에서 관측하며, 경로별 마지막 정상 반영 수정 시각과 현재 수정 시각을 직접 비교한다. 새 경로와 수정 시각이 다른 원본은 처음부터 파싱한다. 요청·모델·진단이 달라질 세션의 관련 원본도 파싱하며, 저장된 원본 관계 메타로 파일명에 스레드 ID가 없는 부모 후보를 찾는다. 무변경 갱신의 본문 읽기는 0바이트다.
- JSONL에서 요청·응답·수명주기와 부모 귀속에 필요한 필드를 선택한다. Skill 수집 설정은 호출 인자와 응답 횟수의 처리 여부를 결정한다. 파일별 응답 후보는 사용량이 가장 큰 기록을 보관한다.
- 통계 조회는 선택한 도표와 표가 사용하는 지표를 계산한다. 입력·출력·캐시 저장·캐시 재사용의 구성별 평균은 평균 토큰 도표에서만 계산하고, 다른 도표에서는 네 필드를 NULL로 반환한다. 도표 선택이 없는 직접 조회 API는 전체 지표를 반환한다.
- 경로가 바뀌면 새 파일과 이전 경로의 소실로 처리한다. 소실된 원본에는 삭제 사용량 보존 설정을 적용한다.
- 통계 기간은 최근 7일·30일·90일·전체 기간·직접 설정 순서로 선택한다. 기본값과 초기화 값은 최근 30일이며, 최근 기간은 통계 시간대의 오늘을 포함한 달력 일수로 계산한다. 영속 갱신 성공 뒤 최근 기간과 전체 기간은 선택 즉시 조회한다. 직접 설정을 열면 시작일·종료일과 달력을 표시하고 조회 버튼으로 적용한다. 적용한 기간과 직접 입력 날짜는 Webview state에 보존한다.
- 통계 진입 시 변경 로그와 관련 원본을 읽어 메모리에서 집계하고, 일별 결과를 저장용 SQLite에 반영한다. 영속 갱신이 성공하면 기본 최근 30일 또는 복원된 기간으로 조회하고 기간·필터·정렬·페이지·세션 결제 조작을 연다. 실패하거나 취소하면 재시도를 표시한다.
- 제공자별 추적·상태 표시줄·사용량 카드·통계 표시는 `claude.enabled`·`codex.enabled` 두 토글로 통일한다. 별도 `codex.showStatusBar` 설정과 저장값 사용은 제거하며, 두 제공자를 모두 끄면 상태 표시줄 항목과 새로고침 버튼도 숨긴다. 기존 계산 데이터는 보관한다.
- quota 게이지와 숫자는 상태 표시줄·사용량 카드 모두 `display.percentage`를 따른다. `used`는 사용량, `remaining`은 잔여량을 표시하며 잔여량은 오른쪽 끝부터 줄고 사용량은 왼쪽부터 차도록 고정한다.
- 사용량 카드는 상태 표시줄에 마우스를 올리면 나타난다. 배포된 확장은 지원되는 로컬 VS Code에서 패치가 필요할 때 준비하고 VS Code 전체 종료 뒤 적용한다. 확인한 설치가 그대로면 시작할 때 적용 기록과 파일 속성만 확인한다. 패치가 적용된 VS Code에서는 호버 상태에서 클릭하면 카드에 포커스를 주어 고정한다. 고정된 상태에서 클릭하면 닫고, 닫힌 상태에서 클릭하면 카드를 열어 고정한다. 클릭으로 닫은 뒤에는 마우스가 항목을 벗어났다 돌아오면 호버로 다시 열린다.
- 메모리 집계 저장은 `memoryStore/` 안에서 영속 반영·값 검증/변환·입출력 타입을 나누고 기존 `memoryStore.ts`는 공개 진입점으로 유지한다. JSONL 파일은 최대 64KiB 단위로 읽고 `JsonlLine`에서 행의 보관 바이트 한도와 이미지 필터를 처리한다. 통계 수집에서 조립이 필요한 줄은 파일별 버퍼에 담아 LF에서 문자열로 파싱한다. 용량이 256KiB를 넘는 버퍼는 줄 처리 직후 놓는다.
- 통계·이름·도구 페이지는 같은 그룹 결과에 전체 개수·비율 분모를 함께 계산하고 후속 빈 페이지에만 별도 count를 조회한다. 일반 화면의 coverage는 진단 목록 없이 counts만 읽는다. 비용은 일별 추정 합계에 조회 시점의 세션 결제 설정을 적용한다.
- 프로젝트는 작업 폴더, 세션은 같은 채팅의 대화 묶음, 대화는 사용자 메시지부터 메인 에이전트 응답까지의 턴이다. 서브에이전트의 사용량은 확인된 부모 대화로 귀속한다. 화면의 대화 수는 완료 대화를 세고, 평균 시간은 소요 시간이 확인된 완료 대화를 사용한다.
- 파일 준비 Worker는 응답 후보와 대화 경계·부모 참조·호출 근거를 반환한다. 수집기는 세션의 후보를 합치고 Codex의 확인된 복사 이력을 제외하며, 응답·턴·스레드 누계로 확인한 누락 사용량을 보충한다. 대화 시작일과 모델을 기준으로 SQLite 일별 합계를 갱신한다.
- 세션별 요청 맵에서 `rootId`로 대화를 찾고, 원래 응답 ID 필드로 후보를 정렬해 중복을 제거한다. 각 응답 그룹의 첫 등장 위치를 기준으로 확정 응답을 반영한다.
- 정상 독립 연결 성분은 입력 순서를 유지하며 최대 16성분·합계 1,000요청까지 한 동기 쓰기 트랜잭션에 반영한다. 단일·큰 성분과 오류·삭제 등 특수 처리는 기존 개별 경로를 사용한다.
- 성분별 snapshot과 평균·rollup의 집계 의미·PK·WAL/FULL 설정을 유지한다. 묶음 실패는 전체 rollback 후 기존 성분별 재시도로 격리하며 settled·affected 확정과 취소 확인은 거래 경계를 따른다.
- 정상 성분 묶음은 제공자와 모델의 일별 합계를 UPSERT하고 Skill은 같은 범위의 횟수를 교체한다. 스키마 v26은 기존 사용량을 일별 표로 이관하고 상세 테이블을 제거한다. 파일 수정 시각과 원본 관계는 다음 수집에 사용한다.
- 스키마 v27은 원본 파일과 일별 사용량의 보조 인덱스 여섯 개를 제거한다. 기본 키와 원본 경로의 고유 제약을 유지하고 이관에서 회수한 페이지는 재사용한다.
- 읽기 크기는 현재 파일 관측값을 사용한다. 원본 관계는 `thread_id`와 `thread_usage`에 저장하고, Codex 부모 참조가 필요한 갱신에서 스레드 ID를 SQLite에서 조회한다.
- 스키마 v30은 `capabilities_collected`로 마지막 정상 파일 읽기의 Skill 수집 여부를 기록한다. Skill 탭은 스킬·서브에이전트·플러그인·모델의 횟수와 비율을 제공하며, 수집을 다시 켜면 누락된 파일을 재파싱한다.
- 정상 저장 묶음은 프로젝트·세션 이름을 키별 한 번 UPSERT한다. COMMIT한 이름은 같은 스캔의 후단 중복 UPDATE를 생략하는 데 사용하며 제목만 바뀐 세션과 특수 snapshot의 순서는 보존한다.

## 2026-11-27

### 대화 조회와 응답 비교에서 후보마다 만들던 복합 문자열 키를 없앤다

- **의사결정** — 사용자는 대화 조회와 응답 비교의 반복 키 생성을 줄이고 개선량을 측정하도록 요청했다. 에이전트는 제공자·세션별 `rootId` 맵을 두고, 원래 응답 ID 필드로 후보를 비교하도록 정했다. 확정 응답 키를 소비하는 콜백이 있으면 반영 시 기존 형식으로 생성한다.
- **근거** — 세션 단위 처리 중 같은 제공자·세션 ID를 반복 직렬화하고, 응답 후보에도 합성 문자열을 붙이던 비용을 줄일 수 있다. 중복 그룹의 첫 등장 위치 및 대화 등록 순서를 보존해 점수·동점·진단 반영이 같은 순서로 진행되도록 했다.
- **결과** — 실로그 최초 수집의 V8 피크 힙은 70.09 → 55.64 MiB, 메모리 집계 시간은 89.18 → 72.33 ms였다. `finish()` 중 힙 증가량은 20.51 → 7.88 MiB였다. 전체 최초 수집 시간과 RSS의 뚜렷한 개선은 관측되지 않았다.
- **검증** — 실로그와 합성 10,000·100대화의 120쌍에서 SQLite 저장값, 토큰 합계와 네 평균 조회가 일치했다. 타입 검사·린트·diff 검사를 통과했다. 일반 자동 테스트는 실행하지 않았다. [A/B 보고서](benchmarks/success/2026-11-27/AggregationCandidateKeysAB-2026-11-27.md)

### 청크 경계를 넘는 통계 로그에서 후보 필드만 모은다

- **의사결정** — 사용자는 한 청크에 들어오는 일반 줄은 기존 문자열 파싱을 사용하고, 경계 줄은 청크마다 검증하면서 필요한 값만 보관하도록 요청했다. 에이전트는 제공자별 선택표에서 후보 필드를 계산하고, LF에서 기존 `type`별 선택과 지연 해석을 적용한다. 문자열 조립이 필요한 줄에는 파일별 버퍼를 재사용한다.
- **근거** — 유형 필드가 뒤에 오거나 중복돼도 최종 유형에 필요한 값을 보존하면서, 수집에 쓰지 않는 큰 필드의 전체 줄 복사와 UTF-8 변환을 피할 수 있다. 문법 오류, 이미지 제거, 바이트 한도 및 미완성 줄의 처리에는 기존 정책을 적용한다.
- **결과** — 실로그 최초 수집에서 버퍼 재사용 기준 대비 읽기·파싱 중앙값은 4,019.48 → 3,974.92ms였고, 최고 파일 워커 `ArrayBuffer` 피크는 60.41 → 50.87 MiB였다. 프로세스 RSS 변화는 작았고 파일 워커 V8 힙은 65.78 → 69.61 MiB였다.
- **검증** — 실로그와 합성 두 규모에서 추출 필드·줄 위치·SQLite 및 조회 결과가 일치했다. 타입 검사·린트를 통과했다. 자동 테스트는 실행하지 않았다. [비교 보고서](benchmarks/failure/2026-11-27/LongJsonlStreamingAB-2026-11-27.md)
- **후속 결정** — 전체 최초 수집 시간은 약 38ms(0.85%) 줄었으며 전체 RSS 변화는 0.4%에 그쳤고 파일 워커 V8 힙 중앙값은 5.8% 늘었다. 사용자 요청에 따라 청크별 후보 필드 선택을 철회했다. 실로그 최초 수집의 전체 시간을 13.1%, RSS를 5.8% 줄인 파일별 줄 버퍼 재사용을 유지했다. [버퍼 재사용 A/B](benchmarks/success/2026-11-27/JsonlRowBufferReuseAB-2026-11-27.md)

### 세션의 응답 키와 도구 호출별로 필요한 후보만 보관한다

- **의사결정** — 사용자는 현재 기능에 맞춰 집계 알고리즘을 최소화하도록 요청했다. 세션 응답은 키별 `Map`에서 비교하고, 원본 안의 같은 도구 호출은 최소 바이트 위치만 남긴다. 저장 배치는 요청 요약과 세션 키를 최종 배열에 바로 넣고 직렬화한 세션 범위를 재사용한다.
- **근거** — 응답 키의 첫 등장 순서는 `Map`의 삽입 순서로 유지할 수 있다. 복사된 도구 호출의 제외 여부는 호출 키 전체에 적용되므로, 귀속에 쓸 위치는 최솟값이면 충분하다. 복사 판정에 쓰는 최초 이벤트 순번은 별도 근거에 있다.
- **결과** — 비교할 응답 후보가 N개, 고유 키가 U개이면 세션 응답 비교는 최악의 정렬 시간 `O(N log N)`에서 평균 `O(N)`으로, 후보 보조 공간은 `O(N)`에서 `O(U)`로 줄어든다. 도구 호출의 위치 기록은 등장 횟수만큼 쌓는 대신 고유 호출당 한 위치를 유지한다. SQL의 일별 합산과 배치 트랜잭션은 기존 경계를 따른다.
- **검증** — 타입·번역 검사, 린트와 diff 검사를 통과했다. 자동 테스트, 실로그 재집계와 성능 측정은 미실행이다. [응답 선택과 복사 판정](refrences/WinnerPolicy.md)
- **후속 결정** — 실로그의 응답 비교에서 모든 후보 키가 고유했고 `Map` 방식의 집계 직후 힙이 증가했다. 사용자 요청에 따라 응답 비교, 도구 호출 위치 보관, SQLite 저장 입력 코드를 적용 전 구현으로 복원했다. [A/B 및 원인 계측](benchmarks/failure/2026-11-27/CurrentAggregationMinimizeAB-2026-11-27.md)

### 한 세션에서 사용자 요청과 답변을 대화 한 건으로 센다

- **의사결정** — 사용자는 프로젝트를 작업 폴더, 세션을 같은 채팅의 대화 묶음, 대화를 사용자 요청 한 번과 그 응답으로 정의하고 Skill 통계 복원을 요청했다. Codex는 통계 표와 도표에서 완료한 대화를 세고, 자식 사용량은 확인 가능한 부모 대화에 합산하기로 했다.
- **근거** — 서브에이전트 스레드를 셀 때마다 대화 수가 늘어나면 사용자가 요청한 횟수와 달라진다. 제공자별 요청 경계와 부모 참조를 사용하면 자식의 모델·토큰·호출을 부모에게 귀속하고, 대화 간의 유휴 시간을 평균 시간에서 뺄 수 있다.
- **결과** — 세션 필터와 세션별 조회 이름을 되돌리고 Skill 네 분류의 일별 저장·설정 연동을 복원했다. 파서 v26은 읽을 수 있는 원본을 다음 갱신에서 다시 집계한다. 이미 소실된 원본에서 턴 구분과 누락된 호출을 복원하는 데는 기존 일별 합계의 한계가 있다.
- **검증** — 타입 검사, 린트, Webview JavaScript 구문 검사, 번역 동기화와 diff를 검토했다. 자동 테스트와 변경 후 VS Code의 실제 통계 갱신은 수행하지 않았다. [설계 명세](refrences/AgentTracker.md) · [로그 필드](refrences/LogParsingFields.md)

### VSIX에 클릭 토글 패치를 포함하고 VS Code 종료 뒤 적용한다

- **의사결정** — 사용자는 배포된 확장이 상태 표시줄 카드의 클릭 토글 패치를 자동 적용하도록 요청했다. 확장 시작 시 실행 중인 로컬 Windows·Linux VS Code 설치 경로와 버전을 사용해 패치를 준비하고, 데스크톱 프로세스가 종료된 뒤 검증된 파일을 교체한다.
- **근거** — 확장의 공개 API는 VS Code 내부 토글을 직접 노출하지 않는다. 실행 중인 VS Code는 시작할 때 읽은 체크섬으로 설치를 검사하므로 파일 교체를 종료 뒤로 미룬다. 설치본별 잠금으로 여러 창의 작업을 하나로 제한한다.
- **결과** — 지원 설치에는 재시작 안내가 표시된다. VS Code를 완전히 종료한 뒤 잠시 기다렸다 다시 열면 기존 위치에서 클릭으로 카드를 고정하거나 닫을 수 있다. 수동 복원한 설치의 자동 재적용은 건너뛴다. macOS 서명 번들, 원격·개발·테스트 호스트와 권한이나 구조가 맞지 않는 설치는 기본 호버와 클릭 열기를 사용한다.
- **후속 정리** — 사용자는 매번 실행할 때 패치를 재탐지하는지 확인을 요청했다. 적용 결과 또는 수동 복원을 확인한 뒤 설치·패치 버전과 workbench 및 product 파일 속성을 기록한다. 같은 설치에서는 기록과 속성만 비교하고, 기록이 없거나 버전·파일이 바뀌면 백그라운드에서 전체 검사를 한다.
- **중단 복구** — workbench 교체 후 체크섬 교체 전에 중단된 경우, 두 설치 파일의 해시가 작업 기록과 일치할 때만 남은 체크섬 교체를 예약한다. 이전 패치에서 갱신 중 두 파일이 모두 직전 상태에 남아 있으면, 같은 작업 기록과 해시를 대조해 교체를 다시 준비한다. 원본 백업은 임시 파일에서 교체하고 잠금 기록 쓰기 오류 뒤에는 새 잠금을 정리한다.
- **처리 최적화** — 준비 단계에서 설치 파일과 패치 결과의 SHA-256을 한 번 계산해 작업 기록과 VS Code 체크섬에 재사용한다. 워커는 종료를 기다리는 동안 편집 범위·삽입 코드·해시와 product 내용만 보관한다. 종료 후 같은 입력으로 확인한 workbench에서 패치 결과를 다시 만든다. 이미 적용된 패치의 일치 판정에는 삽입 위치와 코드를 사용하며 파일 해시도 검증한다.
- **검증** — 타입·번역 검사, 린트와 JavaScript 구문 검사를 통과했다. 후보 VSIX에서 확장 시작 경로와 패치 파일을 확인했다. 실제 설치에서 자동 반영 후 클릭 확인은 미실행이다. [상태 표시줄 설계](refrences/AgentTracker.md#34-상태-표시줄과-카드형-툴팁)

### Codex 응답 병합에서 키 색인 하나와 행별 원본 참조를 사용한다

- **의사결정** — 사용자는 스레드별 `Map`과 응답 배열을 이용해 집계를 단순화하도록 요청했다. 복사본을 병합할 때 만드는 `Map`은 응답 키에서 행 번호를 찾는 데 사용한다. 동점 판정은 채택한 응답의 원본 참조를 같은 행 번호의 배열에 둬서 처리한다. 일별 SQL 전달부에서는 토큰 합계를 최종 입력 행에 바로 넣는다.
- **근거** — 대표 원본의 응답 키를 별도 집합에서 관리하던 과정은 현재 대표 원본과 응답의 원본 참조를 비교하는 것으로 대체할 수 있다. SQL 입력 행을 만들 때도 스레드별 토큰 다섯 값을 담는 임시 배열을 생략할 수 있다.
- **결과** — 대표 원본이 바뀌면 비교 기준만 달라진다. 응답별 최고값·동점 순서·누계 검산 행 번호와 일별 SQL 입력 열 순서를 보존한다.
- **검증** — 타입 검사·린트·diff 검사와 구현 대조를 완료했다. 자동 테스트·실로그 재수집·힙 측정은 미실행이다. [Codex 응답 병합](research/2026-11-27/CodexThreadMerge-Minimization.md) · [일별 SQL 입력](research/2026-11-27/SqlDailyHandoff-Review.md)

### 시각만 필요한 Codex 행과 이긴 응답의 처리를 줄인다

- **의사결정** — 사용자는 접두사로 행을 판별해 필요한 값만 읽고 winner 객체는 비교 뒤 만들라고 요청했다. 한 청크에 완성된 알려진 형식의 Codex `response_item`에는 시각을 바로 사용하는 분기를 적용하고 JSON 문법 상태를 재사용한다. Claude와 Codex의 응답은 점수를 비교한 뒤 이긴 행의 객체를 만든다.
- **근거** — 이 Codex 행은 통계에 시각만 기여한다. 구조와 문법까지 확인하면 중복 키와 손상 기록에 대한 기존 처리를 보존할 수 있다. 다른 필드 순서, 구형 누계, 이미지·경계 줄은 고정 필드 선택기로 처리한다.
- **결과** — 실로그 최초 수집의 파일 Worker JSONL 누적 할당은 831.36 → 290.69 MiB, 최고 피크 힙은 17.19 → 14.84 MiB였다. 최초 수집 시간은 3,009.90 → 3,285.98 ms였다. 이번 변경은 힙 할당 감소를 선택했다.
- **검증** — 타입 검사·린트, JSONL·Zstd 테스트 19개, 실로그와 합성 두 규모의 A/B 120쌍, 독립 토큰 합계 검산과 SQLite 무결성 검사를 통과했다. 전체 Node 스위트의 실패 214개는 기준 빌드에서도 같은 이름으로 재현됐다. [측정 보고서](benchmarks/success/2026-11-27/PrefixWinnerAB-2026-11-27.md)

### Codex 누계 검산에 파서의 응답 행 번호를 재사용한다

- **의사결정** — 사용자는 앞서 힙을 줄인 집계 경로를 단순화하도록 요청했다. 파서가 기록한 누계 시작·끝 행 번호를 그대로 사용한다. 이후에 병합한 복사본이 검산 구간을 가진 대표 원본이 되면 그 파일의 행을 최종 응답 행에 연결하는 `Uint32Array`를 만든다.
- **근거** — 첫 파일의 응답 행과 토큰 버퍼는 수집기가 인수하며, 이후 복사본의 같은 응답은 그 자리에서 교체된다. 기존 행 번호를 사용하면 누계 구간마다 문자열 키 배열을 만들고 다시 색인을 조회하는 과정이 줄어든다.
- **결과** — 수집기의 문자열 색인은 복사본을 합칠 때만 만든다. 시작 경계 응답을 빼고 종료 경계까지 더하는 순서와 복사본의 최고값·동점 규칙을 유지한다.
- **검증** — 타입 검사·린트·diff 검사를 통과했다. 변경 후 실로그 A/B와 일반 자동 테스트는 미실행이다.

### 발견한 로그를 바로 관측하고 Codex 응답 키는 비교할 때 만든다

- **의사결정** — 사용자는 현재 코드를 다시 계측해 힙 사용량을 줄이라고 요청했다. 디렉터리 항목은 발견한 위치에서 같은 관측 함수에 전달하고, Codex 응답 키 색인은 다른 원본이나 누계 구간과 비교할 때 만든다.
- **근거** — 현행 코드의 통계 Worker 프로파일에서 경로 순회의 누적 할당 추정치가 46.22 MiB였으며 집계 직전 Codex 응답 병합에서 약 2.70 MiB가 살아남았다.
- **결과** — 깊이 우선 탐색 순서와 확장자 판정, 파일별 최고 응답을 고르는 방식과 복사본 동점 규칙을 유지한다. 파일별로 확정된 응답 행을 직접 합산하므로 복사본·검산이 없는 스레드에서는 수집기에서 응답 키를 다시 만들 필요가 없다.
- **검증** — 실로그 최초 수집의 집계 직전 힙은 20.69 → 15.83 MiB, 전체 피크 힙은 27.81 → 27.09 MiB였다. 공개 Worker에서 수집·조회 뒤 첫 무변경 갱신의 피크 힙은 24.71 → 30.75 MiB였다. 세 입력의 180쌍에서 SQLite 저장값과 조회 결과가 일치했다. 타입 검사·린트·diff 검사를 통과했으며 일반 자동 테스트는 미실행이다. [A/B 보고서](benchmarks/success/2026-11-26/RefreshHeapAB-2026-11-26.md)

### 구형 Codex의 누계 비교 서명을 ArrayBuffer에 보관한다

- **의사결정** — 사용자는 힙을 많이 쓰는 다음 구간을 찾아 `ArrayBuffer`를 적용하고 실측해 달라고 요청했다. 대상은 구형 Codex의 누계 비교 서명으로 정했다. 파일별 고유 서명을 UTF-8로 저장하고, 각 행이 참조하는 서명 번호와 바이트 위치도 버퍼에 담는다.
- **근거** — 실로그에서는 집계 직전까지 서명 34,189개가 필요했다. 서명을 이전 가능한 연속 바이트로 보관하고, 집계에서 바이트 직접 비교와 중복 확인용 배열·토큰 차이 계산 객체의 재사용으로 임시 할당을 줄인다.
- **결과** — 부모와 자식의 복사 이력은 순서대로 바이트가 정확히 일치한 접두사만 제외한다. 같은 파일의 반복 서명은 행별 번호로 판정하며 집계된 스레드·모델 사용량을 SQLite에 전달한다.
- **검증** — 실로그 최초 수집의 집계 직전 힙은 26.18 → 20.73 MiB, 전체 피크 힙은 28.41 → 27.78 MiB였다. 프로세스 피크 RSS 중앙값은 405.60 → 432.64 MiB였다. 120쌍에서 SQLite 저장값과 조회 결과가 일치했다. 타입 검사·린트·diff 검사를 통과했으며 일반 자동 테스트는 미실행이다. [A/B 결과](benchmarks/success/2026-11-26/LegacySignaturesBufferAB-2026-11-26.md)
- **후속 정리** — 실제 구형 누계가 처음 나올 때만 파서 상태를 만들고, 누계가 있는 파일의 Worker 결과에만 서명과 누계 검증 정보를 묶는다. 첫 응답 토큰은 파싱 값을 재사용하고 같은 턴의 누계 차이는 입력·출력 수치를 직접 비교한다. 후속 정리는 타입 검사·린트·diff로 확인했다. 앞의 A/B 수치는 정리 전 빌드 기준이다.

### JSONL 고정 필드는 모든 줄의 바이트에서 선택한다

- **의사결정** — 사용자는 필요한 값만 문자열로 만들어 달라고 요청했다. 고정 필드 경로에서 완성 줄과 경계·이미지 줄에 같은 바이트 선택기를 사용한다. 파일마다 선택기와 축소 행 버퍼를 재사용한다.
- **근거** — 전체 줄 UTF-8 디코딩과 경계 조각 Latin-1 변환을 줄이면 파일 Worker의 임시 할당을 줄일 수 있다.
- **결과** — 후보 키와 필요한 값만 디코딩 대상에 포함한다. 버리는 값의 JSON 문법, 이미지 본문 제거, 줄 예산, 미완성 줄 보류, 원본 바이트 위치는 계속 검사한다.
- **검증** — 실로그 227,584행과 합성 두 입력의 선택 결과·오프셋이 일치했다. 120쌍에서 SQLite 저장값과 조회 결과도 일치했다. 실로그 최초 수집에서 파일 Worker 피크 힙은 21.34 → 15.54 MiB, 프로세스 RSS는 455.38 → 434.70 MiB였다. 1건 추가 시간은 236.68 → 251.20 ms였다. 타입 검사·린트·diff 검사를 통과했으며 일반 자동 테스트는 미실행이다. ### SQLite 저장 전 응답·구형 누계 토큰을 ArrayBuffer에 담는다

- **의사결정** — 사용자는 메모리 사용량이 큰 구간에 `ArrayBuffer`를 적용해 V8 힙을 줄이고 RSS 증가를 피하도록 요청했다. 실로그에서 힙 사용량이 높았던 파싱·병합 단계의 응답 토큰과 구형 Codex 누계·개별 사용량에 `Float64Array`를 적용한다.
- **근거** — 스레드 합계를 내기 전까지 같은 형식의 토큰 벡터가 여러 행에 남는다. 숫자는 연속 버퍼로 옮기고 ID와 레거시 비교 서명은 문자열로 유지한다. `Float64Array`는 기존 JS `number`의 표현 범위를 보존하며, 병렬 경로에서 버퍼를 전송 목록에 넣으면 같은 숫자 데이터를 복제할 필요가 없다. [이전 실로그 구간별 측정](benchmarks/failure/2026-11-26/DirectDashboardRefreshAB-2026-11-26.md)
- **결과** — 토큰 바이트를 V8 힙 밖에 보관한다. 병렬 경로에서 수신 스레드의 `external`은 이전 버퍼를 포함한다. 대표 원본의 우선순위, 부모 복사 대조, 스레드·모델 집계 및 SQLite 스키마와 저장 입력 계약을 유지한다.
- **검증** — 실로그 733파일 최초 수집의 피크 힙 중앙값은 48.39 → 28.29 MiB, 피크 RSS는 458.97 → 454.67 MiB였다. RSS 범위는 겹쳤고 1건 추가의 메모리 차이는 작았다. 실로그·합성 10,000·100건의 120쌍에서 SQLite 행, 토큰 합계와 네 평균 조회가 일치했다. 타입 검사·린트·diff 검사를 통과했다. [실측 결과](benchmarks/success/2026-11-26/ThreadTokenBufferAB-2026-11-26.md)

### 통계 첫 표를 저장용 SQLite 갱신 후 바로 조회한다

- **의사결정** — 사용자는 A/B에서 측정한 직접 갱신 경로를 적용하고 임시 30일 DB 관련 코드를 제거하도록 요청했다. 로그 파싱, Map 집계, SQLite 저장을 한 번 실행하고 저장된 일별 집계로 첫 표를 표시한다.
- **근거** — A/B에서 기존 DB의 최종 표는 무변경 253.3 → 209.3ms, 요청 1건 추가 258.4 → 221.6ms였다. 빈 DB의 첫 표는 1,342.8 → 2,878.4ms로 늦어졌으며, 연결을 닫은 뒤 DB는 두 방식 모두 824KiB였다. [A/B 결과](benchmarks/failure/2026-11-26/DirectDashboardRefreshAB-2026-11-26.md)
- **결과** — 임시 SQLite 복사, 미리보기용 파일 결과 보관, 전송 메시지와 표시 분기를 제거했다. 갱신 성공 뒤 기본 최근 30일 또는 복원된 필터를 조회한다. 진행 중에는 통계 조작을 잠그고, 실패하거나 취소하면 재시도할 수 있다.
- **검증** — 타입 검사·린트·Webview JavaScript 문법 검사와 갱신·조회 참조를 확인했다. 제품 변경 후 VS Code 화면 검증, 성능 재측정과 자동 테스트 실행은 수행하지 않았다.

### 원본 관계 BLOB을 스레드 ID와 보존 기준으로 바꾼다

- **의사결정** — 사용자 요청에 따라 `source_file.relation_meta`를 `thread_id`와 `thread_usage`로 이관한다. 구형 세션 단위 보존은 0, 스레드 단위 보존은 1로 기록한다.
- **근거** — 부모 후보 선택에는 스레드 ID, 소실 보존에는 ID와 보존 기준만 필요하다. Codex 부모 대조가 필요할 때 관계 ID를 한 SQL 문으로 읽고 기존 파일 순서대로 후보를 선택한다.
- **결과** — 부모 탐색과 원본 소실 보존에서 객체 역직렬화를 없앤다. 이관과 기존 컬럼 삭제는 같은 트랜잭션에 묶는다. NUL을 포함한 ID는 SQLite 조회에서 바이트로 읽어 원래 문자열을 복원한다.
- **검증** — 실로그 714개 기준 새 DB는 960 → 912 KiB, 부모 후보용 관계 조회는 3.559 → 0.879 ms였다. 117쌍에서 토큰 합계·조회 평균이 일치했고, v28 및 설치 DB v19 사본 이관 후 저장값과 SQLite 무결성을 확인했다. 타입 검사와 린트를 통과했다. [A/B 결과](benchmarks/success/2026-11-26/SourceRelationStorageAB-2026-11-26.md)

### 파일 재수집과 일별 조회에 쓰는 값만 전달한다

- **의사결정** — 사용자는 기존 화면과 조회를 유지하면서 winner와 저장에 쓰이지 않는 값을 제거하도록 요청했다. 스키마 v28에서 `source_file.size_bytes`와 `capabilities_collected`를 지운다. 새 관계 BLOB은 별도 컬럼의 세션 ID를 반복해서 저장하지 않는다. Codex의 응답 후보에서는 행 순서를 뺀다.
- **근거** — 읽기 크기는 스캔의 파일 관측값으로 충분하고, 현재 재수집 조건에는 Skill 플래그가 없다. Claude의 동점 처리와 Codex의 누계 검증은 각각 필요한 순서를 계속 사용한다.
- **결과** — 일별 저장 입력에서 조회에 쓰이지 않는 종료 시각, 스레드 진단 플래그와 진단 파일 참조를 생략한다. 소요 시간 계산, 파일 진단, 원본 소실 보존, 이름·비용·도구 조회에 필요한 값은 기존 경로로 처리한다.
- **검증** — 실제 DB 사본의 v27과 v28에서 남긴 8개 표의 데이터가 일치했다. 중복 복사본을 포함한 Claude·Codex 로그 26개를 양쪽에서 수집해 영속 일별 값과 사용량 조회 10종이 일치했고, 무변경 재수집의 본문 읽기는 0바이트였다. SQLite 무결성과 외래 키 검사, 타입 검사와 린트를 통과했다.

## 2026-11-24

### 일별 결과는 한 번 UPSERT하고 사라진 키만 삭제한다

- **의사결정** — 사용자는 기존 일별 행을 통째로 삭제하는 대신 계산된 결과를 한 번 UPSERT하도록 요청했다. 제공자별·모델별 표마다 새 행을 넣고 기존 집계 값이 달라졌을 때만 업데이트한다.
- **근거** — 같은 날짜·프로젝트·세션·모델 키는 SQL 충돌 처리로 갱신할 수 있다. `EXCEPT`으로 새 결과에 없는 키만 찾아 정리하면 이동·삭제 뒤의 이전 사용량도 제거할 수 있다.
- **결과** — 값이 같은 일별 행의 쓰기를 생략한다. 새 합계, 사라진 행과 파일 수정 시각을 같은 트랜잭션에서 반영하고 소실 원본 보존 범위를 유지한다.
- **검증** — 키와 SQL 바인딩을 검토했다. 타입 검사·린트·diff 검사를 통과했다. 실데이터 갱신, 성능 측정과 자동 테스트는 실행하지 않았다.

### 일별 집계 경로를 단일화하고 스레드 저장·조회 코드를 제거한다

- **의사결정** — 사용자는 메모리에서 고른 winner의 합계를 받아 SQL에서 날짜별 결과를 저장하는 경로만 남기도록 요청했다. DB를 열 때 이전 통계를 일별 결과로 이관하고 상세 테이블을 제거하도록 정했다.
- **근거** — 수집·저장·조회가 같은 일별 구조를 사용하면 스레드 행 비교, 응답별 차분과 이전 상세 행으로 돌아가는 분기를 없앨 수 있다.
- **결과** — 새 DB는 일별 구조로 시작한다. 이전 DB는 사용량·비용·도구 집계를 같은 트랜잭션에서 이관하고 완료 후 상세 테이블을 없앤다. 갱신은 일별 결과와 파일 수정 시각을 함께 저장하며 화면도 일별 결과를 읽는다. 과거 DB와 기존 테스트가 참조하는 SQL 및 타입 일부는 이관·검증 참조로 남겼다.
- **검증** — 경로와 SQL 바인딩을 검토하고 타입 검사, 린트, JavaScript 문법 검사 및 diff 검사를 통과했다. 실데이터 이관과 자동 테스트는 실행하지 않았다.

### 파일 변경마다 winner를 다시 구하고 일별 합계만 저장한다

- **의사결정** — 사용자는 파일 수정 시각으로 변경을 찾고, 원본에서 winner를 다시 고른 뒤 SQLite에서 날짜별 결과를 반영하도록 지시했다. 관련 세션의 원본까지 읽어 중복과 귀속을 다시 결정하고, 스레드 시작일과 제공자·프로젝트·세션·모델을 일별 집계 키로 사용한다.
- **근거** — 같은 트랜잭션에서 최종 날짜별 합계와 반영한 파일 수정 시각을 함께 확정하면 재시도해도 같은 사용량을 두 번 더하지 않는다. 기간·모델·프로젝트·세션 조회에는 토큰 합계와 평균의 표본 수를 저장하면 된다.
- **결과** — 첫 갱신 때 기존 토큰·비용·도구 통계를 일별로 이관하고 스레드·응답 상세 행을 정리한다. 통계 화면은 일별 집계를 조회하고 데이터 확인 화면은 원본 파일의 상태와 오류를 표시한다. 삭제 보존이 켜져 있으면 소실 원본이 있는 세션에서 다시 계산한 결과가 없는 날짜의 합계를 유지한다. 같은 세션·날짜에 읽을 수 있는 원본이 있으면 그 원본으로 다시 계산한다.
- **검증** — 원본 감지부터 집계·저장·조회까지 코드와 SQL 바인딩을 검토했다. 타입 검사·린트·JavaScript 문법 검사·diff 검사를 통과했다. SQLite 실데이터 이관·증분 동작과 자동 테스트는 실행하지 않았다.

### 파일을 읽는 동안 응답별 최고값을 확정하고 도착 즉시 병합한다

- **의사결정** — 사용자는 한 번 읽으면서 최고값을 선택하고, 누계와 부모 복사 검산에 필요한 값만 따로 보관하도록 요청했다. 파서는 응답 키별로 토큰이 가장 큰 행을 갱신한다. 수집기는 파일 결과가 도착할 때마다 최고값을 병합한다.
- **근거** — 같은 키의 최고값을 파일 안에서 고른 뒤 파일 간에 비교해도 같은 결과를 얻는다. Codex 누계 구간의 증가량을 첫 등장 응답들의 합이 이미 충족하면 최종 최고값의 합도 충족하므로 그 구간은 전달하지 않는다.
- **결과** — 파일별 중복 응답 배열을 수집기에서 보관하던 단계를 제거했다. 요청 ID가 비어 있는 Claude 기록은 귀속을 확인할 때까지 별도 최고값으로 두고, Codex는 보충 가능성이 있는 누계 구간과 구형 부모 복사 확인용 순서를 유지한다. 파서 버전과 SQLite 형식 변경 없이 적용한다.
- **검증** — 기존 동점 순서, 최초 등장 위치, 구형 복사와 누계 판정 조건을 코드로 대조했다. 타입 검사·린트·diff 검사를 통과했다. 실로그 재수집, RSS 재측정과 일반 자동 테스트는 미실행이다.

### 응답별 최고 사용량과 확인된 누계 증가분을 스레드에 합산한다

- **의사결정** — 사용자는 반복 응답에서 가장 큰 사용량을 쓰고 중단 전에 기록된 토큰을 포함하도록 요청했다. 새 Codex는 턴·응답 ID로 사용량을 비교하고 Claude는 세션 내 응답·요청 ID로 비교한다. 구형 Codex는 첫 누계에서 확인 가능한 `last_token_usage`를 쓰고, 이후 동일 스냅샷과 확인된 fork 복사를 제외한다.
- **근거** — 같은 스레드의 파일 전체 합계를 비교하면 한 파일 안의 반복 응답이나 부모 이력 복사를 구분하기 어렵다. 새 Codex의 개별 `usage`로 직접 집계하고, 이미 관측한 누계 사이에서 독립 근거가 뒷받침한 누락분을 보충한다.
- **결과** — 본문이나 도구 인자 없이 토큰 계산에 필요한 응답·누계 기록을 수집 중에만 보관한다. SQLite에는 스레드·모델 합계를 반영하며 파서 버전 25에서 읽을 수 있는 원본을 다시 파싱한다. 부모 원본이 없을 때는 확인할 수 없는 복사분을 차감하지 않는다.
- **검증** — 실제 로그 703파일의 새 합계 3,471,637,808토큰은 원본 독립 검산과 일치했다. v24의 과다 집계 282,177,382토큰을 제거했다. 최종 전후 1쌍에서 최초 수집이 4.19초에서 3.67초로, 관측 피크 RSS가 377.40 MiB에서 478.73 MiB로 바뀌었다. SQLite 무결성·외래 키·모델 및 기간·세션·프로젝트 합계, 타입 검사·린트·diff 검사를 확인했다. 증분 갱신과 일반 자동 테스트는 미실행이다. [A/B 결과](benchmarks/success/2026-11-24/ResponseThreadAccountingAB-2026-11-24.md)

### 원본 사용량을 스레드 단위로 집계한다

- **의사결정** — 사용자는 세션·스레드 ID만 중복 키로 사용하고 토큰·시간·모델과 함께 읽도록 요청했다. 파일 후보의 입력+출력 합계를 비교하며 동점이면 최신 수정 시각과 경로 순서로 정한다. JSONL의 선택 조각은 한 번에 디코딩한다.
- **근거** — 응답·부모 요청별 객체와 참조를 계속 보유하지 않아도 스레드 합계를 저장할 수 있다. Codex 누계에서는 이전 최대값을 기준으로 증가분을 얻는다. 응답 ID와 부모 관계를 읽지 않으면 누계가 없는 로그의 내부 반복 기록과 fork 복사 이력은 별도로 식별할 수 없다.
- **결과** — 파서 버전 24의 다음 갱신 때 읽을 수 있는 원본을 스레드 행으로 갱신한다. 스레드 수·평균과 기록 시간으로 표시하며 도구 통계 수집을 중단한다. 프로젝트는 파일 경로에서 결정하고 원본 결제 방식은 읽지 않는다. 원본이 남지 않아 재구성할 수 없는 이전 보존 통계는 기존 형식으로 남을 수 있다.
- **검증** — 타입 검사, 린트, 대시보드 JavaScript 문법 검사와 diff 검사를 통과했다. 새 스레드 통계의 실로그 수집·메모리 측정·자동 테스트는 미실행이다.

### JSONL에서 집계와 표시에 쓰는 값만 객체화한다

- **의사결정** — 사용자는 초기 파싱에서 쓰지 않는 속성을 제거하고 실제 로그로 검증하도록 요청했다. 제공자와 행 종류별로 읽는 필드를 정의하고, 일반 응답·도구 결과의 본문과 사용하지 않는 누계·quota 속성은 JSON 구문만 검사한다.
- **근거** — 줄 전체를 객체화하면 바로 버리는 값도 문자열과 배열로 만들어진다. 부모 요청 연결에 쓰는 자식 생성 결과, 과거 로그 지원, 토큰 검산·진단, 제목·비용·도구 통계의 입력은 필요하다.
- **결과** — 일반·압축 로그와 Codex 이름 색인에 필드 선택을 적용한다. 파서 버전 23, 줄 예산, 원본 위치 및 미완성 행 처리 규칙을 유지한다.
- **검증** — 같은 실제 로그 700파일을 새 SQLite DB에 변경 전후 수집했다. 도구 통계 켬·끔 모두 요청 1,536건·토큰 3,157,867,688개·응답 반영 24,390행, 모델·도구·비용·원본 관계 및 전체·일·월·세션·프로젝트 조회가 일치했다. 무변경 갱신의 본문 읽기는 0바이트였고 SQLite 무결성·외래 키 검사와 타입 검사·린트·diff 검사를 통과했다. 도구 통계를 켠 최초 수집 한 번의 관측값은 3.42초에서 3.73초로 늘었다. 일반 자동 테스트는 미실행이다.

### winner 참조 키로 이벤트 순번을 재사용한다

- **의사결정** — 사용자는 실제 로그 관찰 결과에 따라 winner의 참조 속성을 최소화하도록 요청했다. 참조 ID에 원래 이벤트 순번을 쓰고, `index`, `schema`, `offset`은 참조 Map의 값에서 제거했다.
- **근거** — 동점 순서는 참조 ID에서 얻을 수 있다. 복사된 이전 응답은 파일별 복사 이력에서 이벤트 순번으로 찾을 수 있고, 요청의 진단 위치는 파일의 요청 상태와 유효한 이전 형식 근거를 등록할 때 결정된다.
- **결과** — 세션별 비교는 참조 ID로 응답 정보를 찾고, 토큰은 이미 확인한 부모 요청에 합산한다. 복사 이력 제외와 이후 후보 선택에 필요한 근거를 파일 계획에서 유지한다.
- **검증** — 타입 검사·린트·diff 검사를 통과했다. 변경 후 실데이터 비교와 자동 테스트는 미실행이다.

### winner 배열을 참조 ID와 토큰으로 구성한다

- **의사결정** — 사용자는 winner 배열에 참조 ID와 해당 응답의 토큰만 두고 갱신하도록 요청했다. 참조 ID는 파일별 참조 목록에서 응답과 요청을 찾는 배열 인덱스로 정했다.
- **근거** — 최종 응답 키·귀속·이전 형식 판정에 쓰는 속성과 모델·결제는 파일별 참조 목록에서 읽을 수 있다. 최종 비교 점수는 토큰으로 다시 계산할 수 있다.
- **결과** — 파일 준비 이후 winner는 `{ referenceId, tokens }` 형태다. 집계기는 참조 목록으로 부모 요청과 최종 응답 키를 확인하고 winner의 토큰을 요청에 반영한다.
- **검증** — 타입 검사·린트·diff 검사를 통과했다. 이전 winner 형식과 참조 ID 형식으로 같은 실제 JSONL 698파일을 새 DB에 각각 한 번 수집했다. 요청 1,523건·토큰 3,147,422,304개·응답 반영값 24,316행, 모델·도구·비용 및 일·월·세션·프로젝트 조회가 일치했다. SQLite 무결성과 외래 키 검사를 통과했다. 증분 갱신과 일반 자동 테스트는 미실행이다.

### 파일 준비 결과에는 최종 집계용 winner만 담는다

- **의사결정** — 사용자는 부모·서브에이전트 연결에 필요한 근거와 SQL 갱신에 쓰는 winner 값만 남기도록 요청했다. 파일의 응답별 비교가 끝나면 이벤트 종류·진단 플래그·reasoning을 뺀 winner를 만들고, 복사 접두사 뒤의 legacy 대체 후보에도 같은 형식을 적용한다.
- **근거** — 진단 플래그와 reasoning을 사용하는 검증·복사 이력 비교 근거는 원본을 읽으면서 수집한다. 집계기는 응답 식별자·귀속·순서, 입력·출력·캐시 토큰, 모델·결제 값을 사용한다.
- **결과** — 파일 준비 이후와 Worker 전달에서 응답 후보가 들고 있는 필드가 줄었다. 부모 정보와 자식 생성 연결은 파일에서 공유하며 요청 합계와 응답별 SQL 반영값의 형식은 유지된다.
- **검증** — 현재 JSONL 698파일을 빈 DB에 빌드별 한 번 수집했다. 요청 1,523건·응답 반영값 24,316행과 네 평균 조회 결과가 일치했다. 관측 피크 V8 힙은 10.09%, 전체 시간은 0.50% 줄었다. 타입 검사·린트·diff 검사를 통과했다. 일반 자동 테스트와 증분 시나리오는 미실행이다. [A/B 결과](benchmarks/success/2026-11-24/CompactWinnerAB-2026-11-24.md)

### 미관측 Codex 세션 별칭과 중첩 reasoning 대체 필드를 제거한다

- **의사결정** — 사용자는 로컬 로그에서 미사용인 항목 중 제거할 수 있는 것을 빼고 전체 재파싱 결과를 대조하도록 요청했다. 기존 검증에서 확인된 동작을 보존하는 범위로 정하고, Codex `session_meta.thread_id`·`session_meta.sessionId`와 `output_tokens_details.reasoning_tokens` 대체 읽기를 제거했다. 결제 분류는 유지했다.
- **근거** — 조사한 로컬 로그에서 이 세 대체 필드가 관측되지 않았고 기존 테스트에서 사용되지 않았다. 중첩 캐시와 `agent_id`, Claude 사용자 지정 제목·명시 소요 시간은 기존 테스트에서 지원 동작을 확인하는 항목이다.
- **결과** — Codex 세션 메타는 `id`와 `session_id`를 사용하고 reasoning은 `reasoning_output_tokens`를 사용한다. 파서 버전 23으로 올려 다음 갱신 때 기존 파일도 새 규칙으로 다시 읽는다.
- **검증** — 같은 실제 Claude·Codex 사본 696파일을 전후 빌드에서 처음부터 재수집했다. 요청 1,503건·토큰 3,135,757,475개·응답 반영값 24,224행과 모델·도구·비용·이름·일별 집계가 일치했다. 일·월·세션·프로젝트 조회도 일치했고, 원본 상태의 차이는 파서 버전과 기록 시각이었다. 타입 검사·변경 코드 린트·diff 검사를 통과했다. 일반 자동 테스트는 실행하지 않았다.

### 파일별 수정 시각으로만 일반 변경을 판정한다

- **의사결정** — 사용자는 원본 내용 검증과 관련 저장 데이터를 제거하고 수정 시각이 다른 파일을 처음부터 파싱하도록 요청했다. 제공자와 경로가 같은 `source_file` 행의 `mtime_ms`를 `lstat` 결과와 비교한다. 처음 보는 경로, 오류 재시도, 파서 버전 변경과 누락된 도구 수집도 재파싱 대상으로 유지한다.
- **근거** — 파일 단위 체크포인트를 쓰면 전체 스캔 기준 시각이나 파일 해시 없이도 과거 시각으로 바뀐 원본과 처음 발견한 경로를 수집할 수 있다. 변경된 세션의 토큰과 모델을 정확히 계산하려면 관계가 있는 원본도 필요하다.
- **결과** — 스키마 v24는 전역 갱신 기준, 원본 해시·이동 식별 열과 색인을 제거한다. 요청·응답 반영값·진단 참조와 부모 관계 메타는 보존한다. 파일 이동은 새 경로 추가와 기존 경로 소실로 처리하고, 본문 수정 시 기존 `mtime`을 그대로 유지하면 일반 변경 판정에서 제외된다.
- **검증** — 타입 검사·린트·diff 검사를 통과했다. 제거한 테이블과 열을 검사하는 기존 테스트는 유지했으며, 자동 테스트와 실제 DB 이관 실행은 수행하지 않았다.

### 파일을 읽으며 winner를 줄이고 요청 합계를 한 번 UPSERT한다

- **의사결정** — 사용자는 파일을 읽는 동안 응답별 winner와 필요한 상태만 갱신하고, SQL의 이전 값과 대조해 최종 요청 토큰을 한 번 UPSERT하도록 요청했다. 갱신 전체의 winner Map을 제거했다. 세션 하나씩 파일별 winner를 최종 키 순으로 정렬하고 연속한 중복을 한 건으로 합친다.
- **근거** — 직전 [현재 로그 A/B](benchmarks/failure/2026-11-24/SingleWinnerMapAB-2026-11-24.md)에서 갱신 전체에 Map을 두는 방식은 전체 재수집 중 최종 집계가 75.00→88.82ms, 관측 피크 힙이 79.09→94.49MiB였다. 파일 파싱 중 반복 응답을 줄이고, 최종 합계 계산과 저장이 같은 SQLite 상태를 보도록 이전 값 조회를 쓰기 트랜잭션 안에 둔다.
- **결과** — 같은 키를 파일 간에 보더라도 응답은 한 번만 더한다. 최종 요청 합계는 논리 요청 키로 한 번 UPSERT하며 응답별 반영값도 같은 트랜잭션에서 확정한다. 파서 버전 22의 첫 갱신은 기존 원본을 다시 읽어 반영값을 계산한다.
- **검증** — 별도 정적 검토에서 요청 ID 보존, 차분 조회의 트랜잭션 경계, 복사 이력 제외와 삭제·감소·재귀속 경로를 확인했다. 타입 검사·린트·diff 검사를 통과했다. 변경 후 자동 테스트와 A/B 측정은 수행하지 않았다.

### 최종 응답 키로 한 번만 winner를 고른다

- **의사결정** — 사용자는 파일별 비교와 세션별 중복 가능성 분기를 없애고 Map 하나에서 winner를 선택하도록 요청했다. 파싱한 후보는 복사 접두사와 부모 귀속을 확인한 뒤 제공자·세션·최종 응답 키로 비교한다. 기존 DB도 이 순서로 다시 집계하도록 파서 버전을 21로 올렸다.
- **근거** — 변경 전 로컬 로그에서 세션 Map을 조회한 Codex 후보 14,402건 중 최종 키 충돌은 0건이었다. 최종 키와 유효성을 먼저 확정하면 같은 파일에서 반복된 행과 여러 파일의 복제 행에 같은 규칙을 쓸 수 있다. 원본별 패자도 최종 비교 시점까지 응답 후보로 남는다.

- **근거**: JSONL 본문을 열기 전에 얻는 수정 시각으로 처리 순서를 결정한다. 실제 기간 필터는 요청 시각을 사용한다. 먼저 파싱한 결과는 전체 집계에서도 재사용한다. 전체 스캔에서만 영속 통계와 성공 기준 시각을 확정해 나중에 발견되는 관계도 반영한다.
- **결과**: 새 화면과 필터 초기화는 최근 30일을 선택한다. 갱신 중에도 필터와 이름 목록을 조회할 수 있다. 이전 기록은 백그라운드에서 반영되며 끝나는 시점에 현재 선택 조건으로 다시 조회한다. 수정 시각이 오래된 파일의 최근 요청은 전체 집계 단계에서 추가될 수 있다.
- **검증**: 타입 검사·린트·Node 테스트 440개와 격리된 VS Code 스모크 테스트를 통과했다. 합성 Claude 로그 1,020파일·15,300요청 중 최근 20파일·300요청을 사용했다. 각 방식의 3회 중앙값에서 첫 30일 Worker 응답은 3,486.0→244.4ms, 전체 반영 후 같은 조회 응답은 3,486.0→3,610.6ms였다. 갱신 중 세션별 조회와 페이지 이동은 2.0ms였고 최종 집계와 전체 원본 읽기 바이트는 같았다.

### 호버로 열린 사용량 카드를 클릭하면 포커스를 주고 고정한다

- **의사결정**: 사용자는 호버 중 클릭으로 팝업에 포커스를 주고, 이후 클릭 열기·닫기를 유지하도록 요청했다. 팝업 동작, 화면 스타일, 이전 패치 호환 코드를 별도 파일로 분리했다.
- **근거**: 마우스를 누르는 동안 열린 카드를 유지하고, 클릭은 VS Code 내장 토글로 전달한다. 내장 토글은 고정 여부에 따라 카드에 포커스를 주거나 닫는다. 과거 주입과 원본 백업의 호환성은 설치 파일을 갱신할 때 검증한다.
- **결과**: 호버로 열린 카드를 처음 클릭하면 같은 위치에서 고정되며, 마우스를 옮겨도 유지된다. 다시 클릭하면 닫힌다. [상태 표시줄 설계](refrences/AgentTracker.md#34-상태-표시줄과-카드형-툴팁).
- **검증**: 타입 검사·린트·438개 테스트를 통과했다. VS Code 1.147.0에서 호버 중 클릭 포커스, 같은 위치 고정, 마우스 이탈 후 유지, 재클릭 닫기, Esc·바깥 클릭과 6개 언어 카드 갱신을 확인했다. [분리 및 호환 검증](research/2026-11-21/StatusBarToggleRefactor-2026-11-21.md).

### 수정 시각 갱신에서 파일별 관측 기록과 파서 복원을 제거한다

- **의사결정**: 사용자는 수정 시각 기반 알고리즘의 잔재를 제거하고 책임별 메소드로 정리하도록 요청했다. 경로별로 하나의 파일 상태를 만들고, 재파싱이나 소실로 영향 세션이 생기는 경우에 관계 색인을 채운다. 집계는 준비된 winner DTO를 직접 사용한다.
- **근거**: 파일마다 저장한 스캔 ID와 inode 조회는 수정 시각 판정이나 내용 기반 원본 이동 확인에 쓰이지 않았다. 현재 세션과 탐색 순서를 파일 상태에 모으고, 관계 후보·파서 복원·저장 방문 여부를 위해 중복 보관하던 상태를 줄였다.
- **결과**: 무변경 스캔은 원본 행을 다시 쓰지 않는다. 겹치는 로그 루트에서 같은 새 파일을 만나도 파일 ID를 한 번 배정하고 한 번 파싱한다. 종료 시 이름과 전역 기준 시각을 반영한다. 파일별 관측 ID의 물리 열은 SQLite v21 호환용으로 둔다.
- **검증**: 무변경 원본 행에 쓰기가 들어오면 실패하도록 한 회귀 테스트와 겹치는 로그 루트의 첫 갱신을 확인했다. 타입 검사·린트·436개 Node 테스트와 고정 입력의 전후 대조를 수행했다. [단순화 결과와 검증](research/2026-11-21/MtimeRefreshSimplify-2026-11-21.md).

### 마지막 성공 갱신 이후 수정된 JSONL을 처음부터 읽는다

- **의사결정**: 사용자는 파일별 읽기 위치와 갱신용 manifest를 폐기하고 SQLite에 성공한 전역 갱신 시각을 기록하도록 요청했다. 변경 후보와 영향 세션의 관련 원본을 처음부터 파싱하고, winner DTO와 귀속 근거는 해당 갱신 중에만 사용한다.
- **근거**: 완료 시각을 사용하면 탐색 뒤에 수정된 파일이 다음 갱신 범위에서 빠질 수 있다. 잠금을 얻은 직후의 시작 시각을 마지막 트랜잭션에서 확정하며, Windows에서는 파일 수정 시각과 시스템 시계의 짧은 차이를 흡수하기 위해 8ms를 중첩한다. 오류·보류·취소가 발생하면 기존 기준을 유지한다.
- **결과**: 파일별 파서 체크포인트 Map과 재개용 SQLite 열을 삭제했다. 기존 파일 출처·진단·이동 확인 데이터는 보존한다. 과거 수정 시각을 유지한 편집·복사·이동은 증분 대상에서 빠질 수 있다. 첫 수집이나 파서 설정·루트 변경 시 현재 범위를 처음부터 읽는다.
- **검증**: 타입 검사·린트·437개 Node 테스트가 통과했다. 이전 DB 이관, 재시작 후 증분, 마지막 SQL 트랜잭션 실패 뒤 재시도, 관련 파일의 winner 재집계를 확인했다. 실제 855요청과 합성 10,000·100요청의 A/B에서 요청·모델·도구·비용 facts, 토큰 합계와 네 집계가 일치했다. [실측과 재현 방법](benchmarks/success/2026-11-21/MtimeRefreshAB-2026-11-21.md).

### 사용량 카드의 표시 여부를 기준으로 클릭을 토글한다

- **의사결정**: 사용자는 호버 표시와 클릭 열기·닫기를 요청했다. 마우스를 누르는 동안 카드를 유지하고 클릭이 완료되면 현재 표시 여부에 따라 닫거나 연다. 클릭으로 연 카드는 마우스를 옮겨도 유지한다.

- **검증**: 타입 검사·린트·438개 테스트와 격리된 VS Code 1.147.0의 마우스·키보드 검증을 통과했다. 호버 카드를 누르는 동안 표시 유지, 클릭 닫기·재열기, 이탈 후 호버 복구, 바깥 클릭·Esc 닫기와 6개 언어 카드 갱신을 확인했다.

## 2026-11-19

### manifest 변경 판정을 없애고 완성 줄 prefix 해시로 증분을 검증한다

- **의사결정**: 사용자는 완성 줄 위치 P와 원본 `[0,P)` 해시만으로 증분을 판정하고 중간 변경 시 전체 파싱·재집계하며, SHA-256·BLAKE3·XXH3-128과 스레드 처리의 복잡도·정합성·실측을 비교하도록 지시했다. Codex는 크기·mtime fingerprint 생략을 제거하고 기존 manifest를 파일 ID·진단·소실 보존용 `source_file`로 이관했다. 제품 기본값은 Node 내장 SHA-256이며 두 native 해시는 벤치마크 공급자로 비교한다. 파서 문맥·요청별 winner를 메모리에 재사용하고 실패 시 폐기하며, 통계 Worker와 최대 4개의 파일 준비 풀을 사용한다.
- **근거**: 같은 크기·mtime의 중간 수정도 원본 prefix 검증으로 찾을 수 있다. P·해시만으로 이전 누계·응답 중복·미완료 요청·fork 귀속을 복구할 수 없으므로 최소 파서 문맥·winner 보관은 필요하다. 전체 prefix 읽기는 O(N)이고 캐시는 O(R)이며 스레드가 이 차수를 낮추지는 않는다. native 해시의 배포 바이너리·플랫폼 의존성을 제품에 추가하지 않아 내장 SHA-256을 기본값으로 둔다.
- **결과**: 정상 append는 완성 줄 뒤의 새 행만 해석하고 기존 응답 갱신도 반영한다. 해시 불일치·축소·파서/수집 설정 변경은 전체 파싱으로 복구하며 미완성 줄·동점 순서·기존 DB 오류/취소/삭제·이동 보존을 유지한다. DB 재시작 첫 갱신과 Zstd 파일은 전체 파싱한다. 원문·전체 이벤트·블록 색인·파서 상태 blob은 DB에 추가하지 않는다.
- **검증**: 타입·린트·436개 Node 테스트, 준비 포함 1,326표본(본 표본 1,020개)의 facts·조회 대조와 독립 평균 5,304대조를 통과했다. 원본 UTF-8·CRLF·이미지·부분 줄·중간 수정/삽입·축소·실패 복구·파일 Worker 재개·구형 DB 이관·재시작을 검사했다. 현재 836·합성 10,000·100요청에서 전체 prefix 읽기 때문에 갱신이 느려졌고, 2파일 긴 세션의 10,000요청 append는 443.198→365.471ms였다. 현재 SHA-256 파일 Worker 1/4개는 2,672.045→1,273.135ms로 줄지만 최고 관측 RSS는 257.48→344.96MiB로 늘었다. [A/B·복잡도·메모리·정합성 결과와 한계](benchmarks/failure/2026-11-19/PrefixHashAB-2026-11-19.md).

### 평균 토큰 도표에서만 토큰 구성별 평균을 계산한다

- **의사결정**: 사용자는 선택한 탭·도표와 하단 표에서 실제 사용하는 항목만 계산하도록 쿼리 최적화를 요청했다. 에이전트는 기존 `chartMetric`을 집계 SQL 생성에 연결해 평균 토큰 도표에서 입력·출력·캐시 저장·캐시 재사용의 네 평균을 계산하도록 정했다. 총 토큰·요청 수·평균 시간 도표에서는 해당 필드를 NULL로 반환한다.
- **근거**: 하단 표는 총 토큰 평균과 시간·표본 정보를 사용하고, 구성별 평균 네 개는 평균 토큰 도표에서 사용한다. 원본 SQL의 조건부 AVG·캐시 표본 COUNT와 일별 집계 SQL의 구성별 SUM·나눗셈을 선택에 따라 생략할 수 있다.
- **결과**: 제공자별·모델별 집계와 비용 포함 원본 조회에 같은 선택을 적용한다. 응답 필드 이름은 유지하며 도표 선택이 없는 직접 조회 API는 전체 지표를 계산한다. 평균 토큰 선택 시 기존 완료 표본·빈 사용량 제외·캐시 미상 처리를 적용한다.
- **검증**: 화면의 지표 선택부터 메시지·Worker·DB 조회로 전달되는 참조와 원본·일별 집계의 조건별 SQL 구성을 검토했다. 타입 검사·린트·diff 검사를 통과했다. 실제 1,387·합성 10,000·100요청의 96개 조회 조건을 교대 10쌍 비교하고, 독립 집계와 요청 추가 후 정합성을 검증했다. 기본 제공자별 전체 기간 조회는 실제 데이터에서 7.8~17.5% 빨라졌다. [측정 보고서](benchmarks/success/2026-11-12/ChartMetricAB-2026-11-12.md)

### 원본 이동은 내용 검증으로 확정해 inode 재사용에 따른 통계 손실을 막는다

- **의사결정**: 사용자는 CI 실패 원인 분석·해결을 요청하고 이번 복구의 테스트 수정·실행을 허용했다. 에이전트는 Ubuntu에서 확인한 inode 재사용에 의한 잘못된 경로 이동 판정을 수정했다. 새 경로를 발견 단계에서 기존 manifest ID에 연결하던 POSIX 분기를 제거하고, 모든 운영체제에서 파싱된 원본 식별자와 내용 해시를 검증하는 기존 재연결 경로로 처리한다.
- **근거**: 삭제된 파일의 inode는 내용이 다른 새 파일에 재사용될 수 있다. 이전 경로의 부재와 dev/inode 일치만으로 이동을 확정하면 보존할 원본과 토큰이 사라진다. 내용 검증 경로는 같은 크기의 전체 해시 또는 append 전 byte 범위의 해시로 원본 포함 여부를 판단한다.
- **결과**: 다른 내용의 새 파일과 소실된 이전 원본을 별도로 보존한다. 검증된 이동은 새 위치의 manifest ID를 유지하고 기존 행은 통계 반영과 함께 정리한다. inode 재사용을 명시적으로 구성한 기존 회귀 테스트를 보강하고, 하위 에이전트 귀속·묶음 취소·기간 선택·설정 삭제 관련 기존 테스트의 입력과 기대값을 현재 설계에 맞췄다.

### quota QA의 막대 기대값에도 사용량·잔여량 표시 모드를 적용한다

### 확정한 root·그룹·메타데이터를 공유해 반복 알고리즘과 조회를 줄인다

- **의사결정**: 사용자는 서브에이전트로 현재 기능을 유지하면서 알고리즘·쿼리·파싱을 재검토하고 불필요한 방어·확장 코드를 제거하도록 지시했다. 에이전트는 부모 root 해소 뒤의 Union-Find 재병합을 직접 그룹화로 바꾸고, 페이지 GROUP BY의 window 지표를 전체 개수·도구 비율에 공유했다. 요청 저장의 비용 SELECT·Skill 보존 시 미사용 SELECT·중복 정렬·동일 세션 삭제 보존 조회와 coverage의 진단 목록 조회를 제거했다. 세션 결제 변경은 요청별 반복에서 세션 한 번의 비용 집계로 바꿨다. 파싱은 제목 배열·도구 인자 반복 검색·이차 중복 제거·중복 시각 해석·복사와 이미 보장된 범위·identity 검사를 줄였다.
- **근거**: 이미 확정한 root·그룹 집계·요청 ID·Buffer 범위를 다시 계산하거나 확인할 필요가 없다. 새 스키마·인덱스·영속 캐시·dirty mask 없이 기존 결과를 재사용했다. 계보·멤버 Map의 내부 키 순서는 입력순으로 달라질 수 있으나 제품은 root lookup만 사용하며 root별 원본 배열과 winner 순서는 유지한다. 손상 JSONL·부분 줄·압축·fork/legacy·취소·실패 보존·트랜잭션 경계와 입력 수치 검증은 실제 계약이므로 남겼다.
- **결과**: 코드 경로상 결과가 있는 통계·이름 페이지의 데이터 SELECT/GROUP BY는 2→1회, 도구 네 분류 SELECT는 8→4회, coverage는 3→1회다. 후속 빈 페이지의 count와 요청 cursor의 별도 전체 개수는 유지한다. 기존 요청은 비용 비교용 SELECT 한 번을 생략하고 세션 결제 비용 갱신은 요청 수와 무관하게 SQL 한 번을 실행한다. 도구 중복 제거는 입력 순서를 보존하는 Set을 사용한다. 공개 결과 필드·평균/NULL·비용·필터·정렬·페이지·스키마 v19/집계 형식 v2는 유지한다.

### 최종 이름과 결제 설정을 저장 묶음의 고유 키로 처리한다

- **의사결정**: 사용자는 최종 결과에 대해서만 이름을 한 번 저장하도록 알고리즘을 정리하고 A/B 1회를 요청했다. 에이전트는 정상·세션 비중첩 묶음에서 입력을 한 번 색인하고 보존 대상은 제외한 뒤 프로젝트 마지막 이름·세션 마지막 nonempty 이름을 선택했다. FK 부모 이름은 요청보다 먼저 키별 한 번 UPSERT하고 사용자 결제 설정도 세션별 한 번 읽는다. 영향 이름 prune은 묶음 끝에 모으며, 성공 COMMIT한 이름만 반환해 후단의 동일 Codex 제목 UPDATE를 생략한다.
- **근거**: 요청별로 같은 이름 UPSERT·설정 SELECT를 반복할 필요가 없다. 정상 묶음의 관련 SQL은 O(N)에서 O(P+S) 호출로 줄고 전체 요청 처리 차수 O(N)은 유지된다. 계획에 O(N+P+S) 참조/보조 공간이 들며 거래 밖 설정 캐시는 두지 않는다. 빈 이름 보존·사용자 override 우선·요청별 billing fallback·제목만 바뀐 세션의 갱신은 유지하고, 반복 세션 snapshot·삭제·재연결 직접 API는 중간 prune·결제 cascade를 보존하는 snapshot별 호환 경로를 선택했다. 단일·묶음 rollup과 COMMIT 경계도 유지한다.
- **결과**: 현재 805요청·합성 10,000요청의 이름 UPSERT 두 종류·결제 SELECT 합계가 2,415→410회·30,000→250회로 줄었다. 최초 DB 저장은 169.184→165.601ms·1,111.814→1,020.088ms였다. 최초 전체 갱신은 현재 1.12% 느려졌고 합성은 5.00% 빨라졌다. 합성 1건 추가 저장은 10.282→10.956ms로 느려졌으며 단일 AB 관측이므로 안정적인 속도 개선으로 일반화하지 않는다. `storage.metadata`로 이동한 이름·설정 비용을 별도 계측한다.
- **검증**: 새 이름·설정 경계 7개, transaction 직접 검증의 독립 집계 160건·원자성·rollback/retry·취소·삭제 보존·재연결·scanner fallback을 통과했다. ### 변경 세션 rollup을 저장 묶음 마지막에 한 번 수행한다

- **의사결정**: 사용자는 성분마다 반복하는 rollup을 최종 저장 결과에서 한 번 수행하고 개선량을 비교하도록 지시했다. 에이전트는 기존 transaction 안에서 facts·manifest·삭제 보존·이름 정리를 마친 뒤 `(provider, session_id)`를 중복 제거해 요청·모델 daily를 각각 한 번 DELETE·INSERT SELECT하는 방식을 선택했다. 전체 스캔까지 갱신을 지연하지 않고 기존 단일 세션·특수 성분·실패 재시도 경로와 COMMIT 경계를 유지한다.
- **근거**: 각 세션의 메타데이터 확인·SQL 호출·집계 준비를 공유할 수 있다. 고정 SQL에 JSON tuple 목록을 바인딩하고 daily PK 및 기존 요청 세션 UNIQUE→INTEGER PK로 원본 범위를 제한한다. 새 인덱스·TEMP 키 표·스키마 없이 평균의 합계·분모와 모델·캐시 NULL을 보존한다.
- **결과**: 현재 1,346요청·합성 10,000요청의 rollup은 70.517→26.265ms·138.276→101.313ms, DB 저장은 177.331→126.711ms·434.669→395.726ms로 줄었다. 전체 최초 갱신은 2.01%·3.95% 감소했다. 각 daily SQL 호출은 372→25회·100→10회였고 COMMIT은 26회·10회로 같았다. 단일 1건 추가의 일관된 개선은 확인하지 못했고 무변경 전체 갱신은 약 1.99ms·0.17ms 느려졌다. 중간에만 미지원 시각이 생긴 경우 최종 facts가 유효하면 B는 최종 캐시를 유지하며, 공개 조회 결과는 A의 재구축 뒤와 같다.
- **검증**: 준비 3쌍·교대 10쌍에서 A/B 요청·토큰·그룹별 평균·manifest·raw/rollup·독립 JS facts 집계·FK/integrity와 사본 복원이 일치했다. 반복 snapshot·삭제/이동·보존·키 충돌·캐시·시간대·rollup 실패 원자성과 실제 scanner fallback, 기존 묶음 경계·취소 검증을 통과했다. 실제 DB 사본의 PK 탐색 계획과 타입 검사·린트·diff를 확인했다. 강제 종료·전원 손실·경쟁 writer는 검증하지 않았다. ### 정상 성분을 제한된 트랜잭션으로 묶어 반복 COMMIT을 줄인다

- **의사결정**: 사용자는 서브에이전트와 현재 데이터·10,000건의 구간별 상위 두 병목 측정 및 최대 구간 최적화·A/B를 요청했다. 측정 결과 현재 데이터의 COMMIT을 대상으로 정했고, 에이전트는 정상 성분 최대 16개·합계 1,000요청의 순차 apply와 한 번의 COMMIT을 선택했다. 실패 시 전체 rollback 후 개별 재시도하며 성공 COMMIT 뒤에만 원본 settled와 affected를 확정한다. 단일 성분과 한도를 넘는 성분, deferred·오류·orphan·삭제·재연결은 기존 경로로 처리한다.
- **근거**: 현재 최초 저장에서 COMMIT 254.736ms가 최대 구간이었다. 동기화 설정을 유지하며 반복 확정 비용을 분담하면 계산 의미와 기존 SQL을 보존할 수 있다. 한 거래의 잠금 유지와 취소 확인 간격이 길어지는 비용이 있어 성분·요청 수를 제한했다.
- **결과**: 현재 1,341요청의 최초 성분 저장은 409.971→173.802ms, 10,000요청은 510.667→433.178ms였다. 성분 저장 COMMIT은 각각 387→26회·100→10회, 전체 갱신은 6.91%·9.98% 감소했다. 단일 1건 추가는 경로·거래 수가 같아 개선으로 판정하지 않았다. 정상 묶음 전체가 미완료·강제 종료의 확정 경계가 되고, 거래별 최대 유지 시간 중앙값은 5.894→12.608ms·10.303→48.428ms로 늘었다. 10,000요청의 요청 비교·저장과 rollup 재집계는 후속 최적화 대상으로 남긴다.
- **검증**: 준비 3쌍·교대 10쌍에서 A/B 요청·토큰·평균·manifest·raw/rollup·독립 JS facts 집계·FK/integrity가 일치했다. 별도 독립 지표 160건, reader 원자성, 전체 rollback·개별 재시도, 경계·취소·삭제 보존·재연결과 실제 scanner의 중간 저장 실패를 검증했다. 타입 검사·린트·diff 검토를 통과했다. 강제 종료·전원 손실·경쟁 writer 지연은 검증하지 않았다.
