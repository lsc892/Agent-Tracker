# Agent Tracker 기능 의사결정 일지

## 현재 설계 결정 요약

- 정상 독립 연결 성분은 입력 순서를 유지하며 최대 16성분·합계 1,000요청까지 한 동기 쓰기 트랜잭션에 반영한다. 단일·큰 성분과 오류·삭제·재연결 등 특수 처리는 기존 개별 경로를 사용한다.
- 성분별 snapshot과 평균·rollup의 집계 의미·PK·인덱스·WAL/FULL 설정을 유지한다. 묶음 실패는 전체 rollback 후 기존 성분별 재시도로 격리하며 settled·affected 확정과 취소 확인은 거래 경계를 따른다.
- 정상 성분 묶음은 각 snapshot의 facts 반영 뒤 실제 변경 세션을 중복 제거해 COMMIT 전에 최종 facts로 rollup한다. 변경 세션 0개는 생략하고 1개는 기존 경로를 사용한다. 복수 세션은 고정 SQL·JSON tuple 바인딩과 기존 인덱스로 범위를 좁혀 각 daily 표를 한 번씩 교체한다.

## 2026-11-10

### 변경 세션 rollup을 저장 묶음 마지막에 한 번 수행한다

- **의사결정**: 사용자는 성분마다 반복하는 rollup을 최종 저장 결과에서 한 번 수행하고 개선량을 비교하도록 지시했다. 에이전트는 기존 transaction 안에서 facts·manifest·삭제 보존·이름 정리를 마친 뒤 `(provider, session_id)`를 중복 제거해 요청·모델 daily를 각각 한 번 DELETE·INSERT SELECT하는 방식을 선택했다. 전체 스캔까지 갱신을 지연하지 않고 기존 단일 세션·특수 성분·실패 재시도 경로와 COMMIT 경계를 유지한다.
- **근거**: 각 세션의 메타데이터 확인·SQL 호출·집계 준비를 공유할 수 있다. 고정 SQL에 JSON tuple 목록을 바인딩하고 daily PK 및 기존 요청 세션 UNIQUE→INTEGER PK로 원본 범위를 제한한다. 새 인덱스·TEMP 키 표·스키마 없이 평균의 합계·분모와 모델·캐시 NULL을 보존한다.
- **결과**: 현재 1,346요청·합성 10,000요청의 rollup은 70.517→26.265ms·138.276→101.313ms, DB 저장은 177.331→126.711ms·434.669→395.726ms로 줄었다. 전체 최초 갱신은 2.01%·3.95% 감소했다. 각 daily SQL 호출은 372→25회·100→10회였고 COMMIT은 26회·10회로 같았다. 단일 1건 추가의 일관된 개선은 확인하지 못했고 무변경 전체 갱신은 약 1.99ms·0.17ms 느려졌다. 중간에만 미지원 시각이 생긴 경우 최종 facts가 유효하면 B는 최종 캐시를 유지하며, 공개 조회 결과는 A의 재구축 뒤와 같다.
- **검증**: 준비 3쌍·교대 10쌍에서 A/B 요청·토큰·그룹별 평균·manifest·raw/rollup·독립 JS facts 집계·FK/integrity와 사본 복원이 일치했다. 반복 snapshot·삭제/이동·보존·키 충돌·캐시·시간대·rollup 실패 원자성과 실제 scanner fallback, 기존 묶음 경계·취소 검증을 통과했다. 실제 DB 사본의 PK 탐색 계획과 타입 검사·린트·diff를 확인했다. 강제 종료·전원 손실·경쟁 writer는 검증하지 않았다. [상세 결과·원시 자료](benchmarks/2026-11-10/RollupBatchAB-2026-11-10.md).

### 정상 성분을 제한된 트랜잭션으로 묶어 반복 COMMIT을 줄인다

- **의사결정**: 사용자는 서브에이전트와 현재 데이터·10,000건의 구간별 상위 두 병목 측정 및 최대 구간 최적화·A/B를 요청했다. 측정 결과 현재 데이터의 COMMIT을 대상으로 정했고, 에이전트는 정상 성분 최대 16개·합계 1,000요청의 순차 apply와 한 번의 COMMIT을 선택했다. 실패 시 전체 rollback 후 개별 재시도하며 성공 COMMIT 뒤에만 원본 settled와 affected를 확정한다. 단일 성분과 한도를 넘는 성분, deferred·오류·orphan·삭제·재연결은 기존 경로로 처리한다.
- **근거**: 현재 최초 저장에서 COMMIT 254.736ms가 최대 구간이었다. 동기화 설정을 유지하며 반복 확정 비용을 분담하면 계산 의미와 기존 SQL을 보존할 수 있다. 한 거래의 잠금 유지와 취소 확인 간격이 길어지는 비용이 있어 성분·요청 수를 제한했다.
- **결과**: 현재 1,341요청의 최초 성분 저장은 409.971→173.802ms, 10,000요청은 510.667→433.178ms였다. 성분 저장 COMMIT은 각각 387→26회·100→10회, 전체 갱신은 6.91%·9.98% 감소했다. 단일 1건 추가는 경로·거래 수가 같아 개선으로 판정하지 않았다. 정상 묶음 전체가 미완료·강제 종료의 확정 경계가 되고, 거래별 최대 유지 시간 중앙값은 5.894→12.608ms·10.303→48.428ms로 늘었다. 10,000요청의 요청 비교·저장과 rollup 재집계는 후속 최적화 대상으로 남긴다.
- **검증**: 준비 3쌍·교대 10쌍에서 A/B 요청·토큰·평균·manifest·raw/rollup·독립 JS facts 집계·FK/integrity가 일치했다. 별도 독립 지표 160건, reader 원자성, 전체 rollback·개별 재시도, 경계·취소·삭제 보존·재연결과 실제 scanner의 중간 저장 실패를 검증했다. 타입 검사·린트·diff 검토를 통과했다. 강제 종료·전원 손실·경쟁 writer 지연은 검증하지 않았다. [상세 측정과 원시 자료](benchmarks/2026-11-10/TransactionBatchAB-2026-11-10.md).
