# Agent Tracker 기능 의사결정 일지

## 현재 설계 결정 요약

- 원본을 읽는 같은 순회에서 usage winner와 요청 상태·최신 check·도구 중복을 누적한다. raw metadata 재생과 합친 이벤트 정렬을 없애고, 관계 확정 뒤 남은 상태·winner만 병합해 최종 SQL에 반영한다. 정규화·비교점수와 세션 이름·진단 색인을 재사용하며 실제 legacy/fork·실패 보존 계약은 유지한다.
- 정상 독립 연결 성분은 입력 순서를 유지하며 최대 16성분·합계 1,000요청까지 한 동기 쓰기 트랜잭션에 반영한다. 단일·큰 성분과 오류·삭제·재연결 등 특수 처리는 기존 개별 경로를 사용한다.
- 성분별 snapshot과 평균·rollup의 집계 의미·PK·인덱스·WAL/FULL 설정을 유지한다. 묶음 실패는 전체 rollback 후 기존 성분별 재시도로 격리하며 settled·affected 확정과 취소 확인은 거래 경계를 따른다.
- 정상 성분 묶음은 각 snapshot의 facts 반영 뒤 실제 변경 세션을 중복 제거해 COMMIT 전에 최종 facts로 rollup한다. 변경 세션 0개는 생략하고 1개는 기존 경로를 사용한다. 복수 세션은 고정 SQL·JSON tuple 바인딩과 기존 인덱스로 범위를 좁혀 각 daily 표를 한 번씩 교체한다.
- 일별 집계는 요청 38개·모델 37개 상태를 저장한다. 미사용 공통 진단 3개와 모델별 최소 시각을 제거하고 세션 시작은 요청 daily에서 읽는다. 스키마 v19·집계 형식 v2 전환은 원본을 보존하고 파생캐시만 첫 조회에서 재구축한다.
- 정상 저장 묶음은 실제 반영할 최종 요청에서 이름을 모아 프로젝트·세션 키별 한 번 UPSERT하고 사용자 결제 설정도 세션별 한 번 읽는다. COMMIT한 이름은 같은 스캔의 후단 중복 UPDATE를 생략하는 데만 사용하며 제목만 바뀐 세션과 특수 snapshot의 순서는 보존한다.
- 신규 요청은 존재하지 않는 모델·도구 자식을 DELETE하지 않는다. 일별 집계는 변경 범위를 먼저 좁힌 작은 입력에서 사용량 유무를 한 번 확정하고 평균 표본들이 공유한다. 양수 토큰은 모델 확인을 생략하며 0토큰만 모델 기록으로 판정한다. 영속 스키마·집계 상태·기존 요청의 자식 교체와 transaction 경계는 유지한다.

## 2026-11-10

### 신규 자식 삭제를 없애고 일별 집계의 사용량 판정을 공유한다

- **의사결정**: 사용자는 현재 기능을 유지하면서 서브에이전트로 병목을 조사하고 큰 두 구간의 실제 쿼리·알고리즘을 최소화한 뒤 A/B하도록 지시했다. 에이전트는 요청 저장과 일별 집계를 선택했다. 신규 요청의 모델·도구 DELETE를 생략하고, 기존 WHERE로 제한한 좁은 집계 입력을 materialize해 사용량 플래그를 한 번 계산한다. 양수 토큰은 확정값을 쓰고 0토큰만 모델 존재를 확인한다. 기존 요청 교체·ID·updated_at·평균/NULL·부분 날짜·세션 범위 인덱스·스키마 v19/형식 v2는 유지한다.
- **근거**: 10,000건 최초 저장에서 존재하지 않는 자식 DELETE 20,000회가 실행됐다. 집계의 같은 사용량 판정도 여러 표본 식에 반복 삽입돼 입력 단계에서 공유하도록 했다. 32행 INSERT RETURNING 후보는 요청 저장·전체 갱신이 느려져 제거하고, 새로운 ID Map·대기 배열·영속 캐시 없이 불필요한 쿼리만 줄였다. 날짜 함수 호출 수는 줄지 않았고 상관 계획 노드 감소를 행별 실행 횟수 감소로 일반화하지 않는다.
- **결과**: 현재 1,355건·합성 10,000건의 최초 요청 저장은 52.748→44.256ms·276.026→237.589ms, DB 저장 전체는 148.727→141.102ms·452.811→404.756ms였다. 일별 집계는 30.480→30.289ms·112.898→107.372ms로 실제 입력의 효과는 미미했다. 100건 DB 저장은 8.682→9.185ms로 느려졌고 단일 추가 전체 refresh도 세 규모 모두 소폭 악화해 모든 입력에서의 개선으로 주장하지 않는다. 신규 자식 DELETE는 현재 2,710→0회·합성 20,000→0회로 줄었다.
- **검증**: 세 규모의 준비 3쌍·교대 10쌍에서 요청·토큰·평균·그룹 수·facts·raw/rollup·독립 JS 집계·FK/integrity·사본 복원이 일치했다. 요청 수 경계 7종·부분 날짜/미상/두 시간대/빈 페이지 96대조와 별도 transaction의 독립 집계 160건·rollback/retry·reader 원자성·실패 격리·취소·삭제 보존·재연결을 통과했다. 타입·린트·diff를 확인했고 일반 자동 테스트 suite는 실행하지 않았다. [A/B 결과·원시 자료·한계](benchmarks/2026-11-10/QueryMinimizeAB-2026-11-10.md).

### 원본 순회에서 요청 상태를 접고 남은 winner만 최종 집계한다

- **의사결정**: 사용자는 여러 번의 수집·winner·중복 제거 순회를 통합하고 불필요한 예외·방어 코드를 제거한 뒤 기존 데이터와 정합성을 검사하도록 지시했다. 에이전트는 읽는 동안 요청별 turn 상태·최신 check·도구 중복·최소 위치와 usage winner를 함께 누적했다. raw metadata 배열·재생 진입점·합친 이벤트 정렬·반복 정규화·score 재계산·종료 시 outcome 재생을 제거하고 세션 이름·진단도 한 번 색인한다.
- **근거**: 이미 읽은 이벤트를 후단에서 다시 해석할 필요가 없다. 부모/fork·늦은 request 귀속은 작은 근거로 확정한 뒤 남은 상태만 병합한다. current/legacy 중복 의미, 패자 진단·root, 손상 파일·부분 줄·취소·원자성은 실제 계약이므로 보존한다. 최종 행 생성·출력 정렬·DB 변경 비교와 필요한 legacy 위치는 남아 전체 작업을 한 루프라고 표현하지 않는다.
- **결과**: product의 원본 준비·집계 경로와 Worker snapshot이 새 내부 상태를 사용하며 영속 DB 스키마·공개 집계 의미는 유지된다. 현재 823요청·1,538,591,540토큰과 합성 10,000요청의 최초·+1요청/+130토큰 추가·무변경 결과가 기존 구현과 일치했다.
- **검증**: 요청·모델·도구·비용·이름·manifest·진단·평균·raw/rollup·독립 JS facts 집계·FK/integrity·사본 복원이 일치했다. 별도 변경 전/후 이벤트 96 seed·59,136개와 독립 SQL oracle 32 seed, 새 경계 5개도 통과했다. 타입·린트 통과, 전체 432개 중 426개 통과이며 나머지 6개는 A에서도 재현되는 기존 실패다. 단일 참고 시간과 미측정 범위는 [통합 기록](research/2026-11-10/UnifiedStreamingStats-2026-11-10.md)에 둔다.

### 최종 이름과 결제 설정을 저장 묶음의 고유 키로 처리한다

- **의사결정**: 사용자는 최종 결과에 대해서만 이름을 한 번 저장하도록 알고리즘을 정리하고 A/B 1회를 요청했다. 에이전트는 정상·세션 비중첩 묶음에서 입력을 한 번 색인하고 보존 대상은 제외한 뒤 프로젝트 마지막 이름·세션 마지막 nonempty 이름을 선택했다. FK 부모 이름은 요청보다 먼저 키별 한 번 UPSERT하고 사용자 결제 설정도 세션별 한 번 읽는다. 영향 이름 prune은 묶음 끝에 모으며, 성공 COMMIT한 이름만 반환해 후단의 동일 Codex 제목 UPDATE를 생략한다.
- **근거**: 요청별로 같은 이름 UPSERT·설정 SELECT를 반복할 필요가 없다. 정상 묶음의 관련 SQL은 O(N)에서 O(P+S) 호출로 줄고 전체 요청 처리 차수 O(N)은 유지된다. 계획에 O(N+P+S) 참조/보조 공간이 들며 거래 밖 설정 캐시는 두지 않는다. 빈 이름 보존·사용자 override 우선·요청별 billing fallback·제목만 바뀐 세션의 갱신은 유지하고, 반복 세션 snapshot·삭제·재연결 직접 API는 중간 prune·결제 cascade를 보존하는 snapshot별 호환 경로를 선택했다. 단일·묶음 rollup과 COMMIT 경계도 유지한다.
- **결과**: 현재 805요청·합성 10,000요청의 이름 UPSERT 두 종류·결제 SELECT 합계가 2,415→410회·30,000→250회로 줄었다. 최초 DB 저장은 169.184→165.601ms·1,111.814→1,020.088ms였다. 최초 전체 갱신은 현재 1.12% 느려졌고 합성은 5.00% 빨라졌다. 합성 1건 추가 저장은 10.282→10.956ms로 느려졌으며 단일 AB 관측이므로 안정적인 속도 개선으로 일반화하지 않는다. `storage.metadata`로 이동한 이름·설정 비용을 별도 계측한다.
- **검증**: 새 이름·설정 경계 7개, transaction 직접 검증의 독립 집계 160건·원자성·rollback/retry·취소·삭제 보존·재연결·scanner fallback을 통과했다. A/B 요청·토큰·최종 이름·비용·평균·NULL·raw/rollup·원본 상태와 사본 복원이 일치했다. 타입·린트·diff 통과, 전체 427개 중 421개 테스트 통과이며 남은 6개는 A에서도 동일하게 재현했다. [1회 측정·SQL 호출 수·한계](benchmarks/2026-11-10/MetadataBatchAB-2026-11-10.md).

### 미사용 집계 지표와 진단 전용 재집계를 제거한다

- **의사결정**: 사용자는 확인된 미사용 속성 정리 후 이 노트북의 현재 데이터·10,000요청으로 A/B 각 1회를 요청했다. 공통 `unknown_time_turns`·`stale_turns`·`last_successful_update`를 저장·raw/rollup 반환·타입에서 제거하고 모델 daily의 `min_started_at_ms`도 제거한다. 에이전트는 세션 시작을 요청 daily에서 유지하고, 삭제 지표만 반영하던 진단 전용 재집계 호출도 없앴다. 스키마 v19·형식 v2에서 파생캐시만 폐기·lazy rebuild한다.
- **근거**: 공통 3개는 반환 뒤 제품에서 소비하지 않고 모델별 세션 시작도 요청 daily를 참조한다. 원본 facts·manifest·모델·도구·비용·이름·ID, c/r 표본·캐시 NULL·시간 품질·미상 날짜와 PK·인덱스·거래 경계는 유지한다. 집계의 시간·공간 차수는 같고 행 폭·계산의 상수 비용을 줄이며, 기존 DB에는 첫 조회 재구축 비용이 생긴다.
- **결과**: 상태는 요청 41→38개·모델 41→37개다. 현재 798요청·합성 10,000요청의 최초 저장은 176.908→164.916ms·1,147.848→1,084.035ms, rollup은 34.225→34.043ms·269.730→268.088ms였다. 전체 갱신 차이는 0.50%·3.09%였으나 단일 AB 표본이므로 안정적인 개선으로 판정하지 않는다. 단일 추가 저장은 두 규모 모두 느려졌다. 두 daily 본체는 112→104KiB·72→60KiB로 줄었으며 전환 후 첫 조회·재구축은 63.567ms·295.846ms였다.
- **검증**: 양쪽 고정 입력의 요청·토큰·잔존 평균·raw/rollup·독립 JS 집계·FK/integrity·추가량·원본 사본 복원이 일치했다. 실제 구 v18 DB 사본 전환과 v13/v17/v18 회귀, 미상 날짜·NULL·세션 시작·진단 보존·재오픈을 검증했다. 타입 검사·린트·diff 통과, 전체 테스트 420개 중 414개 통과이며 남은 6개는 정리 전 코드에서도 동일하게 재현했다. [1회 측정·한계·원시 자료](benchmarks/2026-11-10/RollupTrimAB-2026-11-10.md).

### 변경 세션 rollup을 저장 묶음 마지막에 한 번 수행한다

- **의사결정**: 사용자는 성분마다 반복하는 rollup을 최종 저장 결과에서 한 번 수행하고 개선량을 비교하도록 지시했다. 에이전트는 기존 transaction 안에서 facts·manifest·삭제 보존·이름 정리를 마친 뒤 `(provider, session_id)`를 중복 제거해 요청·모델 daily를 각각 한 번 DELETE·INSERT SELECT하는 방식을 선택했다. 전체 스캔까지 갱신을 지연하지 않고 기존 단일 세션·특수 성분·실패 재시도 경로와 COMMIT 경계를 유지한다.
- **근거**: 각 세션의 메타데이터 확인·SQL 호출·집계 준비를 공유할 수 있다. 고정 SQL에 JSON tuple 목록을 바인딩하고 daily PK 및 기존 요청 세션 UNIQUE→INTEGER PK로 원본 범위를 제한한다. 새 인덱스·TEMP 키 표·스키마 없이 평균의 합계·분모와 모델·캐시 NULL을 보존한다.
- **결과**: 현재 1,346요청·합성 10,000요청의 rollup은 70.517→26.265ms·138.276→101.313ms, DB 저장은 177.331→126.711ms·434.669→395.726ms로 줄었다. 전체 최초 갱신은 2.01%·3.95% 감소했다. 각 daily SQL 호출은 372→25회·100→10회였고 COMMIT은 26회·10회로 같았다. 단일 1건 추가의 일관된 개선은 확인하지 못했고 무변경 전체 갱신은 약 1.99ms·0.17ms 느려졌다. 중간에만 미지원 시각이 생긴 경우 최종 facts가 유효하면 B는 최종 캐시를 유지하며, 공개 조회 결과는 A의 재구축 뒤와 같다.
- **검증**: 준비 3쌍·교대 10쌍에서 A/B 요청·토큰·그룹별 평균·manifest·raw/rollup·독립 JS facts 집계·FK/integrity와 사본 복원이 일치했다. 반복 snapshot·삭제/이동·보존·키 충돌·캐시·시간대·rollup 실패 원자성과 실제 scanner fallback, 기존 묶음 경계·취소 검증을 통과했다. 실제 DB 사본의 PK 탐색 계획과 타입 검사·린트·diff를 확인했다. 강제 종료·전원 손실·경쟁 writer는 검증하지 않았다. [상세 결과·원시 자료](benchmarks/2026-11-10/RollupBatchAB-2026-11-10.md).

### 정상 성분을 제한된 트랜잭션으로 묶어 반복 COMMIT을 줄인다

- **의사결정**: 사용자는 서브에이전트와 현재 데이터·10,000건의 구간별 상위 두 병목 측정 및 최대 구간 최적화·A/B를 요청했다. 측정 결과 현재 데이터의 COMMIT을 대상으로 정했고, 에이전트는 정상 성분 최대 16개·합계 1,000요청의 순차 apply와 한 번의 COMMIT을 선택했다. 실패 시 전체 rollback 후 개별 재시도하며 성공 COMMIT 뒤에만 원본 settled와 affected를 확정한다. 단일 성분과 한도를 넘는 성분, deferred·오류·orphan·삭제·재연결은 기존 경로로 처리한다.
- **근거**: 현재 최초 저장에서 COMMIT 254.736ms가 최대 구간이었다. 동기화 설정을 유지하며 반복 확정 비용을 분담하면 계산 의미와 기존 SQL을 보존할 수 있다. 한 거래의 잠금 유지와 취소 확인 간격이 길어지는 비용이 있어 성분·요청 수를 제한했다.
- **결과**: 현재 1,341요청의 최초 성분 저장은 409.971→173.802ms, 10,000요청은 510.667→433.178ms였다. 성분 저장 COMMIT은 각각 387→26회·100→10회, 전체 갱신은 6.91%·9.98% 감소했다. 단일 1건 추가는 경로·거래 수가 같아 개선으로 판정하지 않았다. 정상 묶음 전체가 미완료·강제 종료의 확정 경계가 되고, 거래별 최대 유지 시간 중앙값은 5.894→12.608ms·10.303→48.428ms로 늘었다. 10,000요청의 요청 비교·저장과 rollup 재집계는 후속 최적화 대상으로 남긴다.
- **검증**: 준비 3쌍·교대 10쌍에서 A/B 요청·토큰·평균·manifest·raw/rollup·독립 JS facts 집계·FK/integrity가 일치했다. 별도 독립 지표 160건, reader 원자성, 전체 rollback·개별 재시도, 경계·취소·삭제 보존·재연결과 실제 scanner의 중간 저장 실패를 검증했다. 타입 검사·린트·diff 검토를 통과했다. 강제 종료·전원 손실·경쟁 writer 지연은 검증하지 않았다.
