# v0.3.0 알고리즘 개선: v0.2.0 대비

작성일: 2026-11-12, Asia/Seoul.

동일 결과를 확인한 합성 10,000요청의 기존 비교에서 **최초 수집과 첫 조회는 6.447→2.005초(68.9% 단축)**, **전체 재파싱과 첫 조회는 8.794→1.063초(87.9% 단축)**였다. 최초 수집의 최종 요청 집계는 88.1%, DB 저장은 73.5% 줄었다. TEMP 이벤트를 SQL로 다시 집계하던 구조를 원본별 메모리 집계·변경 요청 저장·제한된 묶음 처리로 바꾼 결과다.

이 수치는 **v0.2.0과 2026-11-10 dev의 비교**다. v0.3.0으로 정리하는 현재 HEAD 전체를 새로 측정한 값은 아니다. 실제 로그는 자식 사용량의 부모 합산으로 결과가 달라 동등한 작업의 개선율을 확정하지 못했고, 실제 Codex 1건 추가는 오히려 23.0% 느려졌다. 이 문서는 기존 측정과 현재 코드 검토를 연결하며 새 테스트·벤치마크는 실행하지 않았다.

## 2. 전체 작업은 얼마나 줄었나

각 값은 **v0.2.0 알고리즘 → 11월 10일 dev**, 단위 ms다. 이 표의 모든 시나리오는 갱신 후 첫 조회까지 포함한다.

| 작업 | 합성 10,000요청 | 시간 감소율 | 합성 100요청 | 시간 감소율 |
| --- | ---: | ---: | ---: | ---: |
| 최초 수집 | 6,446.801 → 2,005.323 | 68.9% · 약 3.21배 | 106.536 → 78.349 | 26.5% |
| 변경 없는 갱신 | 96.714 → 86.498 | 10.6% | 13.624 → 6.807 | 50.0% |
| 같은 내용 전체 재파싱 | 8,793.789 → 1,063.349 | 87.9% · 약 8.27배 | 74.745 → 21.372 | 71.4% |
| Codex 요청 1건 추가 | 115.528 → 71.574 | 38.0% | 42.480 → 15.899 | 62.6% |
| Claude 요청 1건 추가 | 120.738 → 71.892 | 40.5% | 44.238 → 15.497 | 65.0% |
| 기존 Codex 응답 연장 | 117.543 → 70.789 | 39.8% | 43.879 → 15.844 | 63.9% |

10,000요청은 200파일·200세션·10프로젝트·6,340,000토큰, 100요청은 2파일·2세션·18,400토큰이다. 제공자별 절반, 세션당 50요청으로 구성했다. A/B의 요청 수·토큰·공통 집계 결과가 일치했고, 6개 작업 모두 B가 10/10쌍 빨랐다.

공통 결과 비교는 물리 ID·갱신 시각을 정규화하고, dev에서 의도적으로 제거한 `unknown_time_turns`·`stale_turns`·`last_successful_update` 세 진단 속성을 제외했다. 독립 JS 기대값은 저장된 정규화 facts를 기준으로 하며 JSONL 파서 전체의 독립 검증은 아니다.

변경 없음에서 본문을 읽지 않는 manifest 재사용은 v0.2.0에도 있었다. 이번 릴리스가 처음 추가한 기능으로 계산하지 않는다. 마찬가지로 일별 rollup·기간/프로젝트 인덱스·Zstd 로그 지원·삭제 원본 통계 보존도 이미 기준 버전에 있다.

## 3. 알고리즘 구간별 직접 비교

**합성 10,000요청**, 단위 ms와 시간 감소율이다. 원본 준비에는 파일 읽기·파싱·원본별 집계와 대기가 포함되며, 최종 집계는 원본 사이의 winner·요청 결과를 확정하는 별도 단계다.

| 구간 | 최초 수집 A → B | 전체 재파싱 A → B | Codex 1건 추가 A → B |
| --- | ---: | ---: | ---: |
| 파일 탐색·이름 준비 | 63.799 → 39.670 · 37.8% | 54.366 → 40.950 · 24.7% | 53.903 → 38.535 · 28.5% |
| 원본 읽기·파싱 준비 | 767.829 → 492.992 · 35.8% | 802.631 → 471.044 · 41.3% | 3.571 → 2.830 · 20.8% |
| 최종 요청 집계 | 1,435.762 → 171.542 · 88.1% | 1,985.845 → 155.395 · 92.2% | 5.691 → 0.837 · 85.3% |
| DB 저장·COMMIT | 2,748.987 → 727.777 · 73.5% | 5,125.481 → 360.477 · 93.0% | 23.718 → 11.214 · 52.7% |
| 첫 월별 조회 | 592.149 → 549.931 · 7.1% | 16.899 → 15.933 · 5.7% | 14.332 → 13.705 · 4.4% |

최초 수집에서 절대 시간이 크게 줄어든 구간은 DB 저장 약 2,021ms와 최종 집계 약 1,264ms다. **최종 집계와 저장의 반복 작업 제거가 핵심**이며, 조회가 모든 경우에 수십 배 빨라진 결과는 아니다. 합성 입력은 작은 파일들로 구성돼 Worker 풀 시작 조건을 충족하지 않았으므로, 이 표의 개선을 병렬화 단독 효과로 설명할 수 없다.

구간별 중앙값을 합해 전체 중앙값을 만들지 않는다. 계측 경계가 완전히 같지도 않다. A의 원본 준비는 reader·adapter·TEMP 적재이고 B는 변경 원본·관련 원본 준비 결과 소비다. COMMIT과 rollup은 DB 저장 내부에 중첩된다. 첫 수집의 조회는 daily 구축을 포함하지만 재파싱·추가는 이미 활성화된 daily를 유지한다.

소규모에서는 손익이 달랐다. 100요청 최초 수집의 원본 준비는 **11.407→15.596ms로 36.7% 증가**, 첫 월별 조회도 **31.904→32.932ms로 3.2% 증가**했다. 같은 내용 재파싱에서 B의 rollup 유지 시간이 0으로 기록된 것은 변경 없는 facts의 재쓰기를 생략한 경우이며, 집계 기능을 제거했다는 뜻이 아니다.

## 4. 현재 코드에서 구간별로 달라진 알고리즘

### 4.1 파일 탐색과 관련 원본 선택

v0.2.0은 `scanner.ts`와 `staging.ts`의 TEMP `scan_files`·`affected`·`links`를 중심으로 변경·관련 파일과 연결 성분을 반복 조회했다. 현재는 manifest를 한 번 읽고 경로·세션·원본 식별자별 Map/Set 색인을 구성한다. 관련 파일은 중복 없는 파일 ID 최소 힙 큐에 넣어 기존 논리 순서를 유지하면서 처리한다. 성분별 파일·요청도 미리 만든 멤버 색인에서 가져온다.

전체 디렉터리 탐색과 `stat`은 여전히 필요하다. 부모 thread를 manifest에서 찾지 못하면 새 미해결 참조마다 경로 후보를 검색하는 fallback도 남는다. 전체 갱신이 변경 파일 수에만 비례하는 watcher나 append checkpoint 구조로 바뀐 것은 아니다.

현재 코드: [탐색](../src/summary/scanner/refresh/discovery.ts), [상태·색인](../src/summary/scanner/refresh/state.ts), [작업 큐·성분 멤버](../src/summary/scanner/worklist.ts), [관련 원본 확장](../src/summary/scanner/refresh/relations.ts).

### 4.2 JSONL 읽기와 파일 준비

양쪽 모두 64KiB 이하 청크로 읽고 JSON을 파싱한다. v0.2.0의 완성 행별 UTF-8 디코딩을 현재는 청크 안의 완성된 줄 구간 디코딩·분할로 묶는다. 청크 경계의 줄·이미지 본문 제거·미완성 마지막 행·Zstd 해제·오류 위치 처리는 별도 행 상태로 유지한다. JSON 선택 파서는 채택하지 않았으며 일반 행도 `JSON.parse`로 검증한다.

파일 하나를 준비하는 같은 읽기에서 SHA-256, identity, usage winner, 요청 상태·최신 check·도구 중복과 부모 생성 근거를 모은다. 후속 metadata 이벤트 배열 재생·합친 이벤트 정렬·반복 정규화를 줄였다. 변경된 파일은 관측한 크기까지 다시 읽으므로 새 바이트만 읽는 구조는 아니다. 필요한 관련 파일도 다시 읽을 수 있고, 이동 prefix 검증에는 추가 읽기가 생긴다.

큰 원본 묶음은 최대 4개의 Worker, 최대 8파일 선행 준비를 사용한다. 풀을 새로 시작할 때 후보가 단일 파일이거나 크기 합계가 1MiB 미만이면 순차 경로를 사용한다. 완료 순서로 DB에 넣지 않고 원래 논리 순서로 결과를 소비한다. Worker는 DB에 접근하지 않으며 갱신 종료 시 정리한다.

현재 코드: [JSONL reader](../src/summary/jsonl/index.ts), [행 상태](../src/summary/jsonl/line.ts), [원본 읽기](../src/summary/scanner/sourceReader.ts), [파일 준비](../src/summary/scanner/sourcePreparation.ts), [Worker 풀](../src/summary/scanner/sourcePool.ts).

### 4.3 중복 응답 선택과 최종 요청 집계

v0.2.0은 파싱 이벤트를 TEMP 표에 적재하고, 연결 성분마다 `component_events`·`winners`·`capability_winners`·`prepared_turns`와 인덱스를 만들었다. 중복 응답은 SQL의 `row_number()`와 정렬로 전체 토큰 벡터의 winner를 선택했다.

현재는 읽는 동안 원본별 Map에 그룹 winner를 남긴다. 같은 그룹의 후보는 input+output 점수와 동점 순서로 비교하고, 교체할 때 기존 숫자 기여를 차감한 뒤 새 기여를 가산한다. 최종 관계가 확정되면 남은 winner와 요청 상태를 부모 요청에 병합한다. 패자의 모든 후보를 후단 집계를 위해 보관하거나 SQL TEMP 이벤트 전체로 다시 만들지 않는다.

Map 조회·갱신의 평균 비용은 작아지지만 최종 행 생성·정렬·DB 비교는 남는다. winner·요청 상태·관계 근거를 메모리에 두는 만큼, 메모리 사용량도 입력의 고유 그룹 수에 따라 늘어난다. 8파일 선행 제한은 전체 집계 메모리 상한이 아니며, 사용량 DTO를 다음 갱신까지 보관하는 영속 캐시도 없다.

현재 코드: [원본별 누적](../src/summary/aggregation/sourceWinners.ts), [winner 선택·차분](../src/summary/aggregation/winners.ts), [최종 집계](../src/summary/aggregation/memoryAggregate.ts), [요청 상태·결과 생성](../src/summary/aggregation/turns.ts).

### 4.4 부모 계보와 서브에이전트 귀속

v0.2.0의 부모 세션 전파에는 128회 반복 상한이 있었고, root가 없는 Codex 자식은 독립 세션으로 집계됐다. 현재는 최상위 root 해소 결과를 재사용해 직접 그룹화하고 누락·충돌·순환을 구분한다. 부모 생성 호출의 thread/agent path 근거로 자식·손자의 사용량을 부모 요청에 합산한다. 근거가 불명확한 비어 있지 않은 자식은 관련 성분의 저장을 보류하고 이전 정상 결과를 보존한다.

자식의 시간·완료·중단 상태는 부모 상태를 덮어쓰지 않는다. 부모 요청의 중단 제외 규칙은 그 자식 기여에도 적용된다. 따라서 독립 자식 요청 수가 줄고 평균의 분모·세션 구성이 달라질 수 있다. 이 부분은 처리 속도뿐 아니라 **집계 의미의 변경**이며, 이전 버전과 실제 요청 수를 무조건 같게 맞출 수 없다.

현재 코드: [root 해소·직접 그룹화](../src/summary/aggregation/parentGroups.ts), [부모 요청 연결](../src/summary/scanner/refresh/relations.ts), [부모 요청 집계](../src/summary/aggregation/memoryAggregate.ts).

### 4.5 이동한 원본 연결

v0.2.0은 비Windows의 dev/inode와 경로 관측을 사용했지만, 이동 후 이전 manifest가 남으면 원본 누락 보존 때문에 추가 사용량 반영이 멈출 수 있었다. 현재는 원본 identity와 정상 반영한 전체 byte의 SHA-256을 저장한다. 이전 경로가 없고 정상 새 후보가 하나이며 기존 내용 전체가 prefix로 확인될 때 새 경로로 연결하고 이전 기록을 같은 저장 transaction에서 정리한다.

모호한 후보·내용이 다른 파일·이미 사라져 검증 정보가 없는 과거 행은 보존한다. 이 검증은 정확한 재연결을 위한 추가 작업이며, 속도가 개선됐다는 직접 수치는 없다.

현재 코드: [내용·prefix 검증](../src/summary/scanner/sourceFingerprint.ts), [연결 후보 선택](../src/summary/scanner/refresh/relations.ts).

### 4.6 요청 저장과 이름·결제 설정

v0.2.0은 영향 세션의 기존 요청을 지우고 전체 snapshot을 다시 INSERT했다. 현재는 요청 키로 기존 facts·모델·도구·비용을 비교해 변경분만 갱신하고 사라진 요청을 정리한다. 새 요청에는 존재하지 않는 모델·도구 자식 DELETE를 실행하지 않는다. 같은 내용의 전체 재파싱에서도 실제 쓰기와 rollup을 생략할 수 있다. 다만 비교를 위해 기존 snapshot의 모든 요청을 살펴볼 수 있으므로 전체 처리 시간이 변경 요청 수에만 비례하지는 않는다.

프로젝트·세션 이름과 사용자 결제 설정은 정상 저장 묶음의 고유 키별로 처리한다. 요청 N건, 고유 프로젝트 P개·세션 S개라면 이 세 종류의 SQL 호출이 요청별 O(N)에서 O(P+S)로 줄어든다. 입력 순회 O(N)은 남고, 같은 키가 다음 묶음에 있으면 그 묶음에서 다시 처리한다. 빈 이름 보존·사용자 결제 override와 제목만 변경된 세션의 별도 갱신도 유지한다.

현재 코드: [요청 비교·저장·metadata](../src/summary/db/memoryStore/index.ts), [값 변환·비교](../src/summary/db/memoryStore/values.ts), [세션 비용 변경](../src/summary/db/billing.ts).

### 4.7 저장 transaction과 일별 rollup

v0.2.0의 성분별 저장을 현재는 정상 독립 성분 최대 16개·합계 1,000요청의 동기 transaction으로 묶는다. 큰 단일 성분·삭제·오류·재연결 등 특수 처리는 개별 경로를 사용한다. 묶음 실패 시 전체 rollback 뒤 성분별 재시도한다. 전체 스캔을 한 transaction으로 묶지 않으며 writer 잠금 안에서 파일 읽기를 기다리지 않는다.

같은 transaction에서 최종 facts 저장을 마친 뒤 실제 변경 세션을 중복 제거해 요청·모델 daily를 묶음당 각각 한 번 DELETE·INSERT SELECT한다. 변경 세션이 없으면 생략하고 하나면 기존 단일 경로를 사용한다. 변경 세션 전체의 facts를 재집계하므로, 바뀐 날짜 버킷만 갱신하는 구현은 아직 아니다.

평균은 합계와 표본 수로 병합하고 NULL·미상 시각·시간대 처리와 기존 PK·인덱스·WAL/FULL 설정을 유지한다. 미사용 집계 지표 제거 후 스키마는 v19·집계 형식은 v2다. 기존 DB의 파생 집계는 필요 시 첫 조회에서 재구축하며, 이 전환 비용은 위 태그 비교에서 측정하지 않았다.

현재 코드: [성분 저장 조율](../src/summary/scanner/refresh/persistence.ts), [묶음 transaction](../src/summary/db/memoryStore/index.ts), [일별 집계 유지](../src/summary/db/rollups.ts), [집계 상태 식](../src/summary/db/rollup-state.ts), [변경 세션 소스 SQL](../src/summary/db/queries/rollup/source.ts).

### 4.8 표·도표·전체 개수 조회

v0.2.0에도 rollup 조회는 있었지만 행·전체 개수·도표를 따로 요청하는 경로가 있었다. 현재는 같은 읽기 snapshot의 페이지 결과를 표와 도표가 공유한다. 결과가 있는 그룹·이름 페이지는 window 지표로 전체 개수를, 도구 페이지는 전체 사용 횟수·최댓값도 함께 읽는다. 범위를 벗어난 후속 빈 페이지에는 별도 count fallback이 남고, 요청 cursor 페이지의 별도 전체 개수 조회도 유지한다.

일반 화면의 coverage는 진단 목록 없이 개수만 읽는다. 비용 포함 조회는 여전히 raw facts를 사용하고, 모든 필터·정렬이 인덱스만으로 해결되거나 모든 조회가 빨라진 것은 아니다.

현재 코드: [통합 페이지·fallback](../src/summary/db/reader.ts), [rollup 페이지 SQL](../src/summary/db/queries/rollup/usage.ts), [도구 window 지표](../src/summary/db/queries/raw/capabilities.ts), [페이지 도표 변환](../src/summary/db/chart.ts).

## 6. 실제 로그의 개선율을 확정하지 않은 이유

태그 직접 비교의 실제 입력은 같은 382파일·556,386,161byte인데도 A가 1,075요청·1,507,810,476토큰, B가 809요청·1,512,226,897토큰을 만들었다. 파싱 실패 파일은 양쪽 모두 0개였다. A/B의 요청·모델·도구·비용·세션·진단과 20종 집계가 달라 동등성 검증에 실패했다.

| 실제 작업·첫 조회 포함 | A → B | 해석 |
| --- | ---: | --- |
| 최초 수집 | 14,242.310→3,592.369ms | 시간은 74.8% 줄었으나 결과가 달라 순수 개선율로 채택하지 않는다. |
| 전체 재파싱 | 14,302.943→3,361.515ms | 시간은 76.5% 줄었으나 같은 이유로 참고 관측에 한정한다. |
| Codex 1건 추가 | 258.192→317.649ms | 23.0% 느려졌다. 실제 추가 갱신이 항상 빨라졌다고 말할 수 없다. |

별도 진단에서는 A에만 있는 266요청이 모두 standalone subagent였고, 공통 부모 요청 26개의 토큰이 증가했다. 이는 부모 합산 변경과 일치하지만 증가분 전체의 정확성까지 독립 JSONL 파서로 증명한 것은 아니다. 버전 내부 facts의 집계 일치와 버전 간 결과 동등성은 구분한다.

실제 Codex 추가에서는 A가 1파일·3,822,842byte, B가 9파일·7,702,884byte를 읽었다. 원본 준비는 72.897→199.790ms로 늘어난 반면 최종 집계는 10.345→6.352ms, DB 저장은 14.747→7.048ms로 줄었다. 부모 관계에 필요한 관련 원본을 더 읽는 비용이 후단 절감보다 컸다. **추가 요청의 남은 병목은 변경·관련 원본 준비 범위**다.

## 7. 남은 비용과 검증 한계

- 전체 파일 탐색·stat과 변경·관련 원본의 재읽기는 남는다. 무변경 본문 읽기 0과 파일시스템 작업 0은 다르다.
- 원본별 winner·요청 상태·관계 색인은 갱신 동안 메모리를 사용한다. 태그 대비 peak RSS나 메모리 감소율은 측정하지 않았다.
- 변경분 저장도 기존 요청 비교를 수행하고 변경 세션의 rollup은 그 세션 전체를 합산한다. 모든 작업이 변경량에만 비례하지 않는다.
- 저장 배칭은 COMMIT 횟수를 줄이는 대신 한 거래의 writer 잠금과 취소 확인 간격을 늘릴 수 있다. 경쟁 writer 지연·강제 종료·전원 손실은 이 문서의 근거 실험으로 확인하지 않았다.
- v0.2.0→현재 HEAD의 기존 DB 전환 시간·누적 디스크 쓰기·UI/IPC·실계정 quota 속도는 미측정이다. 카드·아이콘·언어 기본값·quota 창 제한 수정에는 성능 개선율을 붙이지 않는다.
- 선택 파싱·winner 비교 재사용처럼 성능 회귀로 폐기한 후보는 현재 개선에 포함하지 않는다. [철회 기록](benchmarks/2026-11-10/SelectiveWinnerAB-2026-11-10.md)을 참조한다.
- 태그 직접 비교의 실행기·원시 JSON·소스 ZIP은 당시 사용자 요청으로 정리돼 Markdown 결과만 남아 있다. 후속 11월 11일 측정은 [원시 표본](benchmarks/2026-11-11/AlgorithmMinimizeAB-2026-11-11.json)과 [소스 보관 명세](benchmarks/2026-11-11/AlgorithmMinimizeSources-2026-11-11.json)가 남아 있다.

이번 작업에서는 태그·현재 코드·기존 보고서의 기준과 수치 및 문서 링크를 검토했다. 제품 코드·테스트 코드는 변경하지 않았으며 자동 테스트·새 성능 측정·실계정 호출은 수행하지 않았다.
