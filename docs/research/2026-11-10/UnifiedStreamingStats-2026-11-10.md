# 원본 순회 중 통계 누적 통합

- 기준: 2026-11-10, 제품 코드 `a62f965`와 같은 입력 사본.
- 승인 범위: 사용자가 반복 순회를 하나의 통계 누적 흐름으로 통합하고 불필요한 방어·예외·중간 상태를 제거한 뒤 기존 데이터와 정합성 검사를 요청했다. 해당 범위는 이미 승인됐다.
- 기존 실패 기록의 미커밋 문서 보완은 보존한다.

## 변경 전후와 비용

기존은 파싱 중 사용량 winner를 고르면서 모든 turn/check/capability 이벤트와 모든 usage root 위치를 별도로 보관했다. 최종 집계가 전체 root를 다시 관측하고 metadata+winner를 정렬해 재생했다. 현재는 읽는 동안 turn 상태·최신 check·중복 capability·root 최소 위치를 키별로 접고 남은 상태와 winner만 최종 귀속에 병합한다. 최종 숫자 집계는 winner 교체와 동시에 차감·가산하며 전체 winner를 마지막에 재합산하지 않는다.

입력 이벤트 E, 원본별 고유 요청 상태 U, winner W에 대해 파싱 중 상태 누적은 평균 Map 탐색을 가정해 O(E)다. 최종 재생의 기존 metadata M과 winner를 합친 O((M+W)log(M+W)) 정렬은 제거했다. 이후 병합은 O(U+W+필요한 도구/check·legacy 위치)다. 늦게 확정되는 fork의 legacy 접두사와 요청 귀속 근거, 출력 정렬 및 최종 요청별 SQL 쓰기는 남는다. 전체 작업을 파일 I/O·파싱·DB 반영까지 단 한 번의 루프라고 표현하지 않는다.

metadata 보관은 O(M) 이벤트 객체에서 O(U+고유 check/도구 키+필요한 위치) 상태로 바뀐다. 4,001이벤트 경계 입력은 요청 root 1개·turn 상태 1개·최신 check 1개·winner 1개로 접혔다. 다만 고유 키가 계속 늘거나 legacy 접두사·복사 도구 위치가 많이 필요하면 최악의 선형 보조 공간은 남는다. 세션 진단 색인은 별도의 flag 참조·정렬 배열을 유지하는 비용이 있다. 실제 peak RSS·heap 절감량은 측정하지 않았다.

원본 하나가 실패했을 때 정상 DB를 부분 결과로 덮어쓰지 않도록 읽기 transaction 밖 준비와 최종 facts·rollup transaction 계약은 유지한다. 소스 snapshot의 내부 구조가 바뀌지만 영속 DB 스키마와 공개 집계 의미는 유지한다.

## 실제 적용과 검증

### 통합한 흐름

```text
원본 한 번 읽기·native JSON.parse
  → 이벤트 문자열 한 번 정규화
  → 같은 순회에서 요청 시작·종료·첫 제목·최소 위치·최신 check·도구 중복·usage winner 누적
  → 파일 간 부모/fork/request 귀속 확정
  → 남은 요청 상태와 winner 한 번 병합하며 숫자 기여 차감·가산
  → 최종 요청 행 생성·기존 transaction에서 SQL 반영
```

[SourceWinners](../../../src/summary/aggregation/sourceWinners.ts)는 raw metadata 배열을 보관하지 않는다. 수천 개 turn/check가 같은 요청에 속하면 turn 상태와 최신 check 하나씩으로 접는다. 그룹 점수도 여기서 계산해 [최종 집계](../../../src/summary/aggregation/memoryAggregate.ts)에 전달한다. `events()`의 합친 배열·정렬과 usage마다 `observeRoot()`를 재실행하는 경로, 제품의 raw 이벤트 재생 `add()`를 제거했다. 이전 이벤트 순서 집계는 회귀 비교용 [테스트 fixture](../../../tests/fixtures/event-order-aggregate.ts)에만 있다.

[SourceEvidence](../../../src/summary/aggregation/sourceEvidence.ts)는 이미 정규화된 이벤트를 관측하고 다시 정규화하지 않는다. [요청 결과 생성](../../../src/summary/aggregation/turns.ts)은 세션의 main·최종 이름·정렬된 진단을 한 번 색인하고 wildcard와 해당 요청의 flag만 병합한다. 요청마다 세션 파일 전체를 재검색하지 않는다. 파일별 outcome의 마지막 이벤트와 과거 최대 시각도 상태 병합 중 갱신해 종료 시 전역 outcome 재생을 없앴다.

### 제거하지 않은 의미 있는 처리

- mixed current/legacy 선택, fork 복사 접두사 제외, 늦은 Claude request 보정은 실제 중복 집계 의미가 있어 유지했다. legacy 위치와 복사된 도구 호출 이후의 유효 위치는 경계를 확인하기 위한 최소 근거다.
- 낮은 점수의 후보에만 있는 root·진단을 보존한다. 숫자 패자라는 이유로 요청·오류 근거까지 버리지 않는다.
- malformed JSON·부분 마지막 줄·취소·파일 교체와 실패한 연결 성분의 정상 facts 보존, facts/rollup 같은 transaction 계약은 유지했다.
- 마지막 SQL의 기존 행 비교는 변경 없는 DB 쓰기를 피하는 처리다. 원본 winner를 다시 중복 제거하는 단계가 아니므로 삭제하지 않았다. 출력 행 생성과 SQL 반영 순회도 필요하다.

- 현재 고정 사본은 384파일·561,208,909byte, 823요청·1,538,591,540토큰·190세션·14프로젝트다. Claude 48요청·Codex 775요청이며 A/B의 최초 facts와 평균 결과가 일치했다.
- 같은 기존 Codex 세션에 +1요청/+130토큰을 추가한 뒤 양쪽 모두 824요청·1,538,591,670토큰이다. 기존 행 보존·원본 사본 복원·무변경 본문 읽기 0byte를 확인했다.
- 합성 10,000요청·6,340,000토큰·100세션/100파일에서도 최초·추가·무변경이 일치했다. 추가 후 10,001요청·6,340,130토큰이다.
- 비교 범위는 요청 facts·모델·도구·비용·프로젝트·세션 이름·manifest/진단, raw/rollup 10차원, 제공자/모델의 일·월·세션·프로젝트 평균과 그룹 개수다. 정규화 facts를 SQL과 별도 JS reducer로 계산해 NULL·완료/빈 요청 표본 포함·제외를 대조하고 FK/integrity도 통과했다. 원본 로그·설치 DB는 변경하지 않았다.
- 변경 전 빌드와 최종 빌드의 이벤트 입력 96 seed ×4파일 ×154이벤트=59,136개에서 전체 요청 결과·orphan이 일치했다. 별도로 기존 독립 SQL oracle 32 seed와 새 경계 테스트 5개가 통과했다. 입력 객체 보존·최초 제목·시각 역행·부모로 합쳐지는 다중 root·wildcard 진단 순서·BigInt·Worker snapshot을 포함한다.
- `npm run check`: 타입·린트 통과, 전체 432개 중 426개 통과. 남은 계보·취소 관련 6개 실패는 변경 전 A의 관련 59개 검사에서도 동일하게 재현했다. 실패를 통과시키기 위한 테스트 삭제나 기대값 완화는 하지 않았다.

최종 원시 결과·입력 및 소스/빌드 hash는 [정합성 JSON](../../benchmarks/2026-11-10/UnifiedStreamStatsValidationFinal-2026-11-10.json), 추가 검증 요약은 [Checks JSON](../../benchmarks/2026-11-10/UnifiedStreamStatsChecks-2026-11-10.json)에 있다. 앞선 실패 후보의 원인 분석은 별도 기록으로 보존한다.

### 현재 데이터·10,000요청의 시간 변화

최종 정합성 실행에 기록된 **A→B 1회 관측값**이다. A는 통합 전, B는 현재 통합 구현이며 시간 단위는 ms다. 감소율은 `(A−B)/A×100`으로 계산했다. 데이터 준비·복사·DB 열기·검증·조회·사본 복원은 갱신 시간에서 제외한다.

| 측정 구간 | 현재 데이터 823요청 | 합성 10,000요청 |
| --- | ---: | ---: |
| 최초 전체 갱신 | 4079.132 → 3712.003 (**9.00% 감소**) | 1754.861 → 1605.034 (**8.54% 감소**) |
| 최초 원본 준비 | 3591.042 → 3339.589 (7.00% 감소) | 420.646 → 375.275 (10.79% 감소) |
| 최초 최종 집계 | 185.865 → 88.257 (**52.52% 감소**) | 237.561 → 124.491 (**47.60% 감소**) |
| 최초 DB 저장 | 166.885 → 155.325 (6.93% 감소) | 1035.397 → 1059.116 (2.29% 증가) |
| 실제 요청 1건 추가·전체 갱신 | 335.912 → 325.010 (**3.25% 감소**) | 41.971 → 39.465 (**5.97% 감소**) |
| 추가 시 최종 집계 | 6.706 → 5.323 (20.61% 감소) | 1.859 → 0.760 (59.10% 감소) |
| 추가 시 DB 저장 | 6.632 → 7.144 (7.72% 증가) | 9.954 → 10.108 (1.55% 증가) |
| 변경 없는 전체 갱신 | 96.038 → 103.324 (7.59% 증가) | 40.924 → 24.313 (40.59% 감소) |

최초 전체 갱신에서 줄어든 관측 시간은 현재 약 **367.128ms**, 합성 10,000요청 약 **149.826ms**다. 직접 통합한 최종 집계 구간은 각각 약 **97.609ms·113.071ms** 줄었다. 원본 준비에는 읽기·파싱·원본 상태 누적·Worker 대기가 함께 들어 있으므로 표의 감소율을 순수 JSON 파싱 속도 개선으로 해석하지 않는다. 상위·하위 타이머를 중복 합산하지 않는다.

현재 데이터는 561,208,909byte, 합성은 5,637,210byte여서 요청 건수와 파싱 작업량은 비례하지 않는다. SQL·스키마·COMMIT 정책은 이번 변경 대상이 아니며, DB 저장의 증감은 집계 통합의 직접 SQL 개선으로 판정하지 않는다. 변경 없는 갱신은 양쪽 모두 본문 읽기와 facts 저장을 생략하므로 그 시간 차이도 이번 누적 알고리즘의 효과로 확정하지 않는다.

준비 반복 없이 A가 먼저인 최종 한 쌍이며 OS 캐시·GC·열 상태를 제어하지 않았다. 표는 현재·10,000요청 모두 결과가 같은 실행에서 관측한 차이이고, 안정적인 개선율·변동 폭은 아직 확인하지 않았다. 순수 CPU·peak 메모리와 별도의 독립 실로그 JSONL 파서 oracle도 미측정이다. 이번 문서 보완을 위해 추가 성능 실행은 하지 않았다.
