# 수정 시각 갱신의 파일 읽기 단순화

2026-11-21 작업 트리의 수정 시각 갱신을 기준으로 한다. 파일 읽기 경로는 갱신 엔트리에서 준비 풀을 거쳐 원본 읽기와 winner 선택으로 이어진다. 탐색 시점에 정한 바이트 경계, 원본 해시, 오류 위치, 진행률과 취소, 제한된 Worker 선행 창을 검증한다. [파일 준비](../../../src/summary/scanner/sourcePreparation.ts) · [파일 읽기](../../../src/summary/scanner/sourceReader.ts) · [JSONL](../../../src/summary/jsonl/index.ts)

| ID | 상태 | 판단 |
| --- | --- | --- |
| 읽기-01 | 적용 완료 | 준비 결과에서 바이트·실행 시간 계측값을 지웠다. Worker 입력은 원본 식별자와 읽기 경계만 포함하고 바이트는 진행 이벤트에서 한 번 집계한다. |
| 읽기-02 | 적용 완료 | 파서가 완료할 때 식별 정보를 한 번 받는다. 재개 위치 반환값을 제거하고 현재 행과 오류 위치를 계산하는 오프셋은 읽기 내부에서 관리한다. |
| 읽기-03 | 적용 완료 | 원본 청크 공급과 청크 내 행 파싱을 별도 함수로 정리했다. 각 원본 청크의 바이트 뷰를 한 번 만들고 읽는 동안 사용한다. |

## 근거와 검증

- 준비 결과의 바이트와 실행 시간에는 제품 호출부가 없다. 이전 실험의 스크립트는 `manifest`가 있는 당시 빌드에서 해당 값을 읽는다. 현재 갱신 진행률과 수정 시각 벤치마크는 실제 바이트 콜백과 스캔 단계 시간을 사용한다. Worker에는 원본 바이트 경계와 식별 검사에 쓰는 필드만 전달한다. [이전 풀 벤치마크](../../../tests/benchmarks/scan-source-pool-ab.cjs) · [현재 벤치마크](../../../tests/benchmarks/mtime-refresh-ab.cjs)
- 마지막 완성 줄 위치를 반환하는 필드는 현재 제품의 재파싱 범위에 쓰이지 않는다. 테스트의 UTF-8, Zstd, 마지막 미완성 행, 실제 행·오류 오프셋 기대값은 유지한다. [일반 JSONL 테스트](../../../tests/node/jsonl.test.ts) · [압축 JSONL 테스트](../../../tests/node/compressed-jsonl.test.ts)
- 바이트 수 B, 줄 최대 보관량 L을 기준으로 파일 읽기·파싱은 O(B)이고 기존 청크·줄 상태의 공간은 O(64KiB + L)이다. 청크 파싱 클로저는 계측이 있을 때만 만든다. 이 범위에서 별도 성능 수치는 측정하지 않았다.
- 변경 파일 타입 검사와 린트, `git diff --check`, 일반·압축 JSONL 테스트 18개가 통과했다. 600KiB 로그 두 개로 순차/Worker 준비 DTO 일치, 원본 진행 바이트 합계, 공유 취소의 오류 위치와 부분 식별 정보를 대조했다. 갱신 경계·저장과의 결합은 상위 통합 검증으로 확인한다. [스트리밍 갱신 테스트](../../../tests/node/streaming-scanner.test.ts)
