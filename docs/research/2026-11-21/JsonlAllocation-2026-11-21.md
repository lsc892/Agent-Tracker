# JSONL 중복 파싱과 임시 배열 절감 보고서

## 개선 가설

Codex의 일부 도구 호출은 JSONL 한 줄을 파싱한 뒤, 줄 안의 문자열 인자도 다시 파싱했다. 플러그인 이름을 `mcp__docs__search`처럼 호출명에서 얻을 수 있으면 두 번째 파싱을 생략해 **2회에서 1회**로 줄일 수 있다고 봤다. `exec_command`처럼 인자 내용이 분류에 필요한 경우에는 인자를 계속 파싱한다. [도구 분류 코드](../../../src/summary/parsers/capabilities.ts#L117)

집계는 이벤트 하나를 정규화할 때마다 `Object.entries`로 바깥 배열 하나와 필드마다 `[키, 값]` 배열 하나를 만들었다. 필드를 직접 읽으면 정규화 작업은 그대로 수행하면서 이 임시 배열을 없앨 수 있다. Codex 턴 누계도 전체 토큰 스키마의 검증을 끝낸 뒤 합계 대조에 쓰는 입력·출력 토큰과 식별 정보만 남긴다. 두 변경으로 일시적인 객체와 배열 생성이 줄어 누적 힙 할당량이 낮아질 것으로 봤다. [이벤트 정규화](../../../src/summary/aggregation/sourceEvidence.ts#L20) · [누계 보관](../../../src/summary/aggregation/sourceWinners.ts#L74)

## 측정 결과

| 항목 | 합성 100요청 | 합성 10,000요청 |
| --- | ---: | ---: |
| 도구 문자열 인자의 추가 `JSON.parse` 호출 | 150회 → 0회 | 15,000회 → 0회 |
| 이벤트 정규화의 `Object.entries` 호출 | 500회 → 0회 | 50,000회 → 0회 |
| 위 `Object.entries`가 생성한 임시 배열 | 4,850개 → 0개 | 485,000개 → 0개 |
| 파서·집계 시간 중앙값 | 2.69 → 2.30 ms | 283.00 → 247.11 ms |

10,000요청에서 **두 함수의 호출을 합쳐 65,000회 줄였다.** 임시 배열 485,000개는 이벤트별 바깥 배열 50,000개와 필드별 `[키, 값]` 배열 435,000개를 합한 수다. 두 규모 모두 최종 집계 결과가 일치했다.

| 10,000요청의 힙 측정 | 변경 전 중앙값 | 변경 후 중앙값 |
| --- | ---: | ---: |
| 누적 힙 할당량 추정치 | 234.79 MiB | 159.18 MiB |
| 실행 중 관측한 피크 힙 증가량 | 76.14 MiB | 80.84 MiB |

**누적 힙 할당량 추정치는 75.61 MiB 줄었다.** 실행 중 피크는 4.70 MiB 높았고, 변경 전후 관측 범위는 각각 75.87~88.45 MiB와 80.35~81.80 MiB로 겹쳤다. 이번 측정에서 피크 힙 절감은 확인하지 못했다.

## 측정 범위

Claude와 Codex가 요청 수를 절반씩 차지하는 합성 입력을 사용했다. 집계에서 인자를 쓰지 않는 도구 호출에 약 2 KiB 문자열을 넣었다. 동일한 행 객체를 변경 전(`45800fc`)과 변경 후 파서·집계기에 전달했다. 파일 읽기, 원본 행의 첫 `JSON.parse`, Worker 전송, SQLite 저장은 측정 범위 밖이다.

시간은 준비 후 순서를 교대한 11쌍의 중앙값이다. 누적 할당량은 Node 24의 힙 할당 샘플링 5쌍에서 GC로 회수된 객체까지 포함한 추정치다. 피크는 GC 직후의 `heapUsed`를 기준으로 9쌍을 실행해 매 64행과 파일·집계 단계의 종료 시점에 관측했다.

## 후속 정리

Codex 파서는 공통 행 문맥 객체 없이 각 처리기에 필요한 값을 전달한다. 턴 누계는 기존 토큰 스키마 검증을 거친 뒤 입력·출력만 바로 보낸다. 도구 호출 ID와 이름은 한 번 읽고, 최종 집계에서는 선택한 도구 이벤트를 다시 검사하거나 복사하던 경로를 없앴다. [Codex 파서](../../../src/summary/parsers/codex.ts) · [최종 집계](../../../src/summary/aggregation/memoryAggregate.ts)

직전 구현과 재비교한 결과, 합성 10,000요청에서 턴 누계 이벤트 5,000개는 그대로 전달됐고 그 안에 만들던 토큰 벡터는 **5,000개에서 0개**로 줄었다. 파서·집계 시간 중앙값은 100요청에서 2.38 → 2.26 ms, 10,000요청에서 251.84 → 248.53 ms였다. 두 크기에서 시간 표본 범위가 겹쳤으며 집계 결과가 일치했다. 위 힙 표는 앞선 변경의 측정값이다. 후속 정리는 검증 객체 수와 시간만 비교했다.

`npm run check`에서 타입 검사·린트·테스트 444건을 통과했다. 잘못된 누계 필드의 오류와 발생 순서, 부모 요청 연결, 중첩 도구 호출 순번을 확인했다.
