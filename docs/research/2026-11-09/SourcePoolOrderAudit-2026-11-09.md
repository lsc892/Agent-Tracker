# Worker 풀의 처리 순서와 저장 지연 분석

2026-11-09, Asia/Seoul. 사용자는 파일 준비 Worker의 실행 순서가 꼬여 저장 지연이나 결과 오류가 발생했는지, 파일 준비 직후 풀을 종료하는 방향을 기준으로 분석하도록 요청했다. 제품 코드와 [기존 A/B 원시 결과](../../benchmarks/2026-11-09/SourcePoolAB-2026-11-09.json), 보존된 A/B DB를 읽기 전용으로 대조했다. 새 자동 테스트·재현 스크립트·벤치마크는 작성하거나 실행하지 않았다. 제품 동작은 변경하지 않았다. 대조 범위와 결과는 [분석 JSON](SourcePoolOrderAudit-2026-11-09.json)에 남긴다.

## 1. 판정

**측정한 현재·10,000요청 입력에서는 Worker 완료 순서가 논리 반영·최종 저장 순서를 바꿨다는 근거를 찾지 못했다.** 두 입력 각각 10쌍에서 기존 논리 읽기 순서·결과·저장 단계 호출 수와 보존 DB의 요청·파일 ID 배치가 일치했다. 현재 최초 저장의 시간 증가는 관측됐지만, 순서 오류나 저장 작업 증가로 설명되지 않는다.

파일 준비 직후 Worker 종료는 미사용 Worker의 자원 보유 영향을 분리하는 후보다. 이 변경만으로 결과 순서 오류를 검사하거나 GC를 원인으로 확정할 수는 없다. 이번 분석에서는 조기 종료 후보를 실행하지 않았으므로 그 효과는 미측정이다.

## 2. 코드에서 순서를 보존하는 경계

| 경계 | 현재 코드의 동작 | 순서에 미치는 영향 |
| --- | --- | --- |
| 파일 내부 | [readSource](../../../src/summary/scanner/sourceReader.ts)는 파일마다 parser를 새로 만들고 행마다 index를 증가시킨다. | 다른 파일의 parser 문맥이 섞이지 않는다. |
| 작업 배정 | [sourcePool](../../../src/summary/scanner/sourcePool.ts)은 Worker slot당 job 하나만 배정하고 결과의 파일 ID를 slot의 job과 대조한다. | Worker 완료 순서는 달라도 다른 파일의 결과로 Promise를 완료하지 않는다. |
| 결과 전달 | 메시지 handler는 진행 바이트와 job의 Promise만 완료한다. 관계·세션·최종 winner·DB는 수정하지 않는다. | 완료 순서가 전역 집계 반영 순서가 되지 않는다. |
| 논리 반영 | [inspectBatch·inspectSource](../../../src/summary/scanner/index.ts)는 ID순 batch의 각 파일을 순서대로 await하고, await 전 sequence를 정한 뒤 해당 결과의 identity·세션·오류·prepared를 반영한다. | B·C가 A보다 먼저 끝나도 반영은 A→B→C다. |
| 관련 확장 | 부모 후보는 확정한 ID순 batch로 소비하고, 관련 후보 preview는 큐를 변경하지 않는다. 다음 논리 작업은 기존 최소 ID 큐에서 고른다. | 선행 읽기가 부모 우선순위나 큐의 논리 제거 순서를 바꾸지 않는다. |
| 최종 집계 | collectWinners는 file.sequence로 원본을 정렬하고 [SourceWinners.events](../../../src/summary/aggregation/sourceWinners.ts)는 파일 내 index로 정렬한다. | 동점 winner에 쓰는 ordinal이 완료 시각에 따라 달라지지 않는다. |
| 저장 | 관련 확장·부모 확정·이동 연결·최종 집계를 await한 뒤 연결 묶음별로 [MemoryStore](../../../src/summary/db/memoryStore.ts)의 동기 transaction을 실행한다. 파일 Worker는 DB를 열지 않는다. | 파일 파싱과 DB INSERT가 서로 추월하거나 여러 파일 Worker가 DB 쓰기 잠금을 경쟁하는 구조가 아니다. |

공유하는 데이터는 취소용 SharedArrayBuffer이며 파일별 winner·근거는 메시지로 전달한다. Worker마다 전역 관계 Map이나 DB를 함께 변경하는 경로는 없다. 한 Worker의 message handler는 async 준비를 시작하지만 부모의 slot 제약 때문에 결과를 받기 전 다음 파일을 배정하지 않는다.

정해진 순서를 기다리는 동안 먼저 끝난 결과가 선행 창에 남아 Worker가 일시적으로 쉬는 경우는 가능하다. 이는 순서를 보존하면서 대기 결과 수를 제한하는 비용이며 파일 준비 구간에 포함된다. 저장 구간의 직접적인 순서 충돌과 구분한다.

## 3. 기존 산출물 추가 대조

기존 해시 검사는 물리 ID를 정규화 제외하므로, 그 검사만으로 요청 ID 배치까지 같다고 주장하지 않았다. 이번에는 보존된 각 DB의 요청·파일 ID와 식별자 대응을 별도로 조회했다. 아래 ID 배치는 append·무변경 이후 최종 보존 DB의 상태이며, 모든 SQL 문장의 실행 순서를 기록한 trace는 아니다.

물리적인 Worker 완료 순서는 기존 결과에 기록하지 않았다. 완료 순서 역전 횟수는 알 수 없지만, 기존 코드의 직렬 await와 논리 순서 해시·최종 DB 대조로 그 역전이 논리 반영에 전파됐는지를 살폈다.

| 대조 항목 | 현재 10쌍 | 합성 10,000요청 10쌍 |
| --- | --- | --- |
| 최초·추가·무변경의 논리 읽기 순서 해시 | 모두 일치 | 모두 일치 |
| 읽기 집합·DB 의미 결과 | 모두 일치 | 모두 일치 |
| 제출한 선행 작업과 소비한 작업 수 | 모두 일치 | 모두 일치 |
| 각 저장 단계의 호출 수 | 불일치 0건 | 불일치 0건 |
| 요청의 id→provider/session/root 대응과 ID순 배치 | 모두 일치 | 모두 일치 |
| 파일의 id→provider/path/session 대응과 ID순 배치 | 모두 일치 | 모두 일치 |

저장 단계 호출 수는 facts·모델 교체·Skill 교체·비용 저장·rollup·transaction 등의 계측된 호출 수다. 개별 SQL 문장을 모두 계수하거나 추적한 것은 아니다. 다만 동일 결과를 저장하면서 이 계측 범위에서 재처리·재저장 횟수가 늘어난 흔적은 없다.

## 4. 저장 시간 증가는 별개로 남는다

| 현재 최초 저장 | A 중앙값 ms | B 중앙값 ms | 중앙값 차이 ms | B가 느린 쌍 |
| --- | ---: | ---: | ---: | ---: |
| replaceMemory 전체 | 397.914 | 421.683 | +23.769 | 8/10 |
| facts·모델·Skill·비용 쓰기 | 36.534 | 42.274 | +5.740 | 10/10 |
| COMMIT | 248.842 | 258.396 | +9.554 | 7/10 |

하위 타이머는 서로 포함되므로 증가량을 모두 합산하지 않는다. 중앙값끼리의 차이와 쌍별 차이의 중앙값도 다르다. 저장 저하를 전부 무작위 변동으로 간주하지 않으며 원인을 미확정으로 둔다.

현재 풀은 finally에서 종료하므로 저장 중 파일 Worker는 살아 있다. 그러나 기존 표본에서는 제출한 준비 작업을 모두 await해 소비한 뒤 집계·저장을 시작했다. 따라서 **살아 있는 Worker와 실행 중인 파일 파싱은 같은 의미가 아니다.** 저장과 동시에 실제 파일 파싱이 계속됐다는 근거는 없다.

메시지 복사 이후의 객체 배치·할당·GC 상태, Worker의 남은 메모리와 백그라운드 작업, JIT·CPU 캐시·OS 저장 대기는 가능한 원인 후보다. 기존 산출물에는 Worker CPU·GC 이벤트·heap 추적이 없으므로 어느 후보가 얼마를 차지하는지는 판단할 수 없다. 앞선 GC 설명은 가능성 설명이며 확인된 원인이 아니다.

## 5. 조기 종료 후보가 구분할 수 있는 것

- **현재**: 모든 파일 준비 결과 소비 → 관계·최종 집계 → 저장 → Worker 종료.
- **후보**: 모든 파일 준비 결과 소비와 남은 job 없음 확인 → Worker 종료 → 관계·최종 집계 → 저장. finally의 실패·취소 정리는 유지한다.
- **비교 의미**: 같은 논리 순서·같은 입력을 유지한 채 풀의 자원 보유 시점만 바꾼다. 저장 시간뿐 아니라 종료 시간을 포함한 전체 시간·최종 결과도 함께 봐야 한다. 저장 시간이 줄어도 종료 대기로 전체가 더 느려질 수 있다.
- **추론 한계**: 조기 종료로 시간이 줄어도 GC 하나가 원인이라고 확정할 수 없다. 객체 복사·JIT·캐시·할당 상태의 영향은 별도 관측이 필요하다. 새 비교는 이번 작업에서 수행하지 않았다.

코드·참조 검토와 기존 JSON·보존 DB의 읽기 전용 대조만 수행했다. 오류·취소·실시간 원본 교체 등 모든 스케줄의 안전성을 이번 정상 입력 분석으로 보장하지 않는다. 기능 동작을 바꾸지 않아 기능 의사결정 일지에는 새 항목을 추가하지 않는다.
