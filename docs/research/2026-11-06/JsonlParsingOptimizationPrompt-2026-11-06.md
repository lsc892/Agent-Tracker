## 2. 줄 읽기는 두 후보를 비교

줄의 구분자는 공백이나 띄어쓰기가 아니라 LF(`\n`)다. 원본 바이트 위치로 offset을 계산해 줘.

### 검색 알고리즘 — memchr·SIMD로 LF 위치 찾기

단순히 "줄 단위로 읽는다"로 구현하지 말고, 원본 Buffer에서 LF 바이트 `0x0A`의 위치를 찾는 검색 알고리즘과 그 위치로 구간을 참조하는 단계를 나눠 줘.

```text
원본 배열: [첫 번째 JSON\n두 번째 JSON\n세 번째 JSON\n]
             └── 줄 1 ──┘
                         └── 줄 2 ──┘

Rust: memchr(LF, &bytes[start..]) → 남은 구간 안의 상대 위치 pos → end = start + pos
Node: bytes.indexOf(0x0A, start)  → 버퍼 처음을 기준으로 한 위치 end
원본[start:end]                  → 원본 데이터를 복사하지 않는 줄 구간
다음 검색 시작                   → end + 1
```

- `memchr` 자체는 바이트 위치를 반환한다. 그 결과로 Rust의 `&bytes[start..end]` 또는 Node의 `Buffer.subarray(start, end)`를 만드는 것은 호출부의 역할이다. `subarray`도 view 객체는 만들지만 줄의 바이트 데이터는 복사하지 않는다.
- 검색 결과는 현재 메모리 버퍼 안의 위치다. 비압축 원본의 파일 위치는 버퍼 시작의 원본 위치를 더해 계산하고, 청크에 걸친 줄은 처음 시작한 위치를 유지한다. 디코딩한 문자열 길이로 원본 offset을 대체하지 않는다. 압축 입력은 기존의 원본·해제 위치 계약을 유지한다.
- SIMD 경로의 개념은 `여러 바이트를 벡터로 로드 → 모든 바이트를 LF와 병렬 비교 → 일치한 위치의 비트마스크 생성 → 첫 일치 비트 위치로 바이트 index 계산`이다. 일치가 없으면 다음 벡터 구간으로 이동한다. SSE2의 16바이트·AVX2의 32바이트는 처리 폭의 예시이며, 짧은 입력과 끝부분은 범위를 벗어나지 않는 별도 경로로 처리한다.
- 한 줄을 처리한 뒤 다음 줄부터 검색한다. 이미 검색한 앞부분을 줄마다 다시 훑거나, 원본 전체를 먼저 문자열로 변환해 `split()`한 결과를 구간 참조 최적화라고 보고하지 않는다.
- 바이트 위치 검색과 구간 참조는 별도 최적화다. 전자는 검색 CPU 비용을, 후자는 줄별 바이트 복사·문자열 할당을 줄인다. SIMD도 전체 검색의 시간복잡도는 O(B)이며 입력을 읽지 않고 위치로 순간 이동하거나 처리 폭만큼 속도가 보장되는 것은 아니다. 파일별 스레드 병렬화와도 구분한다.
- [Rust memchr](https://docs.rs/memchr/latest/memchr/fn.memchr.html)와 [CPU별 SIMD 선택](https://docs.rs/memchr/latest/memchr/index.html#crate-features)은 알고리즘 원리의 참고 자료다. 해당 Rust 함수를 TypeScript에서 직접 import하거나 표준 메소드로 실행할 수 있다는 뜻은 아니다. 특정 환경에서 SSE2·AVX2 경로가 실행됐다고 보고하려면 CPU·빌드·실행 경로의 근거를 남긴다.

현재 코드의 숫자 인자 `Buffer.indexOf(10, start)`도 네이티브 검색을 사용한다. 이 작업 환경의 Node v24.14.1에서는 [IndexOfNumberImpl](https://github.com/nodejs/node/blob/v24.14.1/src/node_buffer.cc#L1149-L1170)이 C `memchr`를 호출한다. 따라서 현재 구현을 JavaScript의 1바이트 반복문으로 간주하지 않는다. C 함수 호출이 확인됐다는 사실과 해당 PC에서 어떤 SIMD 명령이 실행되는지는 구분한다.

TypeScript/Node에서 별도 native 의존성 없이 실행할 기본 경로는 다음과 같다.

```typescript
const end = bytes.indexOf(0x0a, start); // LF 검색. 못 찾으면 -1.
if (end !== -1) {
  const lineBytes = bytes.subarray(start, end); // 원본 바이트를 공유하는 view.
  // lineBytes를 동기적으로 소비한 뒤 다음 줄로 진행한다.
  start = end + 1;
}
```

`Buffer.indexOf`의 결과는 버퍼 기준 위치이므로 여기에 start를 다시 더하지 않는다. 위 두 API는 현재 TS/Node 환경에서 사용할 수 있고, Rust 크레이트 도입이 필요하지 않다. Rust의 명시적 SIMD 구현을 그대로 호출하려면 별도의 native addon이나 WebAssembly 인터페이스가 필요하며 이는 선택적인 추가 실험이다.

같은 입력에서 **S0: 현재 Buffer.indexOf**, **S1: 별도 연동으로 SIMD 실행 경로를 확인할 수 있는 검색 구현**을 독립 비교해 줘. S1을 native 호출로 구현한다면 버퍼 단위로 LF 위치들을 반환하는 방식도 후보로 두고 빌드·배포 조건과 호출·전달·위치 배열 생성 비용을 포함한다. 현재 경로가 이미 같은 검색 최적화를 제공한다면 재사용하고 별도 도입의 이득이 없다고 판정할 수 있다. 추가 연동을 하지 못해도 S0와 읽기·파싱 후보 비교는 진행하고 S1만 미측정으로 남긴다.

### 검색 결과로 줄을 공급하는 두 읽기 후보

- **후보 R1 — 청크를 읽으며 줄 구간 참조:** 제한된 버퍼로 읽고 `Buffer.indexOf(10)`으로 LF를 찾는다. 한 청크 안에서 완성된 줄은 `Buffer.subarray()`로 원본 구간을 참조한다. 청크에 걸친 줄만 조립한다. 참조 중인 버퍼를 다음 읽기로 덮어쓰지 않는다.
- **후보 R2 — 파일 전체를 읽고 줄 구간 참조:** 파일을 하나의 Buffer로 읽은 뒤 LF 경계의 구간을 참조한다. 각 줄의 바이트를 별도 배열로 복사하지 않는다. 동시에 읽는 파일 전체의 메모리 비용을 포함해 비교한다.
- 구간 참조는 JSON 역직렬화 전체가 무복사라는 뜻이 아니다. UTF-8 변환과 객체 생성 비용을 따로 측정한다.

## 3. 데이터 파싱은 두 후보를 비교

### 후보 P1 — 표식 선별 후 DOM 파싱

```text
원본 기록 읽기 → 바이트 표식 검사 → 통과한 JSON 한 줄 전체 객체화 → 필요한 값 추출 → DTO
```

- `usage` 같은 바이트 표식으로 파싱 대상을 선별하고, 통과한 줄은 `JSON.parse` 등으로 전체 객체화한 뒤 DTO로 변환해 줘.
- LF의 단일 바이트 검색과 `"usage"` 같은 여러 바이트의 부분 문자열 검색을 구분한다. TS/Node에서는 표식 Buffer를 한 번 만들고 `Buffer.indexOf(표식, start)`에 재사용해 표식별 원본 문자열 변환과 표식 Buffer의 반복 생성을 줄인다. Rust의 [memmem::Finder](https://docs.rs/memchr/latest/memchr/memmem/struct.Finder.html)는 검색 준비 상태 재사용의 참고이며 TS 표준 API가 아니다. 표식 Buffer 재사용만으로 Finder 내부의 준비 상태까지 재사용했다고 보고하지 않는다.
- 여기서 파일 offset은 이전 처리 완료 위치다. 줄 내부의 표식 위치로 파일을 다시 seek하는 방식과 구분해 줘.

### 후보 P2 — 읽는 도중 선별하고 관련 기록만 조립

```text
조각 읽기 → 관련 기록인지 판단 → 관련 기록만 제한 안에서 조립 → JSON 해석 → DTO
```

- 앞부분의 표식으로 관련 여부를 판단하고, 무관한 기록은 남은 조각을 보관하지 않고 줄 끝까지 읽어 넘겨 줘.
- 관련 기록은 원래 순서대로 바이트를 이어 붙여 완성된 JSON 한 줄로 만든다. 조각마다 누적 전체를 다시 복사하지 않는다. 필요한 필드의 조각만 골라 합치는 방식은 아니다.
- 완성 후 바깥 이벤트 종류를 확인하고 필요한 내부 필드를 단계적으로 해석해 줘. 파일 전체를 먼저 읽고 조각으로 나누는 경우와 메모리 효과를 구분해 줘.

두 후보 모두 사용량뿐 아니라 세션·모델·요청 시작/종료·제목·도구 사용·검증에 필요한 기록을 보존해야 한다. 고정된 `"usage":{` 문자열만으로 필요한 기록을 누락시키지 말고, 공백·이스케이프·경계에 걸친 표식과 잘못된 JSON의 기존 오류 처리도 검증해 줘. 판별할 수 없는 기록은 기존 파싱 경로로 처리해 줘.

우선 `R1+P1`, `R2+P1`, `R1+P2`를 비교해 읽기 변경과 선별 변경의 효과를 구분해 줘. 기존 UTF-8 경계, 미완성 끝줄, 이미지 제거, `.jsonl.zst`, 취소·파일 교체/잘림 처리 계약은 유지해 줘.

## 4. 파일 단위 병렬 처리

### 배정 알고리즘 — 파일 크기를 작업량으로 추정하는 LPT

LPT(Longest Processing Time first)는 큰 작업부터 처리량이 가장 적게 배정된 작업자에게 주는 탐욕적 분배다. 여기서는 아직 처리 시간을 모르므로 파일 크기를 예상 작업량으로 사용해 줘. 파일 개수만 똑같이 나누면 큰 파일들이 한쪽에 몰릴 수 있으므로, 작업자별 배정 바이트를 고르게 만드는 것이 목적이다.

1. 수집 단계에서 확보한 파일 경로·크기·원래 순번을 사용한다.
2. 파일을 크기 내림차순으로 정렬한다. 크기가 같으면 원래 순번으로 정렬한다.
3. 각 작업자의 `배정 바이트 합계`와 `파일 대기열`을 초기화한다.
4. 정렬된 파일을 하나씩 꺼내 배정 바이트가 가장 작은 작업자를 찾는다. 동률이면 작업자 번호가 작은 쪽을 선택한다.
5. 그 작업자의 대기열에 파일을 넣고 배정 바이트 합계에 파일 크기를 더한다.
6. 배정 후 작업자들을 병렬 실행한다. 각 작업자는 자신의 대기열에 있는 파일을 하나씩 읽고 파싱한다. 파일 하나를 여러 작업자에게 나누지는 않는다.

파일 크기가 100MB·80MB·30MB·20MB이고 작업자가 2명일 때의 예시다.

| 배정할 파일 | 선택한 작업자 | A의 배정 합계 | B의 배정 합계 |
| --- | --- | ---: | ---: |
| 100MB | A | 100MB | 0MB |
| 80MB | B | 100MB | 80MB |
| 30MB | B | 100MB | 110MB |
| 20MB | A | 120MB | 110MB |

개념 의사코드는 다음과 같다.

```text
files = 크기 내림차순, 원래 순번 오름차순으로 정렬
workers = W개의 { id, assignedBytes: 0, queue: [] }

for file in files:
    worker = (assignedBytes, id)가 가장 작은 작업자
    worker.queue에 file 추가
    worker.assignedBytes += file.size

각 worker를 병렬 실행:
    for file in worker.queue:
        해당 파일을 읽고 파싱해 DTO 결과 전달
```

배정 바이트는 완료한 바이트가 아니라 처음에 배정한 총량이다. 위 방식은 정적인 대기열 분배이며, 실행 중 매번 가장 먼저 빈 작업자에게 파일을 주는 동적 분배와 구분해 줘. 압축률·이미지 비율·레코드 구조에 따라 크기와 실제 처리 시간이 다를 수 있으므로 배정 균형과 시간 균형을 각각 측정해 줘.

파일 F개, 작업자 W명일 때 배정 알고리즘은 정렬 O(F log F), 매 파일마다 작업자를 선형 탐색하는 배정 O(FW), 대기열·작업자 정보 공간 O(F + W)다. 전체 파싱 작업량은 입력 바이트 B에 대해 여전히 O(B)이며, 병렬화가 총작업량의 차수를 줄이는 것은 아니다. 큰 파일 하나를 분할하지 않으므로 그 파일의 처리 시간이 마지막 완료 시각을 좌우할 수 있다.

### 실행 구조 — 파일별 파싱은 병렬, Map·DB 반영은 단일 소유

```text
파일 목록·크기 → LPT 배정
                    ├─ 작업자 A: 파일 읽기 → 줄 검색·선별 → 파싱 → DTO
                    └─ 작업자 B: 파일 읽기 → 줄 검색·선별 → 파싱 → DTO
                                              ↓
                   단일 수집기: 원래 파일 순번·기록 순서로 Map 병합
                                              ↓
                                 dirty DTO → SQL 배치 반영
```

- 파일마다 스레드를 새로 만들지 않고 제한된 Worker 풀을 사용한다. 작업자 수는 파일 수를 넘기지 않으며, 1·2·4명에서 비교해 줘. `Promise.all()`만으로 동기 JSON 파싱 CPU가 병렬화됐다고 판단하지 말아 줘.
- 각 작업자는 파일별 파서 상태와 입력 버퍼를 독립적으로 유지한다. 작업 결과에는 원래 파일 순번과 원본 byte offset을 포함하고, 완료 도착 순서 때문에 중복 선택·모델·시각 등의 결과가 달라지지 않게 해 줘.
- 단일 수집기가 기존의 결정적인 순서로 Map에 병합하고, DB 쓰기는 한 소유자가 담당하게 해 줘. 작업자들이 같은 Map·DB 연결을 동시에 변경하지 않게 해 줘.
- 작업 결과 대기열의 개수·바이트 예산을 제한하고, 수집기가 처리하지 못하면 공급을 멈추도록 해 줘. R2에서는 동시에 읽은 파일 전체 Buffer의 합도 메모리에 포함한다. 작업자 실패·취소 시 처리 완료되지 않은 파일의 offset을 확정하지 않는다.

### 비교 기준

- **병렬화 효과:** 같은 배정 방식에서 작업자 수 1·2·4를 비교한다.
- **LPT 배정 효과:** 같은 작업자 수에서 파일 개수 기준 균등 배정과 LPT 배정을 비교한다. 줄 읽기·파싱 방식은 동일하게 고정한다.
- 파일 크기가 비슷한 입력과 큰 파일·작은 파일이 섞인 입력을 모두 측정한다. 작업자별 파일 수·배정 바이트·실제 처리 시간과 마지막 작업자 완료 시각을 기록한다.
- 전체 시간에는 스레드 생성, DTO 전달·복사, 순서 복원·Map 병합, SQL 반영을 포함한다. 파싱만 빨라졌는데 전체 갱신도 같은 비율로 빨라졌다고 보고하지 않는다. 단일 작업자와 결과·오류·offset이 같은지 확인해 줘.

## 5. Map에서 DTO 중복 제거·갱신

- `Map<안정적인 이벤트 키, DTO>`로 기존 응답을 찾는다. 원본의 응답 ID나 기존 식별 규칙을 재사용하고, 파싱할 때마다 새 UUID를 만들지 않는다. 제공자·세션·응답의 구분이 유지되어야 한다.
- 같은 응답의 스트리밍 토큰 카운터는 필드별 최댓값으로 병합한다. 서로 다른 응답의 사용량은 각각 유지한 뒤 요청 집계에서 합산한다.
- 모델·비용·시각·완료 상태·검증 플래그는 토큰처럼 무조건 max하지 않고 기존 의미를 유지한다. 원본 정정·재작성 등에서 max 병합이 현재 결과를 바꾸면 정확성 실패로 기록해 줘.
- 추가·변경된 키를 dirty 집합으로 관리하고 동일 데이터 재처리 시 DTO와 저장 결과가 불필요하게 변하지 않게 해 줘.

## 6. 변경분 SQL 저장과 DTO 캐시

```text
시작: 유효한 캐시 복원 → Map·파일별 파서 상태 구성
갱신: 원본 추가 구간 파싱 → Map 추가·병합 → dirty DTO 배치 UPSERT → 캐시 저장
```

- SQL에는 전체 Map이 아니라 변경 DTO를 배치 UPSERT한다. 최종 통계와 중복 처리 결과는 현재 구현과 같아야 한다.
- DTO 스냅샷 캐시는 `.pkl`로 저장한다. Node.js/TypeScript에서 실제 Python pickle을 읽고 쓰는 방법과 실행·배포 의존성을 명시해 줘. 확장자만 `.pkl`인 다른 형식을 pickle 구현으로 보고하지 않는다. 구현 제약이 있으면 임의로 형식을 바꾸지 말고 제약을 결과에 적어 줘.
- 캐시에는 DTO 외에 파일별 원본 offset, 크기·변경 검증 정보, 모델·누적 토큰 등 파서 상태, 파서/캐시 버전, DB 커밋 식별 정보를 함께 저장한다.
- 실행 중에는 메모리 Map을 유지하고, 재시작 시 캐시를 한 번 복원한다. offset은 마지막으로 처리 완료한 기록의 끝이며 조각 번호가 아니다. 미완성 기록은 다음 갱신에서 다시 읽는다.
- 이벤트 반영과 진행 위치가 어긋나지 않게 DB 트랜잭션으로 확정하고, 해당 커밋의 캐시를 임시 파일 작성 후 교체한다. DB와 캐시의 커밋이 다르거나 캐시가 손상·무효이면 복구 경로를 사용한다. 파일 삭제·이동·잘림·교체와 기존 이력 보존 정책도 유지한다.
- 원문 본문·이미지 Base64·인증 정보는 캐시에 저장하지 않고, 기존 요청 제목 정책을 유지한다. 전체 캐시 저장·복원 비용을 증분 파싱 시간에서 숨기지 않는다.

## 7. 검증과 결과

- [A/B 테스트 지침](../../../.agents/skills/ab-test/SKILL.md)과 [기존 벤치마크](../../../tests/benchmarks/README.md)를 재사용해 실제 로그의 고정 사본·10,000요청·100요청을 비교해 줘. 준비 3회 후 AB/BA 교대로 각 10회 이상 측정하고 중앙값과 원시 표본을 남겨 줘. 원본 로그는 수정하지 않는다.
- 최초 전체 파싱, 변경 없는 갱신, 요청 한 건 추가, 재시작 후 캐시 복원을 나눠 측정한다. 읽기·선별·JSON 해석·DTO 병합·SQL 커밋·캐시 저장/복원 시간과 읽은 바이트, JSON 해석 건수, 최대 RSS/heap을 기록한다. 일/월/세션/프로젝트 조회는 기존 결과와 성능의 회귀 여부를 확인한다.
- 바이트 검색은 같은 입력의 짧은 줄·긴 줄·LF가 없는 구간을 따로 측정한다. LF 위치 배열이 완전히 같은지 확인하고 검색 시간·처리량, UTF-8 변환·문자열 분할 호출, 복사 바이트와 native 호출 비용을 구분한다. 확인되지 않은 SIMD 사용이나 속도 배수를 가정하지 않는다.
- 동일 이벤트 반복, 스트리밍 중간/최종 응답, 파일 간 복사, Codex 카운터 초기화, UTF-8/CRLF/청크 경계, 거대한 무관 기록·관련 기록, 잘못된 JSON, 취소, 저장 실패·재시작을 검증한다.
- 요청 수·토큰 합계·그룹별 평균·메타정보·오류·원본 offset을 A/B와 독립 기대값으로 대조한다. 결과가 다른 후보는 성능과 관계없이 실패다.
- 보고서는 `현재와의 차이 → 후보별 결과 → 채택/보류와 근거`만 간결하게 정리한다. 미측정 수치를 추정으로 채우지 않는다. 제품 코드를 반영한다면 `npm run check`와 저장소의 설계·의사결정 기록 지침까지 완료한다.
