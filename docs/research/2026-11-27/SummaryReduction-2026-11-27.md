# 현재 통계 집계에서 줄일 수 있는 작업과 저장 공간

현재 기능을 유지할 수 있는 후보를 세 갈래로 조사했다. 실로그 751파일·1,731대화와 합성 10,000·100대화는 직전 A/B에서 고정한 사본을 사용했다. 비교·전달 횟수는 현재 구현의 최초 수집을 한 번씩 실행해 셌다. DB 크기는 같은 데이터의 읽기 전용 사본과 메모리 SQLite에 복원한 표에서 관측했다. Node 24.14.1, SQLite 3.51.2, 파일 워커 최대 4개다. [계측값](SummaryReduction-2026-11-27.json)

## 응답 비교와 누계

| 최초 수집 | 실로그 | 합성 10,000 | 합성 100 |
| --- | ---: | ---: | ---: |
| 확정 응답 수 | 29,123 | 10,000 | 100 |
| 응답 정렬·그룹화의 ID 비교 호출 | 102,160 | 19,753 | 160 |
| 다음 필드까지 비교 | 311 | 0 | 0 |
| Codex에서 턴 ID까지 비교 | 0 | 0 | 0 |
| 같은 턴에 누계 검산 항목이 있는 확정 응답 | 20,436 | 0 | 0 |

실로그의 다음 필드 비교 311회는 모두 Codex에서 같은 응답 ID의 스레드 ID가 달랐다. 스레드 ID를 제거하면 관측된 별개 응답을 같은 그룹으로 처리한다. 턴 ID는 이번 입력에서 비교할 필요가 생기지 않았지만, 현행 중복 범위와 여러 턴에서 같은 응답 ID가 등장할 수 있는 입력을 지원하는 데 쓰인다. Claude 요청 ID는 같은 메시지의 요청 귀속을 정정하거나 별개로 나누는 데 쓰인다. 실로그에서 레거시 대체 후보 경로에 930번 진입했으며 선택할 수 있는 대체 후보는 없었다. [응답 비교](../../../src/summary/aggregation/memoryAggregate.ts#L34) · [대체 후보와 반영 순서](../../../src/summary/aggregation/memoryAggregate.ts#L147) · [중복 정책](../../refrences/WinnerPolicy.md)

턴별 합계를 담는 `totals`는 누계 검산에서만 읽는다. 이미 등록한 `checks`에 없는 턴은 누적을 건너뛸 수 있다. 관측한 확정 응답 중 실로그 8,687개(29.8%)와 합성 입력의 모든 응답이 해당한다. 대화별 토큰·모델 반영과 누락 요청 진단은 유지한다. [검산의 유일한 조회](../../../src/summary/aggregation/memoryAggregate.ts#L238) · [확정 응답 반영](../../../src/summary/aggregation/memoryAggregate.ts#L258) · [검산 대상만 누적한 A/B](../../benchmarks/failure/2026-11-27/CheckedTurnTotalsAB-2026-11-27.md)

검산 유무를 추가로 조회한 후보는 실로그 피크 힙을 56.09 → 55.56 MiB로 낮췄고 집계 시간은 67.51 → 69.87 ms로 늘었다. 두 맵을 조회하는 이 버전은 보류했다. 다음에는 검산 항목에 누적값을 직접 두고 한 번의 조회로 보정까지 연결할 수 있다.

## SQLite 저장 공간

실로그 DB는 996 KiB, 제품 테이블은 8개다. `source_file` 356 KiB와 `UNIQUE(provider,path)` 인덱스 184 KiB가 전체의 54.2%를 차지한다. 고유 인덱스는 기존 파일을 찾고 중복 등록을 막는 경로에서 사용한다. `session_billing`은 이번 사본에 행이 없지만 명시적인 세션 결제 설정을 저장한다. `usage_rollup_meta`에는 시간대와 형식 버전, `usage_capability_daily`에는 Skill 통계가 있다. [파일 식별 스키마](../../../src/summary/db/schema.ts#L118) · [경로 조회와 등록](../../../src/summary/db/sourceFiles.ts#L40) · [결제 설정](../../../src/summary/db/billing.ts) · [일별 테이블](../../refrences/SQLiteTables.md)

| 메모리 SQLite의 압축 후 페이지 합계 | 실로그 | 합성 10,000 | 합성 100 |
| --- | ---: | ---: | ---: |
| 일별 대화·모델 표에서 파생 열 5개 제거 | 236 → 236 KiB | 120 → 120 KiB | 16 → 16 KiB |
| `source_root` 문자열을 정수 외래 키로 저장 | 504 → 428 KiB | 116 → 100 KiB | 16 → 24 KiB |

파생 열은 전체·완료·기록된 완료의 토큰 합계 세 개와 완료 표본의 소요 시간 누락 건수 두 개다. 입력과 출력의 합, 또는 해당 완료 건수에서 소요 시간이 있는 건수를 뺀 값과 총 1,607행에서 일치했다. 표를 복사해 열을 삭제하고 양쪽을 `VACUUM`한 결과 페이지 수가 줄지 않았다. 조회 수식 변경과 스키마 이관을 감수할 만한 저장 효과를 확인하지 못했다. [집계 열 정의](../../../src/summary/db/rollup-state.ts#L24)

모델명 `model`은 `model_key`에서 복원할 수 있다. `N`은 NULL이고, `V`로 시작하는 키는 첫 글자를 빼면 모델명이다. 세 입력의 모델 표 924행이 모두 일치했다. `model`만 삭제한 별도 사본에서도 페이지 수는 같았다. [모델 키 생성](../../../src/summary/db/queries/rollup/source.ts#L8)

실로그 751행의 `source_root`는 서로 다른 경로 3개를 반복 저장했다. 절대 파일 경로와 기존 고유 제약은 유지하고 루트 문자열만 조회 테이블의 정수 ID로 바꾸자, 루트 테이블과 그 인덱스를 포함해 76 KiB 줄었다. 세 입력에서 조인으로 복원한 원본 행과 외래 키를 대조했다. 제품 마이그레이션, 루트 필터와 다중 경로 조회 비용은 미측정이다. 로그가 적은 경우 추가 테이블 두 페이지가 더 큰 비용이었다.

## JS에서 SQLite로 전달하는 값

| 최초 수집 | 실로그 | 합성 10,000 | 합성 100 |
| --- | ---: | ---: | ---: |
| 저장 묶음 | 28 | 13 | 2 |
| 제공자·모델 JSON 합계 | 723,056 B | 3,034,766 B | 30,262 B |
| 중복으로 직렬화되는 세션 범위 | 21,600 B | 6,813 B | 682 B |

제공자·모델 페이로드는 각각 UPSERT와 삭제 대조에 바인딩한다. 삭제에는 제공자·세션·프로젝트·현지 날짜와 모델 키만 필요하다. 재사용 범위가 이미 동일한 세션 JSON은 한 번 직렬화한 값을 공유할 수 있다. 키만 전달하거나 SQL에서 날짜·모델 키를 한 번 계산해 재사용하는 변경의 후보는 페이로드가 큰 합성 입력에서 우선 검토할 수 있다. 소실 원본 보존 시 교체 날짜 범위, 빈 집계, 변경 없는 행의 UPSERT 생략과 실패 시 롤백을 유지해야 한다. 바이트는 실측했고, SQL 구문 변경의 지연과 네이티브 메모리는 미측정이다. ## 정렬용 버퍼

최종 대화·모델·Skill 정렬에서는 비교마다 문자열 두 개를 UTF-8 버퍼로 바꾼다. UTF-16과 UTF-8 순서가 같은 일반 문자열을 직접 비교하고 서로게이트가 들어간 경우 기존 바이트 비교를 적용한 후보를 A/B로 계측했다. 실로그 피크 힙은 55.69 → 54.39 MiB, 합성 10,000대화 피크 힙은 75.75 → 89.91 MiB였다. 1만 대화에서 집계는 빨라졌으나 피크 힙이 늘어 우선순위를 낮췄다.
